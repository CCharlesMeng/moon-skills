**# SDD Frontend Design**

**## 定位与边界**

**\*\*一句话定义\*\***：在编码前，从前端全局视角回答——组件怎么拆、数据从哪来怎么转、拼起来能不能跑。

**\*\*核心价值\*\***：没有它，前端开发者直接从 spec + ux-decode 跳到拆任务编码，缺少全局视角——不确定 task 是否正确，不确定做完能跑。

**\*\*适用场景\*\***：多仓 SDD Design 阶段，本次需求涉及前端时由 \`sdd-design\` **\*\*按需唤醒\*\***（也可独立调用）。

**\*\*不适用场景\*\***：纯后端项目、非增量开发（从零搭建脚手架）、仅样式调整不涉及组件/数据变更。

**\*\*本 skill 做什么\*\***：技术栈推导、组件架构+存量盘点、API 契约解析、数据映射、对接策略、示例数据生成、模块与路由设计。

**\*\*本 skill 不做什么\*\***：编码实现（sdd-dev）、领域 how 正文（requirement-design / story-delta-design）、Explore/PRD 澄清、视觉解码（sdd-ux-decode）、边界条件处理（编码细节）。

**### 多仓双层产物（强制）**

对齐 \`requirement-design\` / \`story-delta-design\`；**\*\*Feature 不单独出前端 delta\*\***。

\| 层级 | 产物 | 内容边界 |

\|------|------|----------|

\| requirement | \`requirement-frontend-design.md\` | 模式、技术栈、共享 IFC/对接策略、模块路由总览、Feature/Story 索引、共享组件 |

\| Story（按需） | \`feature-tree-changes/.../story-delta-frontend-design.md\` | 该 Story 页组件树、SC 对齐契约切片、本页 testability/examples |

\| Feature | （无） | 索引写在 requirement-frontend-design 章节内 |

**## 核心原则**

**### 绝对禁止**

1\. **\*\*不硬编码技术栈\*\*** — 技术栈从项目代码推导，不预设框架/组件库/API 方式

2\. **\*\*不在领域 design 正文重复写前端方案\*\*** — \`requirement-design.md\` 仅追加：\`前端设计详见 requirement-frontend-design.md\`；有前端影响的 \`story-delta-design.md\` 仅追加：\`本 Story 前端设计详见 story-delta-frontend-design.md\`

3\. **\*\*不包含边界条件\*\*** — 数据映射只到字段映射 + 数据转换逻辑，空值/缺省/异常态处理属于编码细节

4\. **\*\*不预设静态数据提供方式\*\*** — 静态数据提供方式从项目约定文件 + 代码实践样例推导（写在组件里 / 独立文件 / API模拟工具 / 测试数据文件等），不预设 mock server

**### 必须做到**

5\. **\*\*模式判定优先于流程执行\*\*** — 进入 8 步流程前必须先判定「完整对接模式 / 静态实现模式」，模式决定哪些步骤产出、哪些 deferred。判定详见步骤 ⓪

6\. **\*\*扩展组件严格约束\*\*** — 优先新增，尽量不修改存量组件；确需扩展时必须标注修改点 + 影响范围 + 用户审批

7\. **\*\*关键决策有多选项时才问\*\*** — 有多种选择并且不确定选哪种时，才暂停问用户确认（如组件库选型、模式判定、扩展审批等）；能从代码推导或只有单一选项的，直接判定，不事无巨细地问

8\. **\*\*缺口必须暴露\*\*** — UI 需要但 API 未提供的字段，必须在数据映射中标出，不能静默忽略

9\. **\*\*降级必须标注\*\*** — 任何降级处理（无 ux-decode、无 API 契约、无项目约定等）在产物中标注降级标记

10\. **\*\*deferred 节必须机器可识别\*\*** — 静态实现模式下置空的节用 \`\<!-- deferred: 原因 -->\` 标记，便于 phase 2 resume 时扫描

**### 张力裁决**

11\. **\*\*新增 vs 扩展\*\*** → 优先新增。扩展必须证明：新增导致的代码重复显著高于修改存量组件的风险

12\. **\*\*数据映射深度\*\*** → 字段映射 + 数据转换逻辑（包含），不含边界条件（不包含）。分界示例见下方

13\. **\*\*示例数据覆盖\*\*** → 仅默认正常数据。异常/边界数据属于编码阶段关注点

14\. **\*\*契约稳定性\*\*** → 前端数据接口契约是稳定锚点，phase 2 API 变化靠转换层吸收；只有契约本身推断错误才改契约，且评估对已编码组件影响

**\*\*数据转换 vs 边界条件的分界\*\***：

\| 类型 | 包含 | 示例 |

\|------|------|------|

\| 数据转换（包含） | 格式变换、枚举映射、计算派生 | timestamp→"3天前"、status 1/2/3→标签、0.856→"85.6%" |

\| 边界条件（不包含） | 空值/缺省/异常态处理 | amount\:null→"--"、list:[]→空态提示 |

**## 执行步骤**

**### ⓪ 模式判定（确认门 ⓪）**

**\*\*做什么\*\***：判定本次设计走「完整对接模式」还是「静态实现模式」，并据此决定后续 8 步的产出范围。

**\*\*两种模式定义\*\***：

\| 模式 | 大白话 | 触发条件 | 产出范围 |

\|------|--------|---------|---------|

\| 完整对接模式 | 前后端完整对接——后端接口已就绪，前端直接对接真实接口 | API 契约文件存在 **\*\*或\*\*** requirement-design.md 含完整接口定义（endpoint + 字段已明确） | 8 步全量产出 |

\| 静态实现模式 | 前端mock数据静态实现——后端接口未就绪，前端先用假数据把页面跑起来 | 无 API 契约 **\*\*且\*\*** requirement-design.md 标注接口待定/后端未就绪 | ③ 置空 deferred；④ 仅产出 4.1 契约；⑤ 改为对接预留策略；⑥ 变为主要产出 |

**\*\*判定流程\*\***（按顺序匹配，命中即判定）：

1\. API 契约文件存在？ → **\*\*完整对接模式\*\***

2\. requirement-design.md 含完整接口定义（endpoint + 字段已明确）？ → **\*\*完整对接模式\*\***

3\. requirement-design.md 标注"接口待定/后端未就绪"？ → **\*\*静态实现模式\*\***

4\. 以上都不满足（requirement-design 对接口只字未提）？ → **\*\*信号不确定 → 确认门 ⓪\*\*** 让用户选择

**\*\*⚠️ 确认门 ⓪\*\***：

\`\`\`

\---

\*\*[确认门 ⓪ — 模式判定]\*\*

上游接口信号扫描：

\- API 契约文件：存在 / 不存在

\- requirement-design.md 接口定义：完整（endpoint+字段） / 待定 / 不确定

自动判定结果：完整对接模式 / 静态实现模式 / 不确定

若不确定，请选择：

1\. \*\*完整对接模式\*\*（前后端完整对接）— 接口已就绪，按 8 步全量产出

2\. \*\*静态实现模式\*\*（前端mock数据静态实现）— 接口未就绪，先用假数据跑通页面，③④ 部分置空 deferred，phase 2 待 API ready 后回填

→ 请确认模式或选择。

**### ① 技术栈推导（自动）**

**\*\*做什么\*\***：扫描项目代码，推导前端技术栈。

**\*\*推导维度\*\***：

\| 维度 | 推导方式 | 影响的决策 |

\|------|---------|-----------|

\| 框架 | \`package.json\` dependencies | 组件写法、模块系统 |

\| 组件库 | import 分析 / dependencies | 组件选型 |

\| 状态管理 | import 分析 | 数据流设计 |

\| 路由方案 | import 分析 / 配置文件 | 路由设计 |

\| API 调用方式 | import 分析 / 配置文件 | 对接方案设计 |

\| 静态数据提供方式 | 项目约定文件 + 代码实践样例推导（详见下方） | 示例数据写入形式（⑥） |

**\*\*静态数据提供方式推导\*\***（静态实现模式下的关键维度）：

读取优先级：

1\. 前端目录显式约定：\`frontend-conventions.md\` / \`coding-guidelines.md\` / \`.cursorrules\` / \`docs/conventions/\*\`

2\. \`AGENTS.md\` / \`CLAUDE.md\`（可能含静态数据约定段）

3\. 项目根 \`README.md\` 的开发约定段

4\. 代码实践样例（代码即 guideline）：扫 \`mock/\` / \`fixtures/\` / \`\_\_mocks\_\_/\` / \`examples/\` 目录 / API 模拟工具配置 / 组件内直接写死的数据

推导决策树（示例数据放哪里）：

\`\`\`

if 项目有专门的示例数据目录（examples/ 或 fixtures/）→ 独立文件

elif 项目装了 API 模拟工具（package.json 有 msw 这类依赖）→ 用 API 模拟工具

elif 项目代码里直接写死了数据 → 写在组件里

else → 默认写在组件里，标 ⚠️ 降级，问用户确认

\`\`\`

**\*\*推导流程\*\***：详见 \`references/tech-stack-detection.md\`，配套确定性解析脚本 \`scripts/parse\_tech\_stack.py\`（解析 package.json 依赖 → 分类映射 + 静态数据信号检测，替代 LLM 读包名猜技术栈；monorepo 用 \`--target-dir\` 指定子包；\`--json\` 输出机器可读格式供下游消费）

**\*\*推导不出来时\*\***：问用户。

**\*\*产出\*\***：技术栈声明（写入 requirement-frontend-design.md 第 1 节）

**### ② 组件架构 + 存量盘点（确认门 ①）**

**\*\*做什么\*\***：先扫描现有组件，再基于存量 + ux-decode + requirement-spec / story-delta-spec 推导组件树，每个组件直接标注复用/新增/扩展。

**\*\*为什么合并\*\***：页面组件划分依赖存量组件——不知道存量有什么，就无法准确判断是新增还是复用。分开做会导致先凭空推导组件树，再比对时大量返工。

**\*\*存量组件扫描\*\***：调用 \`skills/component-scan\` 子 skill（subagent 执行）——脚本 \`scripts/scan\_existing\_components.py\` 做确定性扫描 + LLM 语义匹配 ux-decode 组件词。主 agent 基于返回的匹配清单做分类决策。详见子 skill SKILL.md。

**\*\*输入优先级\*\***：

1\. 存量组件清单（scan\_existing\_components.py 输出）→ 比对基础

2\. ux-decode.md 第 2 节（页面结构：ASCII 线框图 + 方括号组件词嵌套树）→ 主输入

3\. ux-decode.md 第 4 节（交互与数据关联）→ 补充交互组件

4\. ux-decode.md 第 3 节（业务数据要点）→ 补充数据相关组件

5\. requirement-spec.md / story-delta-spec.md FR 列表 → 补充功能需求隐含的组件

6\. 无 ux-decode.md → 降级：从 requirement-spec.md / story-delta-spec.md 推导（精度降低，标注降级）

**\*\*分类规则\*\***：

\| 分类 | 定义 | 审批要求 |

\|------|------|---------|

\| 复用 | 直接使用存量组件，无需修改 | 无需审批 |

\| 新增 | 存量中没有，需新建 | 无需审批 |

\| 扩展 | 存量组件需修改 | **\*\*必须审批\*\***：标注修改点 + 影响范围 |

**\*\*严格约束\*\***：优先新增，尽量不修改存量组件。扩展需证明新增导致的代码重复显著高于修改存量组件的风险。

**\*\*粒度\*\***：组件级（到每个可复用组件，不到按钮/输入框等原子元素）。

**\*\*产出\*\***：组件树 + 分类标注（写入 requirement-frontend-design.md 第 2 节）

**### ④ 数据接口契约 + 数据映射（确认门 ② 的一部分）**

**#### 4.1 前端数据接口契约（两模式都产出）**

**\*\*做什么\*\***：定义前端期望的接口契约——每个接口的请求参数 + 响应结构，每个响应字段标注消费组件.展示位。**\*\*不依赖后端\*\***（静态实现模式下由前端推断，phase 2 后端实现 API 时以此为目标；完整对接模式下以后端 API 为基础对齐）。

**\*\*输入\*\***：ux-decode.md 第 3 节（业务数据要点）+ 第 2 节（页面结构：方括号组件词嵌套树）+ requirement-spec.md / story-delta-spec.md FR 列表 + ③ 接口定义表（完整对接模式）

**\*\*契约稳定性原则\*\***：契约是前端稳定锚点。phase 2 API 变化靠转换层吸收（字段名/结构不同 → 转换层处理）；只有契约本身推断错误才改契约，且评估对已编码组件影响。

**\*\*产出\*\***：前端数据接口契约表（写入第 4 节 4.1），分两部分：

**\*\*接口清单\*\***（接口级）：

\| 契约编号 | 接口名 | 请求参数 | 响应结构概述 | 推断依据 |

\|---------|--------|---------|------------|---------|

\| IFC-1 | getDashboardKpi | page: number; pageSize: number | { kpiCards: KpiCard[]; lastUpdated: string } | ux-decode 第 3 节指标卡数据 |

**\*\*响应字段-消费组件映射\*\***（字段级，到展示位 + 自验证）：

\| 契约编号 | 响应字段路径 | 类型 | 消费组件.展示位 | 自验证（ux-decode 第 3 节溯源） |

\|---------|------------|------|---------------|------|

\| IFC-1 | kpiCards[].value | number | MetricCard.value | 第 3 节"指标卡数值" |

\| IFC-1 | kpiCards[].label | string | MetricCard.label | 第 3 节"指标卡标签" |

**\*\*消费组件多对多\*\***：一个响应字段可被多个组件消费（如 \`kpiCards[].value\` 同时被 MetricCard.value 和 TrendChart.currentValue 消费），在"消费组件.展示位"列用逗号分隔；一个组件也可消费来自不同接口的字段。

**\*\*自验证规则\*\***：每个响应字段必须能在 ux-decode.md 第 3 节业务数据要点中找到对应的数据要点。若找不到 → 标 \`⚠️ 推断：无 ux-decode 溯源，需人工确认\`。ux-decode 第 3 节为空时（弹性填写场景），自验证降级为从 requirement-spec / story-delta-spec FR 推导对应数据要点，标注降级。

**### story-delta-frontend-design.md（按需）**

每个有 \`type=frontend\` 的 Story 一份，与 \`story-delta-design.md\` 同目录。建议骨架：

1\. 归属 Story / SC 锚点索引

2\. 本页组件树（复用/新增/扩展）

3\. 本页 IFC 切片（引用 requirement 级共享契约）

4\. 本页 testability / examples 指针

5\. 降级与 deferred（若有）

**### 编号体系对照**

各步骤产物的编号前缀不同，避免交叉引用时混淆：

\| 编号前缀 | 用于 | 出现步骤 | 引用关系 |

\|---------|------|---------|---------|

\| \`API-x\` | 后端接口（endpoint + 字段） | ③ API 契约解析 | 被 4.2 MAP-x 引用为映射源 |

\| \`IFC-x\` | 前端期望的接口契约 | ④ 4.1 前端数据接口契约 | 被 4.2 MAP-x 引用为映射目标；被 ⑥ 示例数据 conform |

\| \`MAP-x\` | 后端字段 → 前端字段映射 | ④ 4.2 数据映射 | 引用 API-x（源）+ IFC-x（目标） |

\| \`GAP-x\` | 字段缺口（后端无对应字段） | ④ 4.2 缺口分析 | 引用 IFC-x 的字段路径 |

组件（②）不使用编号，直接用组件名（如 \`MetricCard\`、\`WorkOrderTable\`）+ \`[test\:xxx]\` 锚点标识。

**## 降级策略**

\| 缺失项 | 降级方式 | 产物标记 |

\|--------|---------|---------|

\| 无 ux-decode.md | 从 requirement-spec.md / story-delta-spec.md 推导组件需求（精度降低） | 第 2 节标注 \`⚠️ 降级：无 ux-decode.md，组件树从 requirement-spec.md / story-delta-spec.md 推导，精度降低\` |

\| 无 API 契约（模式判定为静态实现） | 走静态实现模式：③ 置空 deferred，4.1 从 ux-decode 第 3 节推断契约，⑥ 产出示例数据，⑤ 改为对接预留策略 | 第 3 节标 \`\<!-- deferred -->\`，第 4.1 节标 \`⚠️ 推断：契约从 ux-decode 推断，待 API 确认\` |

\| 无 API 契约（模式判定为全量但实际缺） | 暂停让用户补全接口方案（仅此一条路径） | — |

\| 无项目约定文件 | 从代码实践样例推导静态数据提供方式；样例也没有 → 默认写在组件里 | 第 1 节标注 \`⚠️ 降级：无约定文件，静态数据提供方式默认写在组件里\` |

\| 存量组件扫描失败 | 用户手动提供组件清单，或全部按"新增"处理 | 第 2 节标注 \`⚠️ 降级：存量扫描失败，全部按新增处理\` |

\| 原型生成失败 | 跳过 ⑧，确认门 ③ 标注跳过原因 | 确认门 ③ 标注 \`⚠️ 跳过：原型生成失败，<原因>\` |

\| 技术栈推导不出来 | 问用户 | — |
