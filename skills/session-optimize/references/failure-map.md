# 失败层地图与常见问题目录

`SKILL.md` 第 2 节给出三分流、五层地图和停止规则，本文件给出分流后的四个追问，以及每一层的常见问题：标准 `Pattern-Key`、判别信号和标准处置。

**怎么用**：定位到某一层后，先在该层的表里找同类。命中就直接复用它的 `Pattern-Key` 和标准处置，不要另起一个说法——同一个问题在不同会话里换了措辞，计数就断了，固化门槛也就失效了。找不到同类才按末尾的规则新造键。

标准处置是默认动作，不是免检通道。任何一条仍要通过 `SKILL.md` 第 4 节的三问（可控条件、改进为什么可能有效、失效条件）和第 5 节的固化门槛；表里的"默认固化目标"只说明够门槛之后往哪写。

写`移交该 skill 维护者`的处置，按 `SKILL.md` 第 6 节先分清本会话是在使用还是在开发那个 skill：默认是前者，产出自带证据的移交说明；只有本会话就在开发它，才由本会话接 `refine-skill` 改写。

## 分流后的追问：一次性上下文与偏好去哪

分流判成`一次性上下文`或`偏好`只说明它不走层地图，不说明到此为止。这两类经常是 skill 缺陷或使用方式偏差的表象：用户之所以要补一条本次运行才成立的事实，可能是 skill 根本没问；用户之所以反复纠正风格，可能是 skill 的默认对谁都不合适。按下表顺序问，**停在第一个成立的**。

| 追问 | 判别 | 去向 |
| --- | --- | --- |
| skill 该声明的输入没声明？ | 这条信息 skill 本该在开工前索要，它没要 | 补输入契约，移交该 skill 维护者（`decision.undeclared-input`） |
| skill 的默认就不对？ | 换个用户在同样场景下也会提同样的纠正 | 改默认，移交该 skill 维护者（`decision.wrong-default`） |
| 用户的使用方式有偏差？ | 用对场景了吗、前置步骤做了吗、触发情境匹配吗 | 产出可直接复制的使用引导（`usage.*`）；复发才考虑固化 |
| 用户该给却没给的背景？ | 只有用户或上游知道，项目里查不到 | L1 `背景输入不足`，产出下次会话输入 |
| 以上都不成立 | | `偏好`按读取点写；`一次性上下文`不成题、不记账、不编 `Pattern-Key` |

**顺序不能反。** 前两问指向 skill，第三问指向使用方式，第四问指向输入——先问 skill 再问人。反过来问，会把 skill 的缺陷记成用户的问题，等于让所有用户各自绕过同一个坑；而 skill 改一次，所有人都不再踩。

**偏好的去向由"下次谁在什么时刻会读到它"决定**，不是由它像什么决定：只在某类任务里成立的，写进对应 skill 既定的知识读取位置；跨任务恒成立的，写常驻上下文；属于项目事实的按`知识缺口`走。指不到一个确定的读取点就不写——没人会读的偏好只是噪音。

## L1 输入 — `背景输入不足`（`input.*`）

目标、约束或项目事实从未提供，且当时无法自行发现。这一层的修法永远不是给 agent 加规则，而是改开局条件。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `input.missing-constraint` | 硬约束（兼容性、性能预算、合规）后期才出现，前面方案返工 | 约束不在项目任何文件里，只有用户知道 | 归为信息不足，不判前期方案错误；产出下次会话输入。复发 ≥3 次 → 申请写入项目约束文档 |
| `input.ambiguous-goal` | 目标有多种合理解读，选错方向后整段返工 | 会话中出现"我是想…"式纠正方向 | 下次开工前一次性批量澄清（P7）；固化为该类任务的开局提问清单 |
| `input.unstated-acceptance` | 没有完成标准，做完无法判断对不对 | 验证方式由 agent 自行发明，用户不认 | 开工前索取可观察的验收标准；固化进项目的任务模板 |
| `input.late-scope-change` | 中途改需求导致已完成工作废弃 | 改动点在用户消息里，不在项目状态里 | 不作为失败归因于任一方；记账观察频率，够门槛 → 申请约定变更成本提示 |
| `input.hidden-owner` | 任务实际依赖他人负责的系统，事后才知道 | 边界信息在会话外 | 移交 + 下次注明边界；固化进项目的角色边界文档 |

## L1 输入 — `知识缺口`（`knowledge.*`）

信息在项目里查得到，但文档缺失、过时或与实现矛盾。这一层最值得修：改一处文档，挡住所有后续会话的同类失败。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `knowledge.doc-stale` | 按文档做失败，实现已改文档没改 | 文档与代码可直接对照出矛盾 | 项目内有权威依据 → 申请修文档（高价值，通常一次即可固化）；默认目标：该文档本身 |
| `knowledge.convention-unwritten` | 仓库有一致惯例但没写下来，产出不符被要求重做 | 现有代码高度一致，文档里没有 | 申请把惯例写进约定文件或 `rules/`；范围写窄，只覆盖已验证的一致部分 |
| `knowledge.undiscovered-asset` | 项目已有脚本、索引或工具，agent 重新造或手工硬做 | 资产存在且可用，只是入口没登记 | 申请在入口文档登记资产及用法；默认目标：项目入口文档 |
| `knowledge.wrong-entrypoint` | 找错入口文件或命令，绕远路才回到正轨 | 正确入口存在但无指引 | 入口文档补路径；复发 → 申请写入 `AGENTS.md` 一类的常驻上下文 |
| `knowledge.doc-contradiction` | 两处文档互相矛盾，按哪份做都被否 | 两份文件都存在且都像权威 | 先定唯一权威源再改；单一权威源确定后一次即可固化 |

## L1 输入 — `使用方式`（`usage.*`）

信息够、工具正常、skill 本身也对，但调用它的方式不对：场景不匹配、前置步骤没做、触发时机不对。这一层的修法是给用户可复制的使用引导，不是给 agent 加规则。归到这一层前先确认四追问的前两问都不成立——只要换个用户也会这么用，那就是 skill 的默认或输入契约有问题，不是这个用户用错了。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `usage.wrong-skill` | 用了与任务不匹配的 skill 或入口，走完一整套才发现不对 | 存在更匹配的入口，且当时依据可见信息就能判断 | 给一句"什么时候用哪个"的使用引导；复发 ≥3 次 → 申请写进该 skill 的适用场景 |
| `usage.skipped-prerequisite` | 跳过 skill 声明的前置步骤直接调用，中途缺料回头补 | 前置步骤写在 skill 里，本轮没做 | 给带前置步骤的调用模板；若前置步骤本该由 skill 自己索要，改判 `decision.undeclared-input` |
| `usage.wrong-timing` | 触发时机不对：问题还在排查时就复盘，任务未收口就固化 | 触发条件已写明，本轮情境不匹配 | 说明正确触发时机；复发 → 申请写进开局清单 |
| `usage.unscoped-request` | 调用时没给范围或重点，agent 自行扩张后被要求收回 | 范围只有用户知道，且一句话就能给 | 给可直接复制的调用措辞；与 `input.missing-constraint` 的区别是那边缺的是约束本身，这边缺的是本次调用的范围 |
| `usage.manual-drive` | 手工逐步驱动本可一次交出去的流程，来回多轮 | 自动路径可用且当时可见 | 给一次到位的调用示例；不因此给 agent 加规则 |

## L2 决策 — `流程/决策`（`decision.*`）

信息充分、工具正常，但计划、验证、边界或协作判断本身不当。多数应写成决策原则，不是永久禁令。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `decision.scope-creep` | 用户要小改，实际动了大面，造成返工 | 会话里有明确的小范围要求 | 提炼"先给最小切片、扩大范围前复述边界"的原则；跨 skill 的规则移交该 skill 维护者 |
| `decision.unverified-claim` | 声称完成但没跑验证，之后被证伪 | 报告完成的那一轮没有工具结果 | 固化"完成必须附可观察证据"；属高危不变量，一次即可申请固化 |
| `decision.correlation-as-cause` | 拿时间相邻当根因，改错对象或回退无关组件 | 排除实验缺失，或回退后故障仍存在 | 要求先做排除实验再定责；未定责的部分照样移交能继续诊断的人 |
| `decision.search-before-read` | 通读大量文件而非先检索缩小范围，上下文被占满后遗漏约束 | 读取文件数与定位收益明显不成比例，且项目已有索引或搜索工具 | 固化"先检索缩小范围，再逐字读"的检索协议；验证用读取文件数、定位耗时、约束遗漏数等可观察指标 |
| `decision.silent-assumption` | 未确认的猜测被当既定前提继续推进，后期被推翻 | 关键前提在会话里从未被确认 | 固化"承重前提必须显式标注并求证"；先做可逆试验 |
| `decision.no-rollback-point` | 大范围改动前没有可回退点，出问题难以复原 | 改动跨多文件且无提交或备份 | 固化"大改前先建可回退点"；属高危不变量 |
| `decision.constraint-drop` | 会话后半程遗漏前面已确认的用户约束 | 约束在会话里出现过且未被撤销 | 固化"交付前逐条复核已确认约束"；配合缩短反馈，不只靠提醒更小心 |
| `decision.premature-abstraction` | 只有一个用例就抽象，后续被迫拆掉 | 抽象引入时缺少第二个真实用例 | 写成决策原则而非禁令：第二个用例出现前不抽象 |
| `decision.undeclared-input` | skill 本该开工前索要的信息没索要，缺料后返工或按猜测推进 | 用户中途补的那条信息属于 skill 该主动问的输入，它却没有对应的输入契约 | 补输入契约，移交该 skill 维护者；不记成用户的`背景输入不足`——该问没问是 skill 的缺陷 |
| `decision.wrong-default` | skill 的默认做法在同类场景下被反复纠正 | 换个用户在同样场景下也会提同样的纠正 | 改默认，移交该 skill 维护者；判成偏好等于让每个用户各自纠正一遍 |

## L3 执行 — `工具使用`（`tooluse.*`）

工具可用，但选型、参数、调用顺序或结果解读错了。改对参数就恢复的一次性手滑，默认只记账不固化。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `tooluse.wrong-arg` | 参数名或路径拼错，改正后立即成功 | 一次改对，无复发，且不存在可加的约束 | 默认只记账，不进主报告、不固化；`Recurrence-Count ≥ 3` 才考虑写调用契约 |
| `tooluse.result-misread` | 工具返回成功但内容为空或不含目标，仍按成功继续 | 后续动作建立在空结果上 | 固化"用结果内容而非退出码判断成功"；属高危不变量 |
| `tooluse.ignored-truncation` | 输出被截断却按完整内容处理，得出错误结论 | 结果里有截断标记 | 固化"命中截断必须换更窄的查询重取" |
| `tooluse.destructive-default` | 用了会改状态的命令，而只读等价物本就存在 | 存在只读替代且当时无需写入 | 固化"诊断阶段只用只读等价物"；属高危不变量 |
| `tooluse.wrong-tool` | 用通用 shell 做本该用专用工具的事（读写文件、检索） | 专用工具可用且更可靠 | 固化工具选择表；跨 skill 的移交该 skill 维护者 |
| `tooluse.no-verify-after-write` | 写入后不复读确认，后续基于假想状态推进 | 写入与后续动作之间没有确认步骤 | 固化"写入后必须复读确认" |

## L4 承载 — `项目实现`（`project.*`）

正确使用之后，项目的代码、测试、配置或运行行为本身有缺陷。这一层可以申请项目内修改；能沉淀为可复用防护的走 `immune-debug`。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `project.config-path` | 配置里的路径或目录层级写错，整类操作空跑 | 用法正确，改配置即恢复 | 申请最小修改 + 现有验证；验证必须能区分"收集到正确目标"和"收集到 0 个" |
| `project.test-blindspot` | 测试没覆盖被改行为，回归漏网 | 改动路径无对应断言 | 申请补测试；可复用的防护走 `immune-debug` 登记 |
| `project.flaky-verify` | 验证本身不稳定，结论不可信 | 同一输入多次结果不一致 | 先修验证再谈功能结论；不要在不稳定验证上叠加修改 |
| `project.env-drift` | 本地与 CI 或依赖版本不一致导致结果不同 | 两侧版本可直接对照出差异 | 申请对齐并固定版本；默认目标：版本约束文件 |
| `project.silent-failure` | 失败被吞掉，返回像成功 | 错误分支无日志或无抛出 | 申请让失败可见；属高危不变量 |

## L5 环境 — `工具本身`（`tool.*`）与 `外部环境`（`external.*`）

参数和用法都正确，问题仍在项目和 agent 之外。这一层**只移交，不在项目里绕过**——绕行方案会把外部问题变成项目里的永久债务。

| Pattern-Key | 典型症状 | 判别信号 | 标准处置 · 默认固化目标 |
| --- | --- | --- | --- |
| `tool.timeout` | 工具或连接器超时，重试无效 | 用法正确，同类调用普遍超时 | 移交平台负责人 + 记账；复发多次 → 申请在文档记"已知限制 + 可接受的绕行" |
| `tool.rate-limit` | 触发速率限制，任务中断 | 返回明确的限流信号 | 移交 + 记账；不通过项目改动隐藏限流 |
| `tool.capability-gap` | 平台没有完成任务所需的能力 | 需求明确，工具集里确实没有 | 移交为能力请求；不虚构替代实现 |
| `tool.stale-index` | 索引或缓存过期，检索结果与实际不符 | 直接读取与检索结果矛盾 | 移交 + 本轮改用直接读取；记账观察频率 |
| `external.permission-denied` | 权限或 scope 缺失，无法读写外部系统 | 项目内没有可修配置 | 移交权限管理员；移交说明含负责角色、未修改原因、建议动作、验证标准 |
| `external.service-5xx` | 第三方服务返回 5xx，与本轮改动无因果证据 | 回退本地改动后故障仍存在 | 移交能继续诊断的负责人，不把接收方写成已证实根因；附可观察的恢复复验标准 |
| `external.network` | 网络不可达或 DNS 失败 | 同类请求普遍失败 | 移交 + 记账 |
| `external.owner-blocked` | 需要其他角色先完成动作才能继续 | 依赖项在他人职责内 | 移交 + 给出可复制的说明和完成标准 |

## 新造 `Pattern-Key` 的规则

1. **先复用**：`grep -rh "Pattern-Key:" .learnings/LEARNINGS.md | sort -u` 看一遍现有键。近似命中优于新造。
2. **格式固定**：`类别.症状`，恰好两级，小写，连字符分隔。类别只能取上表的八个前缀之一（`input`、`knowledge`、`usage`、`decision`、`tooluse`、`project`、`tool`、`external`）。
3. **症状要能复发**：不含文件名、版本号、主机名、人名。`project.config-path` 可以复发，`project.tests-config-json-rootdir` 不会。
4. **一条主题一个键**。同一主题下的次要措施不额外发键。
5. **不新增类别前缀**：八个前缀对应地图的五层，改动它等于改地图，属于 `SKILL.md` 的规则变更，交本 skill 的维护者用 `refine-skill` 处理（`usage` 就是这样加进来的）。
6. **不确定就先记 `不确定`**：没定位到层时不要硬套一个键，在台账里写清缺哪条证据。
