# 移交给 skill 维护者的证据包

`SKILL.md` 第 6 节判定"移交该 skill 的维护者"时，本节给出可直接复制的移交内容。维护者拿到它，在能改写源码的会话里跑 `/refine-skill <skill-name>`。

## 为什么只给证据，不给改法

`refine-skill` 的价值全在它的六条判据：信息不足还是判断错误、哪条假设被反驳、系统性还是偶然、太紧还是太松、委派结构、能不能用更短换更对。这六条都要求手里有 skill 全文——本会话的执行者是那个 skill 的**使用者**，没有全目录，从这个位置想出的改法必然比维护者在持有全文的会话里得出的差。

更要紧的是锚定：移交说明里写了"建议改成 X"，维护者的复盘就从别人的结论开始，第二步"找那条被反驳的假设"被跳过，直接变成评价 X 好不好。一个错误的假设可能有五种表现，改法 X 往往只治一种。**所以改法留白不是省事，是不给答案，让归因从头做一遍。**

对应地，证据要给足：判据一问"当时把该给的信息都给了，agent 还会犯这个错吗"——没写清当时 agent 手上有什么，这一问根本无法回答，维护者只能猜，而猜错的方向通常是"加一条规则"。

## 落盘：文件名与 front matter

聊天里的证据包随会话消失，落盘是它能被投递的前提。投到哪、用哪条命令，见 [feedback-sink.md](feedback-sink.md)；本文件只定文件长什么样。

文件名：`<skill-name>-<YYYYMMDD>-<seq>.md`。`seq` 是同一 skill、同一天已有文件的下一个序号，从 `001` 起。它只防止撞名，不承担计数——复发次数由收件方按包累加，不从文件名读。取序号时只看文件名，不打开已有正文，也不按 `pattern-key` 合并。

**每次移交都新建。** 同一个缺陷被移交两次不是浪费，那正是维护者需要的第二个数据点；在这里查重，收件方手里就永远只有 n=1，系统性判断升不上去。

正文即下一节模板，一字不改。前面加 front matter，**投递方只写五个字段**：

```text
---
skill: <skill-name>
status: pending
created: <YYYY-MM-DD>
pattern-key: <类别.症状>
sink: none
---
```

`skill` 与文件名第一段一致；`created` 是落盘当天；`pattern-key` 与卡片固化行同一把键。`status` 落盘时为 `pending`，投递成功改为 `forwarded`。`sink` 未投递写 `none`——不留空，留空和忘了写分不开；成功则把 `create` 输出的 `<sink>#<id>` 原样抄进去，不自己拼。

不要写 `ledger`。那是收件方消费时追加的第六个字段，投递方填了就是在预言一个还没发生的消费。

先落本地，再投递。成功只改 `status` 和 `sink`；失败保持 `pending` / `none`。

## 模板

落盘时把上一节的五个字段写在最前，再接下面临整块。整块也可直接复制给维护者：

```text
/refine-skill <skill-name>

以下证据来自另一个会话（我是该 skill 的使用者，不是维护者），已按 session-optimize
的移交格式整理。**本包不含改法建议**——归因和改法请你按 refine-skill 的判据自行判定。

## 运行的是哪一份
- 部署形态：源仓 symlink / 本仓 vendored 副本（路径：<path>）
- 版本线索：<最后同步提交或日期；取不到就写"未知">

## 问题
<一句话说清现象和后果，不用分类名>

## 逐条纠正
1. 触发情境：<换个用户在同样场景下也会遇到的描述，不含本仓库特有的文件名>
   错误行为：<agent 实际做了什么，照抄原样，不概括>
   期望行为：<用户当时要的是什么>
   出处：<会话轮次 / 命令与输出 / 文件:行>
2. ...

## 当时 agent 手上有什么
- 已给的指令与约束：<原话或准确摘要>
- 项目里查得到但它没查的：<有就写，没有就写"无">
- 只有用户知道、当时没交代的：<有就写，没有就写"无">

## skill 当时的依据（只引不评）
<如果能指到 agent 似乎在遵循的那句原文，引出来并标 文件:行；指不到就写"指不到具体出处">

## 委派情况
<本轮该 skill 用没用子代理、怎么划分的；没用就写"未委派">

## 复发情况
- 本轮之前在这个仓库里见过同一个问题吗：<能确认的写次数和大致时间；确认不了就写"不确定">
- 来源仓库：<仓库名或代号>；会话日期：<YYYY-MM-DD>
- 已知其他仓库出现过吗：<有就写，没有就写"不确定">

## 脱敏说明
<删掉了什么、为什么（凭据、客户名、私有代码原文、完整日志）>
```

字段取值不明时写"未知"或"不确定"，不要留空也不要编。留白是可判断的证据缺口，编的内容会把归因带偏。

## 每个字段对应哪条判据

| 字段 | 少了它，哪一步做不成 |
| --- | --- |
| 运行的是哪一份 | 陈旧的 vendored 副本上的缺陷可能上游早已修好。不写这条，维护者会去修一个已修的问题，或把真报告当噪音驳回 |
| 触发情境（泛化的） | 第五步要把它变成 `evals/` 用例；含本仓库特有文件名的情境无法重放 |
| 错误行为（原样） | 判据二要找被反驳的假设，概括过的行为已经丢掉了假设的痕迹 |
| 当时 agent 手上有什么 | 判据一的归因问题就是这一条，缺了只能猜 |
| skill 当时的依据 | 判据四分"太紧还是太松"：有原文可引通常是管太死，指不到出处通常是该定的没定 |
| 委派情况 | 判据五的三个方向（该拆没拆、不该拆拆了、拆错了地方）都要看划分方式，看不到就只能当执行问题处理 |
| 复发情况 | 判据三分系统性还是偶然。这一栏经常是"不确定"，那不是缺漏——使用侧的项目台账按规定不记这类问题，投递侧也不查重，所以本会话通常确认不了次数。真正的计数是维护者手上同一个 skill 的包有几份，本栏只补充使用侧能确认的那部分，不要为了填上而估一个数 |

## 脱敏

证据包会离开本仓库交到另一个人手上，尺度比台账严：不含凭据与令牌、客户或内部系统名称、私有代码原文、完整日志、能拼出内部拓扑的路径全貌。触发情境本来就要泛化才能复用，脱敏和它是同一个动作，不冲突。

拿不准某段能不能给，就删掉并在脱敏说明里写明删了什么——维护者可以点名索取，但泄露收不回来。

## 报告里怎么呈现

卡片三行和待移交事项以 `SKILL.md` 第 7 节为准，包括投递结果与路径。本文件只定证据包的正文与落盘形状。
