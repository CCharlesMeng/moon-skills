# 复盘台账：`.learnings/ledger.md`

台账存在的唯一理由是让复发可数。没有它，每次复盘都从 n=1 开始，永远只能提"下次注意"，`SKILL.md` 第 5 节的固化门槛也无从判断。

这份台账记的是**项目作用域**的复发：症状是这个仓库的事实，跨仓库累加没有意义。判据是去向而不是类别——去向指向"移交某个 skill 的维护者"的问题不在这里计数，它会在用到那个 skill 的每个仓库里各自复发，计数器挂在项目上就永远偏低（详见下面的固化门槛一节）。

## 位置与初始化

项目根的 `.learnings/ledger.md`，单文件。不存在时创建：

```bash
mkdir -p .learnings
[ -f .learnings/ledger.md ] || printf '# 复盘台账（session-optimize）\n\n按 Pattern-Key 去重，按 Recurrence-Count 计数。格式见 session-optimize/references/learnings-ledger.md。\n\n本文件独立于同目录下其他工具的 LEARNINGS.md / ERRORS.md 等文件，清理那些文件时不要连带删除本文件。\n\n---\n' > .learnings/ledger.md
```

`.learnings/` 是个公共目录，别的工具也会往里写自己的文件，所以表头要写明归属——有些工具的卸载说明会让人"删除前先检视 `.learnings/`"，那一刻靠的就是这句话。

台账要进版本库。放进 `.gitignore` 会让计数只在本机累积，跨会话、跨机器的复发就再也数不出来。

## 写入权限边界

这是本 skill 唯一免批准的写入，边界要窄：

- **允许**：追加新条目；更新已有条目的 `Recurrence-Count`、`Last-Seen`、`Status`、`See Also`、`Resolution`。
- **不允许**：删除或重写历史条目的事实内容；改 `.learnings/` 下的其他文件（包括旧台账 `LEARNINGS.md` 和别的工具的文件，它们一律只读）；顺手整理格式；用台账写入替代任何需要批准的项目修改。
- **不记**：凭据、令牌、私钥、环境变量值、个人信息、完整日志或完整源文件。证据用短摘要或脱敏摘录，不贴原始输出。
- 子代理不得写台账，只有主 Agent 写。

没有实质问题的复盘不写台账——空跑一轮不该留痕。

## 条目格式

```markdown
## [RETRO-20260806-001] decision.unverified-claim

**类别**: 流程/决策（L2）
**严重程度**: 高
**Status**: pending
**Pattern-Key**: decision.unverified-claim
**Recurrence-Count**: 1
**First-Seen**: 2026-08-06
**Last-Seen**: 2026-08-06

### 问题
报告"测试已通过"时本轮没有跑过测试，用户复核后发现测试实际未执行。

### 证据
- 会话第 12 轮宣告完成，该轮及之前没有测试类工具结果
- 第 14 轮用户指出后重跑，3 个用例失败

### 处置
完成声明必须附可观察证据。本次属高危不变量（会产出错误结果），一次即申请固化。

### Metadata
- 去向: 项目流程文档（待批准）
- 相关文件: docs/workflow.md
- See Also: —
```

### 字段说明

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| ID | `RETRO-YYYYMMDD-XXX` | XXX 为当日序号或 3 位随机字符。前缀不用 `LRN-`：`.learnings/` 是公共目录，别的工具也用 `LRN-YYYYMMDD-XXX`，同一天会撞号，`See Also` 也会指向歧义 |
| `类别` | 八类之一 + 层号 | 取自 `SKILL.md` 第 2 节地图，一条只有一个主类别 |
| `严重程度` | `高` / `中` / `低` | 与主报告一致 |
| `Status` | 见下表 | 条目的生命周期状态 |
| `Pattern-Key` | `类别.症状` | 去重与计数的唯一依据，标准键见 [failure-map.md](failure-map.md) |
| `Recurrence-Count` | 整数 | 命中同一 `Pattern-Key` 时 +1，不新建条目 |
| `First-Seen` / `Last-Seen` | `YYYY-MM-DD` | 计数窗口和衰减都基于 `Last-Seen` |
| `Counting` | `frozen` + 理由 | 可选。按现行规则本不该记在这里的旧条目打上它：计数就地停住，不再 +1，也不参与门槛判断 |

### Status 取值

| 值 | 含义 |
| --- | --- |
| `pending` | 已记账，尚未处置 |
| `experiment` | 已作为下次会话的可逆试验提出，等待观察结果 |
| `promoted` | 已固化进长期资产，在 `Resolution` 里写清写到了哪个文件 |
| `resolved` | 对应缺陷已修复并验证通过 |
| `wont-fix` | 判定不值得处置，在 `Resolution` 里写理由 |
| `needs-review` | 已过期待治理，由衰减规则打上 |

处置完成时追加 `### Resolution` 块，写日期、实际改动或提交、一句结论。固化落成了文档而不是约束时，再记一句为什么（`不可机械判定` / `项目无执行点`），判据见下面的形态一节。

## 查重与计数

记账前必须先查重，否则计数不可信。查重要同时看现台账和同目录的旧台账 `LEARNINGS.md`：

```bash
grep -n '\*\*Pattern-Key\*\*: <类别>\.<症状>' .learnings/ledger.md .learnings/LEARNINGS.md 2>/dev/null
```

旧台账不存在时 `grep` 会以退出码 2 结束（有文件读不到），但对存在的那个文件的输出仍然是正确的——别把它当查重失败，看输出而不是退出码。

**只认顶层加粗的 `**Pattern-Key**:`。** 旧台账里可能混着两种来源：本 skill 早期版本写的条目（要合并计数），和别的工具写的同名文件（不能合并——它有自己的类别词表，把它的条目算进来会让固化门槛提前触发）。区分依据是布局：本 skill 的 `Pattern-Key` 是条目顶层的加粗字段，其他工具通常写成 `### Metadata` 下的 `- Pattern-Key:` 列表项。上面的命令已经锚定加粗形式，不要为了"多找一点"放宽它。

1. **命中现台账**：更新那条已有条目——`Recurrence-Count` +1、刷新 `Last-Seen`、把本次证据要点追加进 `### 证据`（保留原有条目，不覆盖）。严重程度只上调不下调。原条目的 `Resolution` 里记着 `项目无执行点` 时，先看项目现在有没有了；有了就按约束形态重判，那句话存在的意义就在这一刻。
2. **只命中旧台账**：在 `ledger.md` 新建同键条目，`Recurrence-Count` 承接旧值加一，`First-Seen` 沿用旧条目的值，并在 `### 证据` 里注明"计数承接自旧台账 `<旧条目 ID>`"。旧文件保持只读——不改、不删、不搬运条目。同时在总体结论里报一句检测到旧台账，建议维护者迁移；不报的话，还没同步到新版本的其他副本会继续往旧文件写，计数静默分裂成两份，谁都到不了门槛。
3. **未命中但语义相近**：用 `grep -h '\*\*Pattern-Key\*\*:' .learnings/ledger.md .learnings/LEARNINGS.md 2>/dev/null | sort -u` 复查一遍。同一问题换了说法时，复用旧键并在新证据里注明措辞差异，优于新造键。
4. **确实是新问题**：新建条目，`Recurrence-Count: 1`，`First-Seen` = `Last-Seen` = 今天。
5. **`Status` 为 `promoted` 或 `resolved` 的条目又复发**：不新建，改回 `pending` 并 +1，在证据里写明"固化后仍复发"——这是固化措施无效的直接信号，比新条目有价值得多。
6. **旧条目按现行规则本不该记在这里**（当初记成了项目问题，这一轮判明它属某个 skill 的缺陷）：不删、不改事实内容，在条目上加一行 `**Counting**: frozen —— <一句理由>`。`Recurrence-Count` 就地冻结、不再 +1，也不参与固化门槛判断；本轮这次按去向走，交证据包、不在这里计数。删掉历史条目会让台账变得不可信，留着不冻结则让项目侧计数虚高——再来一次就把一条该由维护者改的规则推过门槛，那正是"计数跟着去向走"要拦的事。
7. **一次会话只计一次**：同一个问题被主 Agent、子代理和用户各提一遍，仍然只是 1 次。计数数的是复发，不是有几个人说过；同一份证据的多次转述不构成多源佐证。计数虚高会让固化门槛提前触发，把一次会话的证据当成三次。**本轮内真的独立踩了两次，本轮对计数的贡献也只是 1**：新建条目写 `Recurrence-Count: 1`，命中已有条目就 +1（那个 +1 记的是"本轮又出现过"，不是"本轮出现了几次"）。那两次的作用是走 `SKILL.md` 第 5 节的通道二，不是抬计数。这个计数只数会话，`Recurrence-Count ≥ 3` 那条门槛才有意义——它想要的是三个不同会话的独立证据，本轮加两次就等于用一个会话的证据冒充两个。通道二判的是"等下次"这个前提成立不成立，它读证据，不读这个计数。会话内那两次各自的产物写进 `### 证据`，通道依据写进 `### 处置`。

## 固化门槛与提升目标

**计数器跟着去向走。** 一条只在这个仓库成立的问题记在这里；去向是"移交某个 skill 的维护者"的问题不在这里记账，因为它会在用到那个 skill 的每个仓库里各自复发，计数挂在项目上就永远偏低——它的计数由维护者在源仓用 `refine-skill` 累加（[handoff-prompt.md](handoff-prompt.md)）。卡片的**固化**一行写 `<Pattern-Key> | 移交计数 | 不在本台账记账`。

同一个 skill 缺陷在这个仓库里被移交两次不算浪费：那正是维护者需要的第二个数据点。为了"避免重复移交"而在本地记一笔计数，反而会让门槛在项目侧提前触发，把一条该由维护者改的规则拉进项目文档——第 6 节要拦的就是这个。

**纠正类不走门槛，但照常记账。** L1 `知识缺口` 和 L4 `项目实现` 默认走纠正（判据见 `SKILL.md` 第 5 节）。生命周期没有特例：记账发生在批准之前，所以写入时 `Status: pending`；获批、执行并验证之后才改 `resolved`，`Resolution` 写实际改动。批准被拒的保持 `pending`——`resolved` 的定义是"已修复并验证通过"，提前写等于在台账里留一条假事实，而历史条目的事实内容不允许改回去。

记账不因为已经修好就省掉：同一个东西反复错，正是"该立一条规则了"的信号，那时它自己会过固化门槛。

**纠正带一条配套规则时，仍是一条条目。** 比如修完配置，还想立一条"以后改目录结构必先比对收集数量"。两者共用一个 `Pattern-Key`，`Status` 跟本轮实际发生的写入走（纠正执行完就是 `resolved`）。那条规则怎么写进 `### 处置`，看它过没过门槛：没过就注明它是下次会话的可逆试验，下一轮复发时按它有没有被验证有效来判；本轮就过了某条快速通道的（比如那次纠正之外还发现致因是上游改不动的东西），写成本轮一并申请固化并注明走的是哪条通道，卡片的**固化**一行也照这个写——一条条目里"纠正已修 + 规则待批"是正常状态，不必拆成两条。

门槛见 `SKILL.md` 第 5 节。够门槛时，先定形态，再定位置。

**形态只有两种：约束或文档。** 同一条经验可以是一条自动检查，也可以是一句写在文档里的规则。`SKILL.md` 第 4 节的排序里，"编码成约束"排在"补足上下文"前面，所以先问约束能不能用，再考虑写文档。

走约束形态要两条同时成立：

1. **项目里已经存在一个正在运行、并且已经在检查同类事项的执行点**，本次只是往里加一条规则或一个断言——测试、linter、类型、schema、提交钩子、CI 步骤、封装脚本。**新增独立的检查单元算新建**：新建测试文件、新加 CI job、引入一个 linter 插件都是新建，不算"接进已有执行点"。为一条复盘结论引入检查设施是产品决策，只能建议，不在本轮批准范围内。这条还要看范围：该执行点的作用域不能超出本次问题的作用域，改动它也不能需要本仓之外的角色审批（有 `CODEOWNERS` 一类的先确认当前用户是否在其中）——共享 lint 规则和全仓 CI 步骤影响所有人，那是本轮批准者给不了的授权。
2. **误报代价可接受**——一条会误伤正常写法的检查最终会被整体关掉，比不加更糟。

两条不全成立就落文档，这是正常出口，不是降级。走约束形态时，失效条件有标准答案：这条检查开始误报，或者被人用跳过参数绕过。

**落文档时在 `Resolution` 里记一句为什么**：`不可机械判定` 还是 `项目无执行点`。两者性质不同——前者永远不会变，后者会随项目演进而变。项目后来引入了检查设施，`项目无执行点` 那条就该从文档升级成约束，而这句话是下次复发时判断条件有没有变的唯一依据。

判成哪一个要看规则约束的是什么，不是看仓库里有没有设施：**执行点管不到 agent 在会话里的行为**——遗漏用户口头确认的约束、宣称完成时没有证据支撑，这类规则在任何仓库里都记 `不可机械判定`，哪怕这个仓库 CI 齐全。记错了，下次仓库引入 CI 时会被误判成"条件已变，可以升级成约束"，而它其实还是判不了。

位置按主类别选。纠正做完之后仍有一条规则值得固化时——比如修完配置再加一条校验防止重犯——那条也走下表：

| 主类别 | 项目已有执行点可承载时 | 否则写进 |
| --- | --- | --- |
| `背景输入不足` | 通常没有；项目已有任务模板或 issue 模板时，可加一个必填字段 | 项目约束文档或任务模板（写"开工前必须提供什么"） |
| `知识缺口` | 文档里的命令与示例加进已有的冒烟测试；入口路径加进已有的校验脚本 | 出问题的那份文档本身；跨任务常用的写进常驻上下文文件（如 `AGENTS.md`、`rules/`） |
| `使用方式` | 通常没有；项目已有封装入口时，可在里面加一条前置检查 | 给用户的可复制使用说明；够门槛 → 该类任务的任务模板或开局清单 |
| `流程/决策` | 只有约束项目产物的规则可以（大改前有回退点）；约束 agent 会话内行为的不行（遗漏口头约束、无证据宣称完成），那类一律走文档 | 不属于任何 skill 的流程问题在这里计数，提升目标是项目流程文档；属某个 skill 承重规则的按上面的移交处理，不在这里计数 |
| （上一行的落点不存在时） | — | 不新建一份流程文档：写进项目已有的常驻上下文文件（`AGENTS.md`、`rules/`、`CLAUDE.md` 之类），它本来就是每轮都读的地方。连常驻上下文都没有时才提议新建一份，并在批准请求里说明为什么没有更近的落点 |
| `工具使用` | 把正确用法加进项目已有的封装脚本，让错误用法不可达 | 不牵涉 skill 的调用失误在这里计数，提升目标是工具选择与调用契约；属某个 skill 契约的按上面的移交处理，不在这里计数 |
| `项目实现` | 在已有测试里加断言，或在已有配置校验里加一条 | 测试或配置约定文档 |
| `工具本身` / `外部环境` | — 不在项目内固化 | 只在文档记"已知限制 + 可接受绕行"，并保留移交记录；记账只为观察频率 |

固化内容写成短的预防规则——下次动手前要做什么，不是事故复述。原条目改 `Status: promoted`，并在 `Resolution` 里写清写进了哪个文件。

## 衰减治理

`Last-Seen` 距今超过 90 天的条目打 `needs-review` 并降低置信度，避免过期规则继续看起来可靠。

衰减只看 `Last-Seen`（是否还在复发），不看条目有多老：一条早就固化、之后再没复发的规则，说明它在起作用，不该因为"旧"被降级。
