# session-optimize

在会话结束时复盘真实发生的问题，把证据转化为可验证的改进：

- 当前项目内可以解决的，先给出精确方案，获得批准后再执行；
- 需要其他角色、Skill 或环境处理的，生成可直接复制的移交说明；
- 反复出现的问题记进复盘台账，够门槛后申请固化成长期资产。

除追加复盘台账外，**不会修改文件、配置或外部状态**。

## 适用场景

- 本轮出现用户纠正、返工、验证失败或明显成本浪费；
- 出现有直接证据的高风险近失误；
- 怀疑项目知识、背景输入或协作反馈回路存在缺口；
- 本轮反复纠正同一种默认做法或用法，想弄清该改 skill 还是改调用方式；
- 本轮用过子代理、或本可用而没用，怀疑问题出在划分方式上——该拆没拆、拆错边界、把依赖原文的判断拆了出去；
- 希望审视本轮真实发生的方案选择，而不是泛泛评价风格；
- 希望在会话结束前明确什么值得改、由谁处理、什么该固化下来。

问题仍在排查时先使用诊断类 Skill。

`refine-skill` 不是本 skill 的另一个入口：它是 skill 开发者改写自己 skill 的工具，而 `/session-optimize` 的执行者通常只是某个 Skill 的使用者。所以确认某个 Skill 的规则有问题时，默认产出的是给该 Skill **维护者**的移交说明——他看不到本次会话，说明里自带证据；只有本会话本来就在开发或调试那个 Skill 时，才建议在会话末尾直接接 `refine-skill`。

## 如何调用

```text
/session-optimize
```

也可以补充关注点：

```text
/session-optimize

重点检查这轮工具调用为什么返工，以及下次需要提前提供哪些项目背景。
```

首次调用分析当前可见的完整会话；同一会话再次调用时，只分析上次调用后的可见内容。若上次调用点或早期证据已被上下文压缩截断，会退化为只分析当前可见范围，并在结论中明确说明证据边界。

## 失败层地图

候选事件先分流：只有`失败`走层地图。`一次性上下文`和`偏好`不进层地图，但也不是终点，改走[四追问](references/failure-map.md#分流后的追问一次性上下文与偏好去哪)——先问是不是 skill 该声明的输入没声明、是不是 skill 的默认不对，再问使用方式，最后才问用户该给却没给的背景。

一个失败可以在很多层上被描述，但只有一层是最早能挡住它的地方。按 L1 → L5 逐层问，停在第一个能解释失败的层：

| 层 | 类别 | 默认去向 |
| --- | --- | --- |
| L1 输入 | `背景输入不足` | 下次会话输入（用户提供） |
| L1 输入 | `知识缺口` | 项目文档（可申请修改） |
| L1 输入 | `使用方式` | 使用引导（给用户） |
| L2 决策 | `流程/决策` | 属某个 skill 的规则移交该 skill 维护者；只有不属于任何 skill 的流程问题才申请改项目流程文档 |
| L3 执行 | `工具使用` | skill 契约移交该 skill 维护者 |
| L4 承载 | `项目实现` | 项目内修改（可申请）；防护资产走 `immune-debug` |
| L5 环境 | `工具本身` | 只移交平台负责人 |
| L5 环境 | `外部环境` | 只移交该负责人 |

这个顺序不是偏好：越靠前的层，修一次能挡住的下游失败越多，因此它和"在最早的可控边界实施最小改变"是同一把尺子。跳过前面的层直接归到 L5，等于把可以根治的问题记成了不可控的问题。

容易混的四对用反事实判：项目里查得到就是知识缺口，只有用户知道才是背景输入不足；参数用法都改对后仍异常才算工具本身；现象在项目里但由 agent 的选择触发，仍算流程/决策；换个用户在同样场景下也会这么用，就是流程/决策而不是使用方式。定位不了就写`不确定`并说明缺哪条证据。

常见问题的标准分类、判别信号和标准处置见 [references/failure-map.md](references/failure-map.md)——每一层都有一张常见问题表，先复用表里的标准键和处置，再考虑新造。

## 分类依据与设计原则

### 八类四族：按谁能修分组

| 族（谁能修） | 类别 | 共享去向 |
| --- | --- | --- |
| 只有用户能修 | `背景输入不足` · `使用方式` | 给用户的可复制内容 |
| 项目里能修 | `知识缺口` · `项目实现` | 项目文档 / 项目内修改（可申请） |
| skill 能修 | `流程/决策` · `工具使用` | 移交该 skill 维护者（规则 / 契约） |
| 只能移交 | `工具本身` · `外部环境` | 移交负责人 |

4 族 × 2 类完全平衡，每族共享同一个处置去向——定下类别就定下了去向，不必再查一遍表。加 `使用方式`（`usage.*`）之前，"只有用户能修"这一族只有 `背景输入不足` 一个成员，是八类里唯一的不平衡处，这正是补第 8 类的理由：用户能修的问题本来就有两种，一种是没给背景，一种是用法不对，而后者此前没有位置，只能被硬塞进别的类或干脆丢掉。

### 依据溯源

两种切法交叉：族按处置分（谁能修、往哪走），叶子按性质分（这个失败是怎么来的）。性质的区分借自 James Reason 的事故因果模型——潜在条件（写在文档、规则、配置里，事发前就已存在）和主动失误（当场那一下做错了）是两类不同的东西，Swiss Cheese 的防御纵深也正是"停在最早能挡住它的层"的来源。GEMS 对 mistakes（意图本身就错）与 slips/lapses（意图对、执行走样）的区分，是 `流程/决策` 和 `工具使用` 不能合并的理由：前者要改判断，后者要改调用契约，改法完全不同。横向参照，Ishikawa 6M 也落在 6 类左右，说明这个粒度不是随手定的。

这是类比，不是权威。Reason 讲的是人和组织的事故，不是 agent 会话；引它是因为它把"谁能修"和"什么时候能挡住"说清楚了，不是因为它证明了这套分类正确。分类好不好，只看一件事：同一个问题在不同会话里会不会被归到同一类。

### 三条设计原则

1. **停在最早能挡住它的层，不是找唯一根因。** 复杂协作通常没有唯一根因，找它只会让人停在最好写的那一层。
2. **稳定键让复发可数。** 关键词检索会漏掉换了说法的同一个问题，`Pattern-Key` 不会。计数不可信，固化门槛就只是摆设。
3. **两个出口不是终点。** 判成`一次性上下文`或`偏好`只说明它不走层地图，不说明到此为止——这两类常常是 skill 缺陷或使用方式偏差的表象，还要按四追问再问一次"这是谁的问题"，顺序是先问 skill 再问人。

## 固化机制

单次会话是 n=1 的证据，据此写死规则就是过拟合。固化的作用是把"这次"变成"第几次"：

1. **记账**：进入主报告的每个主题追加一条到 `.learnings/ledger.md`。这是唯一免批准的写入——单文件、只追加、可用 git 回退。
2. **查重**：按 `Pattern-Key`（`类别.症状`）检索，命中就给已有条目 `Recurrence-Count` +1，不新建。关键词检索会漏掉换了说法的同一个问题，稳定的键不会。同一个问题被主 Agent、子代理和用户各提一遍仍然只计 1 次——计数数的是复发，不是有几个人说过。
3. **计数器跟着去向走，不跟着类别走**：台账只记这个仓库作用域的复发。去向是"移交某个 skill 的维护者"的问题不在这里记账——同一个 skill 会在多个仓库里被用到，各仓库各记 2 次，哪份台账都到不了门槛，而它其实已经复发 4 次；这类问题的计数由维护者在 skill 源仓用 `refine-skill` 累加。同一类别里不牵涉 skill 的问题照常记账。
4. **够门槛才固化**：

| 条件 | 动作 |
| --- | --- |
| 首次出现且非高危 | 只记账 + 下次会话的可逆试验 |
| 已证实的高危不变量（数据、安全、错误结果） | 一次即可申请固化 |
| 复发 ≥ 3 次，跨 ≥ 2 个会话，都在最近 30 天内 | 申请写入长期资产 |
| 上轮可逆试验被证明有效 | 申请固化为常规做法 |
| `Last-Seen` 距今 > 90 天 | 标 `needs-review` 并降低置信 |

固化内容写成短的预防规则——下次动手前要做什么，不是事故复述。已固化的条目又复发时，不新建条目，而是改回 `pending` 并注明"固化后仍复发"，这是固化措施无效的直接信号。台账格式、字段和状态流转见 [references/learnings-ledger.md](references/learnings-ledger.md)。

## 独立子代理复核

只要存在候选问题且环境支持委派，会创建一个只读子代理做两阶段独立复核：

1. 主 Agent 先发送最小必要的原始证据和用户约束，不发送自己的结论或分层判断，让子代理独立找问题；证据包末尾会交代删掉了什么、为什么，子代理可以点名索取；
2. 再把候选主题、主类别和方案发给同一个子代理，让它检查证据缺口、替代解释、分层是否停得过早或过晚、更小方案、验证方式和遗漏主题；
3. 主 Agent 保留最终判断，并说明与子代理之间的重大分歧。

复盘中主 Agent 既是被复盘对象又是复盘者，委派归纳买的是一个不受自证偏差影响的视角。但同模型、同脚手架的子代理不是独立样本：它能挡自证偏差，挡不住两边共同的盲区。所以**一致不算佐证**——子代理同意时置信度不上升，只有它带来新证据、替代解释或遗漏主题才算增量；逐项全是"保留"反而要回头查证据包是不是把结论一起送过去了。分歧按证据仲裁而不按谁看得多：子代理每条结论都要带证据引用，主 Agent 驳回它提出的遗漏主题也只能用证据驳回，"我有完整会话而它没有"恰恰说明证据包漏了东西，默认是补包重问。子代理不修改任何状态，也不写台账。

环境能力不足时按阶梯降级：候选问题全为低严重度时跳过独立归纳；无法恢复同一子代理时新建第二个只读子代理复核方案；完全无法委派时由主 Agent 按同一清单自查。

## 报告怎么写

报告写给一个没看过这轮过程的使用者：他要能不重读会话就自己判断——这条问题是否真实、值不值得修、批准后会发生什么。每个主题一张卡片：

```text
### 高 · 测试配置目录写错一层，本轮所有测试都在空目录里空跑

- **问题**：`pytest` 收集到 0 个用例却退出码为 0，任何回归都不会被发现。
- **证据**：第 8 轮 `pytest` 输出 `no tests ran`；`tests/config.json:4` 写 `"rootDir": "tests/unit"`，实际用例在 `tests/`。
- **为什么会发生**：L4 · 项目实现 —— 配置改过一次目录结构，没有验证能区分"通过"和"没跑"。
- **怎么修**：`tests/config.json:4` 改为 `"rootDir": "tests"`，1 行，只影响测试收集。
- **改完怎么验**：`pytest` 收集到 12 个用例并全部执行。
- **什么说明没修好**：仍然 0 收集，或收集到无关目录的用例。
- **谁来做**：我改（待批准）。
- **固化**：`project.config-path` | 第 1 次 | 只记账 —— 首次出现，先修不固化。
```

硬性要求：标题是现象和后果而不是分类名；证据指到会话轮次、命令输出或文件行号，指不到就写"无直接证据"；不用只有本 skill 懂的词；不重复叙述成功步骤，不把提案写成已完成。

一轮只有一个决策点：报告末尾请求批准，不同时追问其他问题。没有实质问题时直接写"本轮无需优化"，不启动子代理，也不写台账。

## 审批与边界

每项待修改内容会先列出精确目标和拟议改动、为什么可能预防复发、风险与影响范围、验证方法和什么结果说明改动没用。如果具体改法能从当前项目查到但尚未明确，会先自行只读定位再提交完整方案，不会让用户补本可自行发现的材料。

只有针对当前方案的明确批准才有效。沉默、以前的泛化授权或"看起来合理"不算批准。执行时若需要增加目标、扩大范围或改变产品行为，会停止并重新申请批准。台账豁免只覆盖 `.learnings/ledger.md` 本身，不覆盖顺手清理或任何项目文件——`.learnings/` 是公共目录，同目录里别的工具的文件（含旧台账 `LEARNINGS.md`）可以读来查重，但一律不写。

以下事项只移交，不直接修改：

- 其他 Skill 或 `session-optimize` 自身的规则——移交给它的维护者，由他用 `refine-skill` 改。移交内容是一份可直接复制的**证据包**：现象、逐条 `触发情境 → 错误行为 → 期望行为`、当时 agent 手上有什么、运行的是哪一份副本、复发次数；**不含改法建议**，因为使用侧手上没有那个 skill 的全文，而给出结论会让维护者跳过归因（格式见 [references/handoff-prompt.md](references/handoff-prompt.md)）；
- 全局配置、依赖或插件安装；
- 外部系统、Git 提交或推送；
- 破坏性操作或需要产品决策的行为变化；
- 证据不足或无法验证的建议。

外部故障即使尚未定责，也会移交给能够继续诊断的负责人。移交说明会区分已知事实与不确定处，并给出下一步和可以实际复验的恢复标准，而不会把接收方写成已经证实的根因。
