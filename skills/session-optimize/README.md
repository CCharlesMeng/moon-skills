# session-optimize

在会话结束时复盘真实发生的问题，把证据转化为可验证的改进方案：

- 当前项目内可以解决的，先给出精确方案，获得批准后再执行；
- 需要其他角色、Skill 或环境处理的，生成可直接复制的移交说明。

首次运行只诊断和提案，**不会修改文件、配置或外部状态**。

## 适用场景

- 本轮出现用户纠正、返工、验证失败或明显成本浪费；
- 出现有直接证据的高风险近失误；
- 怀疑项目知识、背景输入或协作反馈回路存在缺口；
- 希望审视本轮真实发生的方案选择，而不是泛泛评价风格；
- 希望在会话结束前明确什么值得改、由谁处理。

问题仍在排查时先使用诊断类 Skill；已经确认是某个 Skill 的规则有问题时使用 `refine-skill`。

## 如何调用

```text
/session-optimize
```

也可以补充关注点：

```text
/session-optimize

重点检查这轮工具调用为什么返工，以及下次需要提前提供哪些项目背景。
```

首次调用分析当前可见的完整会话；同一会话再次调用时，只分析上次调用后的可见内容。若上次调用点或早期证据已被上下文压缩截断，会退化为只分析当前可见范围，并在结论中明确说明证据边界。

## 核心方法

这个 Skill 不只给错误分类，而是要求每项建议都说清：

```text
发生了什么 → 哪些可控条件促成了它 → 准备怎么改
→ 为什么可能减少复发 → 什么结果说明改动没用
```

一项建议必须经得起两个问题：

1. 如果它当时已经存在，这次失败是否会显著更不可能发生？
2. 什么结果会证明它无效或副作用过大？

无法回答第一个问题的建议通常只是相关性；无法回答第二个问题，就无法判断这项改进是否真的有效。

复杂协作通常没有唯一根因。报告关注有证据的可控条件和最有效的改进，不强行制造确定性，也不以“Agent 做错了”作为最终结论。

## 独立子代理复核

只要存在候选问题且环境支持委派，Skill 会创建一个只读子代理做独立复核：

1. 主 Agent 先发送最小必要的原始证据和用户约束，不发送自己的结论，让子代理独立找问题；
2. 再把主 Agent 的候选主题和方案发给同一个子代理，让它检查证据缺口、替代解释、更小方案、验证方式和遗漏主题；
3. 主 Agent 保留最终判断，并说明与子代理之间的重大分歧。

复盘中主 Agent 既是被复盘对象又是复盘者，委派归纳的目的是引入一个不受自证偏差影响的第二视角；证据打包有损，因此子代理结论只用于交叉检验，最终判断始终在主 Agent。

只创建一个子代理，不允许它继续委派或修改状态。证据包不会复制无关全文、完整日志或敏感信息。没有候选问题时不会为了走流程而启动子代理。

环境能力不足时按阶梯降级：候选问题全部为低严重度时跳过独立归纳，只做方案复核；无法在两阶段间恢复同一个子代理时，新建第二个只读子代理复核方案；完全无法委派时由主 Agent 按同一清单自查，不重复尝试已失败的方式。

## 如何选择改进

优先在最早的可控边界实施最小、可逆且足够有效的改变：

1. 消除致因；
2. 把跨情境成立的不变量编码成约束；
3. 缩短反馈，让错误更早暴露；
4. 补足项目知识或上下文；
5. 最后才使用“下次更小心”式提醒。

情境性选择不会被固化成永久禁令。主题按预期风险下降相对于实施成本、上下文占用和副作用排序，最多保留 5 项。

单次事件可以产生下一次会话的可逆试验，但通常不足以把新流程永久写入项目。除非已经证实高危不变量，否则会先观察试验是否有效或问题是否复发，再申请固化。

同一事件链且去向相同的问题，如果能由一组配套改进共同降低风险，会保留为一个主主题；只有能够独立验证或需要不同负责人时才拆分。

## 审批与边界

每项待修改内容会先列出：

- 精确目标和拟议改动；
- 改动为什么可能预防复发；
- 风险与影响范围；
- 验证方法和什么结果说明改动没用。

如果具体改法能从当前项目查到但尚未明确，Agent 会先自行做只读定位，再提交完整方案；不会让用户补本可自行发现的材料，也不会请求一个内容不明确的批准。

只有针对当前方案的明确批准才有效。沉默、以前的泛化授权或“看起来合理”不算批准。执行时若需要增加目标、扩大范围或改变产品行为，Skill 会停止并重新申请批准。

以下事项只移交，不直接修改：

- 其他 Skill 或 `session-optimize` 自身的规则；
- 全局配置、依赖或插件安装；
- 外部系统、Git 提交或推送；
- 破坏性操作或需要产品决策的行为变化；
- 证据不足或无法验证的建议。

外部故障即使尚未定责，也会移交给能够继续诊断的负责人。移交说明会区分已知事实与不确定处，并给出下一步和可以实际复验的恢复标准，而不会把接收方写成已经证实的根因。

## 输出

一次复盘按实际内容输出：

1. 总体结论；
2. 最多 5 条改进主题；
3. 确有必要时的开发者决策建议；
4. 待批准项目改进；
5. 待移交事项；
6. 仅在背景缺口确实导致问题时提供下次会话输入。

空章节会省略。如果没有实质问题，会明确输出“本轮无需优化”。
