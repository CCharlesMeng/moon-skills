# session-optimize

在会话结束时结合用户指导，独立评审目标、流程和交付，把证据转化为可验证的改进：

- 项目里已经错了的东西（过时的文档、写错的配置、缺失的回归），首次发现就给出精确方案，获得批准后直接改；
- 需要其他角色、Skill 或环境处理的，生成可直接复制的移交说明；
- 从一次经验里提炼的规则先记进复盘台账，够门槛后才申请固化成长期资产。

除追加复盘台账外，**未经批准不会修改文件、配置或外部状态**。证据包的落盘与投递走批准门。

## 适用场景

- 本轮出现用户纠正、返工、验证失败或明显成本浪费；
- 出现有直接证据的高风险近失误；
- 怀疑项目知识、背景输入或协作反馈回路存在缺口；
- 本轮反复纠正同一种默认做法或用法，想弄清该改 skill 还是改调用方式；
- 本轮用过子代理、或本可用而没用，怀疑问题出在划分方式上——该拆没拆、拆错边界、把依赖原文的判断拆了出去；
- 流程顺利但想核查是否选对方案、满足目标并正确交付；
- 希望在会话结束前明确什么值得改、由谁处理、什么该固化下来。

问题仍在排查时先使用诊断类 Skill。

`refine-skill` 不是本 skill 的另一个入口：它是 skill 开发者改写自己 skill 的工具，而 `/session-optimize` 的执行者通常只是某个 Skill 的使用者。所以确认某个 Skill 的规则有问题时，默认产出的是给该 Skill **维护者**的移交说明——他看不到本次会话，说明里自带证据；只有本会话本来就在开发或调试那个 Skill 时，才建议在会话末尾直接接 `refine-skill`。

## 如何调用

```text
/session-optimize
```

调用时提供建设性意见，例如关注点、期望或希望挑战的判断；原因猜测会作为待验证假设。没有提供时会追问一次，可回答“不确定，你独立检查”：

```text
/session-optimize

重点检查这轮工具调用为什么返工，以及下次需要提前提供哪些项目背景。
```

首次调用分析当前可见的完整会话；同一会话再次调用时，只分析上次调用后的可见内容。若上次调用点或早期证据已被上下文压缩截断，会退化为只分析当前可见范围，并在结论中明确说明证据边界。

## 失败层地图

候选事件先分流：只有`失败`走层地图。`一次性上下文`和`偏好`不进层地图，但也不是终点，改走[四追问](references/failure-map.md#分流后的追问一次性上下文与偏好去哪)——先问是不是 skill 该声明的输入没声明、是不是 skill 的默认不对，再问使用方式，最后才问用户该给却没给的背景。

先由独立评审对照目标、契约与产物，验证因果及替代解释，再用 L1 → L5 组织结论，选择有证据支持的最早可控边界。类别不是停止调查的条件：

| 层 | 类别 | 默认去向 |
| --- | --- | --- |
| L1 输入 | `背景输入不足` | 下次会话输入（用户提供） |
| L1 输入 | `知识缺口` | 项目文档（可申请修改） |
| L1 输入 | `使用方式` | 使用引导（给用户） |
| L2 决策 | `流程/决策` | 属某个 skill 的规则移交该 skill 维护者；只有不属于任何 skill 的流程问题才申请改项目流程文档 |
| L3 执行 | `工具使用` | skill 契约移交该 skill 维护者 |
| L4 承载 | `项目实现` | 项目内修改（可申请） |
| L5 环境 | `工具本身` | 只移交平台负责人 |
| L5 环境 | `外部环境` | 只移交该负责人 |

来源缺失、过时或矛盾属于知识缺口；正确可达的知识未获取或未应用属于决策问题，具体调用失误属于工具使用。仅用户或上游掌握且当时不可发现的才是背景输入不足。无法验证的根因保留为假设。已证实的偏差可以先报告；待取证的修法不进入批准。反过来，已有独立依据的局部纠正也不必等待深层原因全部查清。

常见问题的标准分类、判别信号和标准处置见 [references/failure-map.md](references/failure-map.md)——每一层都有一张常见问题表，先复用表里的标准键和处置，再考虑新造。

## 分类依据与设计原则

### 八类四族：按谁能修分组

| 族（谁能修） | 类别 | 共享去向 |
| --- | --- | --- |
| 只有用户能修 | `背景输入不足` · `使用方式` | 给用户的可复制内容 |
| 项目里能修 | `知识缺口` · `项目实现` | 项目文档 / 项目内修改（有独立正确性依据与精确改法时，首次即可申请） |
| skill 能修 | `流程/决策` · `工具使用` | 移交该 skill 维护者（规则 / 契约） |
| 只能移交 | `工具本身` · `外部环境` | 移交负责人 |

4 族 × 2 类完全平衡，每族共享同一个处置去向——定下类别就定下了去向，不必再查一遍表。加 `使用方式`（`usage.*`）之前，"只有用户能修"这一族只有 `背景输入不足` 一个成员，是八类里唯一的不平衡处，这正是补第 8 类的理由：用户能修的问题本来就有两种，一种是没给背景，一种是用法不对，而后者此前没有位置，只能被硬塞进别的类或干脆丢掉。

### 依据溯源

两种切法交叉：族按处置分（谁能修、往哪走），叶子按性质分（这个失败是怎么来的）。性质的区分借自 James Reason 的事故因果模型——潜在条件（写在文档、规则、配置里，事发前就已存在）和主动失误（当场那一下做错了）是两类不同的东西，Swiss Cheese 的防御纵深可作为选择可控边界的参考。GEMS 对 mistakes（意图本身就错）与 slips/lapses（意图对、执行走样）的区分，是 `流程/决策` 和 `工具使用` 不能合并的理由：前者要改判断，后者要改调用契约，改法完全不同。横向参照，Ishikawa 6M 也落在 6 类左右，说明这个粒度不是随手定的。

这是类比，不是权威。Reason 讲的是人和组织的事故，不是 agent 会话；引它是因为它把"谁能修"和"什么时候能挡住"说清楚了，不是因为它证明了这套分类正确。分类好不好，只看一件事：同一个问题在不同会话里会不会被归到同一类。

### 三条设计原则

1. **先验证因果，再选择可控边界。** 检查替代解释和共同致因，不因某层能解释现象就停止调查。
2. **稳定键让复发可数。** 关键词检索会漏掉换了说法的同一个问题，`Pattern-Key` 不会。计数不可信，固化门槛就只是摆设。
3. **两个出口不是终点。** 判成`一次性上下文`或`偏好`只说明它不走层地图，不说明到此为止——这两类常常是 skill 缺陷或使用方式偏差的表象，还要按四追问再问一次"这是谁的问题"，顺序是先问 skill 再问人。

## 固化机制

**先分清在修什么。** 项目内的写入分两类。**纠正**是修一个已被证实为错的事实——过时的文档、写错的配置、被吞掉的错误、没覆盖的回归；它的正确性来自项目里已有的权威依据，不是从一个样本泛化，所以首次发现即可申请修改，只需能指到那条依据、且只改回依据说的样子。**固化**是从一次经验里立一条约束未来的规则，才受下面的门槛约束。判据是一句反事实：假设这个问题以后再也不复发，这条改动还该做吗？类别只提供候选去向，不替代依据与改法；L5 只移交。

单次会话是 n=1 的证据，据此写死规则就是过拟合。固化的作用是把"这次"变成"第几次"：

1. **记账**：进入主报告的每个主题追加一条到 `.learnings/ledger.md`。这是唯一免批准的写入——单文件、只追加、可用 git 回退。
2. **查重**：按 `Pattern-Key`（`类别.症状`）检索，命中就给已有条目 `Recurrence-Count` +1，不新建。关键词检索会漏掉换了说法的同一个问题，稳定的键不会。同一个问题被主 Agent、子代理和用户各提一遍仍然只计 1 次——计数数的是复发，不是有几个人说过。本轮内真的独立踩了两次，本轮也只 +1：那两次是用来走快速通道的，不是用来抬计数的。
3. **计数器跟着去向走，不跟着类别走**：台账只记这个仓库作用域的复发。去向是"移交某个 skill 的维护者"的问题不在这里记账——同一个 skill 会在多个仓库里被用到，各仓库各记 2 次，哪份台账都到不了门槛，而它其实已经复发 4 次；这类问题的计数由维护者在 skill 源仓用 `refine-skill` 累加。同一类别里不牵涉 skill 的问题照常记账。
4. **够门槛才固化**（只管立规则那一侧，纠正不适用）：

| 条件 | 动作 |
| --- | --- |
| 未到复发 3 次，且三条快速通道都不成立 | 只记账 + 下次会话的可逆试验 |
| 已证实的高危不变量（数据、安全、错误结果） | 一次即可申请固化 |
| 同一个 `Pattern-Key` 在本轮内独立发生 ≥ 2 次 | 一次即可申请固化 |
| 致因是本仓库无权改的常驻物，且与本次任务无关 | 一次即可申请固化 |
| 复发 ≥ 3 次，跨 ≥ 2 个会话，都在最近 30 天内 | 申请写入长期资产 |
| 上轮可逆试验被证明有效 | 申请固化为常规做法 |
| `Last-Seen` 距今 > 90 天 | 标 `needs-review` 并降低置信 |

门槛守的是"从一个样本外推"这个动作，所以它只在复发概率得靠猜的时候才有意义。三条快速通道各要一条本轮可核的判据，都不接受对复发概率的自评：

- **高危**要后果实际发生过，定级本身按实际后果，不按假想的最坏后果，所以只有"差点"的近失误进不来。
- **本轮内重复**要两次各自独立、各有产物，同一件事被几方转述不算；本轮对 `Recurrence-Count` 的贡献仍是 1，它证的是"等下次"这个前提不成立，不是已经三次了。
- **常驻致因**要给出本仓库改不动它的证据（submodule 上游 remote、第三方文档、划给别的团队的 `CODEOWNERS`），光指到那个东西不够——那个任何主题都指得出。本仓库改得动的一律不走：能指到依据说明它错了就走纠正改掉它，得先有人拍板哪个算对就把裁决交给用户，两种都不是先立一条规则绕开它。

被外部护栏拦下的零代价破坏性动作只能走通道二，不走通道三——破坏性命令的默认值几乎总是本仓库改不动的第三方物，让它开通道等于每个被拦下的动作都能立刻立一条规则。放宽的只有"要不要等复发"，记账、批准、形态判断一概不变。

够门槛之后先定形态，再定位置。两条同时成立才编码成约束：项目里已经存在一个正在运行、并且已经在检查同类事项的执行点（测试、linter、类型、钩子、CI 步骤），本次只往里加一条；误报代价可接受。新建测试文件、新加 CI job、引入 linter 插件都算新建设施，属产品决策，只能建议。不成立就写文档，并在台账里记明原因是"不可机械判定"还是"项目无执行点"——约束 agent 会话内行为的规则（遗漏口头约束、无证据宣称完成）在任何仓库里都是前者。固化内容写成短的预防规则——下次动手前要做什么，不是事故复述。已固化的条目又复发时，不新建条目，而是改回 `pending` 并注明"固化后仍复发"，这是固化措施无效的直接信号。台账格式、字段和状态流转见 [references/learnings-ledger.md](references/learnings-ledger.md)。

## 独立子代理评审

每次先启动干净上下文的只读 subagent，不以报错或候选问题作为启动条件。主流程见 [SKILL.md 第 3 节](SKILL.md#3-子代理独立评审)：

1. 给原始任务、用户指导、有效约束和知识入口，允许独立检索，建立目标与验收基线。skill 流程和实现本身也要接受审查。
2. 再给原始运行记录与产物，核对遗漏和偏差，验证因果链及替代解释。
3. 最后提供主 Agent 的归因与方案，复核是否有证据、能减少复发。

用户的关注点决定优先级，明确的范围限制决定边界。用户猜测不等于根因；同模型的一致意见也不是独立佐证。调查覆盖目标理解、方案、执行、验证和交付，知识消费只是其中一个维度。时间和记录缺口必须说明，不用事后知识归责、不把缺少读取日志当成未读证据。

不能建立干净上下文或委派失败时明确降级为主 Agent 自查，报告“未完成独立评审”。不因问题轻微跳过独立调查；确无问题才不写台账。

## 报告怎么写

报告写给一个没看过这轮过程的使用者：他要能不重读会话就自己判断——这条问题是否真实、值不值得修、批准后会发生什么。每个主题一张卡片：

```text
### #1 · 中 · 测试根目录多写一层，阻塞本轮验证

- **偏差与证据**：第 8 轮项目测试命令收集到 0 项；tests/config.json:4 指向 tests/tests，清单中的 12 项测试都在 tests/。第 9 轮隔离副本只改路径后收集到 12 项并通过。
- **原因判断**：L4 · 项目实现；配置路径错误有单变量对照支持，配置为何写错尚未查明。
- **建议动作**：我将 tests/config.json:4 改为 "rootDir": "tests"（待批准）；仅影响测试收集，可能暴露此前未执行的测试失败。
- **验收**：复用原命令，收集对象须与 12 项清单一致且测试通过；0 收集、对象不符或测试失败均不通过。
- **固化**：project.config-path | 第 1 次 | pending，纠正待批准，不因此立规则。

待批准：#1，仅修改 tests/config.json:4 的 rootDir 并运行上述验证。
```

硬性要求：标题是现象和后果而不是分类名；证据指到会话轮次、命令输出或文件行号，指不到就写"无直接证据"；不用只有本 skill 懂的词；不重复叙述成功步骤，不把提案写成已完成。

入口指导不足时单独提问一次；报告末尾集中请求修改批准，不同时追问其他问题。完成评审且无实质问题才写“本轮无需优化”及核对范围，不写台账。关键证据不足写“暂无法判断”及缺口。

## 审批与边界

每项待修改内容会先列出精确目标和拟议改动、为什么可能预防复发、风险与影响范围、验证方法和什么结果说明改动没用。纠正与固化分两组列出，纠正组可以整批一次批准——它们各自指向独立的权威依据，逐项确认不增加判断力。如果具体改法能从当前项目查到但尚未明确，会先自行只读定位再提交完整方案，不会让用户补本可自行发现的材料。

只有针对当前方案的明确批准才有效。沉默、以前的泛化授权或"看起来合理"不算批准。执行时若需要增加目标、扩大范围或改变产品行为，会停止并重新申请批准。台账豁免只覆盖 `.learnings/ledger.md` 本身，不覆盖顺手清理或任何项目文件——`.learnings/` 是公共目录，同目录里别的工具的文件（含旧台账 `LEARNINGS.md`）可以读来查重，但一律不写。

以下事项只移交，不直接修改：

- 其他 Skill 或 `session-optimize` 自身的规则——移交给它的维护者，由他用 `refine-skill` 改。移交内容是一份可直接复制的**证据包**：现象、逐条 `触发情境 → 错误行为 → 期望行为`、当时 agent 手上有什么、运行的是哪一份副本、复发次数；**不含改法建议**，因为使用侧手上没有那个 skill 的全文，而给出结论会让维护者跳过归因（格式见 [references/handoff-prompt.md](references/handoff-prompt.md)）。证据包先落盘再按源仓位置投递：源仓在当前仓库内，写进 `<当前仓>/.learnings/skill-feedback/`；源仓不在当前仓库内，投递配置的白名单里有它则提交 issue、本地标已投递，无配置、不在白名单或投递失败则只写 `~/.learnings/skill-feedback/`。探测出源仓路径也不自动跨仓库写入，报告里给出同步命令。路径见 [references/feedback-sink.md](references/feedback-sink.md)；
- 全局配置、依赖或插件安装；
- 外部系统、Git 提交或推送——投递反馈是唯一例外，且须配置已把该 skill 列入白名单、正文已在批准门展示、命令由配置提供；
- 破坏性操作或需要产品决策的行为变化；
- 证据不足或无法验证的建议。

投递配置是单一文件 `.feedback-sink.md`，放在本 skill 目录下，由部署方提供，不进 git，打包时不含它：平台、仓库和 CLI 对每个 skill 都一样，只有 label 随 skill 变，所以四条命令全仓只写一份，配置里的白名单声明哪些 skill 的反馈投到平台，命令里的 `{{skill}}` 承担区分。降级有两种，报告里分开说：配置文件不存在写"未检测到投递配置"，配置在而目标 skill 不在白名单写"该 skill 未纳入投递"——前者是故障，补回配置就恢复；后者是部署方的选择，要投就先把它加进名单。两种都只落本地文件，而用户级目录只在使用者自己机器上，不同人之间仍需人工转交。

外部故障即使尚未定责，也会移交给能够继续诊断的负责人。移交说明会区分已知事实与不确定处，并给出下一步和可以实际复验的恢复标准，而不会把接收方写成已经证实的根因。
