# Session Optimize

复盘不是给过去分类，而是让下一次工作更稳。每个主题都要说清五件事：发生了什么、哪些可控条件促成了它、准备怎么改、为什么这项改动可能减少复发，以及什么结果说明改动没用。首次复盘只诊断和提案；不要制造问题，未经用户批准不得修改任何内容。

## 1. 观察

- 分析自上次 `/session-optimize` 以来的可见会话；首次调用时分析当前可见的完整会话。若上次调用点或早期证据已被上下文压缩、不再可见，退化为只分析当前可见范围，并在总体结论中说明证据边界。
- 优先使用会话原文、工具结果、验证记录和实际 diff。只为核实承重事实读取项目，先搜索和缩小范围，不把复盘扩张成全仓库审计。
- 候选事件记为：`触发情境 → 决策或动作 → 可观察结果 → 实际或可信的潜在影响`。
- 只收录具体失败、用户纠正、返工、验证失败、明显浪费，或有直接证据的高风险近失误。正常探索、个人偏好和猜测不算问题。
- 用户明确指出的问题自动成为候选主题。只有检查完证据且确实没有候选主题时，才结束并说明检查范围。
- 同一事件链、同一去向，且能由一组组合改进共同降低风险的事件，合并为一个主主题；必要的次要措施写进同一主题。只有能独立验证或去向不同才拆分，不按日志条数或未经证实的“同一根因”合并。

## 2. 让一个子代理独立复核

复盘中主 Agent 既是被复盘对象又是复盘者。委派归纳不是为了省力，而是引入一个不受自证偏差影响的第二视角：证据打包必然有损，但子代理的结论只用于交叉检验，不替代主 Agent 的判断——主 Agent 保留会话证据和最终判断。

有候选主题且环境支持委派时，只创建一个只读审查子代理，不允许它继续委派。按两阶段使用同一个子代理：

1. **独立归纳**：只发送最小证据包，不发送主 Agent 的候选主题或方案。证据包包含相关会话原文（标明说话者和必要上下文）、工具/验证/diff 的事实片段及用户约束；不复制无关全文或完整日志，删除凭据、个人信息等敏感内容。让子代理独立提出主题，并按开头的五件事分析。
2. **方案复核**：再把主 Agent 的候选主题和拟议改进发给同一个子代理。要求它逐项输出：`保留/修改/删除 | 证据缺口与替代解释 | 改进是否可能减少复发 | 更小方案 | 验证与失效条件`，并报告遗漏主题。

子代理不得修改文件、配置或外部状态。主 Agent 综合复核结果，对重大分歧说明采纳、修改或拒绝的理由。

按可用能力降级，不重复尝试已失败的方式：

- 所有候选主题初判都为`低`严重程度时，跳过独立归纳，只做方案复核（由子代理或主 Agent 承担均可）。
- 环境无法在两阶段间恢复同一个子代理时，新建第二个只读子代理只做方案复核，独立归纳阶段的结论照常采用。
- 完全无法委派或子代理首次调用失败时，说明原因，由主 Agent 按方案复核的同一清单自查。

## 3. 分析并选择改进

对每个候选主题回答：

1. **发生在哪里**：现象在哪里出现？Agent 的选择、参数或解释错误仍是 Agent 行为；只有正确使用组件后组件仍异常，才算组件故障。
2. **可控条件**：什么可控条件提高了失败概率？不要把“Agent 做错了”当结论，也不要假装复杂协作只有唯一根因；证据不充分时明确写“不确定”。
3. **改进为什么可能有效**：如果这项改进当时已经存在，本次失败是否会显著更不可能发生？答案不明确，就不把它当对策。
4. **失效条件**：什么结果会说明改进没用或副作用过大？永远不会失败的验证没有判断力。

只有同时满足以下条件的主题才进入主报告：有具体证据；可能复发或单次影响足够高；存在可执行改进或明确移交对象；能够说明什么结果代表改进无效。偶发且已恢复、没有可复用预防措施的事件默认忽略。

选择改进时：

- 在最早的可控边界实施最小、可逆且足够有效的改变。依次考虑消除致因、把不变量编码成约束、缩短反馈、补足上下文，最后才是提醒“更小心”。
- 只把跨情境成立的不变量写成硬规则；依赖情境的选择写成决策原则，避免一次失败生成永久禁令。
- 区分提出试验与持久化规则所需的证据：单次事件可以触发下次会话中的可逆试验；除非已证实高危不变量，否则要等复发或试验有效后，才申请写入项目流程。
- 按`预期风险下降 ÷ 实施成本、上下文占用与副作用`定性排序，最多保留 5 个主题。

只评价会话中真实发生、当时已有证据且存在替代方案的开发者决策。区分`错误决策`、`可优化决策`和`信息不足`；明确比较替代方案相对原方案的收益、代价与残留风险，并提炼可复用的决策原则。不要用事后信息或个人风格归咎开发者。

严重程度只用`高`（阻塞、错误结果或数据/安全风险）、`中`（返工、明显降质或重复浪费）、`低`（轻微效率或清晰度损失）。

## 4. 决定修改还是移交

读取和检查可以直接进行；写文件、改配置、运行会改变状态的命令或操作外部系统都必须先批准。

具体改法尚不明确但能从当前项目查到时，先自行只读定位；不要把本可发现的材料退回给用户，也不要虚构方案或请求笼统批准。定位后再提交完整审批方案。

项目内修改只有在目标明确、局部可回退、不改变未确认的产品行为、证据能说明它可能减少复发、现有环境可验证且不依赖外部状态时，才进入审批。每项先展示：

- 精确目标、拟议改动和因果理由；
- 风险、影响范围；
- 验证方法及失效条件。

随后请求用户明确批准，可逐项或整批批准。沉默、推断、历史泛化授权都不算批准。获批后只实施批准范围；若目标扩大、出现新副作用或行为变化，停止并重新申请批准。

其他 Skill 规则统一移交 `refine-skill`。全局配置、依赖或插件安装、外部系统、Git 发布、破坏性操作、产品决策，以及证据不足或无法验证的事项只移交；项目内有权威依据可修复的知识资产可以进入审批。

外部故障尚未定责也要移交给能继续诊断的负责人：写清已知事实、不确定处、下一步和可观察的恢复标准，但不要把移交对象写成已经证实的根因。

## 5. 输出

不要默认创建复盘文件。输出：

1. **总体结论**：问题数、待批准修改数；没有实质问题时明确写“本轮无需优化”。
2. **改进主题**：最多 5 项，列出`严重程度 | 证据 | 可控条件与拟议改进 | 验证及失效条件 | 去向`。
3. **开发者决策建议**：仅在确有决策问题时给出当时证据、判断、替代方案、权衡和下次原则。
4. **待批准项目改进**：精确目标、改动、理由、风险、验证，并明确请求批准。
5. **待移交事项**：负责角色、未修改原因、建议方案、验证标准和可复制说明。
6. **下次会话输入**：只在背景缺口确实导致本轮问题时给出可复制说明。

省略空章节，不重复成功步骤，不把建议写成已完成。用户批准执行后，另列**已批准并完成的改进**，说明批准范围、实际改动和验证结果。
