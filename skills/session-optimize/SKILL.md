# Session Optimize

复盘不是给过去分类，而是让下一次工作更稳。每个主题都要说清五件事：发生了什么、哪些可控条件促成了它、准备怎么改、为什么这项改动可能减少复发，以及什么结果说明改动没用。

不要制造问题。除第 5 节的复盘台账外，未经用户批准不得修改任何内容。

## 交互规范

遵守 [Skill-User 交互黄金原则](../../PRINCIPLES.md)。

| Phase | 用户可见内容 | 结束方式 |
| --- | --- | --- |
| 1 — 观察 | 内联进 Phase 6 的报告（P6） | — |
| 2 — 定位 | 内联进 Phase 6 的问题卡片（P6） | — |
| 3 — 复核 | 仅在与子代理有重大分歧时单独一行说明（P6） | — |
| 4 — 选择改进 | 内联进 Phase 6 的问题卡片（P6） | — |
| 5 — 固化 | 内联进 Phase 6 的问题卡片与总体结论（P6） | — |
| 6 — 报告 | 总体结论 + 问题卡片 + 待批准清单 | 批准门（P4，本轮唯一决策点） |
| 7 — 执行 | 三行索引（P5） | — |

## 1. 观察

- 分析自上次 `/session-optimize` 以来的可见会话；首次调用时分析当前可见的完整会话。若上次调用点或早期证据已被上下文压缩、不再可见，退化为只分析当前可见范围，并在总体结论中说明证据边界。
- 优先使用会话原文、工具结果、验证记录和实际 diff。只为核实承重事实读取项目，先搜索和缩小范围，不把复盘扩张成全仓库审计。
- 候选事件记为：`触发情境 → 决策或动作 → 可观察结果 → 实际或可信的潜在影响`。
- 只收录具体失败、用户纠正、返工、验证失败、明显浪费，或有直接证据的高风险近失误。正常探索、个人偏好和猜测不算问题。
- 用户明确指出的问题自动成为候选主题。只有检查完证据且确实没有候选主题时，才结束并说明检查范围。
- 同一事件链、同一去向，且能由一组组合改进共同降低风险的事件，合并为一个主主题；必要的次要措施写进同一主题。只有能独立验证或去向不同才拆分，不按日志条数或未经证实的"同一根因"合并。

## 2. 定位：走一遍失败层地图

一个失败可以在很多层上被描述，但只有一层是**最早能挡住它**的地方。按 L1 → L5 顺序逐层问，**停在第一个能解释失败的层**，把它记为主类别；一个主题只有一个主类别。

这个顺序不是偏好：越靠前的层，修一次能挡住的下游失败越多，因此它和第 4 节选改进用的是同一把尺子——最早的可控边界。跳过前面的层直接归到 L4/L5，等于把可以根治的问题记成了不可控的问题。

| 层 | 类别 | 判别问题 | 默认去向 |
| --- | --- | --- | --- |
| L1 输入 | `背景输入不足` | 目标、约束或项目事实从未提供，且当时无法自行发现？ | 下次会话输入（用户提供） |
| L1 输入 | `知识缺口` | 信息在项目里查得到，但文档缺失、过时或与实现矛盾？ | 项目文档（可申请修改） |
| L2 决策 | `流程/决策` | 信息充分、工具正常，但计划、验证、边界或协作判断本身不当？ | skill 规则移交 `refine-skill`；项目流程文档可申请修改 |
| L3 执行 | `工具使用` | 工具可用，但选型、参数、调用顺序或结果解读错了？ | skill 契约移交 `refine-skill` |
| L4 承载 | `项目实现` | 正确使用之后，项目的代码、测试、配置或运行行为本身有缺陷？ | 项目内修改（可申请）；属可复用防护资产的走 `immune-debug` |
| L5 环境 | `工具本身` | 参数和用法都正确，工具、连接器或平台仍然异常？ | 只移交平台负责人 |
| L5 环境 | `外部环境` | 权限、网络、第三方服务或其他角色负责的条件导致失败？ | 只移交该负责人 |

三对最容易混的，用反事实判：

- `背景输入不足` vs `知识缺口`：项目里查得到就是知识缺口；只有用户或上游知道才是背景输入不足。
- `工具使用` vs `工具本身`：把参数和用法都改对之后仍然异常，才算工具本身；否则是工具使用。
- `流程/决策` vs `项目实现`：现象出现在项目里但由 agent 的选择、参数或解释触发，仍是流程/决策；只有正确使用后组件仍异常才是项目实现。

不要把"Agent 做错了"当结论，也不要假装复杂协作只有唯一根因。走完地图仍无法归类时写`不确定`，并说明缺哪一条证据，不要为了填格子硬选一层。

常见问题的标准归类、判别信号和标准处置见 [failure-map.md](references/failure-map.md)——先在目录里找同类，再考虑新造。

严重程度只用`高`（阻塞、错误结果或数据/安全风险）、`中`（返工、明显降质或重复浪费）、`低`（轻微效率或清晰度损失）。

## 3. 让一个子代理独立复核

复盘中主 Agent 既是被复盘对象又是复盘者。委派归纳不是为了省力，而是引入一个不受自证偏差影响的第二视角：证据打包必然有损，但子代理的结论只用于交叉检验，不替代主 Agent 的判断——主 Agent 保留会话证据和最终判断。

有候选主题且环境支持委派时，只创建一个只读审查子代理，不允许它继续委派。按两阶段使用同一个子代理：

1. **独立归纳**：只发送最小证据包，不发送主 Agent 的候选主题、分层结论或方案。证据包包含相关会话原文（标明说话者和必要上下文）、工具/验证/diff 的事实片段及用户约束；不复制无关全文或完整日志，删除凭据、个人信息等敏感内容。让子代理独立提出主题，并按开头的五件事分析。
2. **方案复核**：再把主 Agent 的候选主题、主类别和拟议改进发给同一个子代理。要求它逐项输出：`保留/修改/删除 | 证据缺口与替代解释 | 分层是否停得过早或过晚 | 改进是否可能减少复发 | 更小方案 | 验证与失效条件`，并报告遗漏主题。

子代理不得修改文件、配置或外部状态，也不得写台账。主 Agent 综合复核结果，对重大分歧说明采纳、修改或拒绝的理由。

按可用能力降级，不重复尝试已失败的方式：

- 所有候选主题初判都为`低`严重程度时，跳过独立归纳，只做方案复核（由子代理或主 Agent 承担均可）。
- 环境无法在两阶段间恢复同一个子代理时，新建第二个只读子代理只做方案复核，独立归纳阶段的结论照常采用。
- 完全无法委派或子代理首次调用失败时，说明原因，由主 Agent 按方案复核的同一清单自查。

## 4. 选择改进

对每个候选主题回答：

1. **可控条件**：什么可控条件提高了失败概率？证据不充分时明确写"不确定"。
2. **改进为什么可能有效**：如果这项改进当时已经存在，本次失败是否会显著更不可能发生？答案不明确，就不把它当对策。
3. **失效条件**：什么结果会说明改进没用或副作用过大？永远不会失败的验证没有判断力。

只有同时满足以下条件的主题才进入主报告：有具体证据；可能复发或单次影响足够高；存在可执行改进或明确移交对象；能够说明什么结果代表改进无效。偶发且已恢复、没有可复用预防措施的事件默认只记台账，不占主报告。

选择改进时：

- 在第 2 节定位到的那一层实施最小、可逆且足够有效的改变。依次考虑消除致因、把不变量编码成约束、缩短反馈、补足上下文，最后才是提醒"更小心"。
- 只把跨情境成立的不变量写成硬规则；依赖情境的选择写成决策原则，避免一次失败生成永久禁令。
- 按`预期风险下降 ÷ 实施成本、上下文占用与副作用`定性排序，最多保留 5 个主题。

只评价会话中真实发生、当时已有证据且存在替代方案的开发者决策。区分`错误决策`、`可优化决策`和`信息不足`；明确比较替代方案相对原方案的收益、代价与残留风险，并提炼可复用的决策原则。不要用事后信息或个人风格归咎开发者。

## 5. 固化：让同一个坑只踩三次

单次会话是 n=1 的证据，据此写死一条规则就是过拟合。固化机制的作用是把"这次"变成"第几次"：先记账让复发可数，够门槛才申请写入长期资产。

**记账**是本 skill 唯一免批准的写入：每个进入主报告的主题，追加一条到项目根的 `.learnings/LEARNINGS.md`（不存在则创建）。只允许追加新条目和更新已有条目的计数字段；单文件、可用 git 回退。写入前不需批准，写入内容在总体结论里说明。条目格式、ID 规则和字段见 [learnings-ledger.md](references/learnings-ledger.md)。

**先查重，再记账。** 关键词检索会漏掉换了说法的同一个问题，`Pattern-Key` 不会——计数可信，固化门槛才有意义：

```bash
grep -n "Pattern-Key: <类别>.<症状>" .learnings/LEARNINGS.md
```

命中就更新已有条目（`Recurrence-Count` +1、刷新 `Last-Seen`、必要时补 `See Also`），不新建重复条目。`Pattern-Key` 是 `类别.症状` 两级、小写、连字符；症状要泛化到能复发，不含文件名、版本号或主机名。标准键取自 [failure-map.md](references/failure-map.md)，先复用近似键再新造。

**固化门槛**：

| 条件 | 动作 |
| --- | --- |
| 首次出现且非高危 | 只记账，改进以下次会话的可逆试验形式提出，不写长期资产 |
| 已证实的高危不变量（数据、安全或错误结果），且项目内有权威依据 | 一次即可申请固化 |
| `Recurrence-Count ≥ 3`，跨 ≥ 2 个会话，且都落在最近 30 天窗口内 | 申请写入长期资产 |
| 上一轮的可逆试验已被证明有效 | 申请把试验固化为常规做法 |
| `Last-Seen` 距今 > 90 天 | 标 `needs-review` 并降低置信，不让过期规则继续看起来可靠 |

固化目标按主类别取第 2 节的默认去向。固化内容写成短的预防规则——下次动手前要做什么，不是事故复述。跨 skill 的规则一律移交 `refine-skill`，不在这里改写。

## 6. 决定修改还是移交

读取和检查可以直接进行；除第 5 节的台账追加外，写文件、改配置、运行会改变状态的命令或操作外部系统都必须先批准。台账豁免只覆盖 `.learnings/LEARNINGS.md` 本身，不覆盖顺手清理、同目录其他文件或任何项目文件。

具体改法尚不明确但能从当前项目查到时，先自行只读定位；不要把本可发现的材料退回给用户，也不要虚构方案或请求笼统批准。定位后再提交完整审批方案。

项目内修改只有在目标明确、局部可回退、不改变未确认的产品行为、证据能说明它可能减少复发、现有环境可验证且不依赖外部状态时，才进入审批。每项先展示精确目标与拟议改动、因果理由、风险与影响范围、验证方法及失效条件，随后请求用户明确批准，可逐项或整批批准。沉默、推断、历史泛化授权都不算批准。获批后只实施批准范围；若目标扩大、出现新副作用或行为变化，停止并重新申请批准。

其他 Skill 规则统一移交 `refine-skill`。全局配置、依赖或插件安装、外部系统、Git 发布、破坏性操作、产品决策，以及证据不足或无法验证的事项只移交；项目内有权威依据可修复的知识资产可以进入审批。

外部故障尚未定责也要移交给能继续诊断的负责人：写清已知事实、不确定处、下一步和可观察的恢复标准，但不要把移交对象写成已经证实的根因。

## 7. 输出

不产出复盘报告文件；台账是唯一写入。报告写给一个没看过这轮过程的使用者：他要能不重读会话就自己判断——这条问题是否真实、值不值得修、批准后会发生什么。

- 标题就是结论，用具体现象和后果，不要写成分类名。
- 证据必须可核：指到会话轮次、命令与输出、文件与行号。指不到具体位置就写"无直接证据"，不用"多次观察到"充数。
- 修法具体到能照着做：目标、改动、影响面。说不清就先只读定位再报。
- 不用只有本 skill 懂的词：`可控条件`写成"什么让它更容易发生"，`失效条件`写成"什么结果说明这次改动没用"。
- 不重复叙述成功步骤，不把提案写成已完成，不解释流程（P3）。

先给一句总体结论：发现几个问题、几项待批准修改、台账新增和更新各几条。没有实质问题时直接写"本轮无需优化"并停止，不启动子代理，不写台账。

每个主题一张卡片，最多 5 张，按严重程度排序：

```text
### <严重程度> · <一句话说清现象和后果>

- **问题**：现在会怎样，影响谁。
- **证据**：2-3 条可核引用（会话轮次 / 命令与输出 / 文件:行）。
- **为什么会发生**：<L 层 · 类别> — 什么让它更容易发生；证据不足写"不确定"。
- **怎么修**：目标 + 具体改动 + 影响面。
- **改完怎么验**：可观察的结果。
- **什么说明没修好**：能推翻这次改动的结果。
- **谁来做**：我改（待批准）/ 你提供 / 移交 <角色或 skill>。
- **固化**：`Pattern-Key` | 第 N 次 | 只记账 / 申请固化 / 不固化 —— 一句理由。
```

其余章节按需给出，空的省略：

| 章节 | 只在什么时候写 | 内容 |
| --- | --- | --- |
| 开发者决策建议 | 确有当时证据充分却选错的决策 | 当时证据、判断、更小方案的收益与代价、残留风险、下次原则 |
| 待批准项目改进 | 有项目内可修项 | 精确目标、改动、理由、风险、验证；明确请求批准 |
| 待移交事项 | 有跨边界项 | 负责角色、未修改原因、建议方案、验证标准、可直接复制的移交说明 |
| 下次会话输入 | 背景缺口确实导致本轮问题 | 可直接复制的背景说明 |
| 被抑制的候选 | 有偶发已恢复事件 | 一行说明为什么不列为主题及台账去向 |

一轮只有一个决策点（P1）：报告末尾请求批准，不同时追问其他问题。批准并执行后按三行索引收口（P5），产出一行写实际改动的文件和台账条目 ID。
