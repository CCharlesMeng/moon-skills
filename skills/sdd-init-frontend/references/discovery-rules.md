# 发现规则集

每份 baseline 文件配一组**结构判据**。判据看的是「这个文件导出什么、被谁引用、内部调用了什么」，**不是文件名里有没有出现某个英文单词**。

## 为什么不按文件名匹配

按名字猜会同时犯两种错，且两种错互相掩盖。实测一个 8 个源文件的 React 仓，按词表匹配的识别率是 1/5：

| 漏掉的 | 是什么 | 漏的原因 |
| --- | --- | --- |
| `components/StatCard/` | 通用构件 | 词表里没有「组件」这一类 |
| `usePortfolioSummary.ts` | 数据 hook | 判据是路径含 `hook`，而 React hook 叫 `useXxx` |
| `lib/format.ts` | 渲染辅助 | 判据是路径含 `util` |
| `styles/tokens.css` | 设计 token | 判据是分词匹配 `token`，被复数的 `s` 挡掉 |

同时**误吸**：`features/` 含 `feature`、`format.ts` 含 `form`，整棵业务目录被当成范式证据。

结论：候选靠结构判据取，**每条候选都要打开代码确认**才能写成条目。判据只负责把搜索面收窄，不负责下结论。

## 通用取候选手段

| 手段 | 用途 |
| --- | --- |
| 按目录列文件 | 圈定首扫范围内的候选集 |
| 搜导入语句 | 数「被几处引用」，这是通用层与业务层的分层判据 |
| 搜导出符号 | 判断一个文件对外提供什么 |
| 搜框架专有标记 | 判断栈与角色（见各文件的栈内表现） |

「被两个以上**消费单元**引用」是通用层的判据，**不看目录名叫不叫 `common`**。放在 `components/` 下但只有一处引用的，仍然只进路由索引。

消费单元的粒度按 `structure.md` 记的目录实况定，不写死成「特性目录」：按特性分目录的仓算特性目录，按类型分目录的仓算使用它的业务模块，平铺仓算页面文件，`组件库` 形态不适用（对外导出的一切都是公开 API）。写死成特性目录会让这条判据**在平铺仓里根本无法执行**，而平铺仓恰恰最需要「哪些是真通用」这个结论。

### 框架专有标记速查

「搜框架专有标记」要有具体标记才可执行。标记按栈列齐，**一栈都不缺**——只写一栈的标记等于把那一栈的语汇当成通用语汇，换个栈就整节判空：

| 栈 | 构件 | 视图辅助 | 请求出口 | 路由装配 | 状态容器 |
| --- | --- | --- | --- | --- | --- |
| React / Preact / Solid | JSX 返回值 + 框架 hook 调用 | 被构件引用的纯函数 | 客户端实例的构造调用 | 路由组件树，或路由对象数组 | context provider，或 store 读取钩子 |
| Vue | 单文件组件 / `defineComponent` / `<script setup>` | 自定义指令注册 | 客户端实例的构造调用 | `createRouter` + 路由记录数组 | store 定义函数 / `provide` |
| Svelte | `.svelte` 文件 / `$` 前缀响应式声明 | `use:` action | 客户端实例的构造调用 | 文件式路由目录约定，或路由库入口 | 可读 / 可写容器的构造函数 |
| Angular | 组件装饰器 + 模板引用 | 管道装饰器 / 指令装饰器 | 注入式 HTTP 客户端的可注入包装 | 路由模块注册 + 懒加载声明 + 守卫接口实现 | 可注入单例 / 可观察流容器 |
| 小程序 | 平台组件注册 API | 模板过滤 / 处理函数文件 | 平台 request API 的包装 | 页面注册清单 + 分包配置 | app 实例上的全局字段，或平台状态库 |

这些是**框架 API 名，不是命名习惯**。搜它们等于搜「这个文件在框架里扮演什么角色」，与搜文件名里有没有某个英文单词不是一回事——角色由框架定义，文件名由作者当时的心情定义。

**不按文件名或目录名的词表取候选**：`hooks/`、`util/`、`guard`、`permission` 这一类一律不用，理由见[开头的实测](#为什么不按文件名匹配)——召回 1/5，同时把整棵业务目录误吸成范式证据。

标记只负责把搜索面收窄，**每条候选仍须打开代码确认**才能写成条目。表里没有本仓所用栈时，按同样的列去找该栈定义角色的 API，不要退回按名字猜。

## 先定形态，它改判据

栈签名是框架与**形态**两条正交事实，形态必须在其余文件之前定出来，因为下面多组判据依赖它。判据仍看结构，不看名字：

| 形态 | 判据 |
| --- | --- |
| `组件库` | 包清单声明了对外导出入口（`exports` / `main` / `module` / `types`）且构建目标是库；**没有**挂载到 DOM 根节点的应用入口；对外导出面是组件符号的集合 |
| `微前端子应用` | 导出挂载 / 卸载生命周期符号（`bootstrap` / `mount` / `unmount` 或框架等价物），且构建配置把本仓声明为远端暴露 |
| `微前端宿主` | 源码里有运行时加载远端模块的调用，或构建配置声明了 remotes / 子应用注册表 |
| `小程序` | 平台配置文件 + 页面与组件注册 API + 平台特有标签与样式单位；网络请求走平台 API 而非 `fetch` / `axios` |
| `应用` | 有挂载到 DOM 根节点的入口。**默认值**；定不出别的就按这个，并在结论里说明 |

一个仓可以同时是子应用和宿主（多层微前端），如实写两条。形态与框架都写进 `structure.md` 的栈签名，不单独开文件。

形态改判据的地方只有这些，**其余一律走 `应用` 默认，不做形态 × 文件的全矩阵**：

| 形态 | 受影响的判据 |
| --- | --- |
| `组件库` | `components.md` 的通用 / 业务分层判据整体失效，对外导出的构件全部进详表；`routing.md` 与多半的 `api.md` 无内容因此整份删；`structure.md` 增收对外导出面与版本约定 |
| `微前端子应用` | **搜不到统一请求出口时不得直接判「无统一出口」**——出口可能在宿主，要先确认宿主是否注入。增收挂载契约、宿主注入了什么、共享依赖版本约束、样式隔离方式 |
| `微前端宿主` | 增收子应用注册表与加载方式、下发给子应用的能力；`routing.md` 要写清路由在宿主与子应用之间怎么分配 |
| `小程序` | `api.md` 的统一出口判据改成「哪个文件封装了平台 request API」；`styling.md` 的 token 机制与单位按平台实况；`routing.md` 是页面栈与分包配置 |

## `structure.md` — 这是什么栈、什么形态？代码放哪、怎么命名？

形态判据见[上一节](#先定形态它改判据)。框架判据按框架专有标记而不是包名字符串：

| 栈 | 判据 |
| --- | --- |
| React / Preact / Solid | 源码里出现 JSX 返回值 + 框架 hook 调用；构建配置挂了对应插件 |
| Vue | 单文件组件，或 `defineComponent` / `<script setup>` |
| Svelte | `.svelte` 文件，或 `$` 前缀响应式声明 |
| Angular | 装饰器（组件、注入、模块）与依赖注入构造参数 |

不要把 `@types/*`、构建插件、渲染适配包与框架本体并列成一张「框架候选表」——那张表回答不了「这是什么栈」，下游拿它选检视判据会选空。**结论必须是一个具名的栈加一个具名的形态。**

目录实况写**实际形态**，不写应有形态：是按特性分目录、按类型分目录，还是页面平铺。平铺就写平铺，这对下游同样有用。它同时定义了[消费单元](#通用取候选手段)的粒度，所以必须写出来。

命名约定只写**能从多个样本归纳出来的**，而且按本仓所用栈的语汇归纳，不套别栈的习惯：组件文件与目录同名、取数单元统一前缀、样式文件与组件同目录。只有一个样本时不算约定。

同时收「某类东西写在哪个层」这一族，判据都是「找到它、看它在哪个目录、看谁引用它」：

| 目标 | 结构判据 |
| --- | --- |
| 校验规则（schema） | 声明校验形状的模块在哪个层，被谁引用 |
| 共享类型定义 | 只导出类型的模块在哪个层 |
| 领域逻辑 | 不导入任何框架符号、只处理业务规则的模型与用例在哪个层；**没有就如实写没有**，不要把它描述成应该有的分层 |
| i18n 文案资源 | 语言资源文件的位置与命名，以及语言键的组织方式 |
| 监控 SDK 初始化 | 上报 SDK 的初始化调用在哪个入口文件 |
| monorepo 跨 app 共享包 | 本 app 引用了仓内哪些内部包，引用方式是工作区协议还是路径别名 |
| 对外导出面（仅 `组件库`） | 包清单的导出入口指向哪个文件，以及版本与破坏性变更约定 |

## `runtime.md` — 怎么装、怎么起、跑哪些质量命令？

来源是包清单的 script 段、锁文件、Node 版本声明、环境模板、构建与代理配置。**体积与性能预算检查命令也在这里**——它是一条质量命令，不是独立关注点。

**只写 script 名，不写展开后的命令行。** 转述必然有损——曾经把带端口参数的启动脚本转述成不带参数的包管理器调用，端口就此丢失。

只有代码读不出的隐性坑才写正文：必须先起 mock 才能跑某类测试、某命令必须在仓根而非 app 目录跑、某命令依赖外部服务因此不可缓存。

环境变量只记键名、是否敏感、有无模板默认值。**值一概不记。**

质量命令节带一个整数版本号，命令有实质变动时手动加一。

## `components.md` — 拼界面时有哪些现成构件可用？

| 角色 | 结构判据 | 栈内表现 |
| --- | --- | --- |
| 构件 | 导出一个返回视图的符号 | JSX 返回值 / 单文件组件 / `.svelte` / 组件装饰器 / 小程序组件注册 |
| 通用层 | 被两个以上消费单元引用 | 与目录名无关 |
| 业务层 | 只被一个消费单元引用 | 归 `routing.md` 的路由索引，不进本文件 |
| 渲染辅助 | 提供**展示用变换或界面级行为增强**，不发请求、不持有服务端数据，且被构件或模板消费 | 纯函数（各栈通用）/ Vue 自定义指令 / Svelte `use:` action / Angular 管道与指令 / 小程序模板处理函数 |
| 第三方 UI 库 | 包清单里的 UI 组件库依赖，**且**源码或模板里真的引用了它的组件符号 | 各栈各有其库；判据是「有没有用」而不是「装没装」 |
| 库的仓内封装层 | 导出返回视图的符号，其内部渲染的是 UI 库的组件 | 与目录名无关 |

`组件库` 形态下通用 / 业务这条判据不适用：对外导出的构件全部进详表，引用次数只作为参考信息。

**渲染辅助的判据不能写成「导出纯函数」。** 各栈的模板级辅助不都是函数：自定义指令与 action 是带生命周期的对象或函数包装，管道是类。按「纯函数」字面执行会在这几栈里把整节判空，而它们恰恰是这些栈里展示逻辑最常见的落点。判据落在**做什么**（变换展示值、增强界面行为）而不是**是什么形状**。

渲染辅助同时收两类跨关注点入口，判据同上：**取文案的入口**（i18n）与**界面级权限判定辅助**。它们不单独开文件。

UI 库那两行的关键结论是**「使用点是否都经仓内封装」**，判法与 `api.md` 的出口一致：全经封装 → 写成规范；直接引库与经封装混用 → 写「无统一做法」，并说明检视不得据此判「绕过封装」。库导出了哪些组件不写。

构件条目写「何时用」与「不该用它做什么」——后者代码里没有，是最值钱的部分。props 有哪几个不写，代码里有。

## `routing.md` — 加一个页面 / 一条路由要动哪几处？

| 目标 | 结构判据 | 栈内表现 |
| --- | --- | --- |
| 路由表 | 哪个文件构造了路由配置（路径到组件的映射），且被应用入口消费 | 路由配置数组 / 路由模块 / 页面文件目录约定 / 小程序页面注册清单 |
| 文件式路由 | 存在「目录结构即路径」的约定：页面文件所在目录 + 文件名到路径的映射规则 | 与显式路由表互斥，写到哪一种就不写另一种 |
| 守卫 | 在路由进入前执行、能中断或改写跳转的那一处 | 路由钩子 / 高阶包装 / 守卫接口实现 / 页面级鉴权判断 |
| 布局容器 | 被多条路由共用、内部渲染路由出口的构件 | 与普通通用构件的区别是它渲染路由出口 |
| 路由→业务组件索引 | 路由表里每条路径对应的业务构件 | 从 `components.md` 迁来的那节 |
| 参数读取入口 | 取路径参数与查询参数用的符号；是框架原语还是仓内封装 | 有封装就指封装，没有就写「各处直接用框架原语」 |
| 代码分割切点 | 动态导入或懒加载声明出现在哪一层：路由级、页面级，还是完全没有 | 与打包配置一起看；小程序看分包 |

**跳转入口是这份文件最值钱的一条**：搜源码里直接操作 `history` / `location` 或平台跳转 API 的调用点，看是否都经过统一封装。全经封装 → 写成规范；散落多处 → 写「无统一做法」，并说明检视不得据此判违规。

守卫同时是**权限场景**的落点，i18n 的语言前缀路由也在这里。

**具体路由路径与页面清单不进本文件**，理由与 `api.md` 的端点同形：那是 Story 级契约。唯一例外是路由→业务组件索引，它本身就是检索入口。

没有路由库的仓要如实写「无路由机制，单页面挂载」——计划期据此**不发明**一个仓里没有的路由入口，也不假设有页面级代码分割。`组件库` 形态下本文件整份删。

## `api.md` — 怎么跟后端说话？

| 目标 | 结构判据 |
| --- | --- |
| 统一请求出口 | 哪个文件**构造、取得或包装**了 HTTP 客户端，且被多处消费。客户端可能是仓内构造的实例、框架提供靠依赖注入取得的，或平台请求 API 的包装 |
| 有没有绕过 | 全仓搜底层 HTTP 调用，看调用点是否都在统一出口内部 |
| 拦截器与鉴权 | 统一出口内部注册的请求/响应钩子 |
| 错误翻译 | 把 HTTP 状态或后端错误码转成前端错误对象的那一处 |
| mock 约定 | 拦截层的启动方式与 handler 存放位置 |
| 上报出口 | 埋点与前端错误上报的统一封装；它跨进程边界，与请求实例同类 |

**「有几个出口」比「出口是哪个」更重要。** 搜到的底层调用点全在一处内部 → 写成统一出口规范；散落在多处 → 写「无统一做法」规范，并说明检视不得据此判违规。这条结论决定下游要不要判违例，不能省略。

**「构造实例」不是唯一形态。** 有的栈里 HTTP 客户端由框架提供、靠依赖注入取得，仓内的统一出口是一层包着它的可注入服务；按「谁构造了实例」去搜会一无所获，然后判成「无统一出口」。判据要落在**被多处消费的那一层包装**上，构造与注入都算。

`微前端子应用` 形态下搜不到出口时**不得直接判「无统一出口」**：出口可能由宿主注入，要先确认宿主是否下发。

这两条与上一条是同一类错误——**判成「无」会让检视放过真正的绕过**，代价比判错出口位置大得多。

具体接口的 URL、字段、枚举不进本文件。「哪些交互要埋点」同理，那是 Story 级的。

## `data.md` — 拿到的数据在前端怎么持有、怎么流到界面？

| 目标 | 结构判据 | 栈内表现 |
| --- | --- | --- |
| 取数单元 | 导出的符号内部既调用框架状态原语、又经统一请求出口 | hook / composable / 返回可读容器的函数 / 可注入服务 + 可观察流 |
| 缓存库 | 依赖里有取数缓存库且源码里真的用了它的入口 | 与是否装了包无关，要看有没有用 |
| 全局 store | 有 store 定义且被两个以上消费单元消费 | store 定义函数 / 单例可注入服务 / 可写容器 |
| 三态做法 | 取数处对加载中、空结果、失败三种分支的处理形态 | 骨架构件、条件渲染、错误边界 |
| 表单 | 表单库入口 + 校验触发时机（提交时、失焦时、输入时） | 与校验规则写在哪无关，那归 `structure.md` |
| 状态归属边界 | 服务端数据与本地界面状态是否分开持有 | 混装就如实写混装 |
| 权限数据 | 权限 / 角色信息从哪取、持在哪、谁消费 | 守卫怎么用它归 `routing.md` |
| 语言切换状态 | 当前语言持在哪、切换后怎么触发重渲染 | 文案资源位置归 `structure.md` |

三态是下游查得最多的一条。**写清「沿用什么」，让计划期一行引用就够**，不必每个 Story 重新描述。

差架构下的答案同样要写：无缓存无 store、状态留在发起请求的组件内、三态各页自己写——计划期据此不发明 store。

## `styling.md` — 样式值从哪来，允许怎么写？

| 目标 | 结构判据 |
| --- | --- |
| token 集 | 声明了自定义属性、预处理器变量或主题对象字面量的文件 |
| scale 档位 | token 里成组的同前缀命名序列 |
| 主题机制 | 提供主题上下文的那一处 + 消费方式 |
| 工具类方案 | 配置文件里的 scale 定义 + 模板里的类名用法 |
| 硬编码基准 | 有 scale 的维度上，源码里还有多少字面值 |
| 样式隔离（仅微前端） | 子应用样式怎么与宿主隔离：作用域前缀、影子 DOM，还是没有隔离 |

`小程序` 形态的单位与 token 机制按平台实况写，不套 Web 的自定义属性假设。

档位的**具体数值不抄**，只指路到「文件 + 命名前缀」，让消费者一次检索就到。

全硬编码、无 token 的仓要如实写——检视据此**不得**判硬编码违规。

## `testing.md` — 测试用什么写、怎么定位元素、怎么跑？

| 目标 | 结构判据 |
| --- | --- |
| 框架 | 配置文件 + 测试文件里的断言与用例 API 形态；不靠依赖列表猜 |
| 测试类型分布 | 测试文件与被测文件的位置关系、有没有渲染真实组件、有没有起浏览器 |
| 定位约定 | 测试里定位元素用的属性名与查询方式；列表行怎么区分 |
| 跑法 | 单文件怎么跑、按目录怎么跑、要不要先起服务 |

**定位约定是下游写测试时必查的一条**，要写出属性名叫什么、列表类元素按什么区分行。

没有测试框架就如实写——实现阶段据此免测试门禁。
