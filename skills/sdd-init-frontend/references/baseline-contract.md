## 分类依据：文件即消费者问句

**每份文件是一个消费者问句。** 一个条目该不该进某文件，判据只有一条：**它是不是回答该文件问句所必需的事实**。问句自带成员判据，所以不需要靠「类型」列区分同一张表里的条目——**任何需要类型列才能区分内部条目的表，说明它应该被那个类型列切开。**

同一问句内部再按**变更源**切：换后端要改的和换框架要改的不放同一份文件。这是 `api.md` 与 `data.md` 分立的唯一理由。

不按架构分层切分。分层问「它属于哪一层」，一个 `pages/` 平铺、状态全在组件里、各处裸 `axios` 的仓会得到几份空文件，还会诱导把仓库描述成它**应该**的样子——与「无外部基线不得发明视觉数值」是同一类错误。问句问「消费者问什么会找到它」，差架构下同样有答案，而且那个答案往往正是下游最需要的结论。

唯一事实源由三条机制共同保证，不靠自觉：同一条事实只出现在一节、ID 全局唯一、只指路不复制。

## 目录与八份文件

```text
<project-sdd-dir>/frontend-baselines/<repo-id>/
├── index.md        入口与路由，零事实正文
├── structure.md    STRUCT-*
├── runtime.md      RUN-*
├── components.md   COMP-*
├── api.md          API-*
├── data.md         DATA-*
├── styling.md      STYLE-*
└── testing.md      TEST-*
```

| 文件 | 判定问句 | 差架构下的答案（仍有价值） |
| --- | --- | --- |
| `index.md` | 我该读哪条？ | 不适用 |
| `structure.md` | 这是什么栈？代码放哪、怎么命名？ | 「`pages/` 平铺，无特性分层」 |
| `runtime.md` | 怎么装、怎么起、跑哪些质量命令？ | 装起命令永远存在 |
| `components.md` | 拼界面时有哪些现成构件可用？ | 通用详表空则整节删，业务路由索引永远非空 |
| `api.md` | 怎么跟后端说话？ | 「无统一实例，各处裸 `axios`，鉴权头逐处手写，错误码无集中映射」→ 检视据此**不能**判「绕过统一实例」 |
| `data.md` | 拿到的数据在前端怎么持有、怎么流到界面？ | 「无缓存无 store，状态一律留在发起请求的那个组件内，三态各页自己写」→ 计划据此**不要**发明 store |
| `styling.md` | 样式值从哪来，允许怎么写？ | 「全硬编码、无 token，检视不得判硬编码违规」 |
| `testing.md` | 测试用什么写、怎么定位元素、怎么跑？ | 「无测试框架，实现阶段免测试门禁」 |

**「无统一做法」是一等公民条目**，必须写成显式规范，不留空、不省略。它和「有统一做法」一样能决定下游行为，而且往往更关键。

`index.md` 只放三样东西，全部是指向 ID 的行，**零事实正文**：

| 节 | 内容 |
| --- | --- |
| 场景索引 | 「要做列表页 → `COMP-2`、`DATA-1`、`TEST-3`」。场景无穷且互相重叠，只能做索引，不能做切分维度 |
| 单点事实速查 | 栈是什么、测试框架是什么、启动命令是什么，各一行，指向定义它的 ID |
| 文件导航 | 八份文件各一行判定问句 |

**每份文件至少一节；不存在的节整节删掉**，不用「无」「未见」「0 个」填版面。

## 条目格式

### 清单条目（事实）

`<前缀>-<n>`，例如 `DATA-2`。三段，全是代码里读不到的：

| 段 | 内容 |
| --- | --- |
| 指路 | 导出符号 + 所在目录，或文件 + 命名前缀 |
| 一句话 | 是什么、何时用 |
| 证据 | 被几处引用 |

```markdown
| ID | 指路 | 是什么、何时用 | 被引用 |
| --- | --- | --- | --- |
| `API-1` | `src/lib/` 的 `request` 实例 | 全仓唯一 HTTP 出口；任何后端调用都从这里进 | 12 处 |
```

### 规范条目（规则）

`PATTERN-<前缀>-<n>`，例如 `PATTERN-API-1`。**不含路径**——路径只在清单节出现一次。

| 项 | 内容 |
| --- | --- |
| 规则 | 一句可判真假的陈述 |
| 依据清单 | 引用清单条目 ID，不重述路径 |
| 依据样本 | 归纳时看了哪几处代码 |
| 违例判定 | 检视阶段可执行的判法 |

```markdown
#### `PATTERN-API-1` · 请求统一出口

| 项 | 内容 |
| --- | --- |
| 规则 | 所有后端调用必须经 `API-1`，不得直接用 `fetch` / `XMLHttpRequest` / 裸 `axios` |
| 依据清单 | `API-1` |
| 依据样本 | `src/features/portfolio/`、`src/features/checkout/` 共 12 处调用点 |
| 违例判定 | 源码里出现 `axios.` / `fetch(` 而所在文件未从 `API-1` 导入 |
```

ID **只增不改号**。前缀即命名空间，各文件独立编号，并行追加不冲突。`PATTERN-API-1` 的命名空间段仍是 `PATTERN`，按 ID 精确回读与 `PATTERN-*` 全目录 grep 都成立。

## 只指路不复制

**硬门禁。判据：能从某个文件里逐字读到的话，就别写，写路径；必须看多个文件才能得出的，才写。**

| 不该抄（代码里已明确表达） | 该写（只能归纳） |
| --- | --- |
| `request` 导出了哪几个方法、签名长什么样 | 「所有请求必须走 `API-1`，不得直接 `axios`」 |
| 某个卡片组件的 props 有哪几个 | 「该组件用于单个指标数值，不要做多值对比」 |
| 间距档位的具体像素值 | 「间距只能取仓内 scale，不得写字面数值」 |
| 目录树长什么样 | 「本仓 `pages/` 平铺，无特性分层」 |

**必须是门禁而不是格式偏好，因为抄是局部理性的。** 面对一个请求封装，把方法签名抄上去感觉是「更完整、更有帮助」；每一次抄单独看都像改进，累积起来 baseline 就成了 API 文档的劣质副本，而且**转述必然有损**——曾经把 `"dev": "vite --port 5178"` 转述成 `pnpm run dev`，端口就此丢失。门禁的作用是让「更完整」这个诱惑不合法。

**推论：具体接口的 URL、请求/响应字段、枚举不进 `api.md`。** 那是 Story 级契约，事实源是上游 `story-delta-design.md` / `requirement-design.md`。`api.md` 只装跨需求稳定的通信约定。这是 `api.md` 最大的失败模式。

### 路径会变：指路稳定性排序

只指路把失效从静默漂移换成响亮失败：

| 失效形态 | 只指路 | 复制内容 |
| --- | --- | --- |
| 文件移动 / 重命名 | 打开即失败，**当场发现** | 路径同样失效，**外加抄来的内容要重新核对** |
| 文件在、内容变了 | **自动跟上，条目不用改** | 抄来的内容看起来完全正常 → 照抄漏掉新增部分 → **静默错误** |
| 规则本身失效（出现第二个请求实例） | 只能靠消费点自证 | 同样测不出 |

第一行两者代价相同，第二行才是差距所在。

同一事实有多种指法时，选最不易变的：

1. **导出符号 + 所在目录**优于精确文件名——文件重命名远比符号重命名频繁；
2. **命名前缀**（如设计 token 的统一前缀）优于文件行号；
3. **目录级指路**优于逐文件枚举。

指路必须准到「文件 + 命名前缀或章节」，让消费者一次检索就到。这样就不需要为「档位集合对消费者不可读」开例外：消费者自己检索一次，比读一份会漂的副本可靠。

**变更半径被压到一条。** 规范条目只引清单 ID，所以某个入口文件改名时，规范条目一个字不用改，只改那一行清单的指路。复制了签名的话，同一次改名要动路径、抄来的内容、以及所有引用它的规范条目。

**检测是懒惰的，这是特性不是缺陷。** 只有消费者真去读那条才发现指路烂了；长期没人读的条目会一直烂着——而长期没人读的条目本就没有价值。用内容指纹去追这种条目，换来的是每次无关改动都把整份 baseline 判为失效，然后要人重新复核全部手写结论。

## 覆盖声明与依据样本

不使用内容指纹，也没有 `stale` / readiness 回退。跟进方式是**消费点自证 + 就地修**：消费者读到哪条、发现哪条不成立，就地修哪条。

指纹取消后唯一真正缺的语义是「查不到，是仓里没有还是没扫过」。**每个清单节头部一行覆盖声明**补上：

```markdown
<!-- 覆盖：src/components/、src/shared/、src/features/checkout/（2026-08-20） -->
```

| 查询结果 | 结论 |
| --- | --- |
| 覆盖范围内查不到 | 仓里确实没有 |
| 覆盖范围外 | 自行勘察并追加单条 |

首次生成只扫**通用层候选目录**（`components/`、`shared/`、`common/`、`ui/`）加上本次业务已知涉及的模块；业务侧靠增量长。覆盖声明是这个策略对消费者诚实的前提。

两条配套约束：

- **追加清单条目时必须同步更新该节的覆盖声明**，否则声明会随增量失真。
- **规范条目不用覆盖声明，用「依据样本」**：清单节声明的是扫过哪些目录，规范条目声明的是归纳时看了哪几处——粒度不同，不能共用一行。

## 写权限与跟进

| 角色 | 清单节 | 规范节 | 全量重建 |
| --- | --- | --- | --- |
| `sdd-init-frontend` | 可写 | **独占** | 可 |
| `sdd-task-frontend` / `sdd-dev-frontend` | 可追加、可修正**单条**，须同步覆盖声明 | 只读；异议攒进 `dev-review.md` | 不可 |
| `sdd-review-frontend` | 只读 | 只读 | 不可 |

**检视不得修改任何判据。** 让判断者能改自己的判据就等于没有判断；检视发现基准有误只能出 Finding。

跟进节奏：

| 改动性质 | 处理 |
| --- | --- |
| 清单单条（看一眼代码就能验） | 就地改、进本次提交、**不阻塞任何 Task** |
| 规范（要看多个样本才能判） | 攒进 `dev-review.md`，Story 收口时一次确认 |

## 各文件收纳边界

### `structure.md`

栈签名、目录实况、命名约定、校验规则与类型定义写在哪个层。

**栈签名放这里是因为它是「代码放哪、怎么命名」的前置条件，不是并列项**：不知道是 Vue，就无法判断单文件组件是常态还是异常；不知道是 Angular，`module / service / directive / pipe` 这套目录语汇就无从解释。它同时是全局单点事实，`index.md` 的速查节放一行指过来，但正文只在这里。

### `runtime.md`

装、起、跑哪些质量命令；Node 与包管理器约束；环境变量**键名**与是否敏感，**不记录任何值**，模板默认值文本也不记录。

命令一律**指向 `package.json` 的 script 名**，不转述展开后的命令行。只有代码读不出的隐性坑（必须先起 mock 才能跑 E2E、某命令必须在仓根而非 app 目录跑）才写正文。

质量命令节带一个**整数版本号**，质量命令有实质变动时手动加一。它是下游起点命令缓存的键，人和 agent 都能看懂第几版；不用内容哈希。

### `components.md`

分层标注，判定不靠目录名，靠**被两个以上特性引用**：

| 层 | 收录方式 |
| --- | --- |
| 通用构件 | 进详表；空则整节删 |
| 业务组件 | 只进按路由的索引 |
| 渲染辅助（格式化、展示用变换） | 独立小节 |

组件自身的样式实现不进 baseline——代码里已表达。

### `api.md` 与 `data.md`

界线是**进程边界**：边界外的通信约定归 `api.md`，边界内的持有与流动归 `data.md`。

| 归 `api.md` | 归 `data.md` |
| --- | --- |
| 请求实例、baseURL 从哪来 | 数据 hook / composable 清单 |
| 拦截器、鉴权怎么带 | 缓存库及其约定 |
| HTTP 错误怎么翻译成前端错误对象 | 错误对象怎么变成界面的错误态 |
| 超时、重试、取消 | 加载 / 空 / 错误三态的仓内做法 |
| mock 约定 | pending 态与提交防重 |
| 分页 / 排序参数的仓内惯例 | 全局 store 及其消费方 |
| | 表单库选择与校验**时机** |
| | 服务端数据与本地界面状态的边界 |

这条界线让下游两条检视判据各归一处、都单文件可判：请求与错误处理看 `api.md`，状态归属看 `data.md`。

### `styling.md`

token、scale、mixin、工具类、主题对象、硬编码基准。主题机制正文在这里，`components.md` 只留 ID 引用。

### `testing.md`

测试框架、元素定位约定（属性名叫什么、列表行怎么区分）、跑法与范围。

### 表单不是一个关注点

表单是跨关注点的**场景**，不设独立文件，按三段拆：库选择与校验时机归 `data.md`；输入控件与错误展示构件归 `components.md`；校验规则写在哪个层归 `structure.md`。「要做一个表单」由 `index.md` 的场景索引串起来。

### 扩展规则

八份之外一个不预置。新文件仅当三条同时成立才由 `sdd-init-frontend` 创建：有真实下游查询需要；能写出判定问句并且不需要类型列；差架构下答案非空。

## 实证产物的归处

**baselines 目录只放跨需求契约，实证一律不进。** 「契约 vs 实证」这条界线靠实证不落进该目录来保住。

浏览器实证不属于本 skill，由 `sdd-dev-frontend` Phase 0 按当次 Story 是否需要视觉能力决定。命令级实证按调用方式落点：

| 调用方式 | 落点 |
| --- | --- |
| 由 `sdd-dev-frontend` 路由进来（有 `<story-dir>`） | 写进 `<story-dir>`，与 `dev-review.md` 同类 |
| 用户独立调用（无 Story） | **只回话，不落盘** |

## 需求级消费契约

仓库级与需求级的分工不变：仓库范式正文只在仓库级，不下沉为 Requirement 或 Story 副本。

| 事实范围 | 保存位置 | 处理方式 |
| --- | --- | --- |
| 跨 Requirement 的仓库惯例 | baselines 的八份文件 | 保存唯一正文 |
| 同一 Requirement 多个 Story 的选择或偏离 | `requirement-frontend-design.md` 的工程决策 | 只引用 ID，不复制正文 |
| 当前 Story 采用哪些规范 | `dev-baseline.md` 的工程依据 | 只保存 ID |
| 当前 Story 的一次性实现细节 | tasks、代码与验证证据 | 不进 baseline |

### `DEMAND-1` 设计事实

位置 `<requirement-dir>/design-spec/`。基线源、设计 token、内容语义、页面与区块规格。

### Requirement 工程决策

复用已有 `<requirement-dir>/requirement-frontend-design.md`。只有存在跨 Story 选择或偏离时才写；完全沿用仓库规范时整节省略。

```markdown
## 工程决策

| ID | 适用 Story | 决策 | 仓库依据 |
| --- | --- | --- | --- |
| `REQ-DEC-1` | S1、S2 | 取数统一走现有缓存层 | `PATTERN-DATA-1` |
```

### `DEMAND-2` 执行起点

位置 `<story-dir>/dev-baseline.md`。Story 场景、base ref、起点失败集合，以及工程依据：

```markdown
## 工程依据

| Story 需要 | 采用依据 |
| --- | --- |
| 列表取数 | `PATTERN-DATA-1` |
| Requirement 决策 | `REQ-DEC-1` |
```

只写 ID，不复制正文、源码片段或证据表，**也不记录任何指纹**。

### `DEMAND-3` QA 判定

位置 `<story-dir>/dev-baseline.md` 的「QA 基线」。还原侧、功能侧、豁免、缺口与用户确认记录。

### 下游最小读取

| 阶段 | 读取 |
| --- | --- |
| 仓库接入门 | 八份文件是否存在、`structure.md` 的栈签名是否读得出 |
| Phase 0 | `runtime.md`；本次需要的场景经 `index.md` 取 ID |
| 代码侧勘察 | Requirement 工程决策；按 `index.md` 场景索引或 ID 选读对应文件 |
| 实现与检视 | `dev-baseline.md` 工程依据；按 ID 回读唯一正文 |
