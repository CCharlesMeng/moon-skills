# sdd-init-frontend

扫一个独立前端 app，产出**下游真正会查的那九份东西**到该 app 根目录，并且真的装依赖、真的起服务、真的跑通质量命令——不是读读代码就下结论。

## 它产出什么

九份文件，每份是一个问句。查的时候不用猜该翻哪一份：

文件名统一用领域名词：整体概念用单数，可数集合用复数；ID 仍用稳定的短词根，不随文件改名。

| 文件 | 回答 |
| --- | --- |
| `index.md` | 我该读哪条？（场景索引 + 单点事实速查 + 导航） |
| `structure.md` | 这是什么栈、什么形态？代码放哪、怎么命名？ |
| `runtime.md` | 怎么装、怎么起、跑哪些质量命令？ |
| `components.md` | 拼界面时有哪些现成构件可用？ |
| `routes.md` | 加一个页面 / 一条路由要动哪几处？ |
| `api.md` | 怎么跟后端说话？ |
| `data.md` | 拿到的数据在前端怎么持有、怎么流到界面？ |
| `styles.md` | 样式值从哪来，允许怎么写？ |
| `tests.md` | 测试用什么写、怎么定位元素、怎么跑？ |

每份文件里分「清单」（事实：指路 + 何时用 + 被几处引用）和「规范」（规则：怎么判违例）。

表单、i18n、权限、监控埋点、性能预算**不各自开文件**——它们是横跨多个问句的场景，按段拆进上面的文件，靠 `index.md` 的场景索引串起来。

## 先定形态，因为它改判据

第一件事是定出栈签名：框架，加**形态**——`应用` / `微前端宿主` / `微前端子应用` / `小程序` / `组件库`。

形态不是为了描述得更全，是因为同一条结构判据在不同形态下会给出错误答案：组件库里「哪些是真通用」这个判据整体失效，因为对外导出的一切都是公开 API；微前端子应用里搜不到统一请求出口**不等于**没有，出口可能由宿主注入，判成「无」会让检视放过真正的绕过；小程序的请求走平台 API、样式单位与 token 机制都和 Web 不同。

## 判据按角色写，不绑某一栈

React、Vue、Svelte、Angular、小程序共用同一套判据，因为判据问的是**这个文件在框架里扮演什么角色**——导出什么、被谁引用、内部调用什么——而不是它长什么形状。形状是会变的：视图辅助在一栈里是纯函数，在另一栈里是带生命周期的 action，在第三栈里是个类；请求客户端有的仓自己构造，有的栈由框架提供、靠依赖注入拿到。

这件事必须写成判据而不是靠临场发挥，因为**按别栈的形状去搜，结果不是报错而是「查无此物」**：把「渲染辅助 = 导出纯函数」当判据，Angular 与 Svelte 仓的那一节就整节判空；把「统一请求出口 = 谁构造了实例」当判据，靠注入拿客户端的仓会被判成「无统一出口」，检视于是放过真正的绕过。两次都是安静地给出错误答案。

取候选用的框架 API 名按栈列齐在[框架专有标记速查](./references/discovery-rules.md#框架专有标记速查)，一栈都不缺。

## 两条它刻意不做的事

**不抄代码里已经写清楚的东西。** 方法签名、props 列表、token 数值、目录树一律只留指路，不复制。抄进来就是第二事实源，代码一改就悄悄漂了，而且转述必然有损——「一份会漂的副本」比「一个准确的路径」危险得多。

**不给「这个仓架构应该长什么样」下结论。** 各处裸 `axios`、样式全硬编码、状态全塞组件里、连路由库都没有，就如实写成「无统一做法」。这不是缺内容，这正是下游最需要的结论：检视据此**不能**判「绕过统一实例」，计划期据此**不要**发明一个仓里没有的 store 或路由入口。

## 适用场景

- 团队第一次把这套 SDD 流程接到某个前端仓；
- baseline 缺失，或某条结论已经不成立了；
- 只是想知道「这个仓现在能不能直接开发」；
- **通常不需要手动调用**：`sdd-dev-frontend` 开工前发现 baseline 缺失会自动路由过来，完成后自动回到原 Story。

## 怎么用

单 app 仓，第一次接入：

```text
请用 sdd-init-frontend 初始化这个前端仓。
仓库路径：<repo-root>
```

路径和目标 app 会自动探测，不确定的地方才会一次性问你。

monorepo，或只补缺的那几份：

```text
请用 sdd-init-frontend 刷新 <target-app> 的 app baseline。
目标 app：<target-app>（monorepo 中的具体子应用）
只需要重新归纳取数与三态部分（data.md），其余保留。
```

monorepo 检出多个 app 时会一次列出每个 app，并额外提供“整体生成”选项；整体生成仍逐 app 写到各自的 `<target-app>/frontend-baselines/`，不会混成一份仓级 baseline。

## 会发生什么

产物固定写到 `<frontend-root>/frontend-baselines/`。大仓首扫**只扫当前 app 的通用层目录**加上你这次涉及的业务模块，业务侧靠后续增量长——每个清单节头部都写着它扫过哪些目录，所以下游能分清「仓里没有」和「还没扫过」。

然后真的装依赖、起服务、跑质量命令；涉及下载、登录这类有副作用的动作会先请求你授权。浏览器截图与 DOM 采集不在这里做，那是 `sdd-dev-frontend` 按当次 Story 是否需要视觉能力才做的事。

命令跑出来的退出码、耗时、失败摘要**不写进 baseline 目录**——那里只放跨需求的契约。有 Story 目录就写进 Story，没有就直接回话给你。
