# 前端仓初始化

## 目标与边界

以**一个前端仓库及其中一个目标 app**为工作单位，产出 [references/baseline-contract.md](references/baseline-contract.md) 定义的九份文件，并把当前机器准备到能装、能起、能跑质量命令。

执行前先完整读取该契约与 [references/discovery-rules.md](references/discovery-rules.md)。

| 事项 | 本 skill |
| --- | --- |
| 仓库级九份文件 | 负责，且**独占规范节的写权限** |
| 机器准备（装、起、必需服务与身份、质量命令实跑） | 负责 |
| 浏览器实证（截图、DOM 采集、视口与字体） | **不负责**，由 `sdd-dev-frontend` Phase 0 按当次 Story 是否需要视觉能力决定 |
| 需求级 `DEMAND-1~3` | 不负责，由 `sdd-dev-frontend` 在 Requirement / Story 生命周期生成 |
| 项目级跨仓拓扑 | 不负责，由外层流程管理 |

## 路径

| 变量 | 含义 |
| --- | --- |
| `<repo-root>` | 目标前端仓根目录 |
| `<target-app>` | monorepo 中的目标 app；单 app 仓为 `.` |
| `<project-sdd-dir>` | 外层 SDD 项目产物根目录 |
| `<repo-id>` | 仓库稳定标识；默认取仓库目录名，冲突时加远端仓库名或短哈希 |
| `<repo-baseline-dir>` | `<project-sdd-dir>/frontend-baselines/<repo-id>/` |
| `<story-dir>` | 由 `sdd-dev-frontend` 路由进来时的 Story 目录；独立调用时不存在 |

先自动定位。多个 app 同等合理、多个 SDD 根候选或 repo id 冲突时，一轮问完；不要逐项追问。

## 硬门禁

1. **只指路不复制。** 能从某个文件里逐字读到的内容不写进 baseline，只写指路；必须看多个文件才能得出的才写。方法签名、导出列表、props 列表、token 具体数值、目录树一律不抄。判据与稳定性排序见契约。
2. **具体接口的 URL、请求/响应字段、枚举不进 `api.md`。** 那是 Story 级契约，事实源在上游设计文档。`api.md` 只装跨需求稳定的通信约定。
3. **不保存秘密或变量值。** 只记录环境变量键名、是否敏感、是否就绪、有无模板默认值；真实值、模板默认值文本、cookie、token、密码都不记录。
4. **不覆盖已有配置。** 可从模板创建缺失的非敏感本地配置；已有 `.env*`、代理或构建配置不得静默改写。
5. **先准备再降级。** 固定执行「发现 → 准备 → 重试 → 证明可用」；没有实际尝试不得写成限制。
6. **只终止本次启动的进程。** 已存在的端口占用者不能擅自结束。
7. **外部副作用先授权。** 下载安装、写业务数据、seed、codegen、登录外部账号、修改已有仓库配置、终止既有进程前请求授权。
8. **每份文件至少一节；不存在的节整节删掉。** 不用「无」「未见」「未声明」「0 个」填版面。但**「无统一做法」是一等公民条目**，必须写成显式规范——它和「有统一做法」一样能决定下游行为。
9. **实证不进 baselines 目录。** 命令退出码、耗时、失败摘要按调用方式落进 `<story-dir>` 或只回话，见门禁 10。
10. **独立调用时实证只回话不落盘。** 无 `<story-dir>` 时无处可落，落进 baselines 会毁掉「契约 vs 实证」这条界线。
11. **不用内容指纹、不写 readiness 字段、不维护 stale 状态。** 跟进方式是消费点自证 + 就地修；覆盖声明负责区分「仓里没有」和「没扫过」。
12. **规范正文只在仓库级。** 不为 Requirement 或 Story 复制规范条目，也不长期保存候选清单。仍是候选就不落盘。

## 工作流

### Phase 0 — 定位、定形态、定首扫范围

1. 定位 `<repo-root>`、`<target-app>`、`<project-sdd-dir>`、`<repo-id>`，创建 `<repo-baseline-dir>`。
2. 若目录已有文件，走[刷新与路由](#刷新与路由)，不要无条件全量重建。
3. **先定栈签名：框架 + 形态**（`应用` / `微前端宿主` / `微前端子应用` / `小程序` / `组件库`），判据见 `discovery-rules.md`。形态必须在其余文件之前定出来并写进 `structure.md`，因为多组结构判据依赖它——组件库的分层判据整体失效、微前端子应用搜不到请求出口不等于没有、小程序的请求与样式判据都不同。定不出就按 `应用` 处理并在结论里说明。
4. 定首扫范围：**通用层候选目录**（`components/`、`shared/`、`common/`、`ui/`、`lib/`、`utils/` 及其栈内等价物）**加上本次已知涉及的业务模块**。大仓不做全量遍历；业务侧靠增量长，覆盖声明负责对消费者诚实。

### Phase 1 — 逐问句产出九份文件

按 [references/discovery-rules.md](references/discovery-rules.md) 对每份文件依次回答它的判定问句。规则集是**结构判据**——看导出什么、被谁引用、调用了什么，**不是按文件名里有没有出现某个英文单词**。按名字猜会同时漏掉真资产、又把无关文件吸进来。

每份文件的产出顺序固定：

1. 在首扫范围内按该文件的结构判据取候选；
2. 逐条**打开代码确认**，写清单条目——指路、一句话「是什么、何时用」、被几处引用；
3. 节头写覆盖声明，声明扫过哪些目录与日期；
4. 从清单归纳规范条目，写规则、依据清单 ID、依据样本、违例判定；**归纳不出统一做法时，把「无统一做法」本身写成规范**；
5. 该文件没有任何内容时整份删掉，不留空壳。

跨关注点场景（表单、i18n、权限、监控埋点、性能预算）**不开文件**，按契约的归置表拆进上面这些文件，靠 `index.md` 的场景索引串起来。

其余八份写完后写 `index.md`：场景索引、单点事实速查、文件导航，**全部是指向 ID 的行，零事实正文**。

### Phase 2 — 机器准备与命令实证

主动准备到能开发：

| 缺口 | 默认动作 |
| --- | --- |
| 依赖缺失 | 确认包管理器与 lockfile；需要下载时请求一次授权，执行确定性安装后重试 |
| 本地环境文件缺失 | 从模板生成不含秘密的骨架；敏感键合并成一次请求 |
| 端口冲突 | 先识别占用者；仓内支持安全换端口则换，否则请求用户决定 |
| API / 后端不可用 | 优先启动仓内 mock、MSW、fixture server 或文档声明的本地服务 |
| 需要登录 | 打开可复用会话，让用户只完成登录动作，然后继续验证 |
| 缺测试数据 | 优先使用已有 fixture；seed 会写业务仓或外部数据时先请求授权 |

实跑 `runtime.md` 记录的质量命令，证明它们**可运行**。首次接入允许既有代码失败，但不能用「仓库本来就红」掩盖工具链不可用。

`runtime.md` 只保存命令的 script 名、适用范围、前置条件，以及质量命令节的**整数版本号**（质量命令有实质变动时手动加一，它是下游起点命令缓存的键）。本次的退出码、耗时、失败摘要按门禁 9、10 处理。

完成后停止本次启动且不再需要的进程；若服务要留给紧接着的 `sdd-dev-frontend`，在回话里明确 PID、端口与所有权。

### Phase 3 — 自审

- [ ] `structure.md` 的栈签名给出了一个具名的框架**和**一个具名的形态。
- [ ] 九份文件各自能回答它的判定问句；没内容的整份删了，没有空壳。
- [ ] 全文没有抄来的方法签名、props 列表、token 数值或目录树。
- [ ] `api.md` 里没有具体接口的 URL、字段或枚举；`routing.md` 里没有具体路由路径清单（路由→业务组件索引除外）。
- [ ] 分层判据用的是「消费单元」而不是写死的特性目录；平铺仓也真的判出了分层。
- [ ] 跨关注点场景没有各自开文件，都按归置表落进现有文件。
- [ ] 每张表都不需要「类型」列来区分内部条目。
- [ ] 每个清单节都有覆盖声明；每个规范条目都有依据清单 ID 与依据样本。
- [ ] 归纳不出统一做法的地方写了显式的「无统一做法」规范，不是留空。
- [ ] 没有 readiness 字段、指纹或 stale 标记。
- [ ] `index.md` 只有指向 ID 的行。

## 刷新与路由

| 现状 | 动作 |
| --- | --- |
| 目录不存在，或 `index.md` 与 `structure.md` 缺失 | 全量执行 |
| 部分文件缺失 | 先看形态：该形态下本该无内容的（如 `组件库` 的 `routing.md`）就是正确产物，不补；其余只产出缺的那几份，已有文件不动 |
| 消费方报某条清单指路失效 | 只修那一条；这属于 `sdd-task-frontend` / `sdd-dev-frontend` 的就地修权限，通常不必路由到本 skill |
| 消费方报某条规范不再成立 | 由本 skill 重新归纳该规范并更新依据样本；规范节本 skill 独占 |
| 收到 `acceptance.md` 的「规范候选」节 | 按类别处理：`broken` 重新归纳该规范；`new-pattern` 与 `exemption-recurring` **先数复发**——跨 Story 累计到两处以上独立依据样本才写进规范节，只有一处的留在候选里不落盘。复发计数只能在这里做，Story 侧手里永远只有自己那一次 |
| 覆盖声明外的新模块要进清单 | 追加条目并同步覆盖声明 |

**不因为某个文件变了就重扫全仓。** 判据是「有消费者读到了不成立的结论」，不是「有文件的内容变了」。

从 `sdd-dev-frontend` 路由而来时，完成后自动返回原 Story，不要求用户再次发起命令。

## 最终输出

```text

产出：<repo-baseline-dir>/ 下 <n> 份文件（<列出文件名>；因形态而整份省略的写明是哪几份、为什么）
覆盖：<首扫覆盖的目录>
机器：<装/起/质量命令的实证结论；限制与阻断各写影响范围和解除条件>
下一步：<返回原 Story / 唯一解除动作 / 可开始 sdd-dev-frontend>
```
