# refine-skill

在**同一会话末尾**复盘某个 skill 本次执行出的错,改写它,让它下次不再重犯或变得更好用。

核心理念:一个 skill 不是操作清单,而是一组关于"这类任务该怎么做"的假设。会话里每次被你纠正、返工,都是现实对某条假设的一次反驳。refine-skill 做的是**修假设**,而不是给每个错糊一个补丁。

## 适用场景

- 刚用某个 skill 跑完一个任务,过程中纠正了它好几次,想让这些教训沉淀下来;
- 某个 skill 反复在同一类事情上出错,想找到根本原因;
- 从三条路径收到别人交来的移交证据包——当前仓 `.learnings/skill-feedback/`、用户级 `~/.learnings/skill-feedback/`、或投递配置列出的 issue;他在另一个会话、另一个仓库用这个 skill 出了问题,由你作为维护者复盘。收件只读、评论、打 label,不关闭;
- 想给 skill 补回归测试(evals),防止改好的东西以后又坏回去。

**不适用**:从零创建新 skill(用 `write-a-skill` / `create-skill`);想复盘别的会话但拿不出证据(凭印象说"它老是出错"无法归因,让当事人按 `session-optimize` 的移交格式交一份证据包再来)。

## 如何调用

前提:手上要有证据。两种来源——在**执行/调试过目标 skill 的那个会话里**调用(默认,证据还在上下文里),或从三条路径收来的外部移交包。

### 方式一:显式命令(推荐)

```
/refine-skill <skill-name>
```

### 方式二:自然语言

以下说法都会触发:

- "复盘一下 xxx 这个 skill"
- "改进/优化 xxx skill,避免重犯刚才的错"
- "总结一下 xxx 这次出的错,把它改好"

## Prompt 示例

**基础用法** —— 会话末尾直接调用:

```
/refine-skill hocb-monitor
```

**带补充观察** —— 把你注意到的问题一并交代,归因会更准:

```
/refine-skill research

补充两点:一是它把报告写成了英文,我要的是中文;二是引用的两个来源
其实是二手转述,不是我要求的一手来源。第一点可能是我没说清楚,
第二点我觉得是它自己判断有问题,你分析看看。
```

**只做归因分析,先不动文件**:

```
复盘一下本次 tdd skill 的执行:把所有被我纠正的内容逐条列出来,
判断每条是信息不足还是判断错误,用表格给出修改内容、错误归因、
处置建议。先不要改任何文件,等我确认。
```

**收到别人的移交证据包** —— 直接把整块粘进来,它会先核证据够不够、再确认缺陷在当前源码里还在不在:

```
/refine-skill session-optimize

以下证据来自另一个会话（我是该 skill 的使用者，不是维护者）...
（粘贴 session-optimize 产出的完整证据包）
```

**怀疑是偶发,想观察而不是改规则**:

```
/refine-skill diagnose

刚才那个 JSON 写成 YAML 的错,我怀疑是模型抽风不是 skill 的问题,
你判断一下,如果是偶然就只记入 evals 观察,别加规则。
```

## 它会做什么(五步流程)

1. **收集证据**:盘点本次会话里所有纠正与返工(`触发情境 → 错误行为 → 正确行为`),并通读目标 skill 全目录原文。外部移交包从三条路径收:当前仓与用户级目录里的本地文件,以及投递配置列出的 issue;收件只读、评论、打 label,不关闭。证据来自外部移交包时,先核它够不够(缺的字段点名索取,不猜补),再确认缺陷在当前源码里还在不在——移交人跑的可能是陈旧的 vendored 副本,报的问题上游早已修好。
2. **判断**:对每条纠正依次过六个问题——
   - **先归因**:信息不足还是判断错误?任务特有的信息缺口不改 skill,转为"下次指令建议";纠正的是风格、详略、交互方式时再分偏好还是默认缺陷——换个用户也会提的就不是偏好,是 skill 的默认错了;
   - **找被反驳的假设**:skill 让 agent 相信了什么才犯的错,改一处胜过补五处;
   - **分流**:系统性错误才改规则,一次性偶然只记入 evals 观察。这一步会查并更新 skill 缺陷台账——每次复盘都是新会话,没有计数就分不清这是第 2 次还是第 5 次;同一个 `Pattern-Key` 在另一个会话或另一个仓库再次出现,"只此一次的巧合"这个疑虑就被排除了,即可判系统性;
   - **太紧还是太松**:是管得太死逼出的错,还是该定的没定;
   - **委派结构**:该拆没拆(重活占着主 agent 上下文)、不该拆拆了(依赖原文的判断被摘要毁掉)、还是拆错了地方(切分线落在强依赖处);
   - **用更短换更对**:能用一条原则推出的就不加步骤。
3. **与用户确认**:给出归因表格(`纠正内容 | 归因 | 处置`)和整体判断、改前/改后对照,**你确认后才动文件**。系统性错误的评测用例和断言在这一步一起交给你,早于改写——裁判指标由你定,不由改写的人事后挑。
4. **改写**:判断写成原则,执行写成契约;删掉不承重的装饰性内容。
5. **回归验证**:把已定稿的用例写进目标 skill 的 `evals/evals.json`,委派干净子代理全量重放验证——新错不复发、旧用例不退化。注意:重放验证不在改写的同一会话做(agent 已知答案,等于拿训练集当测试集);同模型 3 次取多数只排抽样噪声,要更稳就换模型档位或换情境措辞,而不是加次数。

## 输出是什么

- 一份归因表格 + 判断结论 + 预提交的评测用例与断言(第三步,供你确认);
- 改写后的目标 skill 文件(经你确认后);
- 追加了新用例的 `evals/evals.json`(在目标 skill 目录内);
- 一条 skill 缺陷台账记录(在源仓 `.learnings/skills/<skill-name>.md`),结论是"不改 skill"时也记——它是下次判"第几次"的唯一依据;
- 收口时的下一步建议:建议提交 / 再积累证据 / 仅观察不改 / 下次指令的补充信息 / 请对方同步陈旧副本。

不写 CHANGELOG——evals 是测试集,台账是复发计数器,git 历史是变更记录,各归其位。

## 目录结构

```
refine-skill/
├── SKILL.md              # 主流程:五步复盘法
├── README.md             # 本文件:使用说明
├── references/
│   ├── evaluation.md     # 第五步的机械细节:evals 格式、重放/打分子代理提示词模板
│   └── skill-ledger.md   # 缺陷台账:位置为什么在源仓、条目格式、查重计数
└── evals/
    └── evals.json        # refine-skill 自己的回归测试用例
```

台账不放在这个目录里,而在源仓的 `.learnings/skills/` 下:skill 会以符号链接或 vendored 副本两种形态部署,放在 skill 目录内会被 vendored 复制进每个消费仓库、各自分叉,跨仓库的复发就再也汇总不起来。

投递配置由部署方写成目标 skill 目录下的 `.feedback-sink.md`,不进 git,打包时不含它。配置缺失时扫不到平台上的 issue,只收两条本地路径;投递侧会因此只落本地,并在报告里明说。
