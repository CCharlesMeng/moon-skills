# Refine Skill

**显式调用**:`/refine-skill <skill-name>`,目标就是本次会话里被执行/调试的那个 skill。

一个 skill 不是操作清单,而是一组关于"这类任务该怎么做"的假设。本次会话里每次纠正和返工,都是现实对某条假设的反驳;复盘是修假设,不是给每个错糊补丁。整个过程五步,依次走完,不跳步。

## 第一步:收集证据

两路证据自己拿,不委派子代理——它们经不起摘要:

1. **纠正清单**,逐条记成 `触发情境 → 错误行为 → 用户想要的正确行为`。两种来源:
   - **本次会话**(默认):盘点本次会话的每次纠正与返工。
   - **外部移交包**:使用者在别的会话、别的仓库遇到问题,按 `session-optimize` 的移交格式交来的证据。它也可以从三条路径收件(路径、字段与命令见 [skill-ledger.md](references/skill-ledger.md) 的「收件与去重」)；收件只读、评论、打 label,不关闭。它照样逐条过第二步的判据,但先做两件事。
2. **逐字通读目标 skill 全目录**:`SKILL.md`、`references/`、`scripts/`、`evals/`。

拿到外部移交包时先做的两件事:

- **核证据够不够。** 对着六条判据要的输入清点:当时 agent 手上有什么(判据一)、错误行为是原样还是概括(判据二)、这是第几次(判据三)、能不能指到 skill 里被遵循的那句(判据四)、用没用子代理(判据五)。缺哪条就向移交人点名索取,不靠猜补齐——猜出来的"当时信息充分"会把归因直接推向"加一条规则",那是默认的错误方向。
- **确认缺陷现在还在。** 移交人跑的可能是陈旧的 vendored 副本,报的问题上游早已修好。按包里"运行的是哪一份"对照当前源码:已经修了就不改 skill,回复在哪个提交修的、请他同步副本,并把这次记成副本陈旧而不是 skill 缺陷。

移交包里若带了改法建议(它按格式不该带),不拿它当起点:那是使用者在没有 skill 全文的位置上得出的结论,采纳它等于跳过归因。仍从判据一走。

产出一份纠正清单,进入第二步逐条过判据。

## 第二步:判断

六条依据,每条是一个先于"怎么改"的问题。

**一、先归因:信息不足,还是判断错误。** 对每条纠正问:当时把该给的信息都给了,agent 还会犯这个错吗?**判断错误**(信息充分但推理或决策错了)才是对 skill 假设的反驳,走后面的路。**信息不足**(上下文、约束或目标没交代)再分边界:缺的信息属于 skill 职责内该声明的输入,改法是补输入契约,不是加规则;属于本次任务特有的背景,不动 skill,记成给用户的"下次指令建议"——这次踩的坑,变成下次任务的开局条件。还有第三种:纠正针对的是**风格、详略、交互方式**,两边都不沾。用这句区分:换个用户在同样场景下还会不会提同样的纠正?会,就不是偏好,是 skill 的默认错了。判成偏好的不写成 SKILL.md 里的规则——它改的是默认设定,不是判断逻辑;但不等于不进这个 skill,去向取决于下次谁在什么时刻会读到它:只对这类任务成立,就写进目标 skill 运行时确会读取的位置(它的配置、reference 或知识文件);跨任务恒成立的进常驻上下文或下次指令;指不到一个确定的读取点就不写。判成默认缺陷的交给依据四按"太松"处理,不是丢弃。

**二、找那条被反驳的假设。** 先别问"该加哪句话",先问:skill 当时让 agent 相信了什么,它才这么做?散落的错往往是同一个错误假设的不同表现。找那条改掉就能让一整类错消失的根本误解——改一处,胜过补五处。

**三、分流:系统性,还是一次性偶然。** 一次会话是 n=1 的证据,据此改一条承重规则就是过拟合。偶然(模型抽风、罕见输入、外部故障)不动规则,只把情境追加进 `evals/` 观察。只有系统性失败才值得改规则。

但"复发了它自己会升级"不会自动发生:每次复盘都是新会话,上一次的判断不在上下文里,`evals/` 里的观察用例只说明"见过",不说明这是第 2 次还是第 5 次。所以本步要记账并查重,把 n=1 的疑虑变成可数的事实——记在 skill 源仓,格式与位置见 [skill-ledger.md](references/skill-ledger.md)。

判系统性的依据不是凑够某个次数,而是 n=1 的疑虑到底还成不成立:它担心的正是"只此一次的巧合",而同一个 `Pattern-Key` 在**另一个会话或另一个仓库**再次出现,这个担心就已经被排除了。所以第 2 次即可判系统性,继续累加只用于排优先级。同一会话里被用户、子代理反复提起仍然只是 1 次——数的是复发,不是有几个人说过。

**四、太紧还是太松。** 系统性错误只来自两个方向:skill 管太死把 agent 逼上错路,或该替它定的没定、放任它瞎猜。先答这个,再决定收紧、放宽还是删除。默认往上加步骤,通常是错的方向。

**五、委派结构。** 主 agent 的上下文是整个系统里最贵的资源,但委派也要付费:多跑一个 agent 通常比主 agent 自己做贵,还要付一次打包和一次解读的损耗。先说得出这次委派买到的是什么——隔离的上下文、可并行的搜索覆盖,还是一个不受自证偏差影响的视角;三样都说不出就别委派。目标 skill 的划分错在三个方向:

- **该拆没拆**:主 agent 亲自做**摘要无损**的重活(批量重试、机械比对、按固定判据打分)。这些是委派候选。
- **不该拆拆了**:产出依赖逐字原文或全局判断的工作被派出去,结论建立在有损摘要上,信号已经没了。
- **拆错了地方**:切分线落在强依赖处,子代理之间反复同步、重复劳动,或产出要主 agent 重做一遍才能合并。切分线应落在依赖最弱处——宽搜索、弱依赖的部分适合并行,共享状态、强依赖的部分,通信与合并成本会吞掉收益。

还有一种不显眼的:同质并行。同模型、同提示的 N 个子代理给出同一答案,是一次共模,不是 N 票佐证;靠它们提高覆盖可以,靠它们提高置信度不行。

凡改成委派,提示词必须同时升级成契约(见第四步),否则只是把错误换了个便宜的地方犯。

**六、用更短换更对。** 想加步骤时停一下:有没有一条原则能让 agent 自己推出它?有就加原则。好的改写通常让 skill 更短或持平——删掉 agent 本就会的指令,和新增一样是改进。多次复盘后,守住单一连贯的设计意图,别让它变成补丁的拼盘。

## 第三步:与用户确认

给一份判断,不是一份问卷:先用表格逐条列出纠正——`纠正内容 | 归因(信息不足/判断错误) | 处置(改 skill / 补输入契约 / 下次指令建议)`;再给整体结论:根本误解是什么、系统性还是偶然、太紧还是太松、委派结构有没有问题、打算怎么改(改前/改后对照)。**确认后再动文件。**

确认清单里一并说明台账要记哪几条(`Pattern-Key`、第几次、`Status`)——记账在确认之后随改写落盘,结论是"不改 skill"时也记,否则下次仍从 n=1 开始。

判成系统性的,连同用例和断言一并提交,早于改写。断言只从第一步那条 `触发情境 → 错误行为 → 正确行为` 推出,描述期望的行为,不引用改稿的任何措辞。先改写再补断言,等于让被裁判的人事后挑裁判指标——写出来的断言总会说改稿已经做到的那件事,测多少条都恒过。裁判指标该由目标所有者定,而你正站在他面前。断言定稿后仍要改,说明改写偏离了当初判定的问题,把理由一并说清。

## 第四步:改写

改写时两把尺子,对应指令的两种身份:

- **判断写成原则,执行写成契约。** 需要权衡的内容(改不改、何时改)用原则表达,让强模型能外推到没写到的情境;交给子代理执行的内容写成自包含契约——**输入材料、输出格式、完成判据**三要素齐备,不依赖会话记忆,不留"自行判断"的空隙。skill 本身可能整个跑在能力一般的模型上,所以流程骨架也按契约标准写:显式步骤,无歧义。
- **引用必须承重。** 理论引用只保留改变 agent 行为的那种:删掉这句话行为会变差,才留;不会变差的是装饰,删。行文以人一遍读懂为准,不炫技。

## 第五步:回归验证

prose 没法像代码那样断言对错,但能做概率性回归测试。**不要在写出改法的这个会话里验证——agent 已经知道答案,等于拿训练集当测试集。**

1. 把第三步已定稿的用例与断言写入目标 skill 的 `evals/evals.json`(没有就创建);再补 1-2 个本次**做对了**的行为。格式与维护规则见 `references/evaluation.md`。
2. 委派干净子代理(不带本对话记忆)重放**全套**用例,不只是本次新增的——上上次修好的错,只有全量重放才保证不被这次改动翻出来。用实际使用档位的模型跑,每用例约 3 次取多数。executor 自己落盘、grader 读文件:你不得向 grader 转述执行记录——你是被复盘的一方,转述会把结论一起递过去;取不到记录的那次记 `未验证`,不折进 pass。
3. 3 次取多数只排除抽样噪声,排不掉共模:同模型同提示重放时,skill 文本里那种这个模型会系统性误读的措辞,3 次会一起读错、一起过或一起挂。想让结论更稳,是换一个模型档位或换一种情境措辞再跑一次,不是把 3 次加到 5 次。挂法本身也在指改法:3 次以同一种方式挂,是文本的确定性缺陷,照着改;3 次挂法各不相同,是措辞有歧义,该补的是明确性而不是规则。
4. 通过线两条:新用例不再复发,旧用例仍然全过。旧用例退化才是"质量下降"的真正来源,通常意味着收太紧,往回退再验。
5. 让 grader 顺带批判断言本身:永远会过的断言、没被任何断言覆盖的重要行为,都要报上来。评测标准和 skill 一起进化。

## 收口

不写 CHANGELOG——evals 是测试集,台账是复发计数器,git 历史是变更记录,各归其位。最后给用户一句明确的推荐下一步,从这些里选最合适的;并报三条路径下还剩几个 pending、其中几个超过 30 天未处理。

- 验证通过 → 建议提交(给出简短 commit message),并在接下来几次真实使用中留意是否复发;台账条目转 `fixed` 并写清提交。
- 验证不充分(用例太少 / 非确定性大)→ 建议再积累几次会话证据,暂不改承重规则;台账留 `pending`,下次复发时它就是第 2 次。
- 错误判定为偶然 → 不改 skill,用例已入 `evals/` 观察,台账记 `observing`。
- 移交包来自陈旧副本、缺陷上游已修 → 不改 skill,回复修复提交并请移交人同步副本,台账记 `stale-copy`。
- 归因为任务特有的信息不足 → 不改 skill,给出可直接复制进下次指令的补充信息。
- 改写触及自由度刻度 → 提醒用户这类改动影响面大,建议小步改、多观察。
