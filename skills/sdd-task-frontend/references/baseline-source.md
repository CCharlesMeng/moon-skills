# 基线源与还原轨判定

本文件是 [SKILL.md](../SKILL.md) Step 2 的细则。硬门禁与接缝字段以 SKILL.md 为准，本文不重复。

## 一、两个正交问题

**顺序不可倒，也不可合并成一问。** 合并的典型错误是「没有原型 → 不用做还原」——没有原型不代表没有静态呈现要落地，只代表期望值的出处变了。

```
问题一：本 Story 有没有静态呈现要落地？
   ├─ 没有 → 不出还原 Task，全部逻辑 Task，baseline_source=none
   └─ 有   → 继续问二
问题二：期望值的外部出处是哪一档？
   ├─ 第 1 档 原型     → 还原 Task，可给原型级数值
   ├─ 第 2 档 参照页   → 还原 Task，类比还原，标可信度降级
   └─ 第 3 档 文字规格 → 还原 Task，承诺收窄（见第四节）
```

## 二、问题一：有没有静态呈现

**判据是「这次改动会不会产生或改变用户看到的静态形态」**，不是「有没有碰到 `.vue` / `.tsx` 文件」。

| 有静态呈现（出还原 Task） | 无静态呈现（不出） |
| --- | --- |
| 新增页面、新增区块 | 只改数据流与状态迁移 |
| 改动既有区块的结构或样式 | 只换接口、改请求参数与字段映射 |
| 新增需要样式的状态（禁用态、空态、加载态） | 只改文案（无新增结构） |
| 新增或改动公共展示组件、样式 token | 只改类型定义、常量、路由表条目 |

判为「无」时，在 `tasks.md` 写一行理由：`无还原 Task：本 Story 不产生新的静态形态（<一句话>）`。**不写理由等于漏判**——下游拿到一份没有还原 Task 的前端计划，无法区分「本来不需要」和「上游漏了」。

## 三、问题二：三档判据

三档取**第一个成立的**，不是挑一个喜欢的。

| 档 | 成立条件 | `baseline_source` |
| --- | --- | --- |
| 1 | 存在 HTML 原型目录，且目录内确有对应本 Story 页面的原型文件 | `prototype` |
| 2 | 无原型，但仓内已有**同类**已上线页面可作类比对象 | `reference_page` |
| 3 | 前两档都不成立，但 `story-delta-frontend-design.md` 有可逐条落地的文字规格 | `text_spec` |

三档都不成立时写 `none`，并把「无任何还原基线」进「已知缺口」——这时还原 Task 只能承诺文字规格之外的结构存在性，几乎必然要回流 Design 补规格。

**第 2 档的判定只到「有候选」为止。** 收集候选属事实，**选定哪一个属决策**，归下游 Phase A2 确认门（硬门禁 3）。本 skill 在 `tasks.md` 写候选清单与倾向，`reference_route` 填倾向的那一个并注明「候选，待下游确认」。**不得写成既定结论。**

## 四、第 3 档的承诺收窄

第 3 档没有外部视觉事实，所以只承诺三件事：

1. **仓内 token 一致性**：间距、颜色、字号取自选定的 `PATTERN-*` token，不出现字面量。
2. **「不破」三项**：目标视口下**无横向滚动、无重叠、无内容截断**。
3. **文字规格逐条落地**：`story-delta-frontend-design.md` 写到的每一条都有对应实现。

**禁止写出原型级数值**（硬门禁 4）：具体 px、色值、字号、圆角、阴影参数一概不写。没有基线还给数值就是发明规格，而下游会拿它当冻结期望值去报 GREEN——那时它已经看不出这个数字是谁编的。

响应式同理：上游没给响应式规格时**只承诺「不破」三项**，不发明断点与栅格列数。需要改变布局结构的诉求写成 Open Question 回流，不自行推断。

## 五、档位对下游的连带影响

写清档位不只是标注，它决定下游整段流程的形状。写错的代价不是一个字段，而是一个阶段：

| 档位 | 下游 Phase A 的形状 |
| --- | --- |
| `prototype` | 走完整 A1 抽取管线（脚本 → 切分 → 逐区块规格），A1 / A2 可同波并行 |
| `reference_page` | **整个 A1 跳过**；两侧勘察改串行；代码侧固定 `full`（要收集候选路由与结构化实测值） |
| `text_spec` | **整个 A1 跳过**；两侧勘察改串行；代码侧满足下游全部 `lite` 适用条件才可使用 |
| `none` | 同上，且还原侧期望值只剩结构存在性 |

所以：**`prototype` 只在原型文件真的存在时才写。** 写了但目录是空的，下游会按第 1 档去跑抽取，取不到取值再回退，白跑一轮；反过来漏写成 `text_spec`，下游会跳过本该做的抽取，把有原型的 Story 按无基线执行。

下游会在 Phase 0 核实这个字段（核 `prototype_dir` 是否存在且含 HTML），核不上就自行重判并记一行。**核实机制的存在不是本 skill 可以随便填的理由**——它只是最后一道网。

## 六、与 `restore_tasks` 的联动

判定完成后回填两个字段：

- `baseline_source`：本节判出的档位。
- `restore_tasks`：哪些 Task 编号是还原轮。问题一判「无」时**留空，不写 `none` 字样**——空清单和「不适用」在下游是同一个行为。

`restore_tasks` 只是索引，与实际切分冲突时以 Task 内容为准（`tasks.md` 里那个 Task 有没有样式文件才是判据）。
