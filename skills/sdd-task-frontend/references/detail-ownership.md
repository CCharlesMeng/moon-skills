# 细节归属分类细则

本文件是 [SKILL.md](../SKILL.md)「细节归属」一节的细则。判据与硬门禁 9 / 10 以 SKILL.md 为准，本文按类目给可直接对照的正反例。

**判据只有一条**，逐条细节自问：

> 改掉这个细节，AC 或 mock 集成测试的断言会不会变？
> **会变 → 属 Task。不会变 → 属 Dev。**

反例全部摘自本仓真实前端计划，都是实际发生过的越界。

## 1. 路由与配置

| 属 Task | 属 Dev |
| --- | --- |
| 路由 path 字面量、是否在侧边栏显示、需要的鉴权级别 | 路由对象的字段写法、懒加载方式、放在数组哪个位置 |

| 越界写法 | 应该写成 |
| --- | --- |
| `{ id: 'DOWNLOAD_CENTER', i18nKey: 'menu.downloadCenter', component: () => import('@/views/DownloadCenter'), showInMenu: false, keepAlive: true }` | 「在路由表新增一条不在侧边栏显示的路由，path 为 `/download-center`」 |

路由**能不能访问、显不显示**会改断言；用 `() => import()` 还是别的写法不会。

## 2. 模板与 DOM

| 属 Task | 属 Dev |
| --- | --- |
| 入口的相对位置（在哪个菜单、在哪一项的上方）、`data-automation-id` 锚点 | 标签选择、class 命名、DOM 层级、事件绑定写法 |

| 越界写法 | 应该写成 |
| --- | --- |
| `<span class="top-bar__user-menu-item" @click="goToDownloadCenter">{{ $t('menu.downloadCenter') }}</span>` | 「用户菜单在『退出登录』上方新增入口，锚点 `top-bar-user-download-center`」 |

`data-automation-id` 是例外中的例外：它属 Task，因为测试直接选它，改了断言必然变。class 名不是——除非契约规则拿它当锚点，而那是下游 Phase A1 生成的。

## 3. 请求与数据变换

| 属 Task | 属 Dev |
| --- | --- |
| URL 常量、方法、请求/响应的字段名与命名风格（蛇形/驼峰）、分页参数语义 | 用哪个 axios 实例、拦截器怎么配、转换函数叫什么、写在哪个文件的哪个位置 |

| 越界写法 | 应该写成 |
| --- | --- |
| 「用 `createAxiosInstance()` 创建实例，调 `parseInnerParams` 与 `parseOuterParams` 处理入参，再用 `snakeToCamel` 转响应」 | 「按仓内既有请求范式发 `POST /api/v1/download/task`，响应蛇形转驼峰」 |

字段名会进断言，所以属 Task。`parseInnerParams` 这个名字不会——它甚至可能在实现时被合并掉，而计划里点了名，Dev 就得为了对齐计划保留一个多余的函数。

## 4. i18n

| 属 Task | 属 Dev |
| --- | --- |
| 断言会用到的用户可见文案（提示语、按钮字、错误信息）、必须存在的 key | key 的分组层级、字典文件的组织、复数与插值写法 |

| 越界写法 | 应该写成 |
| --- | --- |
| 把 23 个 key 连中英文案列成三列全表 | 只列断言会用到的那几条：「失败提示为『导出任务创建失败，请重试』」 |

23 个 key 的全表是本仓真实计划里最长的一块。里面绝大多数 key 的文案不进任何断言——它们是字典正文，属实现。

## 5. 状态与交互

| 属 Task | 属 Dev |
| --- | --- |
| 状态迁移的起止态与触发条件、什么条件下禁用、副作用的可观测结果 | 用哪个 API 达成、表达式与分支写法、变量命名 |

| 越界写法 | 应该写成 |
| --- | --- |
| `Modal.alert({ title: t('...'), content: ..., onConfirm: () => { window.open(`/download-center?taskNo=${no}&taskType=${type}`, '_blank') } })` | 「成功后弹确认框，含任务编号；确认后在新标签页打开下载中心并携带 `taskNo` / `taskType`」 |
| `router.replace({ query: {} })` | 「查询完成后清除 URL 上的回填参数」 |

「新标签页打开」「携带这两个参数」会进断言；`window.open` 还是 `router.resolve` + `<a>` 不会。

## 6. 视觉细节

**还原轮的视觉细节不走 Step 3。** 间距、色值、字号、圆角、状态配色属于 QA 基线与冻结契约，是下游 Phase A2 确认门的对象。

| 越界写法 | 问题 |
| --- | --- |
| 「状态标签：PENDING→蓝色、RUNNING→橙色、SUCCESS→绿色、FAILED→红色」 | 造出两处期望值，而计划里这一处**没有外部基线背书** |

要写的只有「状态标签需覆盖 PENDING / RUNNING / SUCCESS / FAILED 四态」——**枚举取值属 Task**（进断言），**配色属基线**（不进 Step 3）。这一条最容易踩，因为它看起来是在补充有用信息。

第 3 档尤其致命：没有原型还给色值，下游会拿它当冻结期望值报 GREEN，那时已经看不出这个颜色是谁定的（[baseline-source.md](./baseline-source.md) 第四节）。

## 与 No Placeholders 的关系

`No Placeholders` 禁的是**待定项**（TBD / TODO / 「适当处理错误」/「参考类似任务」/ 无内容的步骤），**不是要求写得越细越好**。

- 缺了会改断言的契约细节 → **占位符缺陷**，计划失败。
- 写了不改断言的实现细节 → **越界缺陷**，同样是计划失败。

两类都由 Step 8 自审拦截。**必须把「越界」也定成缺陷**，否则只禁占位符时，模型为了过自审会一路往写代码的方向滑：多写不受罚、少写受罚，Step 3 就必然退化成实现代码。这正是本仓既有前端计划的实际形态。

## 自审用的机械信号

Step 8 越界扫描先按信号筛，再按判据判——信号只提示可疑，不直接定罪：

| 信号 | 说明 |
| --- | --- |
| Step 3 里出现 `{` … `}` 对象字面量 | 几乎必然越界 |
| 出现 `<` 开头的模板/JSX 片段 | 同上 |
| 出现 `=>`、`function`、`await` | 在写实现 |
| 出现驼峰函数名后跟 `()` | 点名了内部 helper，除非它是对外 URL 或既有公共 API |
| 出现 `#` 十六进制色值、`px`、`rem` | 视觉细节，属基线 |
| 同一枚举 / 字段清单在文档里出现两次 | 触硬门禁 10 |
