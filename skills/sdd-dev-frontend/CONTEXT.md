# SDD-Dev-Frontend

SDD 流程中前端编码阶段的执行上下文。上游交付 `tasks.md` 与设计文档后，本阶段负责把它们变成可验收的前端代码与证据。

Task、Step、AC 锚点、`tasks.md`、`alpha-tests.md` 这些词沿用 SDD-Task 阶段的既有定义，本表不重复。下面只收本阶段独有、或在本阶段被收窄了含义的词。

## Language

### 工作类型

**还原**：
把 HTML 原型的静态呈现落成目标工程组件代码的工作。判据是「没有可断言的行为分支」。
_Avoid_: 切图、设计稿转代码、静态实现

**逻辑补全**：
在已还原的界面结构上接入状态迁移、条件渲染、数据变换与接口交互的工作。判据是「有可断言的行为分支」。
_Avoid_: 联调、功能开发、交互实现

**勘察**：
开工前对规格侧与代码侧既有事实的只读收集。规格侧形成 QA 基线；代码侧只选择 Requirement 决策与仓库范式 ID，不复制仓库事实正文。
_Avoid_: 调研、分析、探索

**检视**：
实现完成后对成果的只读评估，产出分级结论。
_Avoid_: 评审、走查

**双通道快路径**：
同一 Task 同时含还原与逻辑轮、且两边能在产品实现前取得原因独立的 RED 时，把两轮按 RED / 实现 / GREEN / 记录锁步推进的执行方式。它只共享一次产品实现与按依赖重跑，不合并两套 6 步、证据链或 AC 判断。
_Avoid_: 合并轮次、一次验证两边都算过

### 判定与证据

**仓库 baseline**：
由 `sdd-init-frontend` 维护、同仓所有 Requirement/Story 复用的三类事实：`REPO-1` 环境与运行、`REPO-2` 工程质量、`REPO-3` 工程范式。`repo-baseline.md` 是唯一事实源，保存于 SDD 项目的 `frontend-baselines/<repo-id>/`，不写进业务仓。
_Avoid_: 项目 baseline、Story 环境段、本机快照

**工程依据**：
`dev-baseline.md` 中当前 Story 对 `REQ-DEC-*` 与仓库 `PATTERN-*` 的轻量引用，并记录 REPO-3 指纹。它不保存范式正文、源码片段或证据表。
_Avoid_: Story 范式卡片、代码事实副本、`codebase-brief.md`

**需求执行起点**：
`DEMAND-2`。当前 Story 开工时冻结的范围、目标路由、`base-ref`、账号/角色/fixture/API 模式和质量失败集合。它引用仓库 baseline，但与具体起点提交绑定。
_Avoid_: 仓库环境、工程质量能力

**QA 基线**：
`DEMAND-3`。开工前产出、经人工确认后冻结的完成判定标准，分还原侧与功能侧两部分。它回答「怎样算做完」，不描述怎么做。
_Avoid_: 验收标准（那是上游 AC）、测试计划、DoD

**验收声明**：
一个可独立判定真假的完成主张，来源是 AC、AT 或冻结 QA 基线行。验证与收口都以声明为最小作用域。
_Avoid_: 门禁项、检查项

**声明状态**：
验收声明在当前证据下的状态，只有 `PROVEN`、`UNVERIFIED`、`DEFERRED`。未执行与外部依赖未就绪是不同状态。
_Avoid_: 通过率、基本通过

**风险触发器**：
由计划事实、仓库事实与最终 diff 命中的风险标签。它决定需要哪些验证模块，不用 Story 大小或 Task 数量代替。
_Avoid_: 影响面分级、Impact S/M/L、风险等级

**验证组合**：
当前 Story 的验收声明、风险触发器与验证模块之间的映射。它允许每条声明用最小充分证据完成，并在新风险出现时扩展。
_Avoid_: 固定门禁清单、验证档位

**共享检视证据**：
`review-evidence.json`。保存最终候选代码指纹、验证组合已选命令的原始结果，以及带 fixture / viewport / 运行时 / 依赖范围的浏览器场景事实；不保存通过/不通过判断。Phase B 已实际执行的场景在 Step ⑥ 直接写进来并标 `source: phase-b`，Phase C 只做新鲜度核对与缺口补采。布局、功能、规范与质量角色各自回到自己的基线独立判断。
_Avoid_: 共享结论、复用检视报告、浏览器缓存、Phase B 另存一份可提升事实

**证据纪元**：
一次候选验证中所有适用检视共同引用的代码状态与证据包版本。它约束证据一致性，不要求固定角色数量或墙钟同轮并发。
_Avoid_: 同一批次、四代理同时启动

**新鲜度键**：
判断一次已执行的检查能否被后续 Task 引用的唯一依据。命令类是「完整命令 + scope + toolchain/runtime + 代码指纹」，浏览器场景是「页面 + fixture + viewport + runtime + `depends_on` 逐文件哈希」。键不变就引用，键变化就重跑；两侧共用同一套定义，不为 Phase B 另立批次或意图编号。
_Avoid_: 验证批次、验证意图、VAL-B 编号、证据缓存、一个总体 pass 分给所有消费者

**工作假设**：
已知缺口中存在安全默认值的一类，随 QA 基线确认门同轮列出并经用户确认；确认后与基线同等冻结，变更走硬门禁 8。
_Avoid_: 默认值、暂定方案

**差异清单**：
`restore-report-*.json` 的人类摘要，只列机器报告中的 RED / YELLOW 与补证状态，不再自行判定或复制第二本证据账。
_Avoid_: 视觉 diff、走查记录、问题清单

**还原契约**：
`dev-baseline.md` 中 R1–R6 的 Story 级机器镜像。保存基线内容哈希；基线与契约不一致时拒绝执行。
_Avoid_: 自动验收标准、新基线

**还原报告**：
同一冻结还原契约在 RED / GREEN 阶段执行产生的机器报告。单条状态只有 red、yellow、green；有 RED 即整体 RED，仅 YELLOW 不得判 GREEN。
_Avoid_: 差异清单原文、截图报告

**YELLOW**：
契约规则暂时无法可靠判定，需要明确补证；不是轻微问题，也不是通过。页面不可用、状态 fixture 缺失或机器视觉盲区都可产生 YELLOW。
_Avoid_: 警告、基本通过、待优化

**豁免**：
QA 基线中被显式声明为「允许与原型不一致」的项，每条必须附理由。
_Avoid_: 例外、忽略项

**阻断级**：
使一个或多个验收声明不成立的确证缺陷。它阻止受影响声明成为 `PROVEN`；证据未执行本身属于 `UNVERIFIED`，不是缺陷。
_Avoid_: P0、严重

**建议级**：
检视结论中写入报告但不阻断收口的一类。
_Avoid_: P1、次要

**Deferred**：
因外部依赖未就绪而明确推迟、并在 `alpha-tests.md` 中标注的内容。带 Deferred 标记的 AC 不计为已验收。
_Avoid_: 挂起、待办

### 原型

**design tokens**：
设计稿生成器抽出的跨元素共享值。本阶段优先取单属性、被多处引用的共享类；它是设计稿侧事实，不等于目标仓 REPO-3 中的样式/token `PATTERN-*`。
_Avoid_: 设计变量、仓内 token

**Interface Inventory（界面清单）**：
忽略文案、按 `tag + class` 结构签名去重得到的重复模式清单，编号为 `IC-nn`；编号不是组件名，名称与变体关系由 `extract-prototype` 审订。
_Avoid_: 组件清单、组件库

**锚点**：
用于定位原型区块的 class 结构坐标。同名 class 多处出现时带 DOM 序号；根元素无具名 class 时走最近具名祖先／后代的结构路径。格式化档可附行号坐标，行号不作查找手段。
_Avoid_: 行号范围、语义标签

**区块**：
原型页面中一个可命名的视觉单元，是还原工作的最小指派对象，粒度上通常对应一个组件。
_Avoid_: 模块、组件（组件是代码侧概念，区块是原型侧概念）

**区块规格**：
一个区块一份的 Requirement 级设计稿事实，包含锚点、内容哈希、引用组件与 token、逐元素布局值、实例数据及 R1–R6 覆盖。还原轮以它为取值入口，不直接读取原型 HTML。
_Avoid_: 规格卡、原型片段

**设计事实**：
`DEMAND-1` 的机器入口。`design-facts.json` 中由脚本确定性生成的 Requirement 级事实，包含归一化 DOM/CSS、资源内容/缺失状态、区块、结构、静态文案、token 与布局声明。
_Avoid_: QA 基线、还原契约

**原型指纹**：
归一化 DOM/CSS 与外部资源内容/缺失状态共同计算的 SHA-256。只改 HTML 空白格式不变；结构、文案、CSS、资源内容或缺失状态任一变化都会改变。
_Avoid_: `doc_hash`、文件 mtime

**视觉缓存**：
只为 YELLOW 视觉项按需生成的 Requirement 级原型截图缓存；命中只读复用，键失配创建新版本，不覆盖旧版本。
_Avoid_: 实现证据截图、每轮固定截图

**动态数据位**：
设计稿中代表运行时数据的占位符文案。区块规格只保留格式模板，不把样例值作为 R2 文案期望值。
_Avoid_: 假文案、静态标签

**不破**：
上游未定义响应式规格时，本阶段对目标断点承诺的最低保障：无横向滚动、无重叠、无内容截断。不含任何布局结构变化。
_Avoid_: 响应式适配、移动端支持

### 上游约束

**静态实现模式**：
上游 `requirement-frontend-design.md` 声明的对接模式之一，指不接后端、以静态数据实现界面。它是对接模式的取值，不是工作类型——不可用它指代「还原」。
_Avoid_: 静态实现、mock 模式、假数据模式

## 设计依据

`SKILL.md` 与各 reference 里标「理由见 CONTEXT.md」的几处，理由在这里。**这些是判断要不要改流程时的依据，不是执行步骤**，执行照 `SKILL.md` 走。

### 分段依据：A1 必须跑完才能派 `recon-spec`

QA 基线还原侧的期望值只能取自区块规格。A1 没跑完就派 `recon-spec`，它只有两条路：打开原型 HTML 自己看（撞硬门禁 9，且把整份稿子灌进上下文），或者凭 Story 名推期望值（发明规格）。两条都会让冻结基线失去可追溯性，所以宁可多一个串行段。

代码侧勘察不读设计稿，它的输入是仓库 baseline 与 diff，因此只要 A1 未整段跳过就在 A1 首轮处理，把它从确认门前的关键路径上摊掉：查询对象已知且所需 PATTERN 都能唯一命中、locator 仍有效、未命中强制回退触发器时，由主 agent 做 `lite` 机械选读；其余派 `recon-codebase` 完整勘察。`recon-spec` 等 A1 完成后在 A2 派出。两侧仍汇入同一个确认门——拆到两个确认点上只会让用户多等一次。

### 八个 subagent 不注册为独立 skill

它们每一份都依赖两样东西：主 agent 传入的路径变量取值表，以及上游阶段已经落盘并冻结的产物。单独注册成 skill 后，它们会在没有前置校验的情况下被直接调起，产出的结论追不到基线也追不到指纹——看起来是检视报告，实际是一份无判据的观感清单。

次要理由：skill 列表里多八条高度相似的描述，会挤占其他 skill 的触发预算，也更容易误触发。

### 演进准入规则：新增机制必须成本中性或成本为负

本 skill 的每一道门、核销点和强制表格，都是针对一次真实失败加上的。但「针对真实失败」只证明了必要性，没有约束总量——2026-08-13 到 08-16 的三次提交，提交信息分别写着缩放提速、降本与收敛，实际净增 2,816 行、8 份强制工件。**只声明适用档位不足以拦住这件事，因为它约束的是「谁付」，不是「一共有多少」。**

因此新增或加重任何机制（工件、脚本、强制表格、核销点、门禁项）时，下面三条逐条成立才能落地：

| # | 条件 | 判据 |
| --- | --- | --- |
| 1 | **点名替换** | 写明它替换掉哪一份现有机制，或者为什么现有机制都无法承载这件事。写不出来的不加——「多一份更保险」是这套流程变长的唯一真实原因 |
| 2 | **先真跑再固化** | 任何新增的强制工件或脚本，必须在一个真实 Story 上跑通一次才能升为硬门禁或退出门禁项。未验证的一律标 `experimental`，不进任何门禁、不进[退出门禁](./SKILL.md#退出门禁)、缺席不算降级 |
| 3 | **总量上限** | Story 级强制工件 ≤ 9 份；单个 Phase 的入口必读 ≤ 500 行。超了必须先删够再加，不得以「这次特殊」放行 |

同时仍要**声明它由哪些风险触发器启用、支撑哪些验收声明、缺席时哪些声明会变成 `UNVERIFIED`**；写不出映射的机制不进入验证组合。

第 2 条的实证：验证批次账本（4 份 JSON + 171 行契约 + 795 行脚本）在 08-16 直接升为 Phase B 强制机制，而唯一一次真跑在 08-13——它从未被真实 Story 执行过一次，却让 Phase B 入口必读增加了 171 行。同一次真跑还暴露了更强的信号：15 份强制工件里有 7 份根本没生成，收口整段没走完，仍宣告完成。**文书重到执行时会被跳过，它就不再是质量保障，只剩延迟和一种「已经很严谨」的错觉。**

验证采用**声明驱动**：门禁约束能否把一条验收声明写成 `PROVEN`，风险触发器决定为它执行哪些动作。不可缩放的是来源、状态、证据与缺陷四类诚信；RED/GREEN、命令、浏览器矩阵、截图与独立检视均是可按风险选择的证据策略。唯一执行规则见 [validation-policy.md](./references/validation-policy.md)。

“检视独立”不等于“四份成套”。只有风险触发的检视角色才独立作出判断；多个适用角色可以引用同一份原始事实。代码变化也不把整个证据包一刀切作废，只失效依赖命中的场景与声明。

同理，“有回归依据”不等于每个 Story 都执行 REPO-2 全套命令。验证组合只选择能覆盖风险闭包的命令；触发 `shared-boundary`、`auth`、`write`、`unknown-deps` 或 `build-config`，或者仓库没有可安全收窄的入口时才升级全量门。精确命中状态的旧证据仍可复用为起点事实。

代码侧 `lite` 只消除重复发现，不降低工程依据：它只能在每条需要唯一命中已有 PATTERN、locator 仍成立，且未触发 `shared-boundary`、`new-pattern`、`spec-gap` 或 `unknown-deps` 时成立。否则回完整勘察。

Phase B 只取得当前 Task 所改变声明的因果证据；状态矩阵、跨页判断、宽回归与适用的独立检视在候选稳定后集中执行。同一动作只执行一次并由相关声明引用。省掉的是与当前声明无关的动作，不是把缺证据的声明改写成通过。

执行耗时要按可控边界记录，但它是**度量工具而非交付判据**：`execution-telemetry.json` 默认不开，只在用户要执行量、或正在排查某段流程为什么慢时开启。开了就按稳定子步骤拆，并把 `human_wait` 与 agent 主动时间单列——Phase 总时长把三者混在一起，不能支持下一轮优化。它只记动作边界与计数，不保存 verbose log，也不允许事后按 LOC 估算。任何门禁不因它缺席而拦截：让度量本身变成必答题，是上一版把 15 份工件里 7 份跑丢的原因之一。

### 设计稿链路的问题分流

设计稿 → 抽取 → 规则 → 比对是一条分层链，每层只对一类问题负责。链路出问题时按下面顺序问，答案直接指向改哪层；**不要在下游层修上游层的病**——典型反例是改实现代码去迎合一根写错的字符串针。

| # | 先问 | 是 → 归哪层 | 修法 |
| --- | --- | --- | --- |
| 1 | 抽取缺口清单里有没有新形态？ | 抽取器白名单 | 把该类缺口移进 `extract_design_spec.py` 的能力边界（如新增 token 分类模式、解析 at 规则）；验收标准 = 该 kind 从 gaps 清单消失。边界外形态永远以显式缺口出现，不会静默出错值 |
| 2 | RED 的 expected 与 actual 语义相同吗？ | 比对器等价 | 归一化集中在 `verify_restore_contract.py` 的 normalize / canonicalize 函数族与两端同源的简写别名表（`collect_restore_facts.js` 同步）；新的序列化差异只加这里，不改任何提示词 |
| 3 | expected 本身就不该存在？ | 规则授权 | 改 `recon-spec.md` 的期望值写作约束（如 R1 不得含原型类名、CSS 键用 longhand） |
| 都不是 | 期望值来自失真的需求输入 | 编排输入 | 修上游原型 / 文字规格，走硬门禁 8 重新确认基线 |

运行时的对应规避点（skill 执行中自查，全部档位生效）：A2 回传校验拦「R1 含原型类名」（phase-spec 第 2 节）；Phase B Step ② 拦「语义等价的假 RED」，不修实现、不加豁免、按工具缺口上报（phase-implementation Step ②）；抽取缺口走硬门禁 14 的既有通道。

实证来源：区域流水地图 Story（2026-08-13）的 7 条 RED——4 条比对器等价、1 条规则授权、2 条编排输入，没有一条出在抽取器。

### 无截图能力时：布局检视终止，功能自测试降级

两者相反是刻意的，差别在**判据是否必须经由视觉**：

- 布局与响应式检视的六个维度全部建立在渲染后的视觉观察上（跨页一致性、溢出截断、对齐栅格、叠层）。没有截图能力，它没有任何可判定的输入，硬出报告只能靠猜——所以判终止，并按 [退出门禁](./SKILL.md#退出门禁) 的三档表显式披露。
- 功能自测试的判据是「做这个操作，出现那个可观察结果」。浏览器能跑就能判定，截图只是证据的留存形式；缺了它仍可用文字如实记录实跑过程与结果——所以判降级，在证据里注明缺截图。
