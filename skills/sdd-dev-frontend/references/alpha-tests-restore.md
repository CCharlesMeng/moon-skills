# `alpha-tests.md` 还原证据扩容

本文描述 `sdd-dev-frontend` 阶段对上游 `sdd-task` 产出的 `alpha-tests.md` 做的两处扩容：**新增一节「还原证据记录」**，**扩展既有的「AC ↔ 证据映射」节**。

**这是扩容既有账本，不是新开一本账。** 还原证据必须写进 `alpha-tests.md`，不得另存一份独立的还原验收文件——`alpha-tests.md` 是验收追溯的唯一证据源，这个地位不能被稀释。为什么还原类工作用差异清单而不是失败测试充当 RED 证据，见 [ADR-0001](../docs/adr/0001-restore-uses-diff-list-as-red-evidence.md)。

## 扩容后的章节顺序

| # | 章节 | 本次变更 |

## 一、新增：还原证据记录

### 1.1 记录粒度与写入时机

- **一轮还原对应一条记录。** 一个 Task 内允许多轮 6 步；每个还原轮独立成一条记录，同一 Task 涉及多个区块就有多条记录，不得合并成一条。逻辑轮不进本节，它的证据仍落在 L4 / L3 记录节。
- **在 Step ⑥ 写入。** Step ① 产出的差异清单与 Step ④ 的复核结果，到 Step ⑥ 一起落账，不在中途分次写入。
- **记录编号**用 `R-<Task 编号>-<轮次>`，例如 `R-T3-1`。这个编号是 AC ↔ 证据映射节引用还原证据的唯一定位符。定位到记录里的某一条偏差时，用「记录编号 + 偏差编号」，形如 `R-T3-1 / D-R1-1`。

### 1.2 单条记录的结构

每条记录由四块组成，缺一不可：**记录头 → RED 差异清单 → RED 双方截图 → GREEN 复核**。

#### 记录头

| 字段 | 说明 |
| --- | --- |
| 记录编号 | `R-<Task 编号>-<轮次>` |
| Task | `tasks.md` 中的 Task 编号与标题 |
| 区块 | 原型切分表中的区块名，必须逐字沿用，不得改写 |
| 原型来源 | 原型文件路径 + 行号范围，与切分表一致 |
| 截图视口 | 宽 × 高，取自 `dev-baseline.md` 环境段声明的目标视口 |

区块名逐字沿用切分表，是为了保证同一区块在勘察、实现、检视三个阶段被理解成同一个东西。

**基线源不是 HTML 原型时**，「原型来源」改填基线源：`参照页 <路由> · <区块> · <组件文件> L<起>-L<止>`，或 `文字规格 · <文档章节>`，并在记录头追加一行 `可信度：降级（类比基线 / 无视觉基线）`。字段名与四块结构不变。**不得把参照页路径填成原型路径掩盖降级。**

#### RED 差异清单

按 QA 基线还原侧的六个固定维度逐项列出偏差。**六个维度必须逐条出现，无偏差的维度写「无偏差」，不得省略行**——省略行无法区分「查过没问题」和「压根没查」。

| 偏差编号 | 维度 | 偏差项 | 原型表现 | 实现表现 |
| --- | --- | --- | --- | --- |
| | R1 区块与层级完整性 | | | |
| | R2 文案一致性 | | | |
| | R3 间距与对齐 | | | |
| | R4 状态样式 | | | |
| | R5 空态与边界内容 | | | |
| | R6 指定视口下的布局完整性 | | | |

维度编号 `R1`–`R6` 与 QA 基线模板的还原侧维度一一对应，不得改名或重排。偏差编号带 `D-` 前缀，在所属维度编号后加序号（`D-R1-1`、`D-R3-2`）；同一维度有多条偏差就拆成多行，无偏差的维度保留该行，偏差编号与两侧取值一律填 `—`，与 `diff-list-template.md` 第三节同口径。清单非空即 RED；过程中差异清单的产出格式见 `diff-list-template.md`，落账时一律收敛成本表。

前缀加在偏差侧，是因为 QA 基线的期望值编号（`R1-1`、`R3-2`）被 QA 基线、检视维度清单、AC ↔ 证据映射多处引用，是稳定的规格侧；偏差编号一轮即作废，加前缀成本为零。两套编号不要求一一对应。

**无偏差的行填 `—` 而不是留空。** 空单元格有歧义，读的人分不清它是「确实无偏差」还是「漏填了」；`—` 是明确的「已检视、无偏差」信号。本节要求六个维度即使无偏差也保留行，目的就是证明每个维度都被看过——留空恰好把这个目的破坏掉。

#### RED 双方截图

| 侧 | 截图路径 |
| --- | --- |
| 原型 | |
| 实现 | |

两侧截图必须同视口、同区块、同滚动位置，否则不足以支撑「可观察到」的判定（对应 Step ② 验 RED）。

**路径约定**：本轮的截图一律存进 `<story-dir>/evidence/<Task 编号>-r<轮次>/`，目录名与记录编号 `R-<Task 编号>-<轮次>` 对齐。文件名固定三个：`red-prototype.png`、`red-impl.png`、`green-impl.png`。例如 `R-T3-1` 的 RED 原型截图是 `<story-dir>/evidence/T3-r1/red-prototype.png`。**表里填完整路径，不填相对片段。**

#### GREEN 复核

逐条对 RED 清单里的每个偏差项给出处置结果，偏差编号与 RED 清单一一对应：

| 偏差编号 | 处置 | 复核结果 |
| --- | --- | --- |
| D-R1-1 | | 已清零 / 命中豁免 `EX-n` |

复核结论只有两种合法形态：

1. **清零**——RED 清单每一项都已消除。
2. **剩余项全部命中已冻结豁免**——每个剩余项必须列出它命中的豁免编号，该豁免必须在人工确认门冻结的 QA 基线中已经存在。**开工后新增豁免来消化剩余项，等同于放宽标准，必须走 `dev-baseline.md` 变更记录并重新请用户确认，不得在本节就地追认。**

除这两种之外的任何状态（还剩几项、下轮再改、影响不大）都不是 GREEN，属于阻断级，先修再落账。

GREEN 侧另附实现截图一张；原型截图沿用 RED 的同一张，无需重截。

### 1.4 无截图能力时的降级填法

环境探测判定不具备截图能力时，截图字段填 `降级：源码级对照`，并在该处给出对照所用的原型片段行号与实现文件路径。同时：

- 该条记录在记录头追加一行 `可信度：降级（源码级对照）`；
- 账本头与最终报告都必须告知「本次还原证据为源码级对照而非视觉对照，可信度下降」。

**不得静默降级，不得留空截图字段，不得填写未实际产出的截图路径。**

## 二、扩展：AC ↔ 证据映射

既有列（AC 锚点、覆盖 Task、RED/GREEN 证据链等，以既有账本实际列名为准）全部保持不变，本次只做两件事：**证据类型列新增「还原」值**、**新增状态列**。

### 2.1 扩展后的表

| AC 锚点 | 覆盖 Task | 证据类型 | 证据链 | 状态 |
| --- | --- | --- | --- | --- |
| AC-1.1 | T3 | 还原 | R-T3-1 | GREEN |
| AC-1.2 | T3, T4 | 还原, L4 | R-T3-1；`UT-order-filter-reset-01` | GREEN |
| AC-2.3 | T5 | L3 | `IT-order-export-02` | Deferred |

### 2.2 证据类型列

- 值域为既有取值加上新增的「还原」。既有取值以账本前几节收的证据层级为准（L4 单元测试、L3 单服务单接口集成测试），本次不改动它们的含义。
- **一条 AC 可同时挂多类证据。** 一条 AC 占一行，证据类型列填多值以 `,` 分隔，证据链列按同一顺序逐个给出定位符，两列一一对应。
- 「还原」的证据链填「还原证据记录」节的记录编号（`R-T3-1`），不填截图路径——截图在记录里，映射表只做定位。
- 只挂「还原」证据的 AC 仅限纯呈现类（没有可断言的行为分支）。含行为分支的 AC 必须另挂 L4 或 L3 证据，不得只靠还原证据判定通过。

### 2.3 状态列

值域只有两个值：

| 值 | 含义 |
| --- | --- |
| `GREEN` | 该 AC 的全部证据链已闭环 |
| `Deferred` | 因外部依赖未就绪明确推迟 |

**不设第三个值。** 既不到 GREEN、又不满足 Deferred 条件的 AC 不得进表——它是阻断级问题，先修完再落账。

### 2.4 Deferred 明细

状态为 `Deferred` 的每条 AC，必须在本节末尾的明细子表补齐原因与解除条件，两者缺一不可：

| AC 锚点 | 原因 | 解除条件 |
| --- | --- | --- |
| AC-2.3 | 上游 `requirement-frontend-design.md` 未声明对接模式，导出接口实际不可用，本次降级为静态实现模式 | 接口 `/api/orders/export` 可用后，补一轮 L3 集成证据，状态改为 `GREEN` |

- **原因**必须指名外部依赖是什么、卡在哪里，不接受「暂不支持」这类无主语的写法。
- **解除条件**必须可观察——谁做完什么就算解除。「待后续评估」「视情况而定」不是解除条件。
- **不要拿豁免顶替 `Deferred`**：豁免用于「已经决定就这么做，且这么做是对的」，`Deferred` 用于「外部依赖没就绪，现在做不了」。把后者写成豁免，等于把一条未验收的 AC 洗成已验收。

### 2.5 一条硬规则

> **带 `Deferred` 标记的 AC 不计为已验收。**

收口报告、AC 对账、任何「本 Story 已完成」的结论，一律把 `Deferred` 的 AC 按未验收处理。不得静默通过，不得在汇总口径里把它并入已完成数，不得用「已实现但未验证」之类的措辞模糊掉。
