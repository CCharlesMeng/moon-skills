# 检视维度清单与分级

本文是 Phase C 四份检视的编号、默认级别、覆盖规则与汇总口径的**权威来源**。四份检视提示词（`agents/review-layout.md`、`review-convention.md`、`review-quality.md`、`self-test.md`）保存具体检查动作、前置校验和输出格式；其中重复出现的编号或级别若与本文不一致，以本文为准。

分级的两档定义见 [CONTEXT.md](../CONTEXT.md)：**阻断级**必须修完才能收口，**建议级**写入 `dev-review.md` 但不阻断。**不设第三档。** 够不上这两档的观察不进报告——留一个中间档，所有难判的结论都会滑进去，报告就失去了门禁作用。

---

## 一、编号体系

检视沿用上游已有的编号，不另造一套。

| 命名空间 | 含义 | 定义在哪 |
| --- | --- | --- |
| `R1`–`R6` | QA 基线还原侧六维度 | `references/qa-baseline-template.md` |
| `F1`–`F4` | QA 基线功能侧四维度 | `references/qa-baseline-template.md` |
| `EX-n` | 已冻结豁免 | `dev-baseline.md` 豁免表 |
| `PATTERN-*` / `REQ-DEC-*` | 仓库范式与 Requirement 工程决策 | `dev-baseline.md / 工程依据` → `repo-baseline.md / REPO-3` 或 `requirement-frontend-design.md` |
| `L1`–`L6` | 布局与响应式检视维度 | 本文 |
| `C1`–`C7` | 代码规范检视维度 | 本文 |
| `Q1`–`Q8` | 质量检视维度 | 本文 |
| `REG-n` | 既有主路径回归项 | `agents/self-test.md` |

- 检视结论的编号是维度编号加序号：`L3-2`、`C6-1`、`Q7-3`。
- **功能自测试不用自己的命名空间**，它逐行执行基线功能侧，结果直接挂在 `F1-n`–`F4-n` 上。这样主 agent 能把实测结果贴回基线行，两边对得上。
- 引用基线与代码事实时**原样引用编号，不转述内容**。

## 二、分级规则

四份检视的默认级别写在各自的维度表里。判级时四条规则按顺序压过默认值。

### 规则 1 — 门禁兜底（优先级最高）

不论落在哪个维度、由哪份检视报出，命中下列任一项一律**阻断级**：

这九项与 `SKILL.md` [退出门禁](../SKILL.md#退出门禁) 第 4 条逐条对应：

- AC 未覆盖
- 占位符（TBD / TODO / 无代码步骤）
- 编译期类型错误
- 还原机器报告存在 RED / YELLOW，且未逐条命中已冻结豁免
- 测试红
- 回归相对 Phase 0 基线变差
- 公共样式硬编码
- 调试语句残留
- 无理由的检查抑制（一切让类型检查或 lint 闭嘴的写法，具体关键字按栈见 `stack-antipatterns.md`）

### 规则 2 — 确证的功能缺陷即阻断

规则 1 的九项**不是穷举**，它列的是最容易被磨掉的那几项。这一条补足其余情形：

一条发现如果**能给出具体的触发操作序列，且会产生错误结果**（不是不够优雅、不是将来可能有隐患），就是阻断级。典型是质量检视 Q5 里的竞态覆盖、未清理导致的泄漏、副作用自触发形成的无限循环。

**「确证」是硬条件。** 给不出触发序列的推测不适用本条，按各维度默认级别走。这条规则的口子只对「已经能复现的错误行为」开，否则「万一将来出问题」可以套到任何结论上，两档分级就失效了。

### 规则 3 — 命中已冻结基线即阻断

一条发现如果证明**已冻结 QA 基线的某一行不成立**，且未命中已冻结豁免 `EX-n`，就是阻断级——不管它落在哪个维度、默认级别是什么。

基线是用户确认后冻结的完成判定标准。允许「基线要求了但没做到，只记建议级」，等于给放宽标准开了后门，冻结就白冻了。

**反过来不成立**：命中了 `EX-n` 的偏差不报；无法判定是否命中的，标 `待主 agent 核豁免`，由主 agent 对着 `dev-baseline.md` 豁免表定夺，子代理不自行认定。

### 规则 4 — 无基准不判违规

代码规范检视的判据全部来自 `dev-baseline.md / 工程依据` 引用的仓库范式和 Requirement 决策。**找不到对应基准的，不判违规**，记建议级或不记，并可在 Open Question 里问是否需要形成 Requirement 决策或刷新 REPO-3。

这条守的是代码规范检视「结论可被验证对错」的性质。一旦允许用通用最佳实践顶替仓内基准，它就退化成第二份质量检视，两份并行跑的意义也没了。

### 规则之外

- **Open Question 不判级别。** 需要上游或用户决定的事不是缺陷，单列一节，不计入阻断级条数。
- **Deferred 候选不判级别。** 外部依赖没就绪做不了的事，由主 agent 判 `Deferred`。带 `Deferred` 标记的 AC 不计为已验收，不得拿它顶替通过。

## 三、四份检视的维度清单

### 3.1 布局与响应式检视（`agents/review-layout.md`）

真实数据、真实交互、目标视口下跨页面检视。**不重复还原轮 Step ④** ——那一关是单区块对原型静态核对，这里抓的是当时看不到的东西。

| # | 维度 | 对应基线 | 默认级别 |
| --- | --- | --- | --- |
| L1 | 跨页一致性 | R3（跨页扩展） | 建议级 |
| L2 | 真实数据下的溢出与截断 | R5 | 命中 R5 → 阻断级；否则建议级 |
| L3 | 目标视口下的「不破」三项 | R6 | 阻断级 |
| L4 | 对齐与栅格 | R3 | 命中 R3 → 阻断级；否则建议级 |
| L5 | 真实交互下的状态样式表现 | R4 | 命中 R4 → 阻断级；否则建议级 |
| L6 | 滚动与固定元素行为 | 无对应 | 建议级；破坏「不破」三项时按 L3 判阻断级 |

两条硬约束：

- **视口只取 R6 已冻结的宽度**，不自行增删。
- **响应式不发明。** 「不破」被破必须报（阻断级），但如果唯一解法需要改变布局结构，只描述现象与约束，同时记 Open Question 回问上游，**不在结论里给改结构的修复建议**。上游没给响应式规格时，本阶段只承诺「不破」。

### 3.2 代码规范检视（`agents/review-convention.md`）

基准是工程依据选中的 `PATTERN-*` / `REQ-DEC-*`，每条结论都能被验证对错。范围只限本 Story 的改动。

| # | 维度 | 基准来源 | 默认级别 |
| --- | --- | --- | --- |
| C1 | 目录与文件命名 | 对应 `PATTERN-*` | 建议级 |
| C2 | 组件写法范式 | 对应 `PATTERN-*` | 建议级 |
| C3 | 样式方案一致性与硬编码 | 样式/token `PATTERN-*` | **硬编码颜色 / 间距 / 字号 → 阻断级**；其余建议级 |
| C4 | 请求与错误处理 | 请求/错误 `PATTERN-*` | 建议级；命中规则 2 或规则 3 时升阻断级 |
| C5 | 公共能力复用 | 公共能力 `PATTERN-*` | **建议级** |
| C6 | 类型定义与检查抑制 | 类型/编码 `PATTERN-*` | **无理由的检查抑制 → 阻断级**；类型错误 → 阻断级；其余建议级 |
| C7 | 国际化与文案机制 | 国际化 `PATTERN-*`；工程依据未选择则不适用 | 建议级 |

C3 与 C5 的级别差异是刻意的，C4 默认建议级也是刻意的，理由都见第四节。

### 3.3 质量检视（`agents/review-quality.md`）

没有外部基准，靠通用工程判断。与代码规范检视拆开并行，就是不让主观判断稀释客观判断。**「仓内约定如此/不如此」能判定的不归它**，交代码规范检视。

| # | 维度 | 默认级别 |
| --- | --- | --- |
| Q1 | 组件职责与体积 | 建议级 |
| Q2 | 重复代码 | 建议级 |
| Q3 | 复杂度与嵌套深度 | 建议级 |
| Q4 | 状态放置 | 建议级 |
| Q5 | 副作用管理（依赖、清理、竞态、循环） | 会导致错误行为的 → 阻断级；其余建议级 |
| Q6 | 错误与边界处理完整性 | 命中 F3 某条且未处理 → 阻断级；其余建议级 |
| Q7 | 死代码与遗留 | **调试语句残留、本 Story 新增的占位实现 → 阻断级**；其余建议级 |
| Q8 | 明显性能问题 | 建议级 |

约束这份检视主观性的是一条要求：**每条结论必须写出「为什么现在就得管」**——什么条件下会产生什么可观察的坏结果。说不出后果的风格偏好不进报告。

### 3.4 功能自测试（`agents/self-test.md`）

浏览器实跑。检视项直接派生自冻结基线功能侧，编号沿用基线行号。

| 检视项 | 来源 | 做什么 | 不通过时 |
| --- | --- | --- | --- |
| F1 覆盖层级对账 | 基线 F1 | 标了浏览器自测的进入本轮实跑范围；标了 L4 / L3 的核对测试存在且绿 | 阻断级（AC 未覆盖 / 测试红） |
| F2 AC 可观察判定实跑 | 基线 F2 | 逐行执行「页面与路由 → 操作 → 可观察结果」 | 阻断级 |
| F3 异常与边界实跑 | 基线 F3 | 逐行造触发条件，五类都要有实跑记录 | 阻断级 |
| F4 接口契约实测 | 基线 F4 | 请求参数、字段映射、错误码逐项实测 | 阻断级 |
| REG 既有主路径回归 | 规则 1 的回归门禁，**不来自 QA 基线** | 涉及页面的既有主路径 + test / typecheck / lint / build 对比 `DEMAND-2` 起点失败集合 | 相对起点变差 → 阻断级 |

- **F1 是范围决定项**，它不实跑界面，但堵住「层级声明了却没人做」这个口子。
- **F2–F4 不通过一律阻断级**，因为它直接意味着已冻结基线的某一行不成立（规则 3）。
- **REG 没有对应的 QA 基线维度**，它的判据是 `DEMAND-2` 记下的起点失败集合。起点本来就红的项保持红不算变差；缺起点记录时记 `无基线可比`，不得判定为通过。
- 结果只有 `通过` / `不通过` / `未跑（原因）` 三值。跑不了的记「未跑」，不得改判据让它过。

## 四、刻意的级别差异及其理由

下面几条的级别各有明确理由。**改级别前先读理由**；理由不再成立时才改，不要因为「感觉某条更要紧」就调。

### 4.1 公共样式硬编码（阻断级）vs 公共能力重复实现（建议级）

两条都是「本可以复用却没复用」，级别却相反。四个轴上它们的差别都是同向的：

| 对比轴 | 公共样式硬编码（C3，阻断级） | 公共能力重复实现（C5，建议级） |
| --- | --- | --- |
| 影响半径 | **全局且长期**。token 是主题的唯一开关，硬编码一处，换肤、暗色、品牌调色时这一处就是漏网 | **局部**。一份重复的金额格式化只影响调用它的那几处 |
| 出问题的方式 | **静默**。不报错、不崩、测试照绿，只在视觉上慢慢不一致，等到有人发现，同类硬编码已经繁殖了一片 | **显性**。两份实现行为分叉时会以 bug 形式暴露，有机会被常规手段抓到 |
| 修复成本 | **极低**。字面量换成 token，改动范围就是那一行，没有行为风险，不需要回归 | **高**。抽取或改调既有实现要处理签名差异、边界差异、调用方改动与测试改动，可能波及本 Story 之外 |
| 正当理由 | **几乎没有**。确实需要不一致的极少数情况走豁免即可，成本也就一条豁免记录 | **时有**。既有实现语义不完全匹配、复用会引入不该有的依赖、既有实现自身有问题——都是合理的不复用理由 |
| 判定确定性 | **客观**。与工程依据选中的样式/token `PATTERN-*` 逐条比对，对错分明 | **含灰度**。「本可复用」取决于语义等价性判断，不同人可能给出不同结论 |

**结论**：硬编码是「收益高、成本近乎零、判定客观、几乎没有正当理由」的一类，卡成阻断级不会误伤，也不会逼出无谓返工；重复实现是「收益局部、返工成本高、判定含灰度、常有正当理由」的一类，卡成阻断级会逼着 agent 为了过门禁去做不该做的合并，反而制造风险。

所以后者进报告不进门禁：**证据照给全**（新写的实现在哪、对应哪条 `PATTERN-*`、语义差在哪、能不能直接替换），是否统一交给人判断。

**建议级不等于可以不看。** 它的定义是「不阻断收口」，不是「可以不写」。每条建议级结论都必须完整写进 `dev-review.md` 并保留证据。

### 4.2 可读性、可访问性、性能优化（建议级）

三者的共同点是**没有验收依据**：上游没给规格，仓内也没有基准，判据只能来自通用最佳实践。

卡成阻断级会产生一个具体的坏结果——agent 为了过门禁，会去做一批没有人要求、没有判定标准、也没有测试兜底的改动，在收口前引入新风险。这与本阶段「不发明规格」的立场是同一条。

**但有依据时按规则 3 升级**：

- 焦点态是 R4 已冻结的要求 → focus 不可见是阻断级，不是可访问性建议
- 加载态是 F3 已列的条目 → 缺加载态是阻断级，不是性能建议
- 「不破」三项被破 → 阻断级，即使它看起来像布局美观问题

判断的落点不是「这类问题重不重要」，而是**「有没有一条已冻结的判据说它不成立」**。

### 4.3 绕过请求封装与裸捕获（建议级，可升级）

C4 按 4.1 的四个轴判：它在影响半径与判定确定性上接近硬编码（有请求/错误 `PATTERN-*` 作客观基准），**但修复成本这一轴完全不同**：把一处绕过封装的调用改走仓内封装会改变运行时行为——鉴权头、错误码映射、重试与取消都变了，必须重新验证。此时全部 Task 已经 GREEN，为一条没有失败证据支撑的结论去动运行时行为，是在收口前引入新风险。

所以默认建议级，证据照给全（哪个调用点、绕过了哪条 `PATTERN-*`、少了什么）。真出问题的情形不会漏：

- 裸捕获吞掉错误导致 F3 的错误态不成立 → 规则 3 升阻断级
- 少了鉴权头或错误码映射导致请求实际失败 → 功能自测试会跑出来，规则 2 或规则 3 升阻断级

### 4.4 调试语句残留（阻断级）

它不影响功能，级别却和类型错误一样高，原因是三条同时成立：**判定完全客观**（有就是有）、**修复成本为零**（删掉即可）、**没有任何正当理由**（真需要日志的走仓内 logger，那不算调试语句）。

三条同时成立的项，卡成阻断级不会有任何误伤，也就没有理由留情。**本 Story 新增的占位实现**（`TODO` / 空函数体 / 写死的样例数据顶替真实取数）同理，且它还直接命中门禁的「占位符」一项。

仓内既有的旧调试语句与旧 `TODO` 不在本检视范围内——那是历史债，不由本 Story 的收口来偿。

## 五、汇总口径

主 agent 把四份回传汇总进 `dev-review.md` 时：

1. **去重取高。** 同一处代码被多份检视报出（典型：跨页不一致同时是硬编码、边界缺失同时被质量检视静态发现和功能自测试实跑发现），合并成一条，级别取最高的那一档，并保留各自的证据与编号。
2. **不改级别。** 汇总时只按第二节四条规则判级，不因为条数多就降级、不因为观感上扎眼就升级。要改级别，改本文并写明理由。
3. **阻断级清零才能收口。** 未清零就收口，等于门禁不存在。
4. **Open Question 与 Deferred 候选单独成节**，不计入阻断级条数，但必须在收口报告里出现——它们是需要人决定的事，被折叠掉就等于替人做了决定。
5. **检视报告不复用。** 重跑时代码已经变了，旧结论一律作废，四份全部重跑。
