# QA 基线模板

本模板对应 `dev-baseline.md` 的「QA 基线」一节。它回答「怎样算做完」，不描述怎么做。

**十个维度是固定的，不可增删。** 还原侧六维、功能侧四维，填写者只能填每个维度下的具体期望值与豁免项。本 Story 不涉及某个维度时，保留维度标题，在表格第一行写 `不适用`，并在「具体期望」列写明为什么不涉及。**不得删除维度，不得留空表。**

---

## 一、填写栅栏

模板的目的是逼出**可判定的期望值**。三道栅栏都要过，任何一条不过则该行不合格，退回重填。

### 栅栏 1 — 槽位填满

每条期望值都是一行三列，缺任何一列都不成立。

| 列 | 要求 |
| --- | --- |
| 判定对象 | 页面 / 区块名。区块名必须与原型切分表一致，不自造名字 |
| 具体期望 | 一个可以被判成对或错的陈述 |
| 取证方式 | 怎么判定。还原侧写契约层级与模式：`冻结契约 · render/structure · 锚点 <class>`、`static+render/numeric ±1px`、`render/overflow ≤1px`；只有机器盲区写 `visual（YELLOW 时按需补证）`。功能侧写操作路径或测试层级 |

**锚点的主体是 class 选择器，行号只是附带的引用坐标**，逐字沿用区块规格区块头的「锚点」字段，不自己拼、不自己算。单行导出件无行号可给，末段写 `无行号`，不要编一个范围出来。

### 栅栏 2 — 措辞黑名单与必含要素

「具体期望」列出现以下措辞即不合格：

| 禁用措辞 | 为什么不合格 |
| --- | --- |
| 与原型一致 / 符合设计稿 | 把判定又推回给原型，等于没写 |
| 与现有页面一致 / 与线上保持一致 | 同上一条同类。基线源为参照页时，必须落到参照页的具体路由、区块名与实测数值 |
| 样式正确 / 布局正常 / 表现良好 | 没有判据，任何结果都能自圆其说 |
| 无明显偏差 / 基本对齐 | 「明显」「基本」是可伸缩的口子 |
| 交互合理 / 体验流畅 | 主观词，检视时无法证伪 |
| 适配各端 / 响应式良好 | 上游没有响应式规格时本阶段只承诺「不破」，见 R6 |

每条「具体期望」至少命中以下一项：

- **数值**：px、rem、个数、条数、字符数、断点宽度
- **枚举值**：状态名、颜色 token 名、组件库 size 值、错误码
- **点名清单**：把元素或文案逐个列出，不用「等」「若干」收尾
- **可观察动作**：做什么操作、看到什么结果

### 栅栏 3 — 陌生人判定测试

自问：**一个没看过原型、没参与讨论的人，只拿这一行，能不能判定通过或不通过？**

不能，就是没写完。这一条兜住前两道栅栏漏掉的情况——措辞不在黑名单里、也有数字，但仍然指不到具体东西。

### 提问前 — 证据来源分类

只针对会变成「已知缺口」或 Open Question、进而可能进 P7 的**候选事实/问题**。期望值行本身仍过上面三道栅栏；本表是提问前的第四道关，**先分类，再决定能不能问用户**。

每条候选先填这一行：

| 事实/问题 | repo 有证据 | prototype 有证据 | 分类 | 证据 |
| --- | --- | --- | --- | --- |
| `<候选>` | 是 / 否 | 是 / 否 | `user-only` / `conflict` | `<文件路径或区块规格锚点；两侧皆否时写检索方式>` |

「有证据」= 能直接读出**该事实的答案**（期望值、枚举、数值、文案），不是「提到过这个话题」。区块规格把某态标 `未见`，只证明设计稿没有答案，`prototype 有证据` 仍为「否」。仓内组件库默认不得拿来顶替 R4 / R5 的 `未见`（见 R4），那种情况 `repo 有证据` 亦为「否」。

| 条件 | 分类 | 去向 |
| --- | --- | --- |
| `repo 有证据` 或 `prototype 有证据` 任一为「是」 | （不产出分类值） | **不得提问、不进「已知缺口」**。证据直接写入基线对应位置 |
| 两者都为「否」，且只有用户 / 业务方知道答案 | `user-only` | 可进「已知缺口」，可进 P7 |
| 两侧证据互相矛盾，或与上游 AC / 上游文字规格矛盾 | `conflict` | 可进「已知缺口」，可进 P7；提问时列双方证据，不让用户凭空答 |

**允许产出用户问题的分类值只有这两个**：`user-only`、`conflict`。拼写固定，不得改成中文或别的英文词。

| | 写法 | 判定 |
| --- | --- | --- |
| 正例 | 默认字体：检索 `src/styles/tokens.css` 得 `--font-sans: "PingFang SC"`；设计宽度：读 `design-facts.json` / 区块规格得 `1440px` → 两侧「是」，直接填进基线 R3 / R6，不进「已知缺口」。仅对两侧皆「否」的项标 `user-only`（或证据对撞标 `conflict`）提问，并在「证据」列写清查了哪类文件、哪个锚点 | 合格：先检索再分类；有证据就落基线；提问附检索方式 |
| 反例 | 未查 `tokens.css` / `design-facts.json` / 区块规格，把「默认字体是什么」「设计宽度多少」写成「已知缺口」问用户 | 不合格：repo 或 prototype 已有答案，却进了提问 |

**必含要素**：逐字给出期望文案，含标点、单位、大小写；动态文案给出模板串与占位符。

| 编号 | 判定对象（页面 / 区块） | 具体期望 | 取证方式 |
| --- | --- | --- | --- |
| R2-1 | `<页面>` / `<区块名>` | | 冻结契约 · `render/exact` · 锚点 `<class 选择器>` |

### R3 — 间距与对齐

**必含要素**：给出数值或仓内 token 名（间距、内外边距、栅格列宽、对齐基准线）。只在原型与实现可能分歧的位置写，不要逐元素抄一遍。

| 编号 | 判定对象（页面 / 区块） | 具体期望 | 取证方式 |
| --- | --- | --- | --- |
| R3-1 | `<页面>` / `<区块名>` | | 冻结契约 · `static+render/numeric ±1px` · 锚点 `<class 选择器>` |

| | 写法 | 判定 |
| --- | --- | --- |
| 正例 | 卡片间距 16px（`--spacing-md`）；卡片内边距上下 20px、左右 24px；标题与正文基线间距 8px | 合格：数值 + token 名 |
| 反例 | 间距按原型，整体保持视觉平衡 | 不合格：主观词，无数值 |

### R4 — 状态样式

hover / focus / disabled / 选中 / loading 五态。

**必含要素**：逐态给出触发方式与可观察变化。

**基线源为原型、且区块规格把某一态标 `未见` 时，该态不进本表也不进豁免表，登记进「已知缺口」。** 静态设计稿里没有 hover / focus / disabled / loading，这一维必然大面积 `未见`；拿仓内 token 或组件库默认顶上去，是在没有基线的情况下发明规格，而豁免的语义是「允许与原型不一致」——没有基线就谈不上一致或不一致，写进豁免表等于把「没有规格」洗成「已经决定就这么做」。五态全部 `未见` 时本表第一行写 `不适用`，在「具体期望」列指到对应的已知缺口条目。上游后续补了规格，走变更记录重新确认。

**`不适用` 的理由主句写人话**：先说「设计稿没有画这些状态，所以不设还原判定」这类人能直接懂的结论，检索出处（查了哪个文件哪个锚点）放句尾括号——理由是给确认门的用户读的，出处是给复核的人查的。R5 同此。

| 编号 | 判定对象（页面 / 区块） | 状态 | 具体期望 | 取证方式 |
| --- | --- | --- | --- | --- |
| R4-1 | `<页面>` / `<区块名>` | hover / focus / disabled / 选中 / loading | | 冻结契约 · `static+render/state` · 锚点 `<class 选择器>` |

| | 写法 | 判定 |
| --- | --- | --- |
| 正例 | 表格行 hover 背景变为 `--color-bg-hover`，无位移无边框变化；提交按钮 loading 时左侧出现旋转图标、文案不变、按钮不可点击 | 合格：逐态 + token + 可观察变化 |
| 反例 | 各交互状态样式正常 | 不合格：命中黑名单，且五态未拆开 |

## 五、豁免表

豁免是**显式声明「允许与原型不一致」**，不是放宽标准的后门。每条必须有独立理由，且理由要能被第三方核对。

| 编号 | 所属维度 | 判定对象 | 与原型的偏差 | 实际采用 | 理由 | 有效范围 |
| --- | --- | --- | --- | --- | --- | --- |
| EX-1 | `<R1-R6 / F1-F4>` | `<页面 / 区块>` | | | | |

**可接受的理由，三类**：

| 类型 | 说明 | 理由要附的证据 |
| --- | --- | --- |
| 仓内范式冲突 | 组件库默认样式或仓内既有范式与原型不符，改它会波及本 Story 之外 | 组件或 token 的文件路径，以及会被波及的范围 |
| 原型自身缺陷 | 原型这一处自相矛盾、或与上游文字规格冲突 | 冲突双方的出处（区块规格锚点 + 文档章节） |
| 平台能力限制 | 目标浏览器或运行环境不支持原型的做法 | 不支持的具体特性名 |

**不接受的理由**：时间不够、实现成本高、差异很小、后续再优化、原型可能画错了（无证据）。这些出现即退回。

**豁免与 Deferred 的分界**：因外部依赖（接口未就绪等）做不了的，不走豁免，走 `alpha-tests.md` 的 `Deferred` 标记，并写明解除条件。**带 Deferred 标记的 AC 不计为已验收。** 豁免只用于「已经决定就这么做，且这么做是对的」。

## 八、已知缺口

「已知缺口」是 QA 基线的伴生节，收**已经过证据来源分类、且分类为 `user-only` 或 `conflict`** 的项。结构如下；字段名固定，供 `recon-spec` 与 Phase A2 §4 原样引用。

| 编号 | 缺什么 | 影响哪一块 | 分类 | 证据 | 建议处理 |
| --- | --- | --- | --- | --- | --- |
| G-1 | `<候选事实 / 问题>` | `<维度或前置>` | `user-only` / `conflict` | `<路径或锚点；未见时写「检索 <文件/锚点> → 未见」>` | |

**进表前硬约束**：每一行必须先完成「提问前 — 证据来源分类」。`repo 有证据` 或 `prototype 有证据` 任一为「是」的候选**不得出现在本表**，证据已写入基线对应位置。`分类` 列只允许 `user-only` 或 `conflict`。「证据」列禁止只写「未见」——必须写清查了哪个文件或哪个区块规格锚点之后的未见；`conflict` 行必须列出双方出处。

**同类缺口合并成行**：同一区块、同一维度、同一处理方式的「未见」类缺口写成一行，「缺什么」列内列举各态或各类（如「hover / focus / disabled / 选中 / loading 五态样式均未见」），检索方式写一次。九行长得一样的表比一行清单更难读，也更容易被人整体跳过。
