# Story 产物模板

主 agent 在三个时刻读本文件：**Phase 0 第 2 步起草缺失的 `tasks.md` 等三份产物**时、**Phase 0 新建 `dev-baseline.md`** 时、**Phase C 第 7 节汇总 `dev-review.md`** 时。除起草的三份产物落在 `<story-dir>` 且各自独立成文外，`dev-baseline.md` / `dev-review.md` 也都写在 `<story-dir>`。

`dev-baseline.md` 的「工程依据」「功能理解」「QA 基线」「已知缺口」四节由 Phase A2 追加，字段以 [qa-baseline-template.md](./qa-baseline-template.md) 为准，本文件不重复。

## 一、`dev-baseline.md` 的 `DEMAND-2`

```markdown
# Dev Baseline — <Story 编号与名称>

## 给人的摘要

<Phase A2 落盘时由主 agent 写，**文档口吻**——本节冻结后会被长期、由任何人阅读，**不得出现「现在提出来」「要你点头」这类只在确认门那一刻成立的会话语句**；向用户征求确认的话写在确认门消息里，不落盘。固定三段陈述：
1. **检查什么**——对照什么标准、查哪些东西（业务语言点名，如「卡片结构、标题文字、尺寸颜色逐项对照原型」），数量放句尾括号；
2. **不检查什么**——设计稿没覆盖的部分及其处理方式（如「悬停与空态设计稿未提供，不做还原判定」）；
3. **已确认的偏差与假设**——每条豁免与工作假设一句人话（本来 vs 实际 vs 为什么），写明已经用户确认、后续变更须走「变更记录」重新确认。
**禁止**：用行数统计代替内容（「还原侧 15 行」说明不了任何事）、以编号或内部词（还原侧 / 豁免 / 冻结）开头组织句子——编号只作句尾括号。结尾固定一句阅读指引：「表格中的锚点、指纹、取证方式列供机器校验使用，阅读时只需关注『具体期望』列。」>

> 术语速查：R1–R6 = 还原侧标准（结构 / 文案 / 尺寸 / 状态 / 边界 / 视口）；F1–F4 = 功能侧标准（测试层级 / AC 判定 / 异常边界 / 接口契约）；EX = 经你确认的「允许与原型不一致」；G = 设计稿或上游没给答案的缺口；WH = 缺口的默认处理假设；指纹 = 机器比对用的哈希，人不用读。

## 执行起点（环境）

| 项 | 结论 | 证据 |

| `base-ref` / 起点 SHA / 工作区 | `<取值>` | git 只读命令 |

## 起点质量

| 类别 | 命令 | 结果 | 证据 |
| --- | --- | --- | --- |

| 对象 | 完整指纹 |
| --- | --- |

| REPO-2 | `<sha256>` |
| REPO-3 | `<sha256>` |

```

三条约束：

- **完整哈希只出现在「指纹附录」一处。** 正文任何行需要引用指纹时写「见指纹附录」；把 64 位哈希铺进正文表格是把人读的文件变成机器转储。检视子代理与仓库接入门做指纹比对时，以本附录为准。

- **只有 Story 特有、且初始化阶段无法预先消除的限制才能进入「降级项」。** 页面或 `<browser-driver>` 等仓库必需能力失效时回 Phase -1，不得直接降级。
- **「起点质量」不生成 `REPO-2` 里不存在的类别的表格行。** 上游明确要求但 `REPO-2` 没有对应能力时回 Phase -1 补齐，不在 Story 中写「未提供」。

## 二、`dev-review.md`

```markdown
# Dev Review — <Story 编号与名称>

## 给人的摘要

<每条发现一句业务语言：现象 + 影响 + 建议动作，编号放句尾括号，例：
「新地图卡片和 region-map 演示页上的同类卡片长得不一样（一个有边框阴影、一个没有），是运行时对两种容器的既有分叉，不影响本次验收；要不要统一交给你决定（L1-1）。」
没有发现写「本次检视无需要你关注的发现」。Phase C 汇总时写，Phase D 收口时更新；本节与最终输出的 P8 新发现清单同源。>

| --- | --- | --- | --- |

| --- | --- | --- | --- | --- | --- |

<同上表结构，去掉修复状态列；每条完整保留证据，不摘要>
```

**建议级不等于可以不写。** 它的定义是「不阻断收口」，不是「不进报告」。

## 三、`tasks.md` 等三份产物的最小起草模板

只在 Phase 0 第 2 步判定「可以自动起草」时使用：`<story-dir>` 下没有 `tasks.md`，但当前会话已经把 Story 范围、AC、页面/区块的还原基线和对接模式聊清楚。三份文件独立成文，都写在 `<story-dir>`。

**两条约束优先于模板本身：**

- **会话没聊到的字段一律写「未定义 / 待确认」，不得替用户做设计决策，不得编造响应式规格或状态样式。** 这与硬门禁 7「不发明响应式规格」同一条道理，起草阶段不能破例；「未定义」会照常在 Phase A2 被登记进「已知缺口」，不因为是起草出来的就被放行。
- **起草稿在用户确认前不算已产出的 `tasks.md`。** 过一轮独立确认门（格式见 SKILL.md Phase 0 第 2 步），不与其他决策同轮；用户确认后再落盘。

### 3.1 `tasks.md`

```markdown
# Tasks — <Story 编号 · 名称>

## 计划头

| 字段 | 值 |
| --- | --- |
| Goal | <一句话说清这个 Story 要交付什么> |
| Architecture | <2-3 句：涉及哪些页面/组件、对接哪个接口、静态实现还是完整对接> |
| Tech Stack | <框架 + 语言 + 样式方案，如 React + TS + Vite + CSS Modules> |
| project | <repo-root 的路径或名称> |
| project_type | frontend |
| 归属 Story | <Story 编号 · 名称> |
| frontend_design_path | <story-delta-frontend-design.md 的路径> |

## 项目边界

- 范围内：<本 Story 要改的页面 / 模块>
- 范围外：<明确排除的相邻功能，避免顺手扩大范围>
- 本仓类型：frontend，禁止跨仓任务

## 文件结构

| 文件 | 类型 | 单一职责 |
| --- | --- | --- |
| `<path>` | 样式（还原 Task 专属） | <一句话> |
| `<path>` | 逻辑 / 取数 | <一句话> |
| `<path>` | 测试 | <一句话> |

## Story / AC 追溯表

| AC 锚点 | 覆盖 Task |
| --- | --- |
| AC-x.1 | T1 |
| AC-x.2 | T2 |

## 执行规则

**TDD Iron Law**：没有失败证据就不写实现。失败证据有两种形态：

- **逻辑类工作**：失败的单元测试或单接口集成测试。
- **前端还原类工作**：运行已冻结的外部设计契约；机器报告至少一项明确 RED 才进入实现，无 RED、无 YELLOW 才是 GREEN。

除这两种形态之外，没有失败证据不写实现。

**No Placeholders 铁规**：禁止 TBD / TODO / "类似任务 N" / 无代码步骤。

每步 2-5 分钟一个动作，「写失败证据」和「运行确认失败」是两步，不可合并。**一个 Task 内允许出现多轮 6 步**：还原与逻辑各走一轮，顺序固定为先还原轮、后逻辑轮，每轮独立编号并标注形态。

## Task List

### T1 · <页面名> · 还原

文件清单（样式与骨架，本 Task 独占，逻辑 Task 不得再列样式文件）：

- `<path>`
- `<path>`

区块与原型来源（没有 HTML 原型时写清楚基线出处）：

- <区块名>：基线源「文字规格」，见 `story-delta-frontend-design.md` 对应小节

6 步（形态：还原）：

- [ ] ① RED（还原）—— 运行冻结契约，生成 RED / YELLOW / GREEN 报告；至少一项明确 RED 才进入实现
- [ ] ② 验 RED —— 核对 RED 的外部出处与实现定位
- [ ] ③ GREEN —— 只修报告里的 RED
- [ ] ④ 验 GREEN —— 重跑同一契约，无 RED、无 YELLOW
- [ ] ⑤ REFACTOR —— 按需
- [ ] ⑥ 记录证据并提交

### T2 · <功能名> · 逻辑（AC-x.2）

文件清单（不含样式文件）：

- `<path>`

6 步（形态：逻辑）：

- [ ] ① RED（逻辑）—— 写失败的单元测试或接口集成测试，给出完整代码
- [ ] ② 验 RED —— 运行测试，确认按预期失败
- [ ] ③ GREEN —— 最小实现让测试转绿
- [ ] ④ 验 GREEN —— 测试转绿 + 作用域回归（全量对账在 Phase C 派发前自检）
- [ ] ⑤ REFACTOR —— 按需
- [ ] ⑥ 记录证据并提交

## 计划自审三查

- [ ] AC 覆盖：Story / AC 追溯表中每条 AC 都有 Task 覆盖
- [ ] 占位符扫描：全文无 TBD / TODO / "类似任务 N"
- [ ] 类型一致性：涉及的接口字段类型与 `story-delta-frontend-design.md` 一致
- [ ] 前端行另查 1：组件树 / 界面清单是否已烘焙（首个 Story 可写「无，暂无复用组件」）
- [ ] 前端行另查 2：每个前端 Task 的每一轮 6 步，Step ① 是否明确标注了失败证据形态
- [ ] 前端行另查 3：每个页面的样式是否集中在一个还原 Task 内；逻辑 Task 文件清单是否不含样式文件
- [ ] 前端行另查 4：有无「样式微调」「统一优化」这类没有原型对照范围的 Task

## 风险与回滚

- 关键假设：<...>
- 失败路径：<...>
- 回滚策略：<...>
```

### 3.3 `story-delta-frontend-design.md`（无 HTML 原型时必写）

```markdown
# Story 增量设计 — <Story 编号 · 名称>

## 目标与 AC 引用

- 目标：<一句话>
- AC：AC-x.1, AC-x.2 ...（与 `tasks.md` 的 Story / AC 追溯表一致）

## 对接模式

- <完整对接模式 / 静态实现模式，二选一，写明理由；缺省时 sdd-dev-frontend 会把它记为已知缺口>

## 文字规格（无 HTML 原型时必填）

- 布局结构（自上而下 / 自左向右有几个子节点）

## 当前代码事实

- 变更边界：<明确不动的文件 / 模块>

## 状态、交互、接口与数据映射

| 接口 | 请求参数 | 字段映射 | 错误码处理 |
| --- | --- | --- |

## 风险与依赖

- <...>
```
