#  SDD-Dev-Frontend Agent 框架讨论背景

## 一、项目背景

我们正在设计一套严格遵循 SDD（Spec-Driven Development）的 AI 编码 Skill / Agent 框架。

整体流程大致为：

```text
Requirement Spec
→ Test Design
→ SDD-Design
→ SDD-Task
→ SDD-Dev
→ 集成与交付
```

当前重点讨论 `sdd-design`、`sdd-task` 和 `sdd-dev` 三个阶段。

项目具有以下特点：

* 采用多仓库 Workspace，多个前后端工程可以并行开发。
* 上游会提供较完整的产品规格、验收设计和交互澄清结果。
* 前端设计稿以完整 HTML 原型为主。
* 仓库中存在 Feature 逆向知识、架构知识和编码 Guideline。
* Agent 不能只依赖文档，需要在设计和编码阶段主动探索代码事实。
* 目标不是简单“设计稿转代码”，而是建立规格、设计、代码和验证之间的完整追踪闭环。

## 二、SDD-Design 当前产物

### 1. Requirement 整体设计

`requirement-design.md` 负责描述：

* 设计目标、约束和非目标
* 关键设计决策
* Story 到工程的影响映射
* 多仓库关键交互与调用链
* 数据、接口和内部模型影响
* 技术选型
* DFX
* 风险和 Open Questions
* Story 和微服务归属
* 跨仓依赖和并行开发关系

整体设计回答：

> 多个工程如何共同实现该 Requirement。

### 2. Requirement 前端总案

`requirement-frontend-design.md` 负责描述：

* 完整对接模式或静态实现模式
* Feature / Story / 前端工程索引
* 前端技术栈及代码证据
* 共享组件和跨页结构
* API 对接策略
* 前端数据模型和 API 字段映射
* Mock、静态数据及 Deferred 内容
* 模块、页面和路由
* 跨页状态与交互模型
* HTML 原型到前端业务结构的映射
* 前端 DFX

前端总案回答：

> 多个前端 Story 如何共享统一的架构、组件、状态和接口模型。

### 3. Story 增量设计

每个 Story 下沉具体设计：

```text
story-delta-design.md
story-delta-frontend-design.md
```

Story 设计负责描述：

* Story 实现目标和 AC 引用
* 当前代码事实
* Story 范围内的增量方案
* 具体工程、模块和文件影响
* 状态、交互、接口和数据映射
* 复用点和变更边界
* 风险、依赖和测试关注点

Story 设计回答：

> 当前 Story 具体修改什么，以及如何实现。

## 三、SDD-Task 当前产物
产物一：单仓实现计划（tasks.md）

  回答的问题：「这个仓在 Story 范围内，从 0 到 1 按 TDD 纪律把代码改完，需要改哪些文件、每处做什么、按什么顺序写测试和实现、怎么验证、怎么提交」——假设执行者对代码库零上下文也能直接开工的自包含说明书。

  文件结构：

  ┌─────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │      章节       │                                                                                        负责描述                                                                                        │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 计划头          │ 一句话 Goal、2-3 句 Architecture、Tech Stack、TaskPacket 字段（project / project_type / 归属 Story / testdesign 路径；前端行另填 frontend_design_path）                                │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 项目边界        │ 范围内/外清单，明确本仓是 backend 还是 frontend，禁止跨仓任务                                                                                                                          │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 文件结构        │ 本次新建/修改/测试的精确路径 + 单一职责说明；前端行须对齐组件树                                                                                                                        │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 实现设计要点    │ API/契约、数据/配置、错误处理；前端行含 IFC 切片、对领域 REST 的引用；后端行禁止写前端组件树                                                                                           │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ Story/AC 追溯表 │ 每条 AC 锚点 ↔ 覆盖它的 Task，闭环验收来源                                                                                                                                             │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 执行规则        │ TDD Iron Law（没有失败的测试就不写实现）、No Placeholders 铁规（禁 TBD/TODO/"类似任务 N"/无代码步骤）                                                                                  │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ Task List       │ 每个任务含精确文件清单 + 强制 6 步 checkbox：① RED 写失败测试（完整代码）② 验证 RED（精确命令 + 预期失败输出）③ GREEN 写最小实现④ 验证 GREEN + 全量回归⑤ REFACTOR 按需⑥ 记录证据并提交 │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 计划自审三查    │ AC 覆盖 / 占位符扫描 / 类型一致性；前端行另查组件树/IFC 是否已烘焙                                                                                                                     │
  ├─────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 风险与回滚      │ 关键假设、失败路径、回滚策略                                                                                                                                                           │
  └─────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  粒度纪律：每步 2-5 分钟一个动作，「写失败测试」和「运行确认失败」是两步，不可合并。

  ---
  产物二：开发侧红绿灯账本（alpha-tests.md）

  回答的问题：「每个 AC 锚点的 RED→GREEN 证据链在哪、跑过哪些命令、输出是什么」——Dev 阶段自留的验证账本，区别于黑盒测试人员执行的手工用例。

  文件结构：

  ┌─────────────────────────────┬─────────────────────────────────────────────────────┐
  │            章节             │                      负责描述                       │
  ├─────────────────────────────┼─────────────────────────────────────────────────────┤
  │ 账本头                      │ 关联的 AC 锚点清单、覆盖的 Task 列表                │
  ├─────────────────────────────┼─────────────────────────────────────────────────────┤
  │ L4 单元测试记录             │ 每条任务：测试名 → RED 输出 → GREEN 输出 → 回归结果 │
  ├─────────────────────────────┼─────────────────────────────────────────────────────┤
  │ L3 单服务单接口集成测试记录 │ 同上粒度，但聚焦接口级                              │
  ├─────────────────────────────┼─────────────────────────────────────────────────────┤
  │ AC ↔ 证据映射               │ 每条 AC 锚点对应的 RED/GREEN 证据链，闭环追溯       │
  └─────────────────────────────┴─────────────────────────────────────────────────────┘

  边界：只收 L4 UT + L3 单服务单接口集成测试；黑盒 testcase 不在此处。

  ---
  两个产物的配合

  - tasks.md 是执行说明书（事前）
  - alpha-tests.md 是执行证据账本（事中/事后）

  Task List 的 Step 6 会把证据从 tasks.md 执行过程沉淀到 alpha-tests.md，形成「计划 → 执行 → 证据」的闭环。后续 review/ac 阶段对账时，alpha-tests.md 是验收追溯的唯一证据源。

## 四、SDD-Dev 目标（本文件夹重点）
通过一组subagent实现功能理解和QA基线初始化、编码规范和范式的读取、可用组件的读取、前端代码的静态页面还原、布局检视与优化（如涉及，需要包括响应式增强）、逻辑补全（页面逻辑和后端对接）、代码规范检视、质量检视、功能自测试等功能
