# TDD 执行纪律（蒸馏自 superpowers：test-driven-development + verification-before-completion）

> 本文件是 task / dev 阶段的红绿灯纪律单一来源。它把"验收"从"声称完成"变成"可执行测试契约的强制出口"。

## 一、Iron Law（铁律）

**没有失败的测试，就不写实现代码。** 任何实现代码出现前，必须先存在一个针对该行为、且当前会失败的测试。违反铁律即视为流程失败，必须回退。

## 二、红绿灯环（RED → GREEN → REFACTOR）

1. **RED 写一个失败的测试**：表达一个具体的可观测行为（对齐某条 AT- 用例，即 alpha-tests.md 的 GWT 功能用例标识）。运行它，**确认它因正确的原因失败**（断言失败，而非编译/导入错误）。
2. **GREEN 写最小实现**：只写让该测试通过的最小代码，不提前实现未被测试要求的行为。运行，确认变绿。
3. **REFACTOR 重构**：在测试保持绿色的前提下消除重复、改善命名与结构。每步重构后复跑测试。

一次只推进一个红绿灯环；不要一次写多个测试或多段实现。

## 三、禁止行为清单（Red Flags）

- ❌ 先写实现，再补测试（事后测试不算 TDD）。
- ❌ **修改测试以适配实现**——测试表达验收契约，契约不为迁就实现而改。
- ❌ 删除/跳过/注释/`skip` 失败的测试来"变绿"。
- ❌ 放宽断言、用 `assert true`、捕获并吞掉异常以制造通过。
- ❌ 在没有看到测试先失败的情况下就声称它"验证了"行为。
- ❌ 用打印日志、手工点一下、"看起来对"替代自动化测试证据。

## 四、完成前验证门禁（verification-before-completion）

声称"完成"之前，必须满足：

- [ ] 每条相关 AT- 用例都有对应测试，且经历过"失败→通过"。
- [ ] 测试在**干净环境**可复跑通过。
- [ ] 未通过修改测试、放宽断言或跳过用例来获得通过。
- [ ] `tasks.md` 每个 Task 的 Step 1-6 checkbox 全部勾选（勾选即代表该 Step 的红绿验证已通过）。

**没有新鲜的失败→通过证据，就不得声称完成。** "我相信它能工作"不是证据；运行结果才是。完成状态由 `tasks.md` Step checkbox 承载，不再在 `alpha-tests.md` 记录证据/提交。

## 五、每任务强制步骤序列（writing-plans 结构层）

每个实现任务在 `tasks.md` 中必须内嵌以下 6 步 checkbox（**每步写要点描述，不写全量代码**），不可省略或合并：

1. **Step 1 RED**：写失败测试——**测试要点**（测什么行为 + 关键断言 + 测试文件路径，不写完整测试代码）
2. **Step 2 验证 RED**：运行精确命令，确认因**正确原因**失败（一句话预期失败点）
3. **Step 3 GREEN**：写最小实现——**实现要点**（改哪个类/方法 + 核心逻辑，不写完整实现代码，YAGNI）
4. **Step 4 验证 GREEN**：运行精确命令确认通过 + 全量回归仍绿
5. **Step 5 REFACTOR**：（按需）重构，测试保持绿色
6. **Step 6 提交**：按 tasks.md Step 6 内联提交规范生成 commit message（`【问题单号 Defect】{work_item_id}` + `【修改说明 Modification】{type}({scope}): {description}`）并执行 git commit；**勾选 Step 6 checkbox 即代表 Task 完成（含红绿验证通过）**。不在 `alpha-tests.md` 记录证据/提交（由 tasks.md Step checkbox 承载完成状态）。

## 六、合理化对照（听到这些就停）

| 借口 | 现实 |
|------|------|
| "太简单不用测" | 简单代码也会坏；写测试只需几分钟 |
| "先写实现再补测试" | 事后测试证明不了 TDD；你只是在补覆盖率 |
| "这次先赶进度" | 没有红灯证据的"完成"是幻觉 |
| "手动验过了" | 手动验证不可复跑，不是证据 |
| "改一下测试让它过" | 测试是契约，不为实现让步 |

## 七、分层与职责

- **开发侧（本纪律强约束）**：L3 单服务单接口集成测试（后端=API 接口级契约，前端=mock 集成级，**主**）+ L4 单元测试（公共代码/算法代码等，**辅助**）。落 `alpha-tests.md`，用例标识 `AT-{story_id}-NNN`，向上追溯 `story-delta-spec.md` 的 SC-/BR- 锚点。
  - `alpha-tests.md` 承载 GWT 功能级用例（What to test，框架无关），**不含红绿灯证据/提交记录**；
  - `tasks.md` Step 1/3 写测试/实现**要点**（非全量代码），Step checkbox 承载完成状态；具体代码由 Dev 阶段基于要点 + alpha-tests GWT 用例 + 探测框架（见 `references/test-framework-detection.md`）现写。
- **测试侧（QA）**：L0/L1/L2 黑盒（用户视角）用例，落 `*-testcase.md`，由 sdd-testdesign 独立产出（设计用例 S-/R- + AC 锚点 SDA-/RDA-），到集成环境手工编写脚本。sdd-task 不依赖测试侧产物。
- 开发侧的 L3 集成测试针对**接口级契约**（后端 = API 接口级，前端 = mock 集成级），不等同于黑盒 UI testcase，也不等同于测试侧的 UAT/SIT。
