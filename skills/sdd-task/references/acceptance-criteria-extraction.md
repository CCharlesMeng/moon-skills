# 验收标准提炼方法（单仓功能级）

> sdd-task 从 story-delta-spec.md 的 SC-/BR- 锚点提炼单仓功能级验收用例，写入 alpha-tests.md 的 GWT 章节。
> 遵业界需求分析方法，**不依赖 sdd-testdesign 的 AC 锚点**（AC 锚点是测试侧/领域侧验收基线，开发侧用本方法自建 AT- 用例）。
> 开发侧用例与测试侧用例 level 不同：开发侧 = 单服务内功能/接口/单元测试（L3/L4）；测试侧 = 需求级 UAT/SIT（L0/L1/L2）。

## 2. 需求分析方法体系（ISTQB 黑盒 6 大技术 + BDD/INVEST）

> 目标：**不凭感觉拆**。用系统化技术保证场景完备，每条用例可追溯到具体技术 + 锚点。
> 6 大技术按需求特征选用，非每条用例都过全部技术——但分析时须逐一考虑，确认"不适用"而非"遗漏"。

### 2.1 BDD/GWT（Given-When-Then）— 用例表达结构
- 所有验收用例统一用 GWT 结构表达（非挑选技术，是表达规范）
- Given = 预置条件（数据状态、请求体、组件状态）
- When = 触发动作（API 调用、用户交互、内部事件）
- Then = 可观测结果（响应码、响应体、渲染输出、副作用断言）

### 2.2 场景法 / 用例测试（Use Case Testing）— 从 SC- 派生
- 从 SC-\<X\> 正常流程提炼"主成功场景"用例
- 从 SC-\<X\> 异常/分支流程提炼"扩展场景"用例
- 每个场景至少一条 AT- 用例；端到端多步流程拆分为多条用例，用"预置数据"衔接

### 2.3 等价类划分（Equivalence Partitioning）— 输入域分类
- 对每个 API 参数/表单字段识别有效等价类与无效等价类
- 每个有效等价类至少一条正向用例
- 每个无效等价类至少一条反向用例（400/422 响应）

### 2.4 边界值分析（Boundary Value Analysis）— 边界缺陷
- 对数值/长度/日期类参数识别边界值（最小、最小-1、最小+1、最大、最大-1、最大+1）
- 边界值用例标注 `追溯: BR-\<Y\>`

### 2.5 决策表测试（Decision Table Testing）— 多条件组合业务规则
- **适用场景**：当一条业务规则涉及多个条件组合时（如 状态 × 权限 × 分页维度 的组合），等价类/边界值无法系统覆盖所有组合。
- **方法**：
  1. 识别条件（Conditions）：从 BR- 提取所有影响结果的输入条件（如订单状态、用户权限、分页参数）
  2. 枚举条件取值组合（每条件取"有效/无效"或具体枚举值），生成决策表（每列一个组合）
  3. 对每列确定预期动作（Actions）：成功/拒绝/降级/部分结果
  4. 合并等价列（相同动作的列合并）；每列生成一条 AT- 用例
- **示例**：BR-29c（状态多选）× BR-30（iAuth 权限）× BR-31a（权限未配置）→ 决策表枚举 3 条件组合，生成"有权限+状态匹配→返回数据""有权限+状态不匹配→空列表""无权限→不可见/降级"等用例
- 标注 `追溯: BR-\<Y1\>, BR-\<Y2\>`（多规则组合）

### 2.6 状态迁移测试（State Transition Testing）— 系统状态机
- **适用场景**：当需求涉及实体状态流转时（订单/合同/工单状态机：草稿→待支付→已支付→已取消等），须系统枚举所有合法/非法转换。
- **方法**：
  1. 从 spec/design 识别实体的状态机（状态节点 + 合法转换边）
  2. 为每个合法转换生成一条正向用例（触发动作 → 状态变更 + 副作用）
  3. 为每个非法转换生成一条反向用例（非法触发 → 拒绝/保持原状态 + 错误码）
  4. 覆盖所有状态节点的"进入/退出"至少一次
- **注意**：若 story-delta-spec 未显式定义状态机，但 design 涉及状态字段（如 `status` 枚举），须反向推导状态机并确认；无法推导时记入缺口回流
- 标注 `追溯: SC-\<X\>, BR-\<Y\>`

### 2.7 错误猜测（Error Guessing）— 经验补充 checklist
- **适用场景**：在上述系统技术之外，按经验 checklist 补充易错点用例（不替代系统技术，是补充）
- **checklist**（逐项确认是否适用，适用则生成用例）：
  - 空值/null/缺失必填字段
  - 特殊字符（SQL/HTML/Unicode/超长串）
  - 数据类型不匹配（字符串传数值字段）
  - 重复/并发请求（同一资源并发修改、重复提交）
  - 超时/重试（下游服务超时、重试幂等性）
  - 资源不存在（404：查询不存在的 ID）
  - 权限边界（越权访问他人资源）
  - 数据一致性（部分成功/部分失败的事务边界）
- 标注 `追溯: BR-\<Y\>`（若关联规则）或 `追溯: SC-\<X\>（异常）`

### 2.8 INVEST/SMART 用例质量检查
- Independent：每条 AT- 用例可独立执行，不依赖其他用例的副作用
- Negotiable：用例描述需求而非实现
- Verifiable：Then 中的断言可自动化验证
- Small：一条用例验证一个行为点

## 3. 后端 API 接口级用例提炼规则

### 3.1 从 SC- 提炼 API 用例（场景法）
1. 识别 SC- 场景涉及的对外 API（从 story-delta-spec §6 对外接口契约）
2. 对每个 API 生成：
   - 正向用例：正常请求 → 2xx 响应 + 副作用断言
   - 反向用例：非法请求 → 4xx 响应 + 无副作用
   - 幂等用例（如适用）：重复请求 → 相同结果
3. Given 写请求方法 + 路径 + 请求体 + 预置数据
4. Then 写响应状态码 + 响应体 + 数据库/消息副作用

### 3.2 从 BR- 提炼规则用例（决策表 + 等价类 + 边界值）
1. 识别 BR- 规则涉及的 API 参数/字段
2. **单条件规则**：用等价类 + 边界值生成满足/违反用例
3. **多条件组合规则**：用决策表（§2.5）枚举组合，每列一条用例
4. 对每条规则生成：
   - 满足规则的用例（正向）
   - 违反规则的用例（反向，预期错误码 + 错误消息）
5. 标注 `追溯: BR-\<Y\>`

### 3.3 API 测试维度 checklist（每个 endpoint 系统化覆盖）
> 对每个对外 API endpoint，按以下维度逐一确认是否生成用例（适用则生成，不适用须能说明原因）——这是"不凭感觉"的系统化保证。

| 维度 | 说明 | 是否必测 |
|------|------|---------|
| 正向（Happy Path） | 合法请求 → 2xx + 业务结果 | 必测 |
| 反向校验 | 非法参数/缺必填 → 4xx + 错误码 | 必测 |
| 业务规则执行 | 违反 BR- → 4xx/降级 | 必测（有规则时） |
| 边界值 | 数值/长度/分页边界 | 必测（有边界参数时） |
| 认证/授权 | 无 token/越权访问 → 401/403 | 必测（有鉴权时） |
| 幂等性 | 重复请求 → 相同结果 | 按需（幂等接口必测） |
| 并发 | 并发修改/重复提交 | 按需（有并发风险时） |
| 下游副作用 | 数据库/消息/缓存变化断言 | 必测（有副作用时） |
| 资源不存在 | 404：查询不存在的 ID | 必测（有 ID 参数时） |
| 错误处理 | 下游超时/异常 → 降级/错误码 | 必测（有外部依赖时） |

### 3.4 用例粒度
- 一条 AT- 用例 = 一个 API 调用 + 一组断言
- 复杂场景（多 API 编排）拆分为多条 AT- 用例，用"预置数据"衔接
- **后端用例必须是 API 接口级**（通过 API 端点调用，验证完整调用链），不是内部类单测

## 4. 前端 mock 集成级用例提炼规则

### 4.1 从 SC- 提炼组件交互用例
1. 识别 SC- 场景涉及的前端组件/页面（从 story-delta-frontend-design 组件树）
2. 对每个交互流程生成：
   - 正向用例：用户正常操作 → 渲染成功 + API 调用断言
   - 反向用例：API 返回错误 → 渲染错误提示
   - 空状态用例：无数据时的渲染
3. Given 写组件初始状态 + mock API 响应
4. When 写用户交互动作（点击/输入/路由跳转）
5. Then 写渲染结果断言 + API 调用断言（调用次数/请求体）

### 4.2 mock 策略
- 后端 API 全部 mock（前端用例不依赖真实后端）
- mock 响应数据从 story-delta-spec §6 对外接口契约推导
- 标注 mock 的 API 路径 + 响应码 + 响应体

## 5. AT- 标识分配规则

- 格式：`AT-{story_id}-NNN`（三位序号，从 001 起）
- story_id 取 Story 工作目录名中的 us-id 数字部分（如 `US20250510178479` → `AT-20250510178479-001`）
- 同 Story 同仓内唯一
- 编号顺序：SC- 正向 → SC- 反向 → BR- 规则（等价类/边界值/决策表）→ 状态迁移 → 错误猜测补充
- 每条用例须标注所用技术（场景法/等价类/边界值/决策表/状态迁移/错误猜测），便于复核"不凭感觉"

## 6. 覆盖完整性检查（三重保证，不凭感觉）

> 完备性由三重交叉验证保证，任一未闭合须 Stop 回流。

### 6.1 锚点覆盖矩阵（需求 → 用例）
- 每条 SC- 至少被一条 AT- 覆盖
- 每条 BR- 至少被一条 AT- 覆盖
- 落入 alpha-tests.md §3 覆盖矩阵，缺口列标注未覆盖锚点

### 6.2 API 维度 checklist 闭合（endpoint → 维度）
- 每个对外 API endpoint 按 §3.3 维度 checklist 逐一确认
- 不适用的维度须能说明原因（如"无鉴权"则认证维度标注 N/A + 原因）
- 适用维度必须有对应 AT- 用例；遗漏即缺口

### 6.3 锚点交叉验证（§5 验收场景摘要 → 用例）
- story-delta-spec §5 验收场景摘要的每条 GWT 至少被一条 AT- 交叉验证
- 若 §5 摘要有场景但无 AT- 覆盖 → 缺口，回流 spec 补充或补 AT- 用例

### 6.4 缺口处置
- 缺口记入 alpha-tests.md §3 覆盖矩阵的"缺口"列
- 无法覆盖时 Stop 并回流（spec/design 缺信息 → 回流 sdd-prd/sdd-design；非本仓范围 → 标注范围外）

## 7. 与测试侧用例的边界

| 维度 | 开发侧（本方法，AT-） | 测试侧（sdd-testdesign，S-/R- + AC 锚点） |
|------|----------------------|------------------------------------------|
| Level | L3 单服务单接口集成 + L4 UT | L0/L1/L2 黑盒 UAT/SIT |
| 执行者 | 开发 | QA |
| 载体 | alpha-tests.md | *-testdesign.md / *-testcase.md |
| 框架 | 仓内测试框架（探测） | 测试管理系统/手工脚本 |
| 追溯 | 向上 SC-/BR- | 向上 SC-/JR- |
| 关系 | 独立产出，不依赖测试侧 | 独立产出，不依赖开发侧 |

开发侧 AT- 用例与测试侧 S-/R- 用例各自独立从 spec 派生，互不依赖、互不追溯。
