# session-optimize 入门

一轮活干完了，过程中有过纠正、返工或浪费。这个 skill 把那些坑挖出来，判断每个坑该谁修，然后给你一份可以直接点头的改进清单。

它不会自作主张。除了一个记账文件，**任何修改都要先经你批准**。

> 如果你要做的是「改写某个 skill 的规则」，那是另一个工具的活，见 [refine-skill 入门](refine-skill-入门.md)。本文最后一节会说清什么时候该切过去。

---

## 什么时候调用

这轮出现过下面任一种情况：

- 你纠正过它，或者它返工了
- 验证失败、测试没跑起来、结果是错的
- 明显浪费——绕远路、重复劳动、读了一堆无关文件
- 你怀疑某个 skill 的默认行为有问题
- 这轮用过子代理，或者本可以用而没用，你觉得问题出在活怎么分

**不要在问题还没排查完的时候用它。** 它是复盘工具，不是诊断工具。

## 怎么调用

```text
/session-optimize
```

补一句关注点，归因会更准：

```text
/session-optimize

重点看这轮为什么改了三次才把测试跑通，以及下次开工前我该先给你哪些背景。
```

同一会话里可以调多次。第一次分析整个可见会话，之后只分析上次调用之后的部分。如果早期内容已经被上下文压缩截断，它会退化成只看当前可见范围，并在结论里说明证据边界——不会假装看过。

---

## 它怎么定位问题

同一个失败可以在很多层上描述。「测试没跑起来」既可以说是配置写错了，也可以说是没人验证配置，还可以说是流程里缺一道检查。**只有一层是最早能挡住它的地方。**

它按下面的顺序逐层问，停在第一个能解释失败的层：

| 层 | 问什么 | 谁修 |
| --- | --- | --- |
| L1 输入 | 目标或约束从没给过？项目里查得到但文档过时？用法或时机不对？ | 你 / 项目文档（文档过时的首次即可申请改） |
| L2 决策 | 信息充分、工具正常，但计划或判断本身错了？ | 属某个 skill 的规则 → 移交维护者 |
| L3 执行 | 工具选型、参数、调用顺序错了？ | 移交 skill 维护者 |
| L4 承载 | 正确使用之后，项目代码或配置本身有缺陷？ | 项目内修改（首次即可申请） |
| L5 环境 | 权限、网络、平台本身异常？ | 只移交负责人 |

顺序不是随便排的：越靠前的层，修一次能挡住的下游失败越多。跳过前面直接归到 L5，等于把能根治的问题记成了不可控的问题。

四对最容易混的，用反事实判：

- 项目里查得到就是**文档过时**，只有你知道才是**背景没给**
- 参数和用法都改对之后仍然异常，才算**工具本身**
- 现象出现在项目里但由 agent 的选择触发，仍算**决策问题**
- 换个用户在同样场景下也会这么用，说明是 **skill 的默认错了**，不是你用法不对

定位不了就写「不确定」并说明缺哪条证据，不会为了填格子硬选一层。

## 你会看到什么

一份报告，每个问题一张卡片，最多 5 张，按严重程度排：

```text
### 高 · 测试配置目录写错一层，本轮所有测试都在空目录里空跑

- **问题**：pytest 收集到 0 个用例却退出码为 0，任何回归都不会被发现。
- **证据**：第 8 轮 pytest 输出 `no tests ran`；tests/config.json:4 写
  "rootDir": "tests/unit"，实际用例在 tests/。
- **为什么会发生**：L4 · 项目实现 —— 配置改过目录结构，没有验证能区分
  "通过"和"没跑"。
- **怎么修**：tests/config.json:4 改为 "rootDir": "tests"，1 行。
- **改完怎么验**：pytest 收集到 12 个用例并全部执行。
- **什么说明没修好**：仍然 0 收集，或收集到无关目录的用例。
- **谁来做**：我改（待批准）。
- **固化**：project.config-path | 第 1 次 | 只记账 —— 走纠正，配置本身就是错的；不因此立规则。
```

标题写的是现象和后果，不是分类名。证据必须指到会话轮次、命令输出或文件行号——指不到就写「无直接证据」，不用「多次观察到」充数。

没有实质问题时，它会直接说「本轮无需优化」然后停，不硬凑。

## 你要做什么

报告末尾是**一个批准门**，整轮只有这一个决策点。你可以整批批准、逐项批准，或者只批准其中几条。

**沉默不算批准。** 「看起来合理」不算，以前的泛化授权也不算。执行时如果需要扩大范围或改变产品行为，它会停下来重新申请。

---

## 它会写哪个文件

只有一个文件免批准：**`.learnings/ledger.md`**（项目根）。只追加、单文件、可以 git 回退，不存在时自动创建。

其余一切——改项目代码、改文档、落证据包、投递反馈——都要过批准门。

`.learnings/` 是个公共目录，别的工具也可能往里写自己的文件。它只写自己那一份，同目录其他文件只读来查重，一律不改。

**台账要进 git。** 放进 `.gitignore` 会让计数只在本机累积，跨会话跨机器的复发就再也数不出来。

---

## 为什么它不肯立刻改规则

新用户最常见的困惑：明明发现问题了，为什么只说「记账」不说「改」？

因为**单次会话是 n=1 的证据，据此写死一条规则就是过拟合**。这次的巧合会变成下次的枷锁。

**但这只管立规则，不管修错的东西。** 文档和实现对不上、配置路径写错、示例跑不通——这些第一次发现就会直接进批准清单等你点头改，不用等复发，也不会被移交出去。判据是一句反事实：假设这个问题以后再也不出现，这条改动还该做吗？该做，那就是在修一个本来就错的东西；说不准，那就是在从一次经验里立规则。

修错的东西有两条边界：必须能指到那条依据（文件行号，或任何人重跑都得到同一结果的命令），而且只改回依据说的样子，不夹带顺手改进。满足这两条的可以整批一次批准；跨多个文件或一处以上的那项会单独拿出来问你。

有几种情况它不会当成「修错的东西」处理，而是退回下面的门槛：指不到依据的；两份文档互相矛盾、得先决定哪份说了算的（那是个决策，会单独列出来请你裁决）；改动会变更运行时行为的。文档和代码对不上时它还会先判方向——描述现状的文档以代码为准，定义契约的文档以文档为准，判不准就不改。

下面这张表管的是立规则那一侧：

| 情况 | 动作 |
| --- | --- |
| 还没到复发 3 次，且下面三条都不成立 | 只记账，改进以「下次的可逆试验」形式提出 |
| 已证实的高危不变量（数据、安全、错误结果） | 一次即可申请固化 |
| 同一个问题在这一轮里独立踩了两次或更多 | 一次即可申请固化 |
| 原因是一个你这个仓库无权改的固定东西 | 一次即可申请固化 |
| 复发 ≥ 3 次，跨 ≥ 2 个会话，都在最近 30 天内 | 申请写入长期资产 |
| 上轮试验被证明有效 | 申请固化为常规做法 |
| 超过 90 天没再出现 | 标记待复核，降低置信度 |

等三次是为了确认这不是巧合。所以当这一轮的证据已经能说明它必然还会发生、或者发生一次的代价就已经够高时，再等下去只是白付代价——那就是后三行的三种情况。

它们各自要一条这一轮就能验证的东西，不接受「我觉得这个坑以后会常踩」这种预测：高危要后果真的发生过，「差点出事」不算；这一轮踩两次要两次各自独立、各有各的痕迹，同一件事被你和子代理各说一遍不算；常驻原因不只要指出是哪个配置项、哪个命令的默认值、哪个名字有误导性，还要给出你这个仓库改不动它的证据（上游 submodule、第三方包的文档、归别的团队管的配置）——光指出那个东西不算，任何问题都能指出点什么。你这个仓库改得动的一律不走这条：能证明它现在就是错的，它会直接提议改掉，比立一条规则绕开它更好；能改但得先有人决定改成什么样（比如仓库里两种写法并存、还没定哪个算对），它会把这个决定拿来问你，而不是先立一条规则把没定的事写死。

这三种情况放宽的只是「要不要等」，别的都不变：照样记账，照样要你点头才动手。

计数靠一个稳定的键（`类别.症状`，比如 `decision.unverified-claim`），不靠关键词检索——同一个问题换个说法，关键词就搜不到了，计数一不可信，门槛就只是摆设。

**同一个问题被你、子代理、主 Agent 各提一遍，仍然只算 1 次。** 数的是复发，不是有几个人说过。这一轮里真的独立踩了两次，这一轮也只加 1——那两次走的是上面的快速通道，不是用来抬计数的。因为这个数记的是「在几个会话里出现过」，而「≥ 3 次」那条还要求跨两个会话以上，一轮加两次就会让一个会话自己凑出三次。

### 够门槛之后：先看能不能变成一条自动检查

一条规则写进文档，只有下次有人读到才起作用；变成一条检查，违反时会自己报错。所以够门槛之后它先问能不能编码成约束，写文档是次选。

两条同时成立才走检查：项目里已经有一个正在跑、并且已经在查同类事情的地方（测试、linter、类型、提交钩子、CI 步骤），这次只是往里加一条；而且这条检查不会误伤正常写法——会误报的检查最后会被整个关掉，比不加更糟。

**它不会为此新建设施。** 新建测试文件、新加 CI 任务、引入一个 linter 插件都算新建，那是产品决策，它最多在报告里建议你考虑，不会列进待批准清单。所以纯文档仓、没有 CI 的项目里，固化就是写文档，这是正常结果。

还有一类无论仓库多完备都只能写文档：约束 agent 会话内行为的规则，比如「别漏掉我口头说过的约束」「宣称完成必须附证据」。没有任何检查能看到会话里发生了什么。

## 关于那个独立复核的子代理

复盘时主 Agent 既是被复盘对象又是复盘者。所以只要环境支持，它会派一个只读子代理独立看一遍——先只给原始证据不给结论，让它自己找问题；再把结论发过去让它挑毛病。

但要知道这买到的是什么：**子代理能挡的只有自证偏差，挡不住两边共同的盲区。** 同模型、同脚手架的子代理不是独立样本。

所以**一致不算佐证**。子代理同意时置信度不上升——同模型、同证据得出同一结论是一次共模，不是两票。只有它带来新证据、替代解释或遗漏主题，才算增量。

如果你看到逐项复核全是「保留」、一条替代解释都没有，那通常说明证据包里混进了主 Agent 的结论。

## 发现别人 skill 的问题时会怎样

它**不会**直接去改那个 skill，哪怕源码就在手边。产出的是一份给维护者的**证据包**。

证据包里**只有证据，没有改法**。这不是省事：

你手上没有那个 skill 的全文，从这个位置想出的改法必然比维护者差。更要紧的是锚定——写了「建议改成 X」，维护者的复盘就从别人的结论开始，「找那条被反驳的假设」这一步被跳过了。而一个错误假设可能有五种表现，改法 X 通常只治一种。

证据包会先落盘，再按源仓位置决定去哪：

| 情况 | 落到哪 |
| --- | --- |
| 源仓就是当前仓库 | `<当前仓>/.learnings/skill-feedback/`，进 git，同事可见 |
| 源仓在别处，部署方配了投递且白名单里有它 | 提交到 issue 平台，本地标记已投递 |
| 源仓在别处，无配置 / 不在白名单 / 投递失败 | `~/.learnings/skill-feedback/`，只在你自己机器上 |

**它永远不会跨仓库写入。** 即使能解析出源仓路径，也只在报告里给你一条 `cp` 命令，由你自己执行。

**没有投递配置是正常状态，不是故障。** 报告会明说「未检测到投递配置，本次只落本地文件」，并提醒你用户级目录只在自己机器上、别人拿不到，仍需人工转交。

## 容易踩的坑

**「偏好」不等于「不用管」。** 你纠正它「报告写太长了」，看起来是个人口味。用这句话再问一遍：换个用户在同样场景下还会不会提同样的纠正？会，那就不是偏好，是 skill 的默认错了。

**「一次性上下文」和「偏好」不是终点。** 判成这两类只说明它不走五层地图，不说明到此为止——它们常常是 skill 缺陷或用法偏差的表象，还要再问一次「这是谁的问题」。

**别指望它做全仓审计。** 它只为核实承重事实去读项目，先搜索再缩小范围。想要全面体检，那是别的工具的事。

**移交对象只能是人或角色，不能是 skill。** 「移交 refine-skill」这句话本身就是错的——移交的从来不是一个工具，而是能改写它的那个人。

---

## 什么时候该换成 refine-skill

只有一种情况：**本次会话你就在开发或调试那个 skill，而且源码你能改。**

这时证据还在上下文里，直接在会话末尾接 `/refine-skill <skill-name>` 最划算。

注意那个限定。你在自己仓库里用 `research` skill 查资料，虽然 `research` 的源码就在手边，但这次会话你是在查资料、不是在开发它——这时仍然用 `session-optimize`，它会产出证据包。

```text
# 复盘这轮会话
/session-optimize

# 带关注点
/session-optimize
重点看这轮为什么返工，以及下次我该先提供什么背景。
```
