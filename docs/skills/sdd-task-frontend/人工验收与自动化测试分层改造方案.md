# sdd-task-frontend 人工验收与自动化测试分层改造方案

## 0. 文档定位

本文用于改造 `sdd-task-frontend` 及其上下游契约，使前端 Story 能在质量风险可控的前提下，把不适合自动化、或自动化投入明显高于收益的验收声明交给人工执行，同时避免以下错误：

- 把“不写自动化测试代码”误写成“不需要验收用例”。
- 用 `MANUAL` 代替声明状态，破坏 `PROVEN / UNVERIFIED / DEFERRED` 状态机。
- 把 CSS、真实浏览器或性能场景一概判成“不可自动化”。
- 为了省测试成本，把权限、写操作、状态机、共享能力等高风险行为下放给人工。
- 与仓库已有的还原契约 `visual` 层重复，给同一条视觉声明留下两条都合法的路径。
- 计划已经生成了人工项，但执行、账本和最终验收摘要无法消费。

本方案是前端开发侧的单仓验收分层，不替代测试侧的 L0/L1/L2 UAT/SIT，也不改变后端 Story 的默认 TDD 规则。

## 1. 改造目标与非目标

### 1.1 目标

1. 每条 `SC-`、`BR-`、§5 GWT 仍能追到一个或多个原子 AT，再追到具体 Task 和最终证据。
2. 把“验证范围”“验证方法”“声明状态”拆成正交字段。
3. 只有通过人工资格门禁的声明才允许不写自动化测试代码。
4. 确定性子行为优先使用仓库现有的最窄验证范围；主观或真实环境剩余风险交给人工。
5. 人工验收未执行时保持 `UNVERIFIED`；有合格人工证据后才进入 `PROVEN`。
6. 机械改动允许只使用编译、类型、lint 或构建证据，不强行生成行为测试或人工验收项。
7. `acceptance.md` 能明确列出待人工验收项，且存在待验收项时不能输出无条件“可验收”。
8. 对旧 Story 和旧格式保持向后兼容，避免一次性迁移历史账本。
9. 新增的人工通道不与仓库已有的还原契约 `visual` 层重叠，同一条视觉声明只有一条合法路径。
10. 计划侧的阻塞门不严于执行侧；能力缺口按登记降级处理，不在信息更少的阶段做更不可逆的决定。

### 1.2 非目标

- 不把人工验收写成新的独立交接文件；`tasks.md` 和 `alpha-tests.md` 仍是唯一计划与证据账本。
- 不让 Codex、自测试 agent 或 review agent 冒充实际人工验收者。
- 不因为仓库缺测试框架，就默认把本可自动化的逻辑降为人工。
- 不要求所有前端 Story 都同时覆盖 S1–S3、视觉和人工验收。
- 不在计划阶段固定具体测试命令、浏览器矩阵或全量回归范围。

## 2. 当前问题

### 2.1 现状把所有前端 AT 都写成 mock 集成级

准确的现状是：`sdd-task-frontend` Step 4 要求「按 `extraction_ref` 的规则把 `SC-`/`BR-`/GWT 提炼为 mock 集成级 AT」，`L3` 这个层号只出现在产物四节的节名里（「L3 单服务单接口集成测试记录（前端即 mock 集成级）」），而计划侧还要同时写 L4 节。改造时两处措辞都要动，不要只搜 `L3`。

当前链路中以下位置都带有这一默认：

- `sdd-task-frontend/SKILL.md` Step 4。
- `sdd-task/SKILL.md` 的前端验收提炼、计划写作纪律和执行交接。
- `acceptance-criteria-extraction.md` 的前端章节。
- `tdd-discipline.md` 的 Iron Law、完成门禁和六步任务形状。
- `alpha-tests.md` 通用模板。
- `test-framework-detection.md` 的探测失败即停止规则。

只修改 `sdd-task-frontend/SKILL.md` 会产生“生产者写 `manual_acceptance`、消费者仍强制 RED/GREEN”的断裂。

### 2.2 `test_level=manual` 混合了三个概念

现有提议把 `unit / e2e / manual` 放在同一个字段中，但它们分别属于：

- `S1_COMPONENT / S2_PAGE / S3_STORY`：验证覆盖到当前 Story 的哪一层。
- `test_case / quality_gate / manual_acceptance`：使用哪种验证方法取得证据。
- `PROVEN / UNVERIFIED / DEFERRED`：验收声明当前处于什么状态。

三个维度必须拆开，否则无法表达“同一个页面范围既可以写自动化用例，也可以进行人工体验验收”，也无法看出验证范围的宽窄。

原提议中的 `automated / human / static` 也不属于同一命名维度：`human` 描述执行主体，`static` 描述检查性质，`automated` 描述执行方式。本文统一改为验证工件或活动名，避免字段值交叉重叠。

### 2.3 `MANUAL` 不能作为状态

共享执行契约只有三个最终状态：

- `PROVEN`：已有覆盖声明、环境正确且仍新鲜的证据。
- `UNVERIFIED`：本阶段可做但未做、证据不足或能力不可用。
- `DEFERRED`：外部依赖未就绪，且有明确解除条件。

人工验收是一种验证方法，不是第四种状态。计划阶段生成的人工项仍应是 `UNVERIFIED`。

### 2.4 “不可自动化”的场景定义过宽

- CSS 动画的主观自然度适合人工，但触发状态、元素显隐、明确时长可以自动化。
- DOM 性能的主观卡顿感适合人工，但有量化阈值的性能 AC 应自动测量。
- “需要真实浏览器”不是人工理由；Playwright/Cypress 本身就在真实浏览器中运行。
- 跨页、鉴权、提交等流程风险较高，不应因为 E2E 成本高就默认转人工。
- 颜色、间距、字号、圆角等视觉数值在有外部基线时是机器可判的，不属于人类感知剩余项。

### 2.5 仓库已有一条人类判断通道，必须先对账

`sdd-dev-frontend` 的还原契约已经把视觉判断分成三层：`static` 与 `render` 由结构化采集机器判定，`visual` 层专门承接机器盲区，最终由人比对原型与实现两张图。`restore/run.md` 规定「visual YELLOW 默认落 `UNVERIFIED` 并写补验方式，不默认截图」，`restore/contract.md` 还专门记录了这条通道被滥用的教训：判据原先是散文里一句「……等机器盲区」，结尾那个「等」是敞口，任何判不了的规则都能自称盲区溜进 `visual` 层，以「等人看图」的名义无限期停在 YELLOW，因此后来把盲区从散文改成了枚举。

本方案的 `manual_acceptance` 与这条通道正面重叠。不划清分工，同一个视觉改动就有两条都合法的路径，而人工那条成本更低，分类会稳定偏向它，结果是绕过 R1–R6、冻结哈希与契约校验器——这是本方案唯一可能**削弱现有能力**的地方，其余问题最多是新功能不生效。分工规则见 §4.0。

### 2.6 当前最终摘要无法承接待人工动作

`manage_review_pipeline.py` 当前只聚合 suggestion、open question、deferred、norm_candidate 四类 handoff。待人工验收不是决策，也不是 Deferred；如果不扩展聚合输入，人工项只能留在验收账本深处，最终摘要可能错误地显示“可验收”。

扩展方式必须沿用仓库既有模式。该脚本的设计不变量是「`alpha-tests.md` 是权威登记（agent 写、脚本从不碰）」，`acceptance.md` 的渲染注释也写明「没有任何机器消费这份 Markdown」。而对完全同类的问题脚本已有解法：`--unplanned-carry` 的权威登记同样在 `alpha-tests.md`，传给聚合器的却是主 agent 做的 JSON 投影。人工项照这个模式走，见 §7.5。

## 3. 目标概念模型

### 3.1 四个核心对象

| 对象 | 定义 | 例子 |
| --- | --- | --- |
| 验收声明（AT） | 来自 SC-/BR-/GWT 的原子、可观察结果；AT 是验收声明或验收场景，不等同于自动化测试用例 | 点击保存后出现成功反馈 |
| 验证范围 | 在多大的 Story 内部范围取得证据 | `S1_COMPONENT` → `S2_PAGE` → `S3_STORY` |
| 验证方法 | 用什么工件或活动取得证据 | `test_case`、`restore_contract`、`quality_gate`、`manual_acceptance` |
| 声明状态 | 当前是否已被充分证明 | `PROVEN`、`UNVERIFIED`、`DEFERRED` |

四种方法与现有三种 Task 形态一一对齐：逻辑形态对 `test_case`，还原形态对 `restore_contract`，机械形态对 `quality_gate`，人工例外对 `manual_acceptance`。

- `test_case` 才会产生或执行自动化测试用例。
- `restore_contract` 执行冻结还原契约的规则，证据是契约的 RED/GREEN 报告而不是测试文件；它承接视觉声明，机器盲区剩余项落在契约的 `visual` 层，见 §4.0。
- `quality_gate` 表示类型、编译、lint、构建或引用检查，只用于没有行为分支、因此不创建 AT 的机械 Task。
- `manual_acceptance` 仍然必须有 GWT、预期结果和追溯关系。

把冻结契约显式命名，是为了让「视觉声明该走哪条路」有确定答案，而不是靠一条散在文档里的例外规则去压制 `manual_acceptance`。

### 3.2 建议字段

每条行为或体验 AT 至少包含：

| 字段 | 允许值 / 写法 | 说明 |
| --- | --- | --- |
| `id` | `AT-{story_id}-NNN` | 单 Story 单 app 内唯一 |
| `trace` | `SC-*`、`BR-*`、GWT | 向上追溯 |
| `verification_scope` | `S1_COMPONENT` / `S2_PAGE` / `S3_STORY` | 数字越大范围越宽；所有值都限制在当前 Story；机械 Task 不写该字段 |
| `verification_method` | `test_case` / `restore_contract` / `manual_acceptance` | 行为或体验 AT 只取一个值；已进入冻结契约的视觉声明写 `restore_contract`，见 §4.0；`quality_gate` 只写在不创建 AT 的机械 Task 上 |
| `manual_basis` | 见 §4.4；非 `manual_acceptance` 留空 | 人工例外必须有标准依据 |
| `risk_triggers` | 现有风险 token 子集 | 供 Dev 与最终 diff 合并 |
| `required_environment` | 路由、设备、浏览器、账号或第三方前置 | `manual_acceptance` 必填；只写真正影响判定的环境 |
| `required_evidence` | 截图、视频、审批记录、操作记录等 | `manual_acceptance` 必填；不能只写“人工看一下” |
| `manual_outcome` | `NOT_RUN` / `PASSED` / `FAILED` | 仅人工验收使用；计划初始统一为 `NOT_RUN` |
| `claim_status` | `PROVEN` / `UNVERIFIED` / `DEFERRED` | 计划初始统一为 `UNVERIFIED`；它不是测试结果 |
| `evidence_refs` | 证据 ID、路径或签字记录 | 初始为空，执行阶段回填 |
| `manual_checked_by` | 实际执行人工验收的人员标识 | 仅在人工实际执行后回填，不是计划阶段负责人；审批记录 ID 写入 `evidence_refs` |
| `manual_checked_at` | 人工验收的实际执行时间，带时区 | 仅在人工实际执行后回填 |

本节字段名与枚举值是 v2 的权威词汇。Markdown 可以显示中文列名，但聚合器内存结构和派生 JSON 必须投影回这些名称；除迁移规则外，不再新增 `level`、`test_level`、`evidence_method`，也不使用裸 `status` 或裸 `result` 作为字段名。

范围定义：

| 范围 | 边界 | 典型对象 |
| --- | --- | --- |
| `S1_COMPONENT` | 一个组件或组件切片，外部接口可 mock | 组件交互、三态、请求参数、条件渲染 |
| `S2_PAGE` | 一个完整页面及其页面内协作 | 页面布局、溢出、页面状态、页面级交互 |
| `S3_STORY` | 当前 Story 涉及的完整用户路径 | Story 内跨页面、跨路由、鉴权、提交链路和真实接缝 |

每条 AT 选择能够覆盖声明的最小范围；更高范围表示覆盖当前 Story 的更多协作边界、更慢、更接近真实运行时，不表示质量天然更高。视觉或行为由声明、`risk_triggers` 和下游验证模块表达，不再占用范围枚举，也不扩展到其他 Story。

`S1_COMPONENT` 与 `S2_PAGE` 边界重叠时用一条 tie-break：**能在单组件挂载下观察到的声明写 `S1_COMPONENT`，必须整页渲染才能观察的才写 `S2_PAGE`。** 单条 AT 上不允许写 `S1_COMPONENT/S2_PAGE` 这种二选一，否则同类改动会落到不同范围，§9.2 的指标不可比。

删除 `MODULE` 层：module 是代码组织边界，不是验收观察边界；同一个 hook、store、selector 或 formatter 可能服务一个组件、一个页面或整个 Story，无法稳定排在 component 上面或下面。此类代码仍可使用最窄的自动化测试实现，但其证据回挂到实际证明的 `S1_COMPONENT`、`S2_PAGE` 或 `S3_STORY` AT。完全没有 UI 观察边界的前端 SDK、工具库 Story 不适用这组三层，继续走通用任务契约，不能为兼容它们再造第四层。

计划阶段不分配验收人，也不建组织角色模型。`manual_checked_by` 只记录一个实际执行人工验收的人员标识，并且只在人工实际执行或结果回填时出现，不设计多人会签；审批记录 ID 属于 `evidence_refs`。待人工项由 `acceptance.md` 统一列出，交付团队按自己的流程认领。

没有行为分支的机械 Task 不新增 AT，只声明 `verification_method=quality_gate`、`required_evidence` 和“不需要行为证据”的原因，并省略 `verification_scope`。需求锚点仍必须由该 Story 中真正承载用户行为的 AT 覆盖，不能用机械 Task 代替需求验收。

### 3.3 不设置 `hybrid` AT

混合场景拆成多个原子 AT：

- `AT-001`：点击后打开弹窗、请求参数正确，`S1_COMPONENT + test_case`。
- `AT-002`：弹窗视觉层级和动画自然，`S1_COMPONENT + manual_acceptance`。

同一 AC 可以映射到多条 AT。这样每条声明只有一种完成判据，失效时也只影响相应证据。

### 3.4 建议增加 schema 版本

在 TaskPacket 增加：

```text
verification_schema=v2
```

读取不到该字段的旧 Story 按 v1 原语义处理，不强行映射到三层范围，也不得自动推断为 `manual_acceptance`；只有新增或修改 AT 时才按其可观察验收边界重新分类。

`verification_schema` 只描述 TaskPacket 与验收账本的字段代数，与 `manage_review_pipeline.py` 里的 `SCHEMA_VERSION` 是两个互不联动的版本号，不要因为名字像就一起动。后者约束的是角色回传 result 的结构，脚本会拒收版本不匹配的 result；人工项进入 `review-results.json` 不升 `SCHEMA_VERSION`。

## 4. 测试用例、人工验收与质量门的判定规则

### 4.0 与冻结还原契约的分工

`manual_acceptance` 不得与还原契约的 `visual` 层争夺同一条声明。优先规则只有一条：

**声明涉及的区块已进入冻结还原契约时，该视觉声明写 `verification_method=restore_contract`；机器盲区剩余项由契约的 `visual` 层承接并落 YELLOW，不新建 `manual_acceptance` AT。**

因此 `manual_basis=visual_judgment` 与 `motion_judgment` 只允许用于没有冻结契约覆盖的声明——典型是 `baseline_source=text_spec` 或 `none` 的 Story，以及冻结区块之外的新增区块。有原型或参照页基线时，颜色是 `static_check` 的 token 针、间距是 R3 的 `numeric` + `tolerance` 规则，都由比对器判定，把它们转人工等于丢掉既有覆盖，也正是 §2.4 反对的那类过宽判断。

`device_dependency`、`external_dependency`、`content_approval` 与 `automation_cost_exception` 不受本条限制：它们描述的是环境与语义，不是视觉盲区，与还原契约不同轴，可以和 `restore_contract` 声明在同一 Story 内共存。

### 4.1 判定顺序

对每条需求锚点按以下顺序处理：

1. 拆成原子可观察声明；一个 AT 只验证一个行为点。
2. 判断是否没有行为分支；若是，把它作为机械 Task，设置 `verification_method=quality_gate` 并省略 `verification_scope`，不新增行为 AT。
3. 若是视觉声明且所在区块已进入冻结还原契约，按 §4.0 写 `restore_contract`，到此为止。
4. 检查自动化强制触发器；命中任一项，必须使用 `test_case`，人工验收只能补充。
5. 检查人工资格门禁；全部满足才允许 `verification_method=manual_acceptance`。
6. 其余声明使用仓库已有的最窄验证范围，并以 `test_case` 取得证据。
7. 把判定理由、环境、证据要求和初始状态写入验收账本。

伪代码：

```text
if no_behavior_branch:
  verification_method = quality_gate
  verification_scope = omitted
elif is_visual_claim and block_in_frozen_restore_contract:
  verification_method = restore_contract   # 盲区剩余项归契约 visual 层 YELLOW
  verification_scope = narrowest_applicable_scope
elif hits_automation_mandatory_trigger:
  verification_method = test_case
  verification_scope = narrowest_applicable_scope
elif satisfies_all_manual_acceptance_gates:
  verification_method = manual_acceptance
  verification_scope = narrowest_applicable_scope
else:
  verification_method = test_case
  verification_scope = narrowest_applicable_scope
```

第 3 步放在自动化强制触发器之前，是因为它不放宽任何东西——它把声明推向更强的机器判定。同一区块若还带 `shared-boundary` 等行为风险，按 §3.3 拆成独立 AT 各走各的方法，不要把两件事压在一条声明上。

### 4.2 自动化强制触发器

命中任一项时，`manual_acceptance` 只能补充，不能替代 `test_case`：

- 金额、折扣、日期、排序、格式化、校验和其他确定性计算。
- 等价类、边界值、决策表、状态迁移或多分支错误处理。
- `auth`：权限、身份、租户、越权和鉴权失败。
- `write`：提交、删除、支付、服务端写入或不可逆副作用。
- `async-state`：竞态、取消、重试、轮询、幂等和多阶段异步状态。
- `shared-boundary`：公共组件、公共样式、全局状态、请求封装或共享类型。
- 缺陷修复和已有事故的回归场景。
- 高频核心路径或需要持续回归的跨页流程。
- 明确量化的性能、无障碍、安全或兼容性指标。
- 依赖闭包不明、回归半径不明或 `unknown-deps`。
- 自动化已有稳定入口，新增断言成本低且能稳定复跑。

### 4.3 人工资格门禁

只有同时满足以下条件，才允许 `verification_method=manual_acceptance`：

1. 期望结果包含机器无法稳定判断的人类感知、语义判断，或依赖无法稳定自动构造的真实设备/外部环境。
2. 可机器判定的确定性子行为已经拆出并由 `test_case` 覆盖；没有行为分支的机械检查由 `quality_gate` 覆盖；或明确证明不存在这两类子项。
3. 未命中 §4.2 的自动化强制触发器。
4. 变更范围孤立、容易观察、容易回滚，不修改共享边界。
5. 自动化建设和维护成本明显高于该场景的重复验证收益；不能只写“赶时间”。
6. 已明确验收环境、GWT、证据要求和未通过时的处理入口；`manual_checked_by` 只在实际验收后记录。

任一条件不满足，回到 `test_case`；拿不准时也使用 `test_case`，不静默放宽。

### 4.4 `manual_basis` 枚举

建议只允许以下值，避免自由文本把例外无限扩大：

| 值 | 中文名称 | 适用条件 |
| --- | --- | --- |
| `visual_judgment` | 视觉判断 | 视觉层级、品牌感、留白、字体观感等主观判断；**仅限该区块未进入冻结还原契约**，见 §4.0 |
| `motion_judgment` | 动效体验判断 | 动画自然度、眩晕感、体感流畅度；**仅限该区块未进入冻结还原契约**，见 §4.0 |
| `device_dependency` | 真机或系统能力依赖 | 触摸、软键盘、系统权限、摄像头、打印等真机或系统能力 |
| `external_dependency` | 外部环境依赖 | SSO、浏览器扩展、外部嵌入页等不可稳定构造的真实接缝 |
| `content_approval` | 内容确认 | 文案、运营、法务、业务含义和品牌语气确认 |
| `automation_cost_exception` | 自动化成本例外 | 极低风险、孤立、一次性、可回滚，且自动化成本明显失衡；必须满足全部人工门禁 |

不要设置 `real-browser`、`css` 或 `performance` 这类过宽理由。

`automation_cost_exception` 是本组枚举里唯一自认定的口子：它的判据是成本比较，而写计划的一侧没有外部事实可以反驳自己。本方案不假装能用文字消除它，只要求每次使用都写明被放弃的具体自动化入口和预估维护成本，并接受它由 §9.2 的误分类计数事后收紧。

### 4.5 场景矩阵

| 场景 | 建议结果 | 说明 |
| --- | --- | --- |
| 纯类型、import、引用对齐 | `quality_gate`，省略 `verification_scope` | 编译、类型或构建证据足够，不需要 AT 或人工验收 |
| 组件点击、输入、三态和请求参数 | `S1_COMPONENT + test_case` | 确定性强、复跑价值高 |
| 跨页普通导航 | `S3_STORY + test_case` | 属于当前 Story 的完整路径；优先现有浏览器框架 |
| 鉴权、租户、提交、删除 | `test_case`，必要时再加人工验收 AT | 人工验收不能替代自动化用例 |
| CSS 静态结构、溢出、遮挡 | `test_case`，范围按 §3.2 tie-break 定 | 机器能判断的部分先机器化 |
| 视觉层级、品牌感、动画自然度，区块**已进入**冻结契约 | `restore_contract` | 机器盲区由契约 `visual` 层落 YELLOW，不新建人工 AT |
| 视觉层级、品牌感、动画自然度，**无**冻结契约 | `manual_acceptance` | 范围按 tie-break 定，并写人工验收卡 |
| 真实软键盘、触摸手势、系统权限 | 本地规则 `test_case` + 接缝 `manual_acceptance` | 拆成两条 AT |
| 第三方 SSO 真实账号联调 | adapter/error mapping `test_case` + 接缝 `manual_acceptance` | 高风险主逻辑不能只靠人工 |
| “滚动是否舒服” | `S2_PAGE + manual_acceptance` | 页面范围内的感知性能 |
| “1000 行下交互小于 100ms” | `test_case` | 量化阈值不能转人工 |
| 一次性低风险文案或孤立样式 | `manual_acceptance` | 范围按 tie-break 定；只有全部门禁通过才允许仅人工验收 |
| 缺陷修复 | `test_case` | 必须留下回归保护 |

## 5. 声明生命周期

### 5.1 计划阶段

- 所有 AT 的 `claim_status` 初始为 `UNVERIFIED`。
- `manual_acceptance` AT 写完整人工验收卡，`manual_outcome` 初始为 `NOT_RUN`，不生成测试文件行。
- `test_case` AT 指向建议验证范围和测试文件。
- `restore_contract` AT 指向冻结契约的 R 行，不新增测试文件，也不写人工验收卡。
- 机械 Task 使用 `verification_method=quality_gate` 并写明 `required_evidence`，不新增 AT。
- 所有 SC-/BR-/GWT 必须被至少一条 AT 覆盖；人工不是覆盖豁免。

### 5.2 实现阶段

- `test_case`：按既有最窄验证范围取得 RED/GREEN。
- `restore_contract`：沿用现有还原轮，对冻结契约取 RED 再复跑转绿；`visual` 层 YELLOW 落 `UNVERIFIED` 并写补验方式，不改写为 GREEN。
- `quality_gate`：执行编译、类型、lint、引用或构建检查；不人为制造行为测试。
- `manual_acceptance`：实现候选产品代码，不由 agent 冒充人工签字；将 `claim_status` 保持 `UNVERIFIED` 并登记验收入口。
- 若人工验收 Task 中出现可确定断言或新的高风险触发器，立即重分类为 `test_case` 或拆 AT。

### 5.3 候选验收阶段

- 把同页面、同设备、同账号边界的人工项合并为最短人工操作序列，减少重复往返。
- `acceptance.md` 显示“待人工验收”，列出环境、操作、预期和证据要求，不在计划侧分派人员。
- 存在待人工项时，最终结论只能是“实现完成，待 N 项人工验收”或“部分验收”，不能是无条件“可验收”。

### 5.4 人工结果回填

| `manual_outcome` | `claim_status` | 处理 |
| --- | --- | --- |
| `PASSED` 且证据完整 | `PROVEN` | 回填 `manual_checked_by`、`manual_checked_at`、环境、`evidence_refs` 和相关依赖 |
| `PASSED` 但证据不足 | `UNVERIFIED` | 保留实际人工判断，登记缺失证据；补齐前不能标 `PROVEN` |
| `FAILED` | `UNVERIFIED` | 登记确证阻断，回到修复流程；不能标 `PROVEN` |
| `NOT_RUN` | `UNVERIFIED` | 写补验方式 |
| `NOT_RUN` 且外部依赖未就绪 | `DEFERRED` | 必须写解除条件与恢复入口；不另造 `BLOCKED` 人工结果 |

用户的口头“可以了”只有在能绑定到具体 AT、环境和验收时间时才能成为人工证据；泛泛确认不能批量把所有声明改成 `PROVEN`。

`manual_outcome` 与还原、检视流水线的三色是两套词汇，对账规则只有两条：`FAILED` 与 RED 同级，受硬门禁「三色真实」约束，不得改写为 `PASSED`；还原契约 `visual` 层的 YELLOW 在人工维度上等价于 `NOT_RUN + UNVERIFIED`，而按 §4.0 它本就不该出现在人工表里，若因历史 Story 出现，按 `NOT_RUN + UNVERIFIED` 登记补验方式，不新造第四种人工结果。

必须承认一处无法用规则消除的残余风险：`PROVEN` 要求的 `manual_checked_by`、`manual_checked_at`、`required_environment` 和 `evidence_refs` 四项全部由 agent 写入同一份账本，与命令类证据不同，人工验收没有可复算的外部产物，所以「agent 不代签」在本阶段是纪律而非门禁。要把它变成门禁，唯一可行的加固是要求 `evidence_refs` 至少有一条指向聚合器能实际读到的文件（截图或录屏路径），建议放到 §10 Phase 4 再评估，不在首轮引入。

## 6. 产物结构调整

### 6.1 TaskPacket

建议增加或调整：

```text
verification_schema=v2
component_test_status=<available | absent | unknown>
component_test_framework=<仅 component_test_status=available 时填写框架名>
browser_test_status=<available | absent | unknown>
browser_test_framework=<仅 browser_test_status=available 时填写框架名>
```

`*_test_status` 只描述能力探测结论，`*_test_framework` 只描述框架身份；不得再把状态值伪装成框架名。仓库现状的失败取值是 `test_framework=未识别`，迁移见 §8.2。

缺通道时的处置与执行侧对齐，不在计划侧新设更硬的门：某条 `test_case` AT 的 `verification_scope` 没有对应自动化通道时，默认登记降级理由、把该声明保持 `UNVERIFIED` 并继续出计划。这与 Dev 侧「浏览器能力不可用则模块记未执行、依赖声明保持 `UNVERIFIED`」是同一处置。**只有该声明同时命中 §4.2 的自动化强制触发器时才 Stop 回流。**

这一条是有意放宽现状的。按原提议，只装了组件测试框架而没有 Playwright/Cypress 的仓库（相当常见），任何带跨页导航的 Story 都会因为 `S3_STORY + test_case` 找不到通道而停在计划阶段——而现状下前端一律 mock 集成级，一个框架就能出计划。计划阶段掌握的事实比执行阶段少，不应做更不可逆的决定。放宽的只是「有通道缺口就停」，「探测失败即 Stop」和「不得默认 Jest/Vitest」两条保留。

### 6.2 `alpha-tests.md`

建议保留现有账本，不新增第三份文件。路径名 `alpha-tests.md` 为兼容性名称；文档正文、Skill 指令和交接输出统一称它为“验收账本”，避免让人误以为其中只有自动化测试。最小结构：

```markdown
# <Story> · 验收账本

## S1 组件验证记录
## S2 页面验证记录
## S3 Story 验证记录

## 人工验收记录
| AT | 追溯 | 声明 | 验证范围 | 人工依据 | 环境 | GWT | 所需证据 | 人工结果 | 声明状态 | 人工验收人 | 验收时间 | 证据引用 | 解除条件 | 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

## 还原证据记录
## 计划外承接

## AC ↔ 证据映射
| AC / AT | 声明 | 验证范围 | 验证方法 | 声明状态 | 证据引用 | 新鲜度 | 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## Deferred AC
```

计划初始行固定写 `人工结果=NOT_RUN`、`声明状态=UNVERIFIED`，人工验收人、验收时间、证据引用写“未执行”，解除条件写“不适用”。外部依赖未就绪时保持 `人工结果=NOT_RUN`、把声明状态改为 `DEFERRED`，并将真实解除条件写回本行；`Deferred AC` 只引用该人工行，不复制解除条件正文。

**这张表只给人读。** 聚合器不解析它，机器消费的是主 agent 从同一批事实做的 JSON 投影（§7.5），所以本节不要求列名可被正则解析，也不因表头措辞变化而失败。这一点是刻意设计：两份产物的落盘 schema 由上游 `schema_alpha_tests` 拥有，本 skill 无权固定表头，若把聚合器建成「表头漂移即硬失败」，外部 schema 一次调整就会打断整条流水线。

如果内网 schema 强制只能保留四节，可把“人工验收记录”作为“AC ↔ 证据映射”的子节，但不能塞进 L3/L4 或 Deferred。

### 6.3 `tasks.md` 的人工逻辑 Task

仍保留逻辑、还原、机械三种形态，不新增第四种 Task 形态；逻辑 Task 根据 AT 的验证方法选择步骤分支。

建议模板：

```markdown
### Task N: <名称> [用例: AT-...]

**形态:** 逻辑
**验证方法:** manual_acceptance
**人工依据:** <manual_basis>
**受影响声明:** <AC / AT>

**Files:**
- Modify: `<产品文件>` — <实现什么>

- [ ] **Step 1: 实现人工验收候选** — 在上述文件范围内达成可观察声明；不新增自动化测试文件
- [ ] **Step 2: 通过质量门** — 让受影响范围的编译、类型、lint 或构建保持通过
- [ ] **Step 3: 登记待人工验收并提交** — 回填人工验收卡，`manual_outcome=NOT_RUN`、`claim_status=UNVERIFIED`，沿用提交规范
```

这里“不新增自动化测试文件”只能出现在已经通过人工资格门禁的 Task 中。普通逻辑 Task 继续使用现有 RED/GREEN 形状。

### 7.5 聚合器和自动校验

#### `skills/sdd-dev-frontend/scripts/manage_review_pipeline.py`

建议为 `aggregate` 增加一个与 `--unplanned-carry` 完全同构的参数：

```text
--manual-acceptance <JSON array>
```

**不让脚本解析 Markdown。** 该脚本的设计不变量是「`alpha-tests.md` 是权威登记（agent 写、脚本从不碰）」，`acceptance.md` 的渲染注释也写明「没有任何机器消费这份 Markdown」。而对完全同类的问题脚本已有既成解法：`--unplanned-carry` 的权威登记同样在 `alpha-tests.md`，传入的却是主 agent 做的 JSON 投影。人工项照此办理，好处有三个：不新增 Markdown 解析器、不受上游 `schema_alpha_tests` 调整表头的影响、缺省行为与现有参数一致。

数组每项字段用 §3.2 的权威名：`id`、`trace`、`verification_scope`、`manual_basis`、`required_environment`、`required_evidence`、`manual_outcome`、`claim_status`、`manual_checked_by`、`manual_checked_at`、`evidence_refs`、`resume_condition`。

写入者与读取者固定如下：

- `sdd-task-frontend` 在验收账本创建人工验收行并写初始 `NOT_RUN + UNVERIFIED`。
- `sdd-dev-frontend` 主 agent 在收到真实人工结果后更新同一行，并在调用聚合器时按该行做投影。
- `manage_review_pipeline.py` 只校验投影、渲染 `review-results.json` 与 `acceptance.md`，既不读也不回写 `alpha-tests.md`。

省略该参数时按零人工项处理，与 `--unplanned-carry` 的缺省行为一致，v1 Story 因此天然兼容，不需要「无人工节」这类特判。投影中出现 `manual_acceptance` 项但字段不完整时聚合失败，不静默忽略。事实源仍只有 `alpha-tests.md`；投影是调用参数，不落盘。

聚合规则：

- `manual_outcome` 只允许 `NOT_RUN / PASSED / FAILED`；`claim_status` 只允许 `PROVEN / UNVERIFIED / DEFERRED`，两者不得互相代替。
- 结果与声明状态只允许以下配对：`PASSED + PROVEN`、`PASSED + UNVERIFIED`、`FAILED + UNVERIFIED`、`NOT_RUN + UNVERIFIED`；只有外部依赖未就绪时允许 `NOT_RUN + DEFERRED`。
- `PROVEN` 必须有 `manual_checked_by`、`manual_checked_at`、`required_environment` 和至少一个 `evidence_refs` 条目。
- `NOT_RUN + UNVERIFIED` 进入 handoff，类型为 `manual_acceptance`，属于“需要你处理”的动作，不是 decision。
- `PASSED + UNVERIFIED` 进入证据补齐 handoff；聚合器不得丢失已有人工判断，也不得提前渲染为已证明。
- `FAILED + UNVERIFIED` 形成确证 blocker；失败证据不得被解释成已验证通过。
- `NOT_RUN + DEFERRED` 必须有 `resume_condition`，并同时进入暂缓节。
- 待人工项非空时，摘要不得渲染无条件“可验收”。
- `--decisions` 不能把人工声明改成 `PROVEN`；决定与证据保持分离。
- 人工投影只存在于调用参数和派生的 `review-results.json`；事实源仍只有 `alpha-tests.md`。
- `DISPLAY` 词表补 `manual_acceptance`、`NOT_RUN`、`PASSED`、`FAILED` 的中文词条，并把 `manual_outcome` 加入 `TRANSLATED_KEYS`；否则 `acceptance.md` 里会印生枚举值，与现有 `test_rendered_report_has_no_raw_enum_values` 的意图不符。

全仓只有 6 个产品文件、7 个引用点，改名主体是机械替换：

| --- | --- | --- |

| `sdd-dev-frontend/scripts/manage_review_pipeline.py` | 992 | `DISPLAY` 词表的 key |

技术上是安全的，`story` 这个常见词不会污染自由文本：`display()` 是精确查表而非子串替换，且翻译只作用于 `TRANSLATED_KEYS` 白名单（`result` / `kind` / `level` / `trigger` / `needs_decision` / `status` / `role`），验证模块名不在其中。`test_display_vocabulary_is_complete` 的期望集合也不包含验证模块，换 key 名不会让它变红；词条值「用户路径」原样保留。

其余四处本来就是带反引号的模块并列，直接替换即可。全仓约定：模块 key 一律小写加反引号写作 `story`，需求单元一律写「Story」且不加反引号，TaskPacket 字段仍写 `story=`。

### 8.3 推荐发布顺序

0. 先单独发布双通道框架探测：`component_test_status/framework` 与 `browser_test_status/framework` 分字段。它不依赖人工验收的任何概念，修的是现状确实存在的字段污染（把状态值写进框架名、单字段区分不了组件与浏览器框架、Cypress 可能被当成组件主框架），收益确定、风险最低，还能为后续的范围分层提供可靠的能力事实。
1. 再发布共享契约和下游兼容读取：Dev 能同时读 v1/v2，并落地 §4.0 的还原契约分工与 §7.6 的模块改名。
2. 然后扩展聚合器和模板，确保 v2 人工项有去处。
3. 接着修改 `sdd-task-frontend` 和提炼规则，让生产者开始写 v2。
4. 最后开启严格校验：拒绝 `MANUAL` 状态、缺字段人工验收 AT、高风险仅人工验收，以及已冻结区块的视觉声明被写成 `manual_acceptance`。
5. 观察一个试点周期后，再决定是否移除 v1 默认；不建议首轮删除。

回滚时只需让计划生产者停止写 v2；兼容消费者可以保留，不必回滚历史工件。

### 9.2 试点观测指标

先记录现状基线，再比较：

- 每 Story 新增自动化测试文件数和维护耗时。
- `manual_acceptance` AT 数量、占全部 AT 比例和逾期未验收数。
- 因人工分类不当而被执行阶段升级为 `test_case` 的数量。
- 缺陷回流率、相同问题复发率和共享边界回归数。
- 最终交付时 `UNVERIFIED` / `DEFERRED` 数量。
- 人工验收一次通过率与平均等待时间。

如果自动化数量下降但 `UNVERIFIED` 长期堆积、缺陷复发或高风险声明频繁被误分，说明省下的是执行成本而不是总成本，应收紧人工门禁。

## 12. 建议的决策结论

建议批准以下原则作为本次改造基线：

1. 保留每条需求锚点的验收用例和追溯，不批准“完全无验收声明”的功能改动。
2. 批准 `S1_COMPONENT / S2_PAGE / S3_STORY` 三层验收范围；module 保留为测试实现细节，不进入范围枚举。
3. 批准 `test_case / restore_contract / quality_gate / manual_acceptance` 四种验证方法，与逻辑、还原、机械三种 Task 形态加人工例外一一对齐；`quality_gate` 只用于不创建行为 AT 的机械 Task。
4. 批准人工例外，但仅限通过资格门禁的原子声明。
5. 不批准 `MANUAL` 状态；人工待验收统一为 `UNVERIFIED`。
6. 不批准用“CSS、性能、真实浏览器”作为宽泛人工理由。
7. 批准机械改动不写行为测试，也不要求人工功能验收。
8. 按“双通道探测 → 兼容消费者 → 聚合器 → 生产者 → 严格校验”的顺序发布，双通道框架探测单独先发。
9. 批准把冻结还原契约显式命名为 `restore_contract`，并规定已冻结区块的视觉剩余项继续走契约 `visual` 层，不转人工。
10. 不批准让聚合器解析 Markdown；人工项按 `--unplanned-carry` 的既成模式走 JSON 投影。
11. 不批准在计划侧新设比执行侧更硬的缺通道门；只有命中自动化强制触发器时才 Stop。
12. 批准把模块 `journey` 改名为 `story`，同时要求触发条件补「验证组合含 `story` 模块」量词，并保持 `story` 模块与 `S3_STORY` 范围分属两轴。
13. 接受两处无法用规则消除的残余风险：`automation_cost_exception` 的自认定性质，以及人工签字不可技术强制；两者靠 §9.2 指标观测，不在首轮加门。
