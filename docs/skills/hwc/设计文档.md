## 要解决的问题

输入是一句话功能描述（简单或具体皆可），输出是一份**可直接嵌入公共头尾发布**的华为云风格页面主体（[Q-3](#已决问题) 定：头尾是公共的，不由本 skill 生成），且：

| 要求 | 难点 |
| --- | --- |
| 符合现有设计规则（字色、字号、间距、组件形态） | 合法值有几百个，但不能随便组合 |
| 从设计令牌看，值要遵循组合原则 | 「原则」必须可判真假，否则无法验收 |
| 简单意图要能补全成完整组件方案 | 补什么、问什么必须有依据，不能开放式追问 |
| 拆分 PC / 移动 / 多分辨率 | 现有流水线明令禁止发明响应式规格 |

核心矛盾是最后两条：**要生成一份别人没给你的规格，同时不能是编的**。这份设计文档的全部机制都围绕这一条。

## 勘察结论：这套设计系统是可确定性提取的

这是整个方案能否成立的前提。逐条实测结果：

### 令牌是三层引用结构，不是一张平表

`https://portal.hc-cdn.com/cnpm-baseui/3.0.18/theme-token.css`，446 KB，**777 条 `--por-*` 定义**。

```css
--por-button-size-height-large: var(--por-base-size-48);
--por-font-line-height-22:      var(--por-base-size-22);
```

| 层 | 前缀 | 条数 | 职责 |
| --- | --- | --- | --- |
| 基础标尺 | `--por-base-*` | 133 | 唯一的数值来源，其余层不得写字面量 |
| 语义层 | `--por-color-*`、`--por-font-*`、`--por-radius-*`、`--por-shadow-*`、`--por-border-*` | 137 | 把标尺映射成有语义的角色 |
| 组件层 | `--por-button-*`、`--por-input-*`、`--por-tab-*` 等 21 族 | 507 | 每个组件消费语义层 |

**这就是「值不是随机组合」的物理形态**：字号不是从 777 个值里挑一个，而是选组件令牌 → 解析到语义层 → 落到 `--por-base-size-*` 的某一档。因此合规性**机器可判**——这是本方案区别于「让 AI 照着截图写页面」的根本点。

### 但营销页消费的是第二套令牌体系

**这条是 2026-08-24 补勘的，它限定了上一段的适用范围。** 上面那套三层结构属于 baseui；而 v1 目标页型（营销页）的区块来自 PEP 组件，PEP 自带一套独立令牌，定义在各组件 CSS 的 `:root` 里：

| 族 | 性质 | 实测样例 |
| --- | --- | --- |
| `--primitive-*` | 原色板，**直接写十六进制字面量** | `--primitive-gray-50: #f9fafb`、`--primitive-red-50: rgba(228, 30, 43, .05)` |
| `--text-*`、`--bg-*`、`--card-*`、`--btn-*`、`--grid-*`、`--container-*` | 语义层，引用 primitive | `--text-primary: var(--primitive-gray-900)` |

每个 PEP 组件 CSS 有 **42–44 条非 `--por-*` 定义**，且其自身引用中有 **13–20 条**指向这套体系而非 `--por-*`。

两条直接后果：**① `tokens.json` 必须收两套体系并标出各自适用域**，问句仍是「有哪些合法值」，所以不开新文件，加一列「体系」；**② G1 的「无字面量」判据必须给 primitive 层开例外**——`--primitive-gray-50: #f9fafb` 是上游的正确写法，天真实现会把它判成 RED。

### 上游本身不干净，基线必须如实反映

两处实测缺陷，直接决定门禁 G1 不能天真实现：

| 缺陷 | 实测 | 后果 |
| --- | --- | --- |
| **悬空引用** | 37 个令牌被 `var()` 引用但全文无定义，如 `--por-input-radius`、`--por-color-function-success`、`--por-base-size-66` | 「引用了一个 `--por-*` 名字」不等于「合规」。G1 必须校验**可解析性**，否则拼错名字反而能过门禁 |
| **命名分裂** | `--por-datePicker-*`（1 条，驼峰）与 `--por-datepickerr-*`（21 条，全小写且多一个 `r`）并存 | 基线不能做「规范化」清洗，否则生成物引用的名字在真实 CSS 里不存在 |

结论：**基线是事实的副本，不是事实的改良版。** 上游的错别字和不一致必须原样镜像，但要显式登记为已知缺陷，让下游知道这些不是自己抄错了。

### 类名语法可枚举

来自 `demo/button/index.html` 实测：

```html
class="por-btn por-btn-primary por-btn-large por-btn-md-middle por-btn-xs-small"
```

拆开就是一条可解析的文法：

```
por-<组件>                      基类，必填
por-<组件>-<变体>               primary | secondary | primary-light | light | dark | danger，槽位唯一
por-<组件>-<尺寸>               small | middle | large | block，槽位唯一
por-<组件>-<断点>-<尺寸>        断点级覆盖，xs | sm | md | lg
```

最后一行是关键：**响应式差异被编码进类名，而不是让使用者自己写媒体查询**。这条决定了 `hwc-page` 生成响应式的正确姿势。

### 断点阶梯存在，但有两套且不一致

| 来源 | 阶梯 | 实测出处 |
| --- | --- | --- |
| baseui 栅格 | 768 / 1024 / 1280 / 1600 | `demo/grid/index.html` 的 `por-col-{sm,md,lg}-*` |
| PEP 营销区块 | 599 / 839 / 1024 / 1280 / 1600 | 5 个独立版本组件 CSS 的 `@media` 并集；**严格交集只有 839 / 1280 / 1600**，且存在 840 / 859 / 768 / 1920 噪声档，详见[勘察补正](#勘察补正2026-08-24) |

**两套阶梯必须在基线里显式登记为冲突，不能悄悄选一个。** 已按 [Q-1](#已决问题) 选定 PEP 那套为营销页主阶梯。

### 响应式的表达法是「双份 DOM + 显隐」，不是媒体查询改样式

来自线上页面 SSR 输出：

```html
<div class="banner-item__subtitle hidden--mobile">…</div>
<div class="banner-item__subtitle hidden--web">…</div>
<div class="banner-item__content banner-item__content--70--web banner-item__content--100--mobile">
```

同一副标题在 DOM 里渲染两份，靠 `hidden--mobile` / `hidden--web` 切换。这类约定**不看源码绝对猜不到**，也正是「生成物看起来像但其实不合规」的高发区。

### 交互行为是现成产物，不需要重写

`theme-token.js`（121 KB）不是令牌数据，是 **webpack 打包的 baseui 运行时**：select / datePicker / modal / carousel 的行为逻辑、浮层 12 方位定位、10 种语言包。

因此「可直接发布」所要求的真实交互（而非占位）**由上游提供**，`hwc-page` 的职责是正确接线，不是重新实现。

### 组件目录完整且带规范标记

`demo/componentsList/` 下 30 个组件：`anchor breadcrumb button card carousel checkbox collapse color countDown datePicker fixed-table floor grid icon img-viewer input label level link modal pagination player price rate scrollbar select service-table tab text tips`。

每个组件的 demo 页含**规范标记**（canonical markup），即「这个组件正确写法长什么样」的官方答案。这是基线抽取的一等信息源。

## 为什么不是扩展现有 SDD 流水线

本仓已有 `sdd-init-frontend → sdd-task-frontend → sdd-dev-frontend → sdd-review-frontend`。它**不能**承接本需求，原因是三条硬约束：

| 出处 | 约束 | 冲突点 |
| --- | --- | --- |
| `sdd-dev-frontend` 硬门禁 7 | 「不改设计、**不发明响应式规格**」 | 本需求的核心产出就是响应式规格 |
| `block-spec-template.md` R6 | 「只有输入明确给出时才写具体视口，否则写『未见』」 | 本需求要求主动拆 PC / 移动 / 多分辨率 |
| `sdd-dev-frontend` 基线源 | 设计事实必须来自**已存在的 HTML 原型** | 本需求的输入是一句话，没有原型 |

结论：新需求位于现有流水线的**上游**——它负责生产那份现有流水线拒绝发明的设计事实。这些约束不该被放宽，它们保护的是「不得凭空发明视觉数值」这条正确的原则。本方案的做法不是绕过它，而是**换一个合法的事实源**：把「已存在的原型」替换成「已固化的设计系统基线」，发明依然被禁止。

两者的衔接：`hwc-page` 的产物可直接充当 `sdd-dev-frontend` 的 `<prototype-dir>`，但因其本身已是成品，通常直接发布。

## Skill 划分

**v1 交付 2 个 skill，规划 1 个。** 划分依据是**变更源**，与本仓 `sdd-init-frontend` / `sdd-dev-frontend` 的拆法同源：

| Skill | 变更源 | 频率 | 状态 |
| --- | --- | --- | --- |
| `hwc-baseline` | baseui / PEP 版本升级 | 几个月一次 | v1 |
| `hwc-page` | 每次页面需求 | 每次 | v1 |
| `hwc-conformance` | 对**外部**已有页面做体检 | 按需 | 规划，非 v1 |

### 关于第三个 skill 的取舍

合规门禁是确定性脚本，天然可被 `hwc-page` 内联调用，**不必**为它单独开一个 skill。只有当出现「审计一个不是我生成的页面」这个独立意图时才值得独立——那时需要的是判断能力（这是真违规、是合理豁免、还是基线覆盖不足），而不只是跑脚本。

v1 的处理：门禁脚本由 `hwc-page` 拥有，但 **CLI 契约按可独立调用设计**（输入任意 HTML 路径，输出结构化 JSON），使其日后可零成本提升为 `hwc-conformance`。这样既不过度设计，也不锁死演进路径。

### 数据流

```
线上 CDN（版本锁定）
   │  hwc-baseline（人工触发 / 显式刷新）
   ▼
skills/hwc-baseline/baseline/     ← 仓内固化快照，唯一事实源
   │  hwc-page 只读消费
   ▼
一句话意图 ──▶ 意图补全 ──▶ 组件方案 ──▶ 成品 HTML ──▶ 五道门禁
                  ▲                                      │
                  └──────── 门禁 RED 回修 ◀──────────────┘
```

## `hwc-baseline`：设计系统基线

### 定位

把外部、版本化、分散在多个 CDN 产物里的设计系统，抽取成**仓内固化、机器可读、可 diff** 的唯一事实源。一次建立，显式刷新。

**独占规范节写权限**（沿用 `baseline-contract.md` 的写权限模型）：`hwc-page` 只读，异议只能上报，不能自行改判据。让判断者能改自己的判据，等于没有判断。

### 结构

```
skills/hwc-baseline/
├── SKILL.md
├── README.md
├── references/
│   ├── baseline-contract.md      基线文件划分、条目格式、覆盖声明
│   └── extraction-rules.md       各来源的抽取判据与已知能力边界
├── scripts/
│   ├── extract_baseline.py       vendor/ → baseline/，零 LLM，纯标准库
│   ├── fetch_vendor.py           CDN → vendor/，按 sources.json 拉取并校验哈希
│   └── diff_baseline.py          版本 diff，破坏性变更分类
├── vendor/                       ← 上游原始产物，全量入仓（见偏离节）
│   ├── cnpm-baseui/{3.0.17,3.0.18}/
│   └── pep-components-svelte/<版本>/
└── baseline/                     ← 交付件本体
    ├── index.md
    ├── sources.json              版本锁 + 内容哈希
    ├── tokens.json               两套令牌体系，原样抽取，机器读，带「体系」列
    ├── tokens.md                 分层结构、两套体系的适用域与选值原则（人写归纳）
    ├── components.md             组件类名语法
    ├── composition.md            跨组件的组合文法
    ├── responsive.md             断点阶梯、噪声档归一化规则与各档表达法
    ├── container.md              页面主体外层容器的宽度与栅格起点
    └── interaction.md            baseui 运行时提供的行为与接线方式
```

`page-shell.md` 随 [Q-3](#已决问题) 判「不出头尾」而移出 v1。取代它的 `container.md` 问句被收窄为「页面主体要放进公共外壳，外壳给的容器宽度与栅格起点是多少」——这个事实不能省，否则产出的主体宽度对不上公共头尾。

### 文件划分依据

沿用本仓 `baseline-contract.md` 的核心判据：**每份文件是一个消费者问句**，条目该不该进某文件只看「它是不是回答该问句所必需的事实」。

| 文件 | 判定问句 | 不进这里的例子 |
| --- | --- | --- |
| `tokens.md` / `tokens.json` | 有哪些合法值？怎么分层？哪套体系管哪片？ | 某个组件用了哪个令牌 → `components.md` |
| `components.md` | 有哪些现成组件？各自类名语法是什么？ | 跨组件通用的后缀规则 → `composition.md` |
| `composition.md` | 类名怎么拼才合法？ | 某组件独有的变体枚举 → `components.md` |
| `responsive.md` | 有哪几档断点？每档怎么表达？ | 某组件的断点级尺寸类 → `components.md` |
| `interaction.md` | 交互行为从哪来？怎么接？ | 交互的视觉值 → `tokens.md` |
| `container.md` | 主体外层容器多宽？栅格从哪起算？ | 区块内部结构 → `components.md`；头尾自身 → 不在 v1 |

六个问句均满足本仓扩展规则的三条：有真实下游查询、能写出判定问句且不需要类型列、答案非空。

### 条目格式

复用本仓既有的两类条目，不发明新格式：

**清单条目**（事实）`HWC-<域>-<n>`：

```markdown
| ID | 指路 | 是什么、何时用 | 出处 |
| --- | --- | --- | --- |
| `HWC-COMP-3` | `por-btn` 族，见 tokens.json 的 `por-button-*` | 主操作按钮；页面主 CTA 用 primary，同屏不超过一个 | `demo/button/index.html` |
```

**规范条目**（规则）`PATTERN-HWC-<域>-<n>`，不含路径：

```markdown
#### `PATTERN-HWC-TOKEN-1` · 数值只能来自基础标尺

| 项 | 内容 |
| --- | --- |
| 规则 | 任何尺寸、字号、圆角、阴影的字面量都不得直接书写，必须 `var(--por-*)`；组件层令牌不得绕过语义层直连标尺以外的值 |
| 依据清单 | `HWC-TOKEN-1`、`HWC-TOKEN-2` |
| 依据样本 | `theme-token.css` 中 `--por-button-*` 全族 74 条、`--por-font-*` 全族 50 条 |
| 违例判定 | 产物 CSS 中出现字面量且不等于任何令牌解析值 → 门禁 G1 |
```

### 覆盖声明

首轮不抽全部 30 个组件，只抽**本次要用的 + 通用层**（button / text / grid / card / link / icon）。每个清单节头部一行覆盖声明：

```markdown
<!-- 覆盖：button、text、grid、card、link、icon（baseui 3.0.18，2026-08-21） -->
```

| 查询结果 | 结论 |
| --- | --- |
| 覆盖范围内查不到 | 设计系统里确实没有 → 不得发明 |
| 覆盖范围外 | 增量抽取该组件并同步覆盖声明 |

这是「增量长」策略对消费者诚实的前提。追加条目**必须**同步更新覆盖声明。

## `hwc-page`：意图到成品页

### 定位

单次运行处理**一个页面**。输入一句话意图，输出通过五道门禁的成品 HTML。

### 四个阶段

| Phase | 动作 | 用户可见 | 结束方式 |
| --- | --- | --- | --- |
| 0 | 校验基线就绪、解析目标断点档 | 无（P6 内联） | — |
| A | 意图补全 → 组件方案 | 方案表 + 批量提问 | 确认门（P4） |
| B | 生成成品页 | 无 | — |
| C | 五道门禁 → 回修 | 门禁报告 | 三行索引（P5） |

只有 Phase A 需要用户决策。这是刻意的：**唯一值得打断用户的时刻是「只有你知道」的信息**。

### Phase A：意图补全的机制

这是本需求「简单意图 → 完整组件方案」的落点。关键设计是：**补全由基线缺口驱动，不是开放式追问。**

意图落到候选区块序列后，每个区块的每个字段按来源三分类（沿用 `qa-baseline-template` 的缺口分类思路）：

| 类别 | 判据 | 处理 |
| --- | --- | --- |
| 基线可定 | 值能从 `baseline/` 确定性读出（令牌、默认档位、类名语法） | 静默填入，不打扰用户 |
| 有安全默认 | 基线给不出唯一解，但存在明显缺省（区块顺序、栅格列数、图文左右） | 标 🟡 工作假设，展示但不阻塞 |
| 只有用户知道 | 文案、真实数据、跳转目标、业务语义、品牌资产 | 标 🔴 必答 |

三类之外**不问**。「你想要什么风格」这类问题一律不出现——风格由基线决定，不由用户临场发挥。

一轮批量问完（P7），格式：

```
以下 N 个问题需要你回答：

| # | 问题 | 我的推测 |
|---|------|---------|
| Q-1 | 主 CTA 点击后跳到哪 | — |
| Q-2 | 客户案例区块放 6 个还是 3 个 | 推测 6 个，依据 HWC-COMP-11 默认档 |

🔴 必须回答才能继续；🟡 可确认、纠正或跳过（跳过则记为工作假设）
```

### Phase A 的产出：组件方案

确认门展示的就是它，一张表说清整页：

```markdown
| 序 | 区块 | 采用组件 | 断点行为 | 待定字段 |
| --- | --- | --- | --- | --- |
| 1 | 首屏 banner | `HWC-COMP-1` basic-banner | ≤599 内容宽 100%，≥1280 宽 70% | 🔴 主 CTA 目标 |
| 2 | 能力三栏 | `HWC-COMP-7` card × 3 | ≤839 单列堆叠 | 🟡 推测 3 栏 |
```

冻结后进入 Phase B。开工后放宽期望必须记录理由并重新确认（沿用硬门禁 8 的冻结可追溯）。

### Phase B：生成策略

**不链上游 CDN 的组件 CSS，抽取真实规则后落成自包含样式层。** 理由三条，缺一不可：

| 决策依据 | 推论 |
| --- | --- |
| 产物要「可直接发布」 | 不能依赖别人版本化的作用域哈希类（`svelte-6737yf` 会随组件版本变） |
| 基线选择「固化快照」 | 产物必须自包含、可复现 |
| 门禁是硬门禁 | 必须有属于自己的 CSS 可被扫描；纯外链无物可扫 |

例外：**令牌层 `--por-*` 与 PEP 的 `--primitive-*` / `--text-*` 等保留原名**——那是设计系统契约本身，改名等于脱离设计系统。运行时 `theme-token.js` 直接引用，不重新实现交互。

**作用域哈希是重命名，不是删除。** 2026-08-24 spike 实测（5 份 PEP 组件 CSS，媒体查询上下文敏感的选择器比对）：直接删掉 `.svelte-<hash>` 后，每份仍有 **1–2 处真冲突**——同一选择器在同一 `@media` 下拿到两份不同声明，例如 `@media (max-width: 599px)` 里 `.banner-item__icon` 的 `text-align` 同时被判 `left` 与 `center`。所以剥离必须是**映射到稳定语义后缀**（`svelte-6737yf` → `hwc-banner-1`），保留区分能力、同时去掉随版本漂移的哈希。另有 `svelte-161racf` 在 5 份里全部出现，是跨组件共享哈希，映射表必须全局唯一而非按组件各自编号。

## 标准：五道合规门禁

**硬门禁：不通过即未完成。** 必须修到通过，或显式登记豁免并经用户确认。

沿用本仓既有色号语义，不发明第三套词汇：**RED**（确证违规）/ **YELLOW**（无法判定）/ **GREEN**（通过）。YELLOW 不得改写为 GREEN——这条在 `sdd-dev-frontend` 硬门禁 11 已有先例，此处继承。

| # | 门禁 | 违例判定（机器可执行） | 无法判定时 |
| --- | --- | --- | --- |
| G1 | 令牌合规 | 两条判据都要过：**① 无字面量**——颜色 / 字号 / 行高 / 圆角 / 阴影 / 间距的字面量不等于任何令牌解析值且未写成 `var()`；**唯一例外是 primitive 层的定义处**（`--primitive-*: #f9fafb` 合法，消费处写字面量不合法）；**② 可解析**——引用的令牌在 `tokens.json` 两套体系之一中确有定义，不落在 37 个已知悬空引用上（除非提供 fallback） | 解析链跨文件断裂 → YELLOW |
| G2 | 类名文法 | `por-*` 类不能被 `composition.md` 的文法解析；或同一槽位重复填充（如同时 `primary` 与 `secondary`） | 组件不在覆盖范围 → YELLOW |
| G3 | 断点完备 | 声明支持的每一档，缺少对应表达（断点类名或媒体查询）。**判定前先按 `responsive.md` 的归一化规则折叠噪声档**（实测上游存在 `840px` 与 `839px` 并用，5 处 vs 1 处），否则同一档会被数成两档 | 产物落在归一化容差外的自造档位 → YELLOW |
| G4 | 交互态完备 | 可交互元素缺少 hover / focus-visible / active / disabled 任一态 | 需实际渲染才能判的态 → YELLOW |
| G5 | 无发明 | 产物引入 `baseline/` 中不存在的 `por-*` 类名 | — |

### 三条配套约束

**G1 报告必须给出可执行的修法**，不能只说「这里违规」：

```json
{ "gate": "G1", "level": "RED", "loc": "page.css:142",
  "found": "font-size: 15px",
  "nearest": ["--por-font-size-14", "--por-font-size-16"],
  "note": "15px 不在基础标尺上；标尺无 15 档" }
```

**G4 的存在理由是「可直接发布」。** 如果产物只是原型，交互态可以缺；既然是成品，缺交互态就是缺功能，不是缺打磨。

**豁免不吸收工具缺口。** 若 RED 实为比对器的序列化差异（如 `rgba(0,0,0,.08)` vs `rgba(0, 0, 0, 0.08)`），只允许补归一化后重跑，不允许加豁免。此条直接继承 `sdd-dev-frontend` 硬门禁 16，那里已有踩坑记录。

## 演进方式

### 版本刷新：diff 门控，不是直接覆盖

「顺手升个版本」会静默打断产物。**实测证据**——3.0.17 → 3.0.18 的 datepicker 令牌族：

```
3.0.17: --por-color-datepicker-input-background
3.0.18: --por-datepickerr-color-input-background
```

整族**改名**（且上游带拼写错误，多一个 `r`），不是新增。总数从 769 变 777 只多了 8，完全掩盖了这次 21 条的重命名。**只比总数一定漏判。**

因此 `diff_baseline.py` 必须把变更分三类，处理方式不同：

| 类别 | 判据 | 处理 |
| --- | --- | --- |
| 新增 | 新版有、旧版无，且无同义旧名 | 自动并入，不打扰 |
| 改值 | 名相同、解析值不同 | 列出受影响产物，需用户确认 |
| 破坏性 | 删除，或删除+新增构成重命名 | **阻断**。逐条给迁移映射，确认后才写入 |

**上游拼写错误必须原样镜像，不得修正。** `datepickerr` 就是它的真名；基线是事实的副本，不是事实的改良版。

### 覆盖增长：用到才抽，抽了就声明

首轮 6 个通用组件。`hwc-page` 用到覆盖外组件时，增量抽取该组件并同步覆盖声明，不重扫全库。判据是「有消费者读到了查不到的结论」，不是「上游有文件变了」。

### 三类跟进的分界

沿用本仓「消费点自证 + 就地修」，不引入内容指纹、不维护 stale 状态：

| 改动性质 | 处理 | 是否阻塞 |
| --- | --- | --- |
| 清单单条指路失效（看一眼就能验） | `hwc-page` 就地修，随本次提交 | 不阻塞 |
| 规范条目可能不成立（要看多个样本） | 攒进本次运行的 handoff，收口时一次确认 | 不阻塞 |
| 上游版本变更 | 走 `diff_baseline.py` 门控 | 破坏性变更阻断 |

### 断点冲突的长期处理

两套阶梯（baseui 768/1024/1280/1600 与 PEP 599/839/1024/1280/1600）不是错误，是两个体系各自演化的结果。基线中**并存登记**，由 `responsive.md` 声明各自适用域；`hwc-page` 按页面类型选择，选择结果写进冻结方案，不在生成时临时决定。

### v2 候选（明确不在 v1）

| 项 | 触发条件 |
| --- | --- |
| `hwc-conformance` 独立 skill | 出现「审计非本工具生成的页面」这一独立意图 |
| 自定义头尾 | 需求明确要求不用公共头尾。届时头尾的设计与实现须符合现有风格，事实源要重新勘察（导航数据、多语言、登录态都在公共头尾里） |
| `m` / `pc` 分构建 | 单份响应式产物实测不达标 |
| 控制台后台页支持 | 当前只做营销 / 产品页；控制台的表单表格设计语言差异大，需独立勘察 |
| 视觉回归对比 | 门禁全部转 GREEN 之后再谈；机器可检项没做完之前不引入截图 |

## 与现有仓库约定的偏离

两处，均已于 2026-08-24 批准。

### 「只指路不复制」在外部 CDN 产物上不适用 · 已批准

本仓 `baseline-contract.md` 列为硬门禁：「能从某个文件里逐字读到的话，就别写，写路径」，并明确点名「间距档位的具体像素值」不得抄。其论证是：文件在、内容变了的场景下，只指路能自动跟上，复制会静默失效。

**该论证依赖「指路目标是本地可 grep 且会原地演化的代码」。** 外部版本化 CDN 产物不满足这个前提：

| 维度 | 本地代码仓 | 版本锁定的 CDN 产物 |
| --- | --- | --- |
| 内容会原地变吗 | 会 | 不会。变了就是新版本号 |
| 指路能自动跟上吗 | 能，这是收益来源 | 无收益可言 |
| 指路会怎么失效 | 文件移动 → 打开即失败 | URL 404 → **整个基线一起失效** |
| 离线可用 | 是 | 否 |

因此本 skill 族的规则调整为：

> **可机器抽取的原样固化（`tokens.json`），人写的只写归纳（`*.md` 的规范条目），两者不重叠。**

原门禁真正要防的是**转述有损**（文档里那个把 `vite --port 5178` 转述成 `pnpm run dev` 丢掉端口的例子）。这条防线在新规则下**更强而非更弱**：`tokens.json` 由脚本原样抽取、零人工转述；人写的部分被限制为「归纳」，本就不该出现具体数值。

批准范围限于**版本锁定的外部 CDN 产物**；本仓自身代码与文档仍走「只指路不复制」。落地时需在 `sdd-init-frontend/references/baseline-contract.md` 增补这条例外，注明适用前提是「指路目标不会原地演化」。

**本节自身就是这条偏离的反面教材**：初版附录把 PEP 组件 URL 转述成 `{basic-banner,video-card,...}`，漏掉了真实路径里的 `cnpm-pep-` 前缀，照抄去拉取会得到 403。这正是「人写的部分不该出现可机器抽取的具体值」的实证。

### 上游原始产物全量入仓 · 已批准

`.gitignore` 写着「打包产物一律不进仓：内容不可 diff、不可复核」。`vendor/` 里的 `theme-token.js` 是 121 KB 的 webpack bundle，正撞这一条。

批准理由与例外边界：

| 项 | 内容 |
| --- | --- |
| 为什么必须入仓 | ① 离线可用；② `diff_baseline.py` 的用例需要 3.0.17 与 3.0.18 两份 `theme-token.css` 并存当 golden fixture，那 21 条重命名是天然用例；③ CDN 一旦 404，整个基线连带失效 |
| 例外只开给谁 | 版本锁定、由 `sources.json` 记内容哈希的第三方产物。本仓自产的打包物仍禁止入仓 |
| 不可 diff 的那部分怎么办 | `theme-token.js` 不做逐行 diff，只比内容哈希；它是运行时黑盒，本设计从不解析其内部 |
| 待确认 | 本仓通过 GitHub 公开分发（README 的一键安装指向 `raw.githubusercontent.com`），镜像华为云生产资产的分发合规性由使用方确认 |

`README.md` 与 `PRINCIPLES.md` 的其余约定全部沿用，无偏离。

## 勘察补正（2026-08-24）

Phase B「剥离作用域哈希落成自包含样式层」是初版全文唯一没有实测证据的论断，故先做 spike。结论是**前提成立但不无损**，同时挖出三处会改判据的事实。

| # | 发现 | 实测 | 对设计的改动 |
| --- | --- | --- | --- |
| 1 | 附录的 PEP 组件 URL 不可复现 | 真实路径带 `cnpm-pep-` 前缀，且 `folded-pictext` 实为 `cnpm-pep-folded-pictext-svelte`。按初版写法拉取得 403 `AccessDenied` | 修正附录出处表；`sources.json` 必须存全 URL，不得由人拼装 |
| 2 | PEP 自带第二套令牌体系 | 每组件 42–44 条非 `--por-*` 定义，`--primitive-*` 直接写十六进制 | `tokens.json` 收两套；G1 给 primitive 定义处开例外 |
| 3 | 断点阶梯的「一致复现」不成立 | 严格交集只有 839/1280/1600；`video-card` 用 `840px`（5 处）而非 `839px`；`basic-banner` 另有 859/768/1920 | `responsive.md` 增归一化规则；G3 判定前先折叠噪声档 |
| 4 | 删哈希会撞车，但量很小 | 媒体查询上下文敏感比对：每份 CSS 真冲突 1–2 处（如 `.banner-item__icon` 在 `max-width:599px` 下 `text-align` 同时是 `left` 与 `center`）；`svelte-161racf` 在 5 份中全部出现，是跨组件共享哈希 | Phase B 改为「映射到稳定语义后缀」，映射表全局唯一 |

复现方式：`vendor/` 拉齐后跑 `extract_baseline.py` 与门禁用例即可，本轮 spike 的一次性脚本不入仓。
