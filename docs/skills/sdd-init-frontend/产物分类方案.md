# sdd-init-frontend 产物分类方案(定稿)

解决 `产物分类问题-handoff.md` 第 8 节的未决问题。本文自包含,可直接作为改造依据;背景、四次失败尝试与七条约束的推导见 handoff。

---

## 1. 核心主张

1. **主分类维度 = 关注点,定义收紧为「消费者问句」,文件即问句。** 一个条目该不该进某文件,判据是「它是不是回答该文件问句所必需的事实」。问句自带成员判据,这是它与尝试 4「主题标签」式关注点的本质区别(满足 C2)。
2. **同一关注点内部再按变更源切。** 「都跟数据有关」是主题相似性,不是内聚:请求封装换后端要改、换框架不用改,store/hook 反之。变更源不同就分文件——这是 `api.md` / `data.md` 分立的唯一理由。
3. **资产不独立成文件**,按「消费者通过哪个问句检索到它」归入对应关注点文件的清单节。这是 handoff 候选思路 1 与 2 的合体;思路 4(组件单切)实现为 `components.md` 内的 D2 分层,不升格为顶层维度。
4. **每份文件统一两节骨架:「清单」(事实)+「规范」(规则)。** 同时兑现 C6(事实/规则分离)与 D9(写权限分级)。
5. **只指路不复制,立为硬门禁**(见 §3.2)。
6. **场景只做索引,不做切分**(handoff 第 7 节结论,保留)。

### 不采用架构分层,理由不是审美

「按前端整体架构设计切分」即 handoff 的尝试 3,已验证失败两条:对差架构不鲁棒(C1,`pages/` 平铺的仓会得到三份空文件);且诱导 agent 把仓库描述成**它应该的样子**而非实际的样子——与「无外部基线不得发明 px」同类错误,发明对象从视觉数值换成架构。

但八文件与架构分层**高度重叠**(components≈表现层,api≈基础设施层,data≈应用层,styling≈表现层横切,structure/runtime/testing≈工程支撑)。换掉的不是分类结果,是**成员判据**:分层问「它属于哪一层」(差架构下无答案),问句问「消费者问什么会找到它」(永远有答案)。架构的组织力保留,脆弱性去掉。

### 唯一事实源由三条机制保证,不靠自觉

D8「同一条事实只出现在一节」+ ID 全局唯一 + 只指路不复制(不产生第二份 API 描述)。

## 2. 文件结构

```
frontend-baselines/<repo-id>/
  index.md        # 入口与路由,零事实正文
  structure.md    # STRUCT-*  栈签名、目录实况、命名约定
  runtime.md      # RUN-*     装 / 起 / 跑哪些质量命令
  components.md   # COMP-*    通用构件详表 + 业务组件路由索引 + 渲染辅助
  api.md          # API-*     与后端通信的跨需求约定
  data.md         # DATA-*    客户端数据的持有与流动、三态、表单、状态边界
  styling.md      # STYLE-*   token、scale、主题、硬编码基准
  testing.md      # TEST-*    框架、定位约定、跑法
```

判定问句与差架构下的非空答案(C1 验收):

| 文件 | 判定问句 | 差架构下的答案(仍有价值) |
| --- | --- | --- |
| `index.md` | 我该读哪条?(纯路由:场景索引 + 单点事实速查表 + 文件导航,只有指向 ID 的行) | 不适用 |
| `structure.md` | 这是什么栈?代码放哪、怎么命名? | 「`pages/` 平铺,无特性分层」 |
| `runtime.md` | 怎么装、怎么起、跑哪些质量命令? | 装起命令永远存在 |
| `components.md` | 拼界面时有哪些现成构件可用? | 通用详表空则整节删(D7),业务路由索引永远非空 |
| `api.md` | 怎么跟后端说话? | 「无统一实例,各处裸 axios,鉴权头逐处手写,错误码无集中映射」→ review 据此**不能**判「绕过统一实例」 |
| `data.md` | 拿到的数据在前端怎么持有、怎么流到界面? | 「无缓存无 store,状态一律留在发起请求的那个组件内,三态各页自己写」→ task 据此**不要**发明 store |
| `styling.md` | 样式值从哪来,允许怎么写? | 「全硬编码、无 token,review 不得判硬编码违规」 |
| `testing.md` | 测试用什么写、怎么定位元素、怎么跑? | 「无测试框架,dev 免测试门禁」 |

### `api.md` 与 `data.md` 的界线是进程边界

边界外的通信约定归 api,边界内的持有与流动归 data。

| 归 `api.md` | 归 `data.md` |
| --- | --- |
| 请求实例在哪、baseURL 从哪来 | hook / composable 清单 |
| 拦截器做了什么、鉴权怎么带 | 缓存库(React Query / SWR)及其约定 |
| HTTP 错误怎么翻译成前端错误对象 | 错误对象怎么变成 UI 的错误态 |
| 超时、重试、取消 | 加载 / 空 / 错误三态的仓内做法 |
| mock 约定 | pending 态与提交防重 |
| 分页 / 排序参数的仓内惯例 | 全局 store 及其消费方 |
| | 表单库选择与校验**时机** |
| | 服务端数据 vs 本地 UI 状态的边界 |

副产品:`stack-signals.md` 的两条 review 判据各归一处、都单文件可判——`request-and-error-handling` → `api.md`,`state-placement` → `data.md`。

### 栈签名留在 `structure.md`,理由须写明

栈签名是全局单点事实(review 靠它选 `stack-signals.md` 读哪一节),看起来像外挂,但按问句判据通过:不知道是 Vue,就无法判断 `.vue` 单文件组件是常态还是异常;不知道是 Angular,`module / service / directive / pipe` 这套目录语汇就无从解释。**栈是「代码放哪、怎么命名」的前置条件,不是并列项。** 不放 `index.md`,否则「正文事实不进 index」这条守不住;index 只放一行指向 `STRUCT-1` 的速查行。

这条理由必须落进 `structure.md` 的节首,否则下一个维护者会认为是随手塞的。

## 3. 文件内部骨架与 ID

### 3.1 条目格式

- **清单条目** `<前缀>-<n>`(如 `DATA-2`):指路 + 一句话「是什么、何时用」+ 证据(被几处引用)。三段全是代码里读不到的,没有一段是抄的。
- **规范条目** `PATTERN-<前缀>-<n>`(如 `PATTERN-API-1`):规则陈述 + 依据的清单 ID(D8)+ **依据样本**(归纳时看了哪几处代码)+ review 可执行的违例判定方法。**不含路径**,路径只在清单节出现。
- ID 只增不改号;前缀即命名空间,各文件独立编号,并行追加不冲突。
- **「无统一做法」是一等公民条目**,必须写成显式规范,不留空。
- `PATTERN-API-1` 的命名空间前缀仍解析为 `PATTERN`,`sdd-review-frontend` 的 `PATTERN-*` grep 与 `fe-id-prefix` 检查均零改动(C7)。

### 3.2 只指路不复制(硬门禁)

**判据**:能从某个文件里逐字读到的话,就别写,写路径;必须看多个文件才能得出的,才写。

| 不该抄(代码里已明确表达) | 该写(只能归纳) |
| --- | --- |
| `request.ts` 导出 `get/post/put/del` 及签名 | 「**所有**请求必须走 `request.ts`,不得直接 axios」 |
| `StatCard` 的 props 是 `label/value/tone` | 「`StatCard` 用于单个指标数值,不要做多值对比」 |
| token 档位 `--space-1: 4px` … `--space-6: 32px` | 「间距只能取 `--space-*`,不得写字面 px」 |
| 目录树长什么样 | 「本仓 `pages/` 平铺,无特性分层」 |

**必须是门禁而非格式偏好,因为抄是局部理性的。** 面对 `request.ts`,把四个方法签名抄上去感觉是"更完整";每次单看都像改进,累积起来 baseline 就成了 API 文档的劣质副本。这正是 handoff §3.1 的复发机制:现行 `REPO-1` 是 `package.json` 的重排版,且**转述有损**——`"dev": "vite --port 5178"` 抄成 `pnpm run dev`,端口丢了。门禁的作用是让「更完整」这个诱惑不合法。

**推论:具体接口的 URL、请求/响应字段、枚举不进 `api.md`。** 那是 Story 级契约,事实源是 `story-delta-design.md` / `requirement-design.md`,`sdd-task-frontend` 已有「只引用不重定义」硬门禁。`api.md` 只装跨需求稳定的通信约定。这是 `api.md` 最大的失败模式,须在文件节首明写。

### 3.3 路径会变:指路稳定性排序

只指路把失效从静默漂移换成响亮失败:

| 失效形态 | 只指路 | 复制内容 |
| --- | --- | --- |
| 文件移动 / 重命名 | 打开即 404,**响亮失败** | 路径同样失效,**外加抄来的内容要重新核对** |
| 文件在、内容变了(`request.ts` 加了 `patch`) | **自动跟上,条目不用改** | 抄的四个签名看起来完全正常 → agent 照抄漏掉 `patch` → **静默错误** |
| 规则本身失效(出现第二个请求实例) | 指纹也测不出,只能消费点自证 | 同样测不出 |

第一行两者代价相同,复制只多一笔核对;真正的差距在第二行。

**指路按稳定性排序**(同一事实有多种指法时选最不易变的):

1. 指**导出符号 + 所在目录**(`src/lib/` 下的 `request` 实例)优于精确文件名——文件重命名远比符号重命名频繁
2. 指**命名前缀**(`--space-*`)优于文件行号
3. 目录级指路(`src/components/` 下的通用构件)优于逐文件枚举

指路必须够准(文件 + 命名前缀或章节),这样就不需要为「档位集合对消费者不可读」开例外:review 自己 grep 一次比读一份会漂的副本可靠。

**变更半径被 D8 压到一条。** 规范条目只引清单 ID,所以 `request.ts` 改名成 `http.ts` 时,`PATTERN-API-1`「所有请求必须走 `API-1`」一个字不用改,只改 `API-1` 那行的路径。复制了签名的话,同一次改名要动路径 + 签名 + 所有引用它的规范条目。

**坦白的代价:检测是懒惰的。** 只有消费者真去读那条才发现路径烂了,长期没人用的条目会一直烂着。这可接受——长期没人用的条目本就无价值,而指纹机制会为这种条目每次把 readiness 打回 `DRAFT`,那正是 §3.3 那个 bug 的本质(改一行 `format.ts` 就要人重新复核全部手写范式)。**懒惰检测在这里是特性,不是缺陷。**

### 3.4 覆盖声明(取消指纹后的语义补丁)

每个清单节头部一行,声明本节扫过哪些目录、何时:

```markdown
<!-- 覆盖:src/components/、src/shared/、src/features/checkout/(2026-08-20) -->
```

消费点自证(D3)据此区分「仓里没有」和「没扫过」:覆盖范围内查不到 = 确实没有;范围外 = 自行勘察并追加单条(D9)。这是 D5「首扫只覆盖候选目录、业务靠增量长」对消费者诚实的前提。

两条配套约束:

- **task / dev 追加清单条目时,必须同步更新该节的覆盖声明**,否则声明会随增量失真。
- **规范条目不用覆盖声明,用「依据样本」**(§3.1):清单节声明的是扫过哪些目录,规范条目要声明的是归纳时看了哪几处——两者粒度不同,不能共用一行。

### 3.5 版本号取代指纹

指纹(SHA-256)全面废除(D3)。唯一还需要「内容变了没」信号的地方是 `manage_execution_evidence.py` 的质量命令结果缓存,改为**人类可读的整数版本号**:

- 参数 `--repo2-fingerprint <hex>` → `--quality-version <int>`
- 取值来自 `runtime.md` 质量命令节的一个显式版本号,质量命令有实质变动时由 init 手动 +1
- 缓存键的语义不变(值变则缓存失效),但人和 agent 都能看懂它是第几版,而哈希两者都看不懂

## 4. 归属与边界裁决

资产归入「消费者通过哪个问句找到它」的文件;跨问句资产归更专门的一个,其余位置只写 ID 引用(D8)。

| 资产 | 归属 | 理由 |
| --- | --- | --- |
| `Table`、`StatCard`、样式化基础组件(`Button` / `Stack`) | components | 写 JSX / 模板时 import |
| `format.ts` 等渲染辅助 | components(独立小节) | 拼界面时会用;不为它发明新文件 |
| `request.ts`、拦截器、鉴权、错误码映射 | api | 通过「怎么跟后端说话」找到 |
| `usePortfolioSummary`、缓存库、全局 store | data | 通过「数据在前端怎么持有」找到 |
| token、scale、mixin、utility class、theme 对象 | styling | 写样式声明时取值 |
| 主题机制(`ThemeProvider` + theme) | styling,components 留 ID 引用 | 回答「样式值从哪来」 |
| 组件自身的样式实现 | 不进 baseline | 代码里已表达 |
| 具体接口的 URL / 字段 / 枚举 | 不进 baseline | Story 级契约,§3.2 |

### 表单不是一个关注点,是跨关注点的场景

不设 `forms.md`,按三段拆:

| 表单的哪一面 | 归属 |
| --- | --- |
| 表单库选择、校验触发**时机**、提交 pending 与防重 | data |
| 输入控件、错误消息的展示构件 | components |
| 校验规则**写在哪个文件 / 层**(schema 集中还是内联) | structure |

「要做一个表单」由 `index.md` 的场景索引跨文件串起来,与 C5 一致。

### 扩展规则

核心八文件之外一个不预置。新文件仅当(a)有真实下游查询需要、(b)能写出判定问句并通过杂物袋检测器、(c)差架构下答案非空时,由 init 创建(D9),需求走 D10 攒批。

## 5. 写权限与跟进

三层分工(D9 / D10):

| 角色 | 清单节 | 规范节 | 全量重建 |
| --- | --- | --- | --- |
| `sdd-init-frontend` | 可写 | **独占** | 可 |
| `sdd-task-frontend` / `sdd-dev-frontend` | 可追加、可修正**单条**(须同步覆盖声明) | 只读,异议攒进 `acceptance.md` | 不可 |
| `sdd-review-frontend` | 只读 | 只读 | 不可 |

**否定裁决:review 不得修改任何判据。** 让判断者能改自己的判据就等于没有判断。review 发现基准有误只能出 Finding,由 Story 收口时走 D10 确认。

跟进节奏(D10):清单单条改动**就地做、进本次提交、不阻塞任何 Task**;规范改动攒进 `acceptance.md`,Story 收口时一次确认。分界线是「看一眼代码就能验」还是「要看多个样本才能判」。

## 6. 实证产物的归处

**`onboarding-report.md` 不再是 baseline 产物。** baselines 目录只放跨需求契约,「契约 vs 实证」界线靠实证不进该目录来保住。浏览器实证按 D4 整体移交 `sdd-dev-frontend` Phase 0 按需做——这是现行 init 显得重的最大单一来源。

命令级实证的落点分两种调用方式:

| 调用方式 | 落点 |
| --- | --- |
| 由 `sdd-dev-frontend` Phase -1 路由进来(有 `<story-dir>`) | 写进 `<story-dir>`,与 `acceptance.md` 同类 |
| 用户独立调用 init(无 Story) | **只回话,不落盘** |

独立调用时无处可落又不能落进 baselines,回话是唯一不破坏界线的选择。

## 7. 验证结论

- **九条消费者查询**(handoff §2)全部命中:#1 走 index 场景索引跨文件取 ID;#3 / #5 / #8 走速查表或对应文件;#6 grep `PATTERN-*` 全目录唯一命中;#7 走 api 的清单 + 规范;#9 走 styling;#2 走 data 的三态规范;#4 走 testing 的定位约定。
- **七条约束**(handoff §6):C1 见 §2 问句表第三列;C2 问句即判据;C3 无 shared / common 文件;C4 未用生命周期切分;C5 场景仅在 index;C6 清单 / 规范分节;C7 前缀化 `PATTERN` ID 全局唯一。**杂物袋检测器:八份文件没有任何一张表需要类型列。**
- **耦合**:仅三条单向 ID 引用,无双向依赖——api 错误对象 → data 三态;styling 主题机制 → components 引用;structure 校验规则位置 → data 校验时机。
- **对 handoff §3 缺陷的修复**:3.1 → runtime 指路优先不转述;3.2 → 发现方式改为 agent 逐文件回答问句(D1),不再靠文件名词表;3.3 → 指纹已废(D3),覆盖声明补语义缺口;3.4 → `rendering_contract` 随脚本消失、框架字段落地 structure、组件由 components 承载。

## 9. 第二轮:形态、路由与三处补漏

八份落地后复审发现四个缺口,本轮全部修掉。**四个里有三个是同一类错误:把「应用形态的 Web SPA」当成了唯一世界。**

### 9.1 仓库形态成为栈签名的第二条正交事实

原栈签名只有框架,判据表只枚举 React / Vue / Svelte / Angular。缺的不是更多框架——**框架轴本来就够用,缺的是「这是个什么形态的前端仓」这条正交轴**:`应用`(默认)/ `微前端宿主` / `微前端子应用` / `小程序` / `组件库`。

形态是一等事实的理由不是描述得更全,而是**它改判据**。同一条结构判据在不同形态下会给出错误答案,其中两条是假阴性,比空文件危险:

| 形态 | 判据失效点 |
| --- | --- |
| `组件库` | 「被两个以上消费单元引用」整体失效——对外导出的一切都是公开 API |
| `微前端子应用` | 本仓搜不到统一请求出口**不等于**没有,出口可能由宿主注入。判成「无统一做法」会让检视放过真正的绕过 |
| `小程序` | 请求走平台 API、样式单位与 token 机制都不同,Web 的 `fetch` / `axios` 信号不适用 |

形态与框架同放 `structure.md` 的栈签名,**不单独开文件**——它和框架同类,是「代码放哪、怎么命名」的前置条件。必须在 Phase 0 先定并写进 `structure.md`,其余文件才能开始。判据差异只写真正不同的格子,不做形态 × 文件全矩阵。

元框架(Next / Nuxt / Remix / SvelteKit / Astro)按用户决定**不扩**。

### 9.2 分层判据从「特性目录」泛化成「消费单元」

这是一处**内部矛盾**而非覆盖不足:判据写死「被两个以上**特性目录**引用」,可 §2 问句表同时声称平铺仓也有答案。平铺仓里没有特性目录,判据无法执行——而平铺仓恰恰最需要「哪些是真通用」这个结论。

改成「消费单元」,粒度按 `structure.md` 已记的目录实况定:特性目录 / 使用它的业务模块 / 页面文件 / `组件库` 形态不适用。三处同改:`components.md` 收纳边界、`discovery-rules.md` 通用取候选手段、`data.md` 全局 store 判据。

### 9.3 新增 `routing.md`,业务组件路由索引从 `components.md` 迁入

原设计没有路由的问句,而「加一个页面」是最高频的前端任务;路由只以「业务组件按路由的索引」的形式寄居在 `components.md`,「怎么新增一条路由、守卫写在哪、代码分割在哪切」无处可去。

按 §「扩展规则」三条准入,`routing.md` 全过:有真实下游查询;问句「加一个页面 / 一条路由要动哪几处」自带成员判据、不需要类型列;无路由库的仓答「单页面挂载」,仍能阻止计划期发明路由。**它是那条扩展规则的第一个样例。**

顺带把业务组件路由索引整节迁进来,理由是它答的本来就是「哪条路径由谁渲染」= 路由问句,而只被一个消费单元引用的业务面板也算不上「拼界面时的现成构件」。**这一步让 `components.md` 变小而不是让总面积变大。**

配一条与 `api.md` 端点同形的守卫:具体路由路径与页面清单不进本文件,唯一例外是路由→业务组件索引本身。

**一次性 ID 例外要记在案:** 迁移把 fixture 的 `COMP-2` 改成了 `ROUTE-2`,违反「ID 只增不改号」。可接受的前提是当时仓内只有 fixture 一份数据、无真实仓在库;`COMP-2` 作为退役号不再复用,并在 `components.md` 里写明。**这是例外不是先例**,以后跨文件迁条目一律新增号、旧号退役。

### 9.4 跨关注点场景按「表单」先例归置,不新建文件

i18n / 权限 / 监控埋点 / 性能预算原先都无处可去。它们和表单同类:横跨多个问句,给每个开文件会立刻与现有文件重叠。判据统一成一句——**能不能写出一个自带成员判据的问句**;问不出的是场景,拆进现有文件靠 `index.md` 场景索引串。归置表见契约。四个场景里有两个用到 `routing.md`(权限守卫、语言前缀路由),这是 §9.3 该独立成文件的第三条理由。

同时给 `structure.md` 补上「某类东西写在哪个层」这一族的其余成员:领域逻辑(与框架无关的模型与用例)、monorepo 跨 app 共享包。

### 9.5 顺手修掉的接入门 bug

原接入门查「八份文件是否存在」,与「空文件整份删」直接冲突——`组件库` 形态下 `routing.md` 与 `api.md` 本就不该存在,按份数查会把正确产物判成不合格。改成只查两样:`index.md` 存在(它只做路由,恒存在)、`structure.md` 读得出具名框架 + 具名形态(栈签名恒存在)。四处同改:契约的下游最小读取表、`sdd-dev-frontend/SKILL.md` 硬门禁 0、`phase-entry.md`、`docs/.../README.md`。

### 9.6 生成路径补执行覆盖

扫描器删除后,生成路径**零执行覆盖**:14 条 evals 全是情景判断题,而 fixture baseline 是手写冻结的静态文件、`setup.py` 只做拷贝,所以「agent 面对一棵真实文件树能不能产出正确的九份」在改版后一直没被测过。补第 15 条端到端用例:拿 fixture 仓的实际文件构成当输入、冻结的那份 baseline 当对照。**不恢复脚本**——那是上一轮刚拆掉的东西,恢复它等于把识别率 1/5 的问题请回来。

## 10. 遗留待定

按用户决定不做:元框架栈签名扩展(Next / Nuxt / Remix / SvelteKit / Astro)、SSR 服务端与客户端边界。两者都属框架轴扩展,本轮范围只到形态轴。

生成结果的**可复现性**仍是敞口:全程靠 agent 判断,同一个仓两次跑不保证逐字节相同。第 15 条端到端用例只能测「结论对不对」,测不了「两次是否一致」。这是上一轮用可读性与不误报换来的代价,记在这里以免被当成新发现。
