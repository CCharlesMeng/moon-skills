# sdd-dev-frontend 样式还原验证 V2 计划

## Summary

把还原轮从“人工差异清单 + 每轮截图”升级为“冻结设计契约 + 红黄绿机器报告 + 按需截图”。

- 保留 R1–R6、QA 基线确认门、六步 RED/GREEN 语义和外部基线原则。
- 机器检查覆盖结构、文案、token、计算样式、几何布局和状态；截图只处理机器无法可靠判断的项目。
- 首版按“可执行闭环”规划，不只修改文档。
- 本计划完成后归档在项目级维护文档目录 `docs/skills/sdd-dev-frontend/`。

## Key Interfaces

新增三类机器可读工件：

1. `design-facts.json`：Requirement 级原型事实，由现有抽取脚本确定性生成。

- 包含规范化 DOM/CSS 哈希、资源内容哈希、区块锚点与哈希、结构、静态文案、设计 token 和布局声明。
- 原型指纹同时覆盖 DOM/CSS、外部资源及缺失状态，不能只使用当前 `doc_hash`。

2. `restore-contract.json`：Story 级冻结还原契约，是 `dev-baseline.md` 中 R1–R6 的机器镜像。

- 每条规则包含基线编号、维度、区块、判定对象、期望值、检查模式、容差、状态场景和设计事实出处。
- `dev-baseline.md` 仍是人类可读的权威；JSON 保存其内容哈希。两者不一致时拒绝执行。
- 实现侧定位单独保存为运行适配信息，优先级为 role/name → 精确文案 → 稳定 test id → CSS；禁止依赖构建生成的随机 class。

3. `restore-report-red/green.json`：每次运行的机器报告。

- 单条状态只有 `red`、`yellow`、`green`。
- RED 必须包含期望值、实际值、契约出处和实现定位。
- YELLOW 必须包含无法判定的原因及要求的补证方式。
- 汇总规则：有 RED 即 RED；无 RED 但有 YELLOW 即 YELLOW；全部规则已验证或命中冻结豁免才 GREEN。
- `alpha-tests.md` 保持唯一证据账本，只记录报告指纹、路径、摘要和可选截图，不复制第二本账。

## Implementation Changes

### 1. 设计事实与视觉缓存

扩展 [extract_design_spec.py](../../../skills/sdd-dev-frontend/scripts/extract_design_spec.py)，在现有 Markdown 产物之外生成稳定 JSON：

- 资源指纹按“文件内容哈希”计算；缺失资源以稳定的 missing 标记进入指纹。
- 重新格式化 HTML 不改变原型指纹；DOM、CSS、资源内容或缺失状态变化必须改变指纹。
- 视觉基线采用懒生成，只在存在 YELLOW 视觉项时截图。
- 缓存键固定为：原型指纹 + 区块锚点 + 视口 + DPR + 浏览器引擎/版本 + 字体指纹。
- 缓存写入 `<design-spec-dir>/visual-baseline/<fingerprint>/`，包含 PNG 和 `manifest.json`；命中时只读复用，失配时创建新版本，不覆盖旧版本。
- Story 证据引用缓存指纹和路径；实现侧视觉截图仍写入 Story 的 evidence 目录。

### 2. 三层检查能力

在 [SKILL.md](../../../skills/sdd-dev-frontend/SKILL.md) 中定义固定检查层级：

- 静态预检：扫描必需文案/i18n key、仓内 token、禁用字面量和状态选择器。静态通过不能替代 render-required 规则的 GREEN。
- 结构化渲染：在浏览器中注入只读采集脚本，读取 DOM、`getComputedStyle`、`getBoundingClientRect`、滚动尺寸和状态结果，不生成图片。
- 视觉补证：仅处理阴影观感、字体栅格、图片裁切、复杂叠层等无法结构化判定的规则。

默认容差：

- 文案、数量、顺序、token 和枚举值精确匹配。
- 颜色规范化后精确匹配。
- 尺寸、间距和对齐允许 ±1 CSS px。
- 横向溢出、裁切或重叠超过 1 CSS px 判 RED。
- 无法安全表达容差的规则标 YELLOW，不得自行扩大容差。

R1–R6 的默认检查映射：

- R1：DOM 存在性、数量、顺序和父子结构。
- R2：渲染文案与格式模板。
- R3：token 静态预检 + computed style/几何值。
- R4：状态选择器预检 + 实际触发后的计算样式。
- R5：明确状态 fixture 下的结构、文案和布局；造不出状态则 YELLOW。
- R6：指定视口下的滚动、重叠和裁切几何检查；纯源码检查不得判 GREEN。

不新增 Playwright 等仓内依赖；结构化采集使用现有浏览器能力和随 skill 保存的无依赖 JS 采集片段。

### 3. 还原轮六步改写

- Step ① RED：运行同一份冻结契约，生成 RED/YELLOW/GREEN 报告；至少一项 RED 才允许进入实现。
- Step ② 验 RED：核对 RED 的外部出处和实现定位；YELLOW 先走结构化补证，仍无法判定才使用缓存原型图。视觉发现偏差后转成明确 RED。
- Step ③ GREEN：只修复报告里的 RED 项。
- Step ④ 验 GREEN：重跑同一契约；无 RED、无未解决 YELLOW且回归未变差才 GREEN。
- Step ⑤ REFACTOR：重构后重跑同一检查。
- Step ⑥ 落账：写入 RED/GREEN 报告引用、契约哈希、视觉缓存指纹及可选截图。

特殊分支：

- 初次运行全部 GREEN：取消该还原轮并记录原因。
- 初次只有 YELLOW：先补证；发现偏差才转 RED，无偏差则取消还原轮。
- 页面无法启动：只执行静态支持项；R6 和依赖级联/字体/实际状态的规则保持 YELLOW，不能伪装成视觉 GREEN。现有降级收口只能声明未验证维度。
- 已有 Story 没有 JSON 契约：继续支持旧截图流程，不要求迁移历史证据。

### 4. 文档与决策记录

- 新增 ADR，记录“外部设计契约成为主要失败证据，截图退为选择性观察手段”；保留 ADR-0001 的历史理由并补交叉引用。
- 同步更新差异清单、QA 基线、`alpha-tests.md` 证据格式及使用说明；差异清单改为机器报告的人类摘要，不再要求固定的 RED 双方截图。
- Phase C 布局检视暂不重构，本次只改 Phase B 还原轮；后续可独立评估是否复用结构化采集能力。

## Test Plan

在现有两份原型 fixture 上扩展 [test_extract_design_spec.py](../../../skills/sdd-dev-frontend/evals/test_extract_design_spec.py)：

- 相同 DOM/CSS、资源、区块、视口和环境稳定命中缓存。
- 只改变空白格式不失效；改变 HTML、CSS、资源内容、缺失状态、视口、DPR、浏览器或字体任一项必须失效。
- R1/R2 精确差异、R3 ±1px 容差、R4 状态变化、R5 fixture 缺失、R6 溢出/重叠分别产生预期颜色。
- 有 RED 时汇总为 RED；仅 YELLOW 时不得 GREEN；全部通过或命中冻结豁免才 GREEN。
- 静态通过但结构化渲染失败时以 RED 为最终结果。
- 无截图能力不影响机器可检项；无页面能力时 render-required 项保持 YELLOW。
- `dev-baseline.md` 与契约哈希不一致时硬失败。
- 旧版还原证据仍可读取，既有抽取指标与缓存行为不退化。

按 `refine-skill` 补充全量评测用例：

- 新增“机器可检项目不截图”“YELLOW 不得冒充 GREEN”“资源变化使视觉缓存失效”等失败用例。
- 保留“冻结基线不可放宽”“外部基线不可由实现反推”等既有正确行为。
- 改写后用无本会话记忆的干净 agent 全量重放，每个用例三次取多数；新用例通过且旧用例无退化才完成。

## Assumptions

- 默认采用可执行闭环方案，因为仅改文档不能消除主观截图判断。
- 首版不做像素级自动 diff；截图仍由视觉检查处理机器盲区。
- 原型视觉缓存是 Requirement 级事实，实现报告和实现截图是 Story 级证据。
- `dev-baseline.md` 与 R1–R6 仍是唯一判定标准，不新增维度。
- 当前工作树已有多份未提交修改；实施前先读取相关 diff，所有改动基于现状增量合并，不覆盖或回退用户修改。
