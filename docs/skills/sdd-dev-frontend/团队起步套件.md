# 团队起步套件：没有 sdd-task / sdd-design 时如何用起 sdd-dev-frontend

> 本文是项目级维护与使用说明，不属于 Skill 运行时上下文。运行时行为以 [`SKILL.md`](../../../skills/sdd-dev-frontend/SKILL.md) 为准——`tasks.md` 缺失时的自动起草分支已经写进 `SKILL.md` Phase 0 第 2 步，是 `sdd-dev-frontend` 自己的能力，不需要专门念一句触发语。

## 这份文档解决什么问题

`sdd-dev-frontend` 被设计成一条流水线里的一环：它假定 `sdd-design`、`sdd-task` 已经跑过，`tasks.md`、`alpha-tests.md`、`story-delta-frontend-design.md` 已经摆在那里。但这两个上游阶段**不在本仓库里**——如果你的团队还没有一套产出这三份文件的流程，你会在第一步就被 [硬门禁 1](../../../skills/sdd-dev-frontend/SKILL.md#硬门禁)「没有 `tasks.md` 不准开工」挡住。

`tasks.md` 缺失时有两条路，都能满足硬门禁 1，只是发生的时机不同：

| | 什么时候用 | 谁做、什么时候做 |
| --- | --- | --- |
| **让 skill 自动起草** | 需求已经在当前对话里聊清楚了，不想额外准备文件 | 你直接调用 `sdd-dev-frontend`；Phase 0 第 2 步自己发现 `tasks.md` 不存在，判断会话内容够不够，够就当场起草并过一轮确认门，不够就先按 P7 问缺口。**不需要专门的触发语**，这是 Phase 0 的默认分支，见 [SKILL.md](../../../skills/sdd-dev-frontend/SKILL.md#phase-0--需求执行起点) |
| **自己先手写** | 想在调用 skill 之前就把文件准备好（比如离线整理、多人过一遍再定稿） | 你照本文末尾的模板写完，放进 `<story-dir>`，再调用 `sdd-dev-frontend`；这时 `tasks.md` 已存在，Phase 0 直接跳过起草分支 |

两条路产出的文件形态完全一样，`sdd-dev-frontend` 分不出、也不关心是谁写的、什么时候写的。

**它不能替代什么**：不产出真正的设计评审、不做多人协作的任务拆解、不解决多 Story / 多仓协调。团队规模变大、Story 变复杂之后，应该换回正式的 `sdd-design` / `sdd-task`（见本文末尾「什么时候该换回正规上游」）。

## 你到底需要几份文件

| 文件 | 谁读它 | 从哪来 |
| --- | --- | --- |
| `tasks.md` | `sdd-dev-frontend` 唯一执行清单 | 你写，或 Phase 0 自动起草（模板见 [story-artifact-templates.md](../../../skills/sdd-dev-frontend/references/story-artifact-templates.md) 第三节） |
| `alpha-tests.md` | 证据账本 | 你写空骨架，或随 `tasks.md` 一并自动起草；执行过程中 skill 自动扩容 |
| `story-delta-frontend-design.md` | 提供还原基线的文字规格 / 对接模式 | 同 `tasks.md` |
| `dev-baseline.md` / `restore-contract.json` / `dev-review.md` 等 | Phase A2 之后的全部产物 | **skill 生成**，你不用管 |

`requirement-frontend-design.md`（跨 Story 的前端总案）不是硬性前置——[何时使用与前置条件](../../../skills/sdd-dev-frontend/SKILL.md#何时使用与前置条件) 里它是「否，缺失时记为已知缺口」，第一次试跑可以先不管它。

## 五步上手清单（走自动起草路径）

1. **装插件**。按仓库根目录 [README](../../../README.md#安装) 的一键脚本或 `npx skills add` 安装。
2. **选一个足够小的 Story 练手**。建议：单页面、无跨页状态、3～5 条 AC、不需要新增跨页公共组件。第一次不要挑「整站改版」这种量级。
3. **在对话里把需求聊清楚**：目标页面/组件、AC、还原基线（HTML 原型 / 参照页 / 文字规格三档之一）、对接模式（完整对接 / 静态实现）。这四项就是 Phase 0 判断「能不能自动起草」的依据，聊得越具体，起草稿里「未定义」就越少。
4. **直接调用**，不需要提前准备文件：

   ```text
   请使用 sdd-dev-frontend 执行 <Story 名>。

   目标前端仓：<repo-root>
   Story 目录：<story-dir>
   还没有 tasks.md，请按我们刚才聊的内容自动起草，起草完先给我确认。
   ```

   `sdd-dev-frontend` 不会自动触发（`disable-model-invocation: true`），必须像上面这样明确点名。`<story-dir>` 下没有 `tasks.md` 时，Phase 0 第 2 步会自动判断能不能起草：够就起草并单独一轮请你确认，不够就先问清楚缺什么，都不需要你额外说什么触发语。
5. **确认起草稿**：Phase 0 会把起草的 `tasks.md`（以及缺失的 `alpha-tests.md` / `story-delta-frontend-design.md`）全文贴出来，确认或指出要改的地方；确认后自动落盘，流程接着往下走。

想先手写再调用，见下面「三份产物的最小模板」——两条路殊途同归。

## 三份产物的最小模板

Phase 0 自动起草直接复用 [sdd-task-frontend 模板](../../../skills/sdd-task-frontend/templates/tasks-frontend.md)，还原 / 逻辑切分和六步证据意图只在 [前端 SDD 执行契约](../frontend-sdd/执行契约.md) 定义一次。

三份分别是：`tasks.md`（计划头、项目边界、文件结构、Story / AC 追溯表、执行规则、Task List、计划自审三查、风险与回滚）、`alpha-tests.md`（空骨架，执行中自动扩容）、`story-delta-frontend-design.md`（无 HTML 原型时必写的文字规格）。手写时没聊清楚 / 拿不准的字段一律写「未定义」，不要编——这条规则手写和自动起草共用。

## 常见坑

| 坑 | 后果 | 怎么躲 |
| --- | --- | --- |
| Step ① 没标「还原」还是「逻辑」 | 执行侧默认按逻辑类处理，还原工作被要求写 DOM 断言测试，退化成橡皮图章测试 | 模板已经把形态写死在每个 Task 标题和 Step ① 前缀里，照抄 |
| 逻辑 Task 的文件清单里混了样式文件 | 触发「越界改样式」升级，或让前面的还原 GREEN 报告失效却没人发现 | 严格按模板「文件结构」表分类，逻辑 Task 清单不出现 `.css` / `.module.css` |
| 文字规格里写了「示例文案」当固定文案 | R2 文案一致性期望值被污染，检视阶段报出偏差却查不到源头 | 拿不准是不是固定文案就写「未定义」，不要编 |
| 一个 Story 塞太多页面 | Phase A2 确认门内容爆炸，QA 基线难以在一轮确认清楚 | 第一次练手只选一个页面 |
| 没写「已知缺口」就指望 skill 帮你补 | 确认门会因缺口太多而被打断反复补问 | 响应式、hover/focus 这类维度没有基线时，直接在文字规格里写「未定义」，skill 会自动登记进「已知缺口」 |
| 指望自动起草把没聊到的字段补成具体数值 | 「基线必须来自事实」的前提被破坏，QA 基线确认门看起来通过了，实际确认的是编出来的东西 | Phase 0 的起草分支已经把这条写成硬规则：没聊到就写「未定义 / 待确认」，交给起草确认门和 Phase A2 的 QA 基线确认门处理，不替用户拍板 |
| 需求本身还没聊清楚就想让 skill 起草 | Phase 0 会拒绝起草或问一堆缺口，看起来像卡住了 | 状态样式、异常分支这些先在对话里聊过一遍再调用；一个 Requirement 下有多个 Story 需要跨 Story 对齐时，Phase 0 也会拒绝起草，直接改用 `sdd-task` |

## 什么时候该换回正规上游

出现以下任一情况时，说明手写 / 自动起草模式的成本已经超过引入 `sdd-design` / `sdd-task`（或团队内等价的设计评审 + 任务拆解流程）的成本：

- 一个 Requirement 下有多个 Story，需要跨 Story 复用组件与设计决策；
- 需要多人并行写 `tasks.md`，且需要评审对齐颗粒度；
- 需要正式的设计稿（HTML 原型）而不是文字规格；
- 需要把 AC 拆解、测试设计留痕给测试 / PM 复核，而不只是团队内部对齐。
