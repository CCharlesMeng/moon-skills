# 团队起步套件：没有 sdd-task / sdd-design 时如何用起 sdd-dev-frontend

> 本文是项目级维护与使用说明，不属于 Skill 运行时上下文。运行时行为以 [`SKILL.md`](../../../skills/sdd-dev-frontend/SKILL.md) 为准。

## 这份文档解决什么问题

`sdd-dev-frontend` 被设计成一条流水线里的一环：它假定 `sdd-design`、`sdd-task` 已经跑过，`tasks.md`、`alpha-tests.md`、`story-delta-frontend-design.md` 已经摆在那里。但这两个上游阶段**不在本仓库里**——如果你的团队还没有一套产出这三份文件的流程，你会在第一步就被 [硬门禁 1](../../../skills/sdd-dev-frontend/SKILL.md#硬门禁)「没有 `tasks.md` 不准开工」挡住。

这份套件给你一条更便宜的路：**手写一份最小但合规的 `tasks.md` / `alpha-tests.md` / `story-delta-frontend-design.md`**，跳过完整的设计评审与任务拆解工具，用最小成本跑通第一个 Story，验证这套流程是否值得在团队里推广。

**它不能替代什么**：不产出真正的设计评审、不做多人协作的任务拆解、不解决多 Story / 多仓协调。团队规模变大、Story 变复杂之后，应该换回正式的 `sdd-design` / `sdd-task`（见本文末尾「什么时候该换回正规上游」）。

## 你到底需要几份文件

| 文件 | 谁读它 | 团队自己写，还是 skill 生成 |
| --- | --- | --- |
| `tasks.md` | `sdd-dev-frontend` 唯一执行清单 | **你写**（本文给模板） |
| `alpha-tests.md` | 证据账本 | **你写空骨架**，执行过程中 skill 自动扩容 |
| `story-delta-frontend-design.md` | 提供还原基线的文字规格 / 对接模式 | **你写**（本文给模板） |
| `dev-baseline.md` / `restore-contract.json` / `dev-review.md` 等 | Phase A2 之后的全部产物 | **skill 生成**，你不用手写 |

`requirement-frontend-design.md`（跨 Story 的前端总案）不是硬性前置——[何时使用与前置条件](../../../skills/sdd-dev-frontend/SKILL.md#何时使用与前置条件) 里它是「否，缺失时记为已知缺口」，第一次试跑可以先不管它。

## 五步上手清单

1. **装插件**。按仓库根目录 [README](../../../README.md#安装) 的一键脚本或 `npx skills add` 安装。
2. **选一个足够小的 Story 练手**。建议：单页面、无跨页状态、3～5 条 AC、不需要新增跨页公共组件。第一次不要挑「整站改版」这种量级。
3. **选还原基线**：没有 HTML 原型时，直接用「文字规格」档最省事——不需要设计师配合，缺点是证据可信度会降级（[基线源](../../../skills/sdd-dev-frontend/SKILL.md#基线源没有-html-原型时)第 3 档）。有现成的同类页面时，可以让 skill 在 Phase A2 帮你找参照页，可信度比文字规格高。
4. **照下面的模板手写三份文件**，放进 `<story-dir>`（建议目录布局见 [README「典型目录布局」](./README.md#产物之间如何交接)）。
5. **正式调用**：

   ```text
   请使用 sdd-dev-frontend 执行 <Story 名>。

   目标前端仓：<repo-root>
   Story 目录：<story-dir>
   本 Story 没有 HTML 原型，按 story-delta-frontend-design.md 的文字规格和仓内 token 执行，
   并在 QA 基线确认门里显式标记基线源降级。
   ```

   `sdd-dev-frontend` 不会自动触发（`disable-model-invocation: true`），必须像上面这样明确点名。

## 三份产物的最小模板

模板已经把 [`sdd-task-amendments.md`](../../../skills/sdd-dev-frontend/references/sdd-task-amendments.md)（失败证据两形态）与 [`sdd-task-frontend-split.md`](../../../skills/sdd-dev-frontend/references/sdd-task-frontend-split.md)（还原 / 逻辑按形态切分）里要求上游做到的写法直接落进去，照抄即可，不需要你重新理解那两份文档的推导过程。

### 模板一 · `tasks.md`

```markdown
# Tasks — <Story 编号 · 名称>

## 计划头

| 字段 | 值 |
| --- | --- |
| Goal | <一句话说清这个 Story 要交付什么> |
| Architecture | <2-3 句：涉及哪些页面/组件、对接哪个接口、静态实现还是完整对接> |
| Tech Stack | <框架 + 语言 + 样式方案，如 React + TS + Vite + CSS Modules> |
| project | <repo-root 的路径或名称> |
| project_type | frontend |
| 归属 Story | <Story 编号 · 名称> |
| frontend_design_path | <story-delta-frontend-design.md 的路径> |

## 项目边界

- 范围内：<本 Story 要改的页面 / 模块>
- 范围外：<明确排除的相邻功能，避免顺手扩大范围>
- 本仓类型：frontend，禁止跨仓任务

## 文件结构

| 文件 | 类型 | 单一职责 |
| --- | --- | --- |
| `<path>` | 样式（还原 Task 专属） | <一句话> |
| `<path>` | 逻辑 / 取数 | <一句话> |
| `<path>` | 测试 | <一句话> |

## Story / AC 追溯表

| AC 锚点 | 覆盖 Task |
| --- | --- |
| AC-x.1 | T1 |
| AC-x.2 | T2 |

## 执行规则

**TDD Iron Law**：没有失败证据就不写实现。失败证据有两种形态：

- **逻辑类工作**：失败的单元测试或单接口集成测试。
- **前端还原类工作**：运行已冻结的外部设计契约；机器报告至少一项明确 RED 才进入实现，无 RED、无 YELLOW 才是 GREEN。

除这两种形态之外，没有失败证据不写实现。

**No Placeholders 铁规**：禁止 TBD / TODO / "类似任务 N" / 无代码步骤。

每步 2-5 分钟一个动作，「写失败证据」和「运行确认失败」是两步，不可合并。**一个 Task 内允许出现多轮 6 步**：还原与逻辑各走一轮，顺序固定为先还原轮、后逻辑轮，每轮独立编号并标注形态。

## Task List

### T1 · <页面名> · 还原

文件清单（样式与骨架，本 Task 独占，逻辑 Task 不得再列样式文件）：

- `<path>`
- `<path>`

区块与原型来源（没有 HTML 原型时写清楚基线出处）：

- <区块名>：基线源「文字规格」，见 `story-delta-frontend-design.md` 对应小节

6 步（形态：还原）：

- [ ] ① RED（还原）—— 运行冻结契约，生成 RED / YELLOW / GREEN 报告；至少一项明确 RED 才进入实现
- [ ] ② 验 RED —— 核对 RED 的外部出处与实现定位
- [ ] ③ GREEN —— 只修报告里的 RED
- [ ] ④ 验 GREEN —— 重跑同一契约，无 RED、无 YELLOW
- [ ] ⑤ REFACTOR —— 按需
- [ ] ⑥ 记录证据并提交

### T2 · <功能名> · 逻辑（AC-x.2）

文件清单（不含样式文件）：

- `<path>`

6 步（形态：逻辑）：

- [ ] ① RED（逻辑）—— 写失败的单元测试或接口集成测试，给出完整代码
- [ ] ② 验 RED —— 运行测试，确认按预期失败
- [ ] ③ GREEN —— 最小实现让测试转绿
- [ ] ④ 验 GREEN —— 测试转绿 + 全量回归
- [ ] ⑤ REFACTOR —— 按需
- [ ] ⑥ 记录证据并提交

## 计划自审三查

- [ ] AC 覆盖：Story / AC 追溯表中每条 AC 都有 Task 覆盖
- [ ] 占位符扫描：全文无 TBD / TODO / "类似任务 N"
- [ ] 类型一致性：涉及的接口字段类型与 `story-delta-frontend-design.md` 一致
- [ ] 前端行另查 1：组件树 / 界面清单是否已烘焙（首个 Story 可写「无，暂无复用组件」）
- [ ] 前端行另查 2：每个前端 Task 的每一轮 6 步，Step ① 是否明确标注了失败证据形态
- [ ] 前端行另查 3：每个页面的样式是否集中在一个还原 Task 内；逻辑 Task 文件清单是否不含样式文件
- [ ] 前端行另查 4：有无「样式微调」「统一优化」这类没有原型对照范围的 Task

## 风险与回滚

- 关键假设：<...>
- 失败路径：<...>
- 回滚策略：<...>
```

### 模板三 · `story-delta-frontend-design.md`

```markdown
# Story 增量设计 — <Story 编号 · 名称>

## 目标与 AC 引用

- 目标：<一句话>
- AC：AC-x.1, AC-x.2 ...（与 `tasks.md` 的 Story / AC 追溯表一致）

## 对接模式

- <完整对接模式 / 静态实现模式，二选一，写明理由；缺省时 sdd-dev-frontend 会把它记为已知缺口>

## 文字规格（无 HTML 原型时必填）

按区块列出，每个区块至少覆盖：

- 布局结构（自上而下 / 自左向右有几个子节点）
- 文案（逐字，不要用「示例文案」代替）
- 间距、对齐、圆角、边框（能对齐仓内 token 就直接写 token 名，不要发明数值）
- 状态样式：hover / focus / disabled / 选中 / loading（没有就写「未定义」，不要编）
- 空态与边界内容（字段缺失、超长文案怎么显示）
- 响应式要求（没有就写「未定义，仅承诺不破：无横向滚动、无重叠、无内容截断」）

## 当前代码事实

- 复用的既有组件 / 方法：<...>
- 变更边界：<明确不动的文件 / 模块>

## 状态、交互、接口与数据映射

| 接口 | 请求参数 | 字段映射 | 错误码处理 |
| --- | --- | --- | --- |

## 风险与依赖

- <...>
```

## 常见坑

| 坑 | 后果 | 怎么躲 |
| --- | --- | --- |
| Step ① 没标「还原」还是「逻辑」 | 执行侧默认按逻辑类处理，还原工作被要求写 DOM 断言测试，退化成橡皮图章测试 | 模板已经把形态写死在每个 Task 标题和 Step ① 前缀里，照抄 |
| 逻辑 Task 的文件清单里混了样式文件 | 触发「越界改样式」升级，或让前面的还原 GREEN 报告失效却没人发现 | 严格按模板「文件结构」表分类，逻辑 Task 清单不出现 `.css` / `.module.css` |
| 文字规格里写了「示例文案」当固定文案 | R2 文案一致性期望值被污染，检视阶段报出偏差却查不到源头 | 拿不准是不是固定文案就写「未定义」，不要编 |
| 一个 Story 塞太多页面 | Phase A2 确认门内容爆炸，QA 基线难以在一轮确认清楚 | 第一次练手只选一个页面 |
| 没写「已知缺口」就指望 skill 帮你补 | 确认门会因缺口太多而被打断反复补问 | 响应式、hover/focus 这类维度没有基线时，直接在文字规格里写「未定义」，skill 会自动登记进「已知缺口」 |

## 什么时候该换回正规上游

出现以下任一情况时，说明手写模式的成本已经超过引入 `sdd-design` / `sdd-task`（或团队内等价的设计评审 + 任务拆解流程）的成本：

- 一个 Requirement 下有多个 Story，需要跨 Story 复用组件与设计决策；
- 需要多人并行写 `tasks.md`，且需要评审对齐颗粒度；
- 需要正式的设计稿（HTML 原型）而不是文字规格；
- 需要把 AC 拆解、测试设计留痕给测试 / PM 复核，而不只是团队内部对齐。
