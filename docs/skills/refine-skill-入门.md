# refine-skill 入门

你刚调试完一个自己维护的 skill，过程中纠正了它好几次。这个工具把那些纠正变成对 skill 的改写，并配上回归测试，防止改好的东西以后又坏回去。

它的前提很硬：**手上要有证据。** 凭印象说「它老是出错」无法归因。

> 如果你是在用别人维护的 skill、只想复盘这轮会话，那是另一个工具的活，见 [session-optimize 入门](session-optimize-入门.md)。

---

## 核心理念：修假设，不是打补丁

一个 skill 不是操作清单，而是**一组关于「这类任务该怎么做」的假设**。

你每次纠正它，都是现实在反驳其中某一条假设。所以第一反应不该是「该加哪句话」，而是「skill 当时让 agent 相信了什么，它才这么做」。

散落的五个错，往往是同一条错误假设的五种表现。找到那一条，**改一处胜过补五处**。

这也解释了为什么它经常建议**删**而不是**加**。默认往上加步骤，通常是错的方向——好的改写往往让 skill 更短或持平。

---

## 什么时候调用

- 刚用某个 skill 跑完任务，过程中纠正了它好几次
- 某个 skill 反复在同一类事情上出错，想找根本原因
- 收到别人交来的移交证据包，由你作为维护者复盘
- 想给 skill 补回归测试

**不适用**：从零创建新 skill（那是 `create-skill` 的活）；想复盘别的会话但拿不出证据——让当事人先按 `session-optimize` 的移交格式交一份证据包。

## 怎么调用

最简单的形式，在**调试过它的那个会话末尾**：

```text
/refine-skill hocb-monitor
```

把你注意到的一并交代，归因会更准：

```text
/refine-skill research

补充两点：一是它把报告写成了英文，我要的是中文；二是引用的两个来源
其实是二手转述，不是我要求的一手来源。第一点可能是我没说清楚，
第二点我觉得是它自己判断有问题，你分析看看。
```

只要分析、先别动文件：

```text
复盘一下本次 tdd skill 的执行：把所有被我纠正的内容逐条列出来，
判断每条是信息不足还是判断错误，用表格给出处置建议。
先不要改任何文件，等我确认。
```

怀疑是偶发、不想改规则：

```text
/refine-skill diagnose

刚才那个 JSON 写成 YAML 的错，我怀疑是模型抽风不是 skill 的问题。
如果是偶然就只记入 evals 观察，别加规则。
```

## 五步流程

1. **收集证据** —— 逐条记 `触发情境 → 错误行为 → 你想要的正确行为`，并逐字通读目标 skill 全目录。这两件事它自己做，不委派——摘要会把关键信号弄丢。
2. **判断** —— 六条判据依次过（下一节详说）。
3. **和你确认** —— 归因表格 + 改前/改后对照 + 预先写好的测试断言。**确认后才动文件。**
4. **改写**
5. **回归验证** —— 换一个干净会话重放全套用例。

---

## 六条判据

这是这个工具真正的价值所在。每一条都是一个先于「怎么改」的问题。

**一、先归因：信息不足，还是判断错误。**

问一句：当时把该给的信息都给了，agent 还会犯这个错吗？

- **判断错误**（信息充分但推理错了）—— 这才是对 skill 假设的反驳，往下走。
- **信息不足** —— 再分边界：属于 skill 职责内该声明的输入，改法是补输入契约而不是加规则；属于本次任务特有的背景，不动 skill，记成给你的「下次指令建议」。
- **风格、详略、交互方式** —— 两边都不沾，走判据四按「默认设定」处理。

**二、找那条被反驳的假设。** 先别问「该加哪句话」。

**三、系统性还是一次性偶然。** 偶然（模型抽风、罕见输入、外部故障）不动规则，只把情境追加进 `evals/` 观察。只有系统性失败才值得改规则。

判系统性的依据不是凑够某个次数，而是「只此一次的巧合」这个疑虑还成不成立。**同一个键在另一个会话或另一个仓库再次出现，第 2 次就够了**——继续累加只用于排优先级。

**四、太紧还是太松。** 系统性错误只来自两个方向：skill 管太死把 agent 逼上错路，或该替它定的没定、放任它瞎猜。先答这个，再决定收紧、放宽还是删除。

**五、委派结构。** 主 agent 的上下文是整个系统里最贵的资源，但委派也要付费。三个错误方向：

- **该拆没拆** —— 主 agent 亲自做摘要无损的重活（批量重试、机械比对、按固定判据打分）
- **不该拆拆了** —— 依赖逐字原文的判断被派出去，结论建立在有损摘要上
- **拆错了地方** —— 切分线落在强依赖处，子代理之间反复同步或产出要重做一遍才能合并

还有一种不显眼的：同模型同提示的 N 个子代理给出同一答案，是一次共模，不是 N 票佐证。

**六、用更短换更对。** 想加步骤时停一下：有没有一条原则能让 agent 自己推出它？删掉 agent 本就会的指令，和新增一样是改进。

---

## 为什么断言先于改写

第三步会把测试用例和断言一起交给你，**早于改写**。

这不是流程洁癖。先改写再补断言，等于让被裁判的人事后挑裁判指标——写出来的断言总会说改稿已经做到的那件事，测多少条都恒过。

断言只从第一步那条 `触发情境 → 错误行为 → 正确行为` 推出来，描述期望的行为，**不引用改稿的任何措辞**。断言里出现改稿的原句或专有词，就是它在测文本而不是测行为的信号。

如果断言定稿后还要改，说明改写偏离了当初判定的问题，它会把理由一并说清。

---

## 回归验证的三个陷阱

**不要在写出改法的这个会话里验证。** agent 已经知道答案，等于拿训练集当测试集。要换一个不带本次对话记忆的干净子代理。

**3 次取多数排不掉共模。** 它只能排除抽样噪声。skill 文本里那种这个模型会系统性误读的措辞，3 次会一起读错、一起过或一起挂。想让结论更稳，是**换一个模型档位或换一种情境措辞**，不是把 3 次加到 5 次。

**挂法本身在指改法。** 3 次以同一种方式挂，是文本的确定性缺陷，照着改；3 次挂法各不相同，是措辞有歧义，该补的是明确性而不是规则。

通过线两条：新用例不再复发，**旧用例仍然全过**。旧用例退化才是「质量下降」的真正来源，通常意味着收太紧，往回退再验。

## 它会写哪些文件

| 文件 | 是什么 |
| --- | --- |
| 目标 skill 的 `SKILL.md` / `references/` | 改写结果（经你确认后） |
| 目标 skill 的 `evals/evals.json` | 回归测试集 |
| 源仓 `.learnings/skills/<skill-name>.md` | 缺陷台账 |

**不写 CHANGELOG。** evals 是测试集，台账是复发计数器，git 历史是变更记录，各归其位。

### 台账为什么在源仓，不在 skill 目录里

因为 skill 有两种部署形态：符号链接到源仓（一份共享），或实体副本（N 份各自分叉）。

放在 skill 目录内，实体副本那条路会把台账复制进每个消费仓库，在那里分叉、被提交进别人的代码库，还把「这个 skill 老在哪出错」的内部记录一起带走，下次同步又被覆盖。

放在源仓的 `.learnings/skills/` 下，它在 `skills/` 之外，永远不会被带出去，而计数天然汇总——这正是它要解决的问题：**同一个缺陷在 3 个仓库各出现 1 次，只有一个跨仓库的计数器能看出它已经复发 3 次。**

### 即使判为偶然也要记账

否则下一次仍然从 n=1 开始，判据三永远升不上去。

`Status` 有五个取值：`pending`（已记账未处置）、`observing`（判为偶然，只入 evals）、`fixed`（已改写并验证通过）、`wont-fix`、`stale-copy`（报告来自陈旧副本，上游已修）。

**已经 `fixed` 的条目又复发时，不新建条目**，而是改回 `pending` 并 +1，注明「改写后仍复发」。这是改法无效的直接信号，比一条新条目有价值得多——它说明上次找的假设找错了，回判据二重找。

## 收别人交来的反馈

使用者跑 `session-optimize` 发现你维护的 skill 有问题时，会产出一份证据包。你跑 `refine-skill` 时从三条路径收：

| 路径 | 在哪 |
| --- | --- |
| 当前仓 | `<当前仓>/.learnings/skill-feedback/` |
| 用户级 | `~/.learnings/skill-feedback/` |
| 平台 | 由部署方的投递配置声明 |

没有投递配置就只收前两条，收口时会说明是「没找到配置」还是「这个 skill 不在白名单里」——前者是故障，补回配置就恢复；后者是部署方的选择。

### 拿到证据包先做两件事

**核证据够不够。** 对着六条判据要的输入清点：当时 agent 手上有什么、错误行为是原样还是概括、这是第几次、能不能指到 skill 里被遵循的那句、用没用子代理。缺哪条就点名向移交人索取，**不靠猜补**——猜出来的「当时信息充分」会把归因直接推向「加一条规则」，那是默认的错误方向。

**确认缺陷现在还在。** 移交人跑的可能是陈旧副本，报的问题上游早已修好。已经修了就不改 skill，回复在哪个提交修的、请他同步副本，这次记成 `stale-copy` 而不是 skill 缺陷。

### 移交包里带了改法建议怎么办

**不拿它当起点。** 那是使用者在没有 skill 全文的位置上得出的结论，采纳它等于跳过归因。仍从判据一走。

### 收件的边界

只读、评论、打 `consumed` label，**不关闭平台上的记录**。关掉等于把计数依据藏进另一个列表。

去重完全靠台账：收件前查 `来源` 里有没有这个包的标识，命中就跳过。**一个包计一次**——同一个键下的 N 个包来自 N 个会话，那正是判据三要的第 N 个数据点，合成 1 次等于把系统性判据废掉。

---

## 容易踩的坑

**别在没有证据的会话里调用。** 第一条判据就答不上来，后面全是猜。

**别期待它把每个错都改掉。** 判为偶然的只进 evals 观察，判为「你没说清」的转成下次指令建议，判为偏好的可能只改默认设定而不写成规则。真正落进 `SKILL.md` 的是那条被反驳的假设。

**改写触及自由度刻度时要小步走。** 收紧和放宽的影响面都很大，改完多观察几次真实使用。

**evals 会自己发福。** 总量控制在 10 条左右，加新用例时顺手修剪已失效的情境。

```text
# 在调试过它的那个会话末尾复盘并改写
/refine-skill <skill-name>

# 只要归因分析，先别动文件
复盘一下本次 <skill-name> 的执行，逐条列出被我纠正的内容，
判断每条是信息不足还是判断错误，给出处置建议。先不要改任何文件。

# 怀疑是偶发
/refine-skill <skill-name>
刚才那个错我怀疑是模型抽风。如果判定为偶然就只记入 evals 观察，别加规则。

# 处理别人交来的证据包
/refine-skill <skill-name>
（粘贴完整证据包）
```
