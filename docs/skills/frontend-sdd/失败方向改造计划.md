# 失败方向改造计划

## Summary

`sdd-dev-frontend` 的判据归属已经收紧到机械可判。这一轮修的是另一条轴：**机制出错时往哪边倒**。

现存四处失效的失败方向是假阴性——出问题时它们静默地放行，而不是报错：

- 检视回传的三个出口成本倒挂，最便宜的那个不留痕、不降级；
- 验证组合的收窄是免费且不可见的；
- 角色判断没有失效键，但收口文档已经承诺按键失效；
- Task 末步两次写入不是原子的，续跑没有裁决规则。

四项都能靠确定性校验封住，**skill 正文净增约 4 行**。

第五处嫌疑——起点缓存的手动版本号——核查后是健全的，理由记在「不做与待定」，避免下次有人再当缺陷修一遍。

四项已落地，实际净增 6 行、六道门全部通过变异测试；与本计划的偏差记在末节「落地记录」。

本计划只描述改造，不改动代码。

## 判则：写在哪里

| 内容 | 载体 |
| --- | --- |
| 调用哪个脚本、输出怎么分流、无法机械判定的顺序约束 | skill 正文 |
| 判据实现、拒绝路径、错误文案 | `scripts/` |
| 代价对比、为什么不选另一种做法、被否决的方案 | 本文件 |

**能由脚本判的，不写进 skill 正文。** 一条确定性校验换掉的是散文规则，不是叠加在散文规则之上——落地时同步删掉被它取代的那句提示词纪律。每项改造都给出 skill 侧净增行数，超出预算就说明判据没有真正下沉到脚本。

## 现状偏差

### 1. 三个出口的成本倒挂

`manage_review_pipeline.py` 对同一份 `RoleResult` 的三种维度结论要求不同：

| 出口 | 校验要求 | 对声明的后果 |
| --- | --- | --- |
| `unrun` | 必须有 `known_gaps` | 依赖声明降 `UNVERIFIED` |
| `clear` | `evidence_ids` 只需是 list，**空数组通过** | 声明可升 `PROVEN` |
| `skipped` | 只需一段**自由文本** `reason` | 维度从会计消失，不影响任何声明 |

诚实落在最贵的一端。一个判不了 C4 的角色写 `{"dimension": "C4", "reason": "本 Story 未触碰请求封装"}` 即可交差，与正当使用无法区分——而 `skip_when` 条件全是「diff 不涉及 X」形态的**可判事实**，主 agent 手里就有 diff。

`review-request.md` 硬约束 3 写了「`skipped` 只记被分配后才发现不适用的那些」，没有任何东西验证它。

### 2. 组合收窄免费且不可见

`validation-policy.md` 第二节：未列出的角色或维度不是「未执行」，也不生成占位结果。

于是漏标一个 `shared-boundary` 会让对应角色静默消失——没有 `known_gaps`、没有 `UNVERIFIED`，声明照常收成 `PROVEN`。而 `assigned_dimensions` 由写代码的同一个 agent 从它自己的 diff 算出。

`review-request.md` 刻意不设级别覆盖字段，理由是「开一个覆盖入口等于把定级搬回调用方，还顺带给了悄悄降级的口子」。同一条论证一字不改地适用于 `assigned_dimensions`：去掉一个维度与把它的 finding 定成 P3 效果等价，但更便宜、更不可见。贵的那条路已封，免费的那条还开着。

### 3. 角色判断没有失效键

`phase-review-closeout.md` Phase D 第 2 条要求「按 `depends_on` 失效命中的命令、场景、**角色判断**和声明」。

但 `RoleResult` 只有一个全局 `code_fingerprint`，`merge_evidence_additions` 对不匹配直接抛错。角色判断没有文件级键，这条承诺无法执行。实际结果是：Phase D 改一行 CSS，五份判断在契约上整体作废，存活与否退回主 agent 自由裁量且不留痕。

不对称还是反的：机器还原报告的重跑便宜、可随时重来；角色判断贵，却只能全丢。

### 4. 末步两次写入不是原子的

`phase-implementation.md` 第五节的末步是「回填账本 + 勾 checkbox」两次写入。中途断掉会留下两个真相源不一致，而续跑规则只说「以 checkbox 定实现进度、以账本定声明状态」——它假设两者各自可信，没有给不一致时的裁决。

## 改造项

### 一、diff 分类器：下限的唯一来源

新建 `scripts/classify_diff.py`。输入 `<base-ref>` 与工作区，输出两组机械事实：

- **`risk_triggers` 下限**：按路径与文件类型判定的 `visual` / `navigation` / `shared-boundary` / `build-config`。需要语义判断的 token（`async-state`、`spec-gap`、`unknown-deps`）不产出，仍由主 agent 声明。
- **`skip_when` 类别命中表**：逐条给出 diff 是否触碰该类别（新增/重命名文件、样式或 token、请求或错误映射、类型声明或检查抑制……），键用 checklist item 的 slug。

一个脚本、两个消费者（改造项二、三），下限语义只有一份。

**主 agent 只能在下限之上扩，不能在下限之下缩。** 确有理由收窄时写进 `validation_portfolio.portfolio_narrowed[]`（维度、理由、diff 事实），聚合器把它渲进 `acceptance.md`。收窄从不可见变成必须署名。

- skill 侧：`validation-policy.md` 第三节加 1 行（下限来源与只能扩），`review-evidence.md` 的 `validation_portfolio` 示例加 1 个字段。**净增 2 行。**
- 本文件承载：为什么给下限而不是给全量、为什么调用方不能收窄。

### 二、三个出口成本对齐

`clear` 与 `skipped` 各加一道确定性校验，`unrun` 不变：

| 出口 | 新增校验 |
| --- | --- |
| `clear` | `evidence_ids` 非空，且每项能在证据包解析到（`BE-n`、`quality_gate.commands[].name`、`path:Lx-Ly`、`PATTERN-*`、`REQ-DEC-*`） |
| `skipped` | 新增 `skip_condition` 字段，值为 checklist item 的 slug；分类器判定该类别**被 diff 触碰**时拒绝这条 `skipped` |

`skipped` 从此只能用在分类器同意的地方。判不了的维度重新落回 `unrun` + `known_gaps`，也就是落回「会降级依赖声明」的那条路——这正是它本来该在的位置。

- skill 侧：`review-result-contract.md` 第二节两处**改写**（`evidence_ids` 写成非空可解析、`skipped` 加字段），无新增段落。**净增 0～1 行。**
- 本文件承载：三个出口的成本梯度、为什么不给 `skipped` 加豁免通道。

### 三、`judged_files` 兑现现有承诺

`RoleResult` 顶层加 `judged_files[]`（仓库相对路径 + 采集时 sha256）。聚合时校验它是 `code.files` 的子集；空数组只允许出现在 `status != executed` 的结果里。

Phase D 修复后按交集判定：修复文件与某角色的 `judged_files` 无交集时该角色判断存活，有交集才失效重派。这不是新规则——`phase-review-closeout.md` 已经要求按键失效，本项只是把键补上，同时把那条里的「`depends_on`」改成对角色判断成立的键名。

- skill 侧：`review-result-contract.md` 加 1 行字段说明，`phase-review-closeout.md` Phase D 第 2 条改 1 处键名。**净增 1 行。**
- 本文件承载：为什么角色判断需要独立于 scenario 的失效键。

### 四、末步 commit point

`phase-implementation.md` 第五节定顺序与裁决：先回填 `alpha-tests.md`，后勾 checkbox；checkbox 是 commit point。续跑时——

- 勾了但账本没有该 Task 记录 → 末步未完成，重做末步；
- 账本有记录但未勾 → 已完成，补勾。

- skill 侧：**净增 1 行**（顺序 + 两条裁决压在一行内）。
- 本文件承载：无需展开，规则本身就是判据。

## 守卫检查

新增的都是脚本拒绝路径，按本仓约定归 `evals/`，不进 `check-consistency.mjs`：

- 每条新拒绝路径补一对用例（拒绝一条、正当放行一条）：空 `evidence_ids`、不可解析 `evidence_ids`、被 diff 反驳的 `skipped`、`judged_files` 越界。
- 每条都做变异测试：人为制造对应缺陷后确认它报失败。抓不到东西的检查只会让人学会忽略它。
- `classify_diff.py` 要被 references 实际调用，满足 `fe-script-owner` 与 `fe-script-paths`。

## 接缝契约同步

[`接缝契约.md`](./接缝契约.md) 需同步：

- 第 1 节路径变量：消费方里的脚本数量跟进（现文写「三个脚本」，实际已是五个，一并修正）。
- 第 10 节子代理派发协议：回传形状加 `judged_files`。
- 第 3 节机械检查表：新脚本纳入脚本类检查的覆盖说明。

按该文件的变更流程，契约变更不得与功能改动混在同一个提交。

## 执行顺序

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| 1 | 末步 commit point | 低，改动局部 |
| 2 | `clear` 收紧 | 低，单点校验，不依赖分类器 |
| 3 | `judged_files` | 中，动回传 schema 与 Phase D |
| 4 | `classify_diff.py` 与组合下限 | 高，新脚本 |
| 5 | `skipped` 反驳门 | 中，依赖阶段 4 |

阶段 1、2 可合成一个提交。阶段 4 最容易因其他改动返工，宜单独走并跑绿单测。阶段 5 必须在 4 之后——先做会因为拿不到命中表而退化成又一条散文规则。

## 不做与待定

| 项 | 判断 |
| --- | --- |
| `quality_version` 一致性断言 | **不做，机制本来就健全。** 曾怀疑手动整数忘记加一会让起点失败集合被静默复用。核查 `manage_execution_evidence.py` 后不成立：`state_fingerprint` 已经把仓库状态（HEAD、staged/unstaged diff 哈希、未跟踪文件哈希）、`quality_commands` 全文、`toolchains`、`runtime` 一并哈希，`fingerprint_miss_reason` 已能报出 `quality-commands-changed`。任何会让复用变得不安全的变化都已经让 HIT 不成立，版本号只是一个额外的人工失效杠杆，忘记加一不会放行任何东西。**不要再把它当缺陷修。** |
| `EX-n` 跨 Story 累积计数 | **待定**。Story 级目录装不下，仓库级归 `sdd-init-frontend`。先定账本归属再谈，本计划不动。 |
| baseline 就地修登记、`new-pattern` 候选回流 | **待定**。是同一条 handoff 分类（Dev 发现的仓库级事实变化没有回流通道），但要先与 init 侧确认所有权边界。 |
| `depends_on` 运行时下限（CDP 采实际加载资源） | **暂不做**。收益明确但成本高；等分类器落地、看它的下限思路实际效果再评估。 |
| 同维度加第二判（检视集成） | **不做**。同模型第二判不产生独立样本，成本换不到可靠性。维度分区是正确的成本选择。 |
| 声明加 `baseline_origin`（区分期望强度） | **不做**。识别的问题是真的（`text_spec` 协商出的期望与原型抽取的期望同样写 `PROVEN`），但它属于验收语义变更，不属失败方向，另立计划。 |

## Assumptions

- 分类器只产出可由路径与文件类型判定的下限；需要语义判断的触发器仍归主 agent，不假装能机械化。
- `skip_when` 条件当前全是「diff 不涉及 X」形态，因此可被 diff 事实反驳。出现非 diff 形态的条件时，该条豁免于反驳门并在 checklist 侧标注。
- 每项改造落地时删掉被它取代的散文规则，净增行数按删改后计。
- 每项动手前先读实现确认缺口真实存在。本计划初稿的五项里有一项是脚本已覆盖的假缺口，先读代码就能省掉一次无效改动。

## 落地记录

六道确定性门：`clear` 需非空证据、证据可解析、`judged_files` 必填、`judged_files` 属被检视代码状态、`skipped` 受 diff 反驳、组合下限需承接或署名收窄。每道都做过变异测试——注掉判据后，恰好对应那条用例失败。

skill 正文实际净增 6 行：`validation-policy.md` +3、`role-result.md` +2、`review-evidence.md` +1；`phase-implementation.md` 与 `phase-review-closeout.md` 是纯改写，净增 0。

四处与计划不同，都是实施中发现更好的做法：

| 项 | 计划 | 实际 | 为什么 |
| --- | --- | --- | --- |
| `judged_files` 形状 | 路径 + 采集时 sha256 | 只有路径 | 哈希已在证据包 `code.files` 里，再存一份是同一事实两个来源 |
| 下限的执行点 | `validation-policy.md` 的散文规则 + `portfolio_narrowed[]` | `aggregate --diff-facts` 变成必填参数，聚合器直接拒绝未署名的收窄 | 散文规则拦不住收窄；聚合是所有路径的唯一咽喉，放这里才是确定性约束 |
| `portfolio_narrowed` 的键 | 维度 | 触发器 | 只有触发器有机器下限；维度的收窄由 `skipped` 反驳门管，两者不该混用一个字段 |
| 证据可解析的范围 | 只查 `coverage` | 同时查 `findings` / `open_questions` / `deferred_candidates` | 编造一个 `BE-9` 在哪个字段都是同一个静默漏洞，且是同一个函数调用 |

分类器的规则表在冒烟测试中改过一次：初版对文档生效，把散文里提到的 `axios` / `i18n` 当成代码事实。现在路径与内容规则都只作用于源码后缀，`test_classify_diff.py` 有一条用例钉住这个行为。

`skipped` 反驳门只覆盖 `C1` / `C3` / `C4` / `C6` / `C7` / `Q7`——其余维度的 `skip_when` 不是 diff 可判形态，永不被反驳。这不是遗漏：反驳门的安全方向是「宁可少反驳」，误反驳只会逼出一次本可省略的判断，漏反驳才会放行谎言。
