# 前端 SDD 链路接缝契约

这里列的每一条都**跨越至少两个模块**：它变了以后，别人的文件或用例会失效。模块清单与评测方式见 [模块与评测.md](./模块与评测.md)。

这份表有两个用途：改接缝时知道要同步改哪些地方；建 fixture 时知道**要冻结哪些样本**——下表每一条的产物形态，都是某个模块用例的输入。

fixture 现场在 [`skills/sdd-dev-frontend/evals/fixtures/`](../../../skills/sdd-dev-frontend/evals/fixtures/README.md)，一条命令展开。

---

## 一、变更流程

改任何一条接缝，同一个 PR 内必须做完三件事：

1. 改契约本身（在下表的「唯一定义位置」）；
2. 改**全部消费方**（下表已列出，改前用检索复核一遍，表可能滞后）；
3. 同步更新 fixture 里冻结的对应样本（下表「fixture 样本」一行指到哪份），并加一条会失败的用例。

契约变更 PR 不得夹带功能改动——两者混在一起时，用例挂了分不清是接缝改错了还是功能改错了。

## 二、契约清单

### 1. 路径变量

| 项 | 值 |
| --- | --- |
| 唯一定义位置 | [`SKILL.md#路径变量`](../../../skills/sdd-dev-frontend/SKILL.md#路径变量) |
| 消费方 | 八份 agent 提示词（派发时追加的取值表）、全部 references 中的路径写法、三个脚本的参数 |

### 2. ID 命名空间

本表是**唯一注册处**，加新前缀先在这里登记。`tests/check-consistency.mjs` 的 `fe-id-prefix` **现读本表**，改这里就够了、也必须改这里——代码里不再有第二份白名单。

| 前缀 | 含义 | 定义位置 |
| --- | --- | --- |
| `AC-<n>` / `AC-<n>.<m>` | 验收标准锚点；**上游所有**，本链路只消费与追溯 | 上游产出的 `tasks.md` / `alpha-tests.md`（前端行来自 `sdd-task-frontend`） |
| `STRUCT-*` | 栈签名、目录实况、命名约定 | `sdd-init-frontend/references/baseline-contract.md` |
| `RUN-*` | 装 / 起 / 质量命令 | 同上 |
| `COMP-*` | 通用构件、业务组件路由索引、渲染辅助 | 同上 |
| `API-*` | 与后端通信的跨需求约定 | 同上 |
| `DATA-*` | 客户端数据的持有与流动 | 同上 |
| `STYLE-*` | token、scale、主题、硬编码基准 | 同上 |
| `TEST-*` | 测试框架、定位约定、跑法 | 同上 |
| `PATTERN-*` | 仓库工程规范；写作 `PATTERN-<上表前缀>-<n>`，命名空间段仍是 `PATTERN` | 同上 |
| `REQ-DEC-*` | Requirement 工程决策 | 同上 |
| `DEMAND-1~3` | 需求级三类事实 | 同上 |
| `IC-nn` | 界面清单重复模式 | `agents/extract-prototype.md` |
| `R1–R6` / `F1–F4` | QA 基线还原侧 / 功能侧 | 分类定义在 `references/qa-baseline-template.md`；检视侧同号出现在 `sdd-review-frontend` 的 `restore.md` / `self-test.md` 的 `legacy_id`，那里只写怎么判、不重定义分类 |
| `EX-n` | 冻结豁免 | 同上 |
| `L1–L6` | 布局与响应式检视维度 | `sdd-review-frontend/frontend-code-checklists/layout.md` 的 `legacy_id`；分配规则在 `sdd-dev-frontend/references/validation-policy.md` |
| `C1–C7` / `Q1–Q8` | 代码规范 / 质量检视维度 | 同上目录的 `convention.md` / `quality.md`；分配规则同上 |
| `BE-n` | Phase C 共享浏览器证据场景 | `references/review-evidence.md` |
| `REG` | 既有主路径回归 | `sdd-review-frontend/frontend-code-checklists/self-test.md`；Phase C 门面仍是 `agents/self-test.md` |
| `P1–P8` | 输出规范 | `SKILL.md#输出规范` |
| `GT-n` / `NG-n` / `OPT-n` | 种子缺陷用例的必报 / 不得报 / 可选项 | `sdd-review-frontend/evals/cases/*/ground-truth.md` |

**禁止**：`P0`、`S-<n>` 这类未注册前缀（后者曾在 `recon-spec.md` 里存在过，是漂移事故）。`VAL-B-*` 随验证账本一同下线，不要重新登记——它在本表里多留了两个提交，而 `fe-id-prefix` 现读本表，等于把一个已删命名空间继续算作已批准。`REPO-1~3` 同理：仓库 baseline 改成按消费者问句分八份文件后该命名空间整体废除，不要因为在旧文档里见过就重新登记。

`SHA-256`、`ISO-8601` 这类标准名不是 ID 命名空间，**不在本表登记**；它们形状上像前缀，只在机械检查里按误报豁免。

**Story ID 不是本链路的命名空间**，由上游 `sdd-task` 决定形态（实际为 `US<数字>`，如 `US20250510178479`）。工件里的 `story` 字段一律写 `<Story ID>` 占位，**不要造 `ST-<n>` 这类本地前缀再来这里登记**——曾经有过一次，来源只是某份 JSON 示例里的样例值。

| 项 | 值 |
| --- | --- |
| 唯一定义位置 | [`references/qa-baseline-template.md`](../../../skills/sdd-dev-frontend/references/qa-baseline-template.md) |

### 7. 两档分级与四条定级规则

| 项 | 值 |
| --- | --- |
| 唯一定义位置 | [`sdd-review-frontend/SKILL.md#定级`](../../../skills/sdd-review-frontend/SKILL.md#定级)（P 级与升级顺序）；P 级到 `blocker` / `suggestion` 的落盘映射在同包 [`references/role-result.md`](../../../skills/sdd-review-frontend/references/role-result.md) |
| 消费方 | 各检视提示词（含还原格 `agents/review-restore.md`）、[`review-pack-adapter.md`](../../../skills/sdd-dev-frontend/references/review-pack-adapter.md)、[`review-request.md`](../../../skills/sdd-dev-frontend/references/review-request.md)、`SKILL.md` 退出门禁、`references/phase-review-closeout.md` |
| fixture 样本 | `sdd-review-frontend/evals/cases/*/ground-truth.md` 的「应判级别」列——定级规则一改，这一列必须重算 |
| 变更代价 | 中高 |

**不设第三档。** 各检查项的默认级别在 review 包 checklist 里调；`sdd-dev-frontend` 侧不留任何级别定义，只消费 `level` 字段。

**请求契约不带级别字段。** 调用方想让某条在本 Story 更严重时，正确做法是把它写进冻结声明，让升级顺序第 1 条自然触发——开一个覆盖入口等于把定级搬回调用方，还顺带给了悄悄降级的口子。`fe-review-ownership` 守这条边界。

### 8. 硬门禁与退出门禁的编号

| 项 | 值 |
| --- | --- |
| 唯一定义位置 | [`SKILL.md#硬门禁`](../../../skills/sdd-dev-frontend/SKILL.md#硬门禁)、[`SKILL.md#退出门禁`](../../../skills/sdd-dev-frontend/SKILL.md#退出门禁) |
| 消费方 | 热路径实际按编号引用的只有 `references/restore-contract.md`（硬门禁 16 两处）；其余按编号引用集中在本文件与 `docs/skills/sdd-dev-frontend/团队起步套件.md`。`evals/evals.json` 的 `gates` 字段是唯一的覆盖索引 |
| fixture 样本 | `evals.json` 的 `gates`；由 `fe-gate`（编号可解析）与 `fe-gate-coverage`（每条门禁有用例）两条检查守 |
| 变更代价 | 中。**编号是被引用的，插入新条目时不得重排既有编号**，只能追加 |

**22 条门禁没有一条被脚本引用**（`rg '门禁' scripts/` 为空），所以「这条门禁被遵守了吗」只能靠情景题测量，不能靠运行时拦截。因此加一条门禁的门槛是：**能写出至少一条会因为它不成立而失败的 `evals.json` 用例**。写不出来的规则该写进所在章节的散文，不要占编号——编号会带来「不得重排」的约束和一个没有裁判的漂移面。

当前 **22/22 全覆盖**，`tests/check-consistency.mjs` 的 `KNOWN_UNCOVERED_GATES` 已空。那张表只许变短：往里加条目必须写明为什么这条门禁不值得测。

## 三、机械检查

下列检查覆盖上表中可被自动验证的部分，应固化进 `evals/` 并在每个 PR 上跑：

| # | 检查 | 防的是 |
| --- | --- | --- |
| 1 | 所有 Markdown 相对链接与锚点可达 | 移动章节后留下死链 |
| 2 | 提示词里出现的 `<变量>` 都在路径变量表中定义 | 变量改名后的静默失效 |
| 3 | 被引用的硬门禁 / 退出门禁编号存在 | 重排编号造成的错引 |
| 4 | 维度名（`C5` / `C6` 等）跨文件一致 | 改名只改了一处 |
| 5 | ID 前缀在第 2 节白名单内 | `S-<n>` 那类幽灵前缀 |
| 6 | 每份 `agents/*.md` 具备三节结构 | 新增子代理漏掉前置校验 |
| 7 | 脚本路径带 `<skill-dir>` 前缀 | 换 cwd 后跑不起来 |
| 8 | `scripts/` 下每个脚本都有提示词在调用它 | 瘦身删掉调用点后，判据从确定性退回散文，而单测还全绿 |
| 9 | 本文件提到的文件路径都真实存在 | 注册表指向已删文件；`fe-link` 抓不到行内 code，`fe-id-prefix` 又现读本表 |
| 10 | 每条门禁都有 `evals.json` 用例断言它 | 散文门禁没有裁判，改动后静默失效；棘轮双向守，补了用例必须删豁免 |

**十项已全部脚本化**，落在 `tests/check-consistency.mjs` 的第 9 节，跑法：

```bash
node tests/check-consistency.mjs
```

每项都做过变异测试：人为制造对应缺陷后该项确实报 FAIL。**新增检查项必须同样验证过能失败**——抓不到东西的检查只会让人学会忽略它。

`fe-id-prefix` 一项扫描时会跳过本文件：本文是命名空间注册处，必然要提到每一个前缀。
