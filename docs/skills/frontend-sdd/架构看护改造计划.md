# 架构看护改造计划(task 及以后)

> 范围:`sdd-task-frontend`、`sdd-dev-frontend`、`sdd-review-frontend`、`sdd-init-frontend` 及共享契约。
> 上游 `sdd-design-frontend` 的配套改动见同目录 [sdd-design-frontend-修改方向.md](./sdd-design-frontend-修改方向.md),两份文档的接缝字段以本文「接缝契约」节为准。

## 一、要解决的缺陷

现有链路里,init 管「仓库现状是什么」(描述性),review 管「是否偏离现状」(符合性),但没有环节回答「现状应该变成什么」(演进)。具体表现:

| 症状 | 现状为什么拦不住 |
| --- | --- |
| AI 把 10 行的事写成 200 行 | 计划没有规模锚点,执行期没有对账物,review 的复杂度检查只在超阈值时报 P2 建议级 |
| 过度设计(用不到的抽象层、预留 props、配置项) | quality-lens 八项里没有 Speculative Generality 这一项;计划自审也不查 |
| 模块腐化后每个 Story 继续往里塞 | quality-lens 报了 `component-responsibility-size` P1/P2 后,发现无处沉淀——规范候选回流只处理「规范变了」,不处理「模块该整备了」 |
| 设计不合适时硬塞实现 | 整条链路没有 preparatory refactoring(先整备再实现)的任务形态与安放点 |

对应业界实践:规模预算对应小 PR 文化(有预算才有超支概念);简化遍对应「让模型删代码」的实证经验;整备任务对应 Kent Beck "make the change easy, then make the easy change" 与 Fowler 的 preparatory refactoring;债务复发升级对应演进式架构的反馈环,并且完全复用本仓已有的复发计数机制(规范候选/化石台账)。

## 二、四个机制

### 机制 1:规模预算与偏差对账

**预算档位**(初始参考值,跑两个迭代后按实际分布校准):

| 档位 | 净增行数 | 说明 |
| --- | --- | --- |
| `S` | ≤ 50 | 免对账,避免小改动摩擦 |
| `M` | ≤ 200 | 常规 Story |
| `L` | ≤ 600 | 上限档;计划期预估超 L 即回流拆 Story,与既有「Task 数超 8 回流」同构 |

**流转**:design 给量级(见方向文档)→ task 翻译成 TaskPacket 字段 `size_budget`;design 未给时 task 按文件清单自估档位并标注自估。→ Dev 在 Phase C 进入时用 `classify_diff.py` 的 diff 机械事实对账。

**偏差处理**(实际净增 > 档位上限 × 2 时,S 档免):

1. 先做一遍**简化遍**:以删减为唯一目标重过本 Story diff。约束:不改可观察行为、不引入新抽象、不触碰冻结契约期望;简化改动按既有 `depends_on` 失效机制重取证据,不新增机制。
2. 简化后仍超 → 不阻断,但偏差事实与解释经 `aggregate` 参数渲进 `acceptance.md`(该文件整文件覆盖,不手写),让超支至少是显式的、可追溯的。

**为什么放 Phase C 入口而不是 review 之后**:检视和取证要针对简化后的最终 diff,否则简化会把已派发的检视判断整批失效。

### 机制 2:过度设计看护(Speculative Generality)

两道:计划自审拦「计划里的过度设计」,quality-lens 拦「执行期长出来的过度设计」。判据都是可检索的反向条件,不是「应该简单」这种口号。

### 机制 3:整备任务(preparatory refactoring)

设计权在 design:只有 `story-delta-frontend-design.md` 的「整备项」节能产生整备 Task,task 不自行发明(勘察发现结构风险但上游没标时,写进「风险与回滚」回流,不自造)。整备 Task 行为不变、由既有测试或还原契约守护、单独提交(`refactor` type,提交规范已有此类型)。

### 机制 4:架构债台账与复发升级

复用规范候选回流的既有管道,新增一类候选:

```text
quality-lens 结构性发现(P1/P2)
  → Phase C aggregate 以 --arch-debt 参数渲进 acceptance.md「架构债候选」节
  → init 刷新时收割进 <repo-root>/.learnings/frontend-arch-debt.md(与化石台账并列)
  → 同一模块被 ≥2 个独立 Story 点名 → init 标 pending-refactor
  → design 开工时只读台账,命中本次触及模块且 pending-refactor 的必须裁决:
     产出整备项,或显式豁免并记原因(不许静默)
  → init 复审时验证症状是否还在:已修复标 resolved,还在保持 pending
```

**所有权约定**(与化石台账的差异要显式写明):台账只有 init 写;design 只读。复发计数只能在 init 做——Story 侧手里永远只有自己那一次,这与规范候选的既有约定一致。

**入选范围**:仅 quality-lens 中 `component-responsibility-size`、`duplicated-code`、`state-placement` 三项的发现,且症状主体是**存量模块**(纯本 Story 新增代码的发现不进台账,它们该在本 Story 内修)。

### 6. `sdd-review-frontend/frontend-code-checklists/quality.md`

新增一项(机制 2 的执行侧),格式沿用现有条目:

```markdown
## `speculative-generality`

- normative_level: SHOULD
- default_severity: P2
- max_severity: P2
- skip_when: 本次 diff 无新增导出、抽象层或可配置参数时记 `skipped`。

**过度设计**:本次新增的通用性是否有真实消费者。
   - 新增导出未被本 Story 任何其他文件、AT 或 AC 消费 → P2。
   - 抽象层(接口 / 基类 / 包装函数)只有一个实现且无第二消费者 → P2。
   - props / 参数 / 配置项没有任何调用方传入非默认值 → P2。
   - 「未来可能用到」不构成豁免;上游设计文档明确要求的预留除外,判「预留但有设计依据,依据是…」也算覆盖。
```

## 四、接缝契约(与 sdd-design-frontend 的约定,内网优化不得破坏)

| 接缝 | 形状 | 消费方 |
| --- | --- | --- |
| `story-delta-frontend-design.md` 新增「整备项」节 | 表:目标模块(仓内真名) / 症状与台账条目 ID(若有) / 整备动作(行为不变) / 守护证据(既有测试或还原契约) / 预计量级 | `sdd-task-frontend` 切整备 Task |
| `story-delta-frontend-design.md` 头部新增「规模量级」字段 | `S` / `M` / `L`,含一句判定依据 | `sdd-task-frontend` 翻译为 `size_budget` |
| `<repo-root>/.learnings/frontend-arch-debt.md` | init 独占写;条目含:模块路径、症状、来源 Story、证据指向、状态(`pending` / `pending-refactor` / `resolved`) | `sdd-design-frontend` 只读并裁决 |
| 裁决豁免记录 | design 在 `requirement-frontend-design.md` 记「豁免 + 原因」,不写台账 | 人工追溯 |

## 五、实施批次

| 批次 | 内容 | 依赖 |
| --- | --- | --- |
| P0(纯文档,当天可完成) | 清单 3 的计划自审三条、清单 6 的 quality 新项 | 无 |
| P1(规模预算链路) | 清单 1、2、3 的 size_budget、4、5、8 | classify_diff.py 补行数输出(已核实缺失) |
| P2(架构债闭环) | 清单 7、9、10;design 侧台账消费(内网) | P1 的 aggregate 改动;design 方向文档落地 |

P0 先行的理由:零机制成本、立即生效;两条对齐后先观察一两个 Story 的实际拦截效果,再为 P1 的档位数值提供校准样本。

## 六、显式不做的事

- 不在 baseline 写任何量化上限——init 的既有禁令(不从代码样本推断行数/复杂度上限)保持;`size_budget` 是 Story 级 TaskPacket 字段,不进九份文件。
- 不新增 lint 级行数硬门禁——预算是对账锚点,超支的出路是简化或显式登记,不是拒绝提交。
- 不给 review 增加「设计 lens」——设计判断的安放点在 design 阶段(见方向文档),review 只认症状与证据,维持「本包只做判断」的定位。
- task 不自造整备 Task、dev 不在简化遍里做行为变更——设计权单一所有者不破。
