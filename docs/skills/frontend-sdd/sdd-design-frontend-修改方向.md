# sdd-design-frontend 修改方向(供内网详细优化)

> 背景:整条 SDD 链路里,init 管「仓库现状是什么」,review 管「是否偏离现状」,但「现状应该变成什么」(架构演进、防腐化、防代码膨胀)没有归属。设计阶段是这个决策权的天然所有者。
> 下游(task 及以后)的配套改造见同目录 [架构看护改造计划.md](./架构看护改造计划.md);本文末尾「接缝契约」是两边的共同约定,内网优化时字段与节名不得偏离,否则下游读不到。

## 现状评估:已经做对的,别在优化时丢掉

当前版本的步骤 ②(组件架构 + 存量盘点)已经具备:先扫存量再推组件树、复用/新增/扩展三分类、扩展必须审批。这是复用判定的正确骨架,方向 1-5 都是在这个骨架上补,不是推翻。

## 方向 1:存量事实源与 init 的 baseline 对齐(最高优先)

**问题**:当前用自带的 `component-scan` 子 skill 扫存量,与 `sdd-init-frontend` 产出的 `frontend-baselines/` 九份文件是**两套并行的存量事实源**,互不引用。后果:① 扫描结果用完即弃,每个 Requirement 重扫一遍;② design 看到的存量和 dev 勘察(recon)看到的存量可能不一致;③ baseline 里的 `PATTERN-*` 规范(请求封装、三态处理、测试定位约定)design 完全感知不到,组件树可能与仓库既有范式冲突,到 dev 阶段才被 convention-lens 拦下——拦截点太靠后。

**改法**:

- 目标 app 存在 `frontend-baselines/` 时,存量盘点**先读 baseline**:`components.md`(现成构件与封装层)、`data.md`(状态容器与三态)、`api.md`(请求出口)、`styles.md`(token);`component-scan` 降级为 baseline 缺失时的兜底,并提示先跑 `sdd-init-frontend`。
- 复用判定范围从「组件」扩大到 hook、请求封装、状态容器、工具函数——baseline 的清单条目本来就覆盖这些,只差 design 去读。
- baseline 的单条清单指路失效时按「消费点自证、就地修单条」处理(与 recon 的既有规则一致),不重扫全仓。

## 方向 2:新增产出「整备项」(preparatory refactoring)

**问题**:发现「扩展目标组件已经是 God 组件」时,当前只有两条路——硬扩展(继续腐化)或新增(制造重复),没有第三条「先整备再实现」。

**改法**:

- **识别时机**:② 存量盘点做扩展审批时,对扩展目标做一次健康度判断(职责数、是否被架构债台账点名,见方向 4);以及读台账时命中本次触及模块。
- **判定门槛**:整备项必须同时满足——症状有证据(台账条目或本次盘点的具体代码指向)、整备后本次实现显著变简单(说得出简化点)、有守护证据(存量测试或可冻结的还原契约)。三者缺一就不立项,防止「顺手重构」失控。
- **产物**:写进 `story-delta-frontend-design.md` 新增的「整备项」节(格式见接缝契约),下游 `sdd-task-frontend` 会把它切成排在最前的整备 Task,行为不变、单独提交。
- **确认门**:整备项与扩展审批同门(确认门 ①)展示,用户逐条决策:同意整备 / 拒绝(硬扩展并记原因) / 改为新增。

## 方向 3:新增产出「规模量级」

**问题**:下游没有任何规模锚点,AI 把 10 行的事写成 200 行时,执行期与检视期都无从对账。

**改法**:

- 每个 `type=frontend` 的 Story,在 `story-delta-frontend-design.md` 头部给出规模量级:`S`(净增 ≤50 行)/ `M`(≤200)/ `L`(≤600),附一句判定依据(参考组件树新增节点数、IFC 数、复用比例)。
- 预估超 `L` 视为 Story 过大信号,回流拆 Story——与下游「Task 数超 8 回流」同构,把拆分决策提前到设计期。
- 量级是给下游的对账锚点,不是给设计者的 KPI;判不准时宁可给高一档并说明不确定性,下游超 2 倍才触发动作。

## 方向 4:消费架构债台账(回流闭环的设计侧半环)

**问题**:review 阶段的结构性发现(God 组件、重复实现、状态错层)目前报完即沉没,同一模块每个 Story 被点名一次、每次都不了了之。

**改法**:

- 下游会把这类发现沉淀到 `<repo-root>/.learnings/frontend-arch-debt.md`(`sdd-init-frontend` 独占写,design **只读**),同一模块被 ≥2 个独立 Story 点名会标 `pending-refactor`。
- design 开工时(建议在 ② 之前)读台账,与本次需求触及的模块求交集;命中 `pending-refactor` 的**必须裁决**——产出整备项(方向 2),或显式豁免并把原因记进 `requirement-frontend-design.md`。不许静默跳过:静默是债务永远躺在建议级的根因。
- design 不写台账、不做复发计数——计数需要跨 Story 全局视角,只有 init 有;这与既有「规范候选复发计数只能在 init 做」的约定一致。

## 方向 5:过度设计的设计侧看护

**问题**:「优先新增,尽量不修改存量」(核心原则 6 / 张力裁决 11)防的是改坏存量,但代价是系统性催生重复与平行实现;同时确认门 ① 问用户「组件粒度是否合适」,却没有自查项,用户往往也判不出来。

**改法**:

- 确认门 ① 增加两条自查(agent 先自查再呈给用户,与扩展审批同表展示):
  - 每个「新增」组件/抽象都能指到消费它的 SC/FR;指不到的从组件树删除。
  - 「新增」与某存量资产语义重叠但仍选择新增时,必须写一行重叠说明——这行下游会作为 `duplicated-code` 债候选的线索,让「优先新增」的代价进入台账而不是无声累积。
- 张力裁决补一条:单一消费者的抽象层默认不建(组件、hook、Service 均适用);上游明确要求预留的除外并注明依据。

## 顺带修正(内网优化时一并处理)

- frontmatter `name: sdd-frontend-design` 与目录名 `sdd-design-frontend` 不一致,统一成一个。
- 文件当前是富文本导出格式(`\---`、`\*\*` 转义),内网定稿时转为干净 Markdown,否则 agent 读取时判据会被转义符干扰。

## 接缝契约(与下游的共同约定,不得偏离)

| 接缝 | 形状 | 消费方 |
| --- | --- | --- |
| `story-delta-frontend-design.md` 新增「整备项」节 | 表列:目标模块(仓内真名) / 症状与台账条目 ID(若有) / 整备动作(行为不变) / 守护证据 / 预计量级 | `sdd-task-frontend` 切整备 Task,排最前,`refactor` 提交 |
| `story-delta-frontend-design.md` 头部「规模量级」字段 | `S` / `M` / `L` + 一句判定依据 | `sdd-task-frontend` 翻译为 TaskPacket `size_budget`;缺失时下游自估并标注 |
| `<repo-root>/.learnings/frontend-arch-debt.md` | 只读;条目含模块路径、症状、来源 Story、证据指向、状态 | design 裁决 `pending-refactor` 条目 |
| 豁免记录 | `requirement-frontend-design.md` 记「豁免模块 + 原因」 | 人工追溯;init 复审台账时可见症状仍在则条目保持 pending |

## 验收这份方向落地与否的判据

1. baseline 存在时,产物中的复用结论能引用 `PATTERN-*` 或 baseline 清单条目(而不是只有 component-scan 的扫描输出)。
2. 台账有 `pending-refactor` 且命中触及模块的 Requirement,其产物里能找到对应的整备项或显式豁免,找不到即流程违例。
3. 每个 frontend Story 的 delta 设计都有规模量级与依据。
4. 组件树里不存在指不出消费方 SC/FR 的新增节点。
