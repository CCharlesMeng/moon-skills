# 检视职责归位改造计划

## Summary

把 `sdd-dev-frontend` 与 `sdd-review-frontend` 的边界从「大体分好了」收紧成「机械可判」：

- **检视能力全部来源于 `sdd-review-frontend`**：检查项、判据、默认级别、格子互斥、回传形状只有一份，在包里。
- **规划、唤起、非默认约束全部来源于 `sdd-dev-frontend`**：选哪几格、何时派、传什么，以及本 Story 的冻结声明、豁免、容差、级别覆盖。
- 运行时判据当前已基本归位；**待修的是五处反向泄漏**，其中一处是两份契约互相打架的真缺陷。
- 两项已定：`restore-lens` 接进 Phase C 成为第五格；种子缺陷用例随 checklist 搬进 review 包。

本计划只描述改造，不改动代码。

## 归属判则

| 关注点 | 归属 | 载体 |
| --- | --- | --- |
| 检查项、判据、默认级别、格子互斥、回传形状 | `sdd-review-frontend` | `frontend-code-checklists/` · `roles/` · `references/role-result.md` |
| 选哪几格、哪些维度 | `sdd-dev-frontend` | `references/validation-policy.md` |
| 何时派、传什么、聚合落盘 | `sdd-dev-frontend` | `agents/` · `references/review-pack-adapter.md` · `scripts/manage_review_pipeline.py` |
| 冻结声明、豁免、容差、起点失败集合、级别覆盖 | `sdd-dev-frontend` | `dev-baseline.md` → 新增请求契约 |

**机械判据**（可自动检查，见第六节）：

- review 包里不出现只有调用方才知道的词：`<story-dir>`、`验证组合`、`Phase C`、`sdd-dev`。
- dev 侧不出现 `default_severity`、`max_severity`、`normative_level`，也不出现维度定义表。

包被独立调用（审 PR、无 Story 上下文）时仍要能工作，所以请求契约的每个字段都必须有默认值，dev 提供的是**覆盖**而非**必填**。

## 现状偏差

### 1. 设计文档里仍是抽包前的判据全文

[`方案设计.md`](../sdd-dev-frontend/方案设计.md) 第八节逐条展开 L1–L6、C1–C7、Q1–Q8 与功能侧四维度，第九节写死了分级门禁。这已经不只是冗余，而是与包内判据**实质冲突**：

| 设计文档 | 包内 checklist |
| --- | --- |
| 「公共样式硬编码 → 阻断级」 | convention 开篇：硬编码、检查抑制、裸请求、调试残留**不按类型自动升级** |
| 「调试语句 → 阻断级」 | quality 的对应条默认 P2，只有证伪冻结声明或确证错误结果才升 |

两条冲突都已被种子缺陷用例站在包这一侧判定：`convention-01` 的 GT-6～GT-8 要求硬编码判建议级，`quality-01` 的 GT-4 要求调试语句残留判建议级。设计文档是过期的那一份。

[`README.md`](../sdd-dev-frontend/README.md) 的 Phase C 表与 `README.html` 中的维度块是同一份副本的薄版本。

### 2. `skip_when` 混了规划与判据，两份契约互相打架

`references/role-result.md` 要求：未分配的维度在 `coverage` 与 `skipped` **两边都不出现**。

`frontend-code-checklists/self-test.md` 五条的 `skip_when` 写的是「验证组合未分配任何 F1 行时记 `skipped`」。

同一情形，一个说不准出现，一个说记 `skipped`。根因是 `skip_when` 同时承担了两件事：

- **调用方没派**——规划，属 dev，应由「不下发」实现；
- **现象不触发**——判据，属包。

restore 的 `skip_when`（「基线未生成 R1」）与 layout / convention / quality 的（「diff 不涉及共享样式」）都是后者，是对的。只有 self-test 五条串了台。

### 3. review 包反向写死了调用方

- `references/gate-matrix.md` 开篇枚举「本包只在 `sdd-dev` 派格」「`sdd-prd` / `sdd-design` 不派前端代码格」「`sdd-archive-workspace` 是 rollup 门禁」。
- 五份 `ROLE.md` 的 YAML 各有 `gate: sdd-dev`，正文各有一句「本角色只占 `sdd-dev` 的 CODE-XXX」。
- `references/role-result.md` 枚举了 dev 的四个角色名。

这些都是**规划**知识，按判则属 dev。

### 4. 缺一份「非默认约束」的正式入口

dev 交给包的东西现在散在四处：`validation_portfolio.review_dimensions`、`dev-baseline.md` 的冻结 R/F 行、`EX-n` 豁免表、`DEMAND-2` 起点失败集合，外加 `<browser-driver>`。包侧只能用 `reads:` 列层名间接指代。

「默认值在包里、覆盖值在 dev」目前只是口头约定，没有可校验的载体。

### 5. R/F 分类描述两处各写一份

`references/qa-baseline-template.md` 定义 R1 为「必须出现的区块、顺序、父子关系与数量约束」，`frontend-code-checklists/restore.md` 近乎逐字重复。F1–F4 与 self-test 同理。

按判则，**分类定义是标准约束，归 dev**；checklist 只该写怎么判。L/C/Q 不受影响，那些维度本来就是包自己的。

## 改造项

### 一、判据唯一

清理 [`方案设计.md`](../sdd-dev-frontend/方案设计.md) 第八、九节：删掉维度清单与分级门禁正文，只保留设计理由——为什么规范与质量拆开并行、为什么布局检视放在最后、为什么不设第三档。这些是 ADR 性质的，不会随 checklist 漂移。判据一律改指针。

[`README.md`](../sdd-dev-frontend/README.md) 的 Phase C 表收缩为一句加链接；`README.html` 的维度块同步。

### 二、`skip_when` 语义收敛

self-test 五条的 `skip_when` 改成按约束触发（「基线无 F3 行」），不再引用「验证组合」。包不需要知道这个概念。改完 `role-result.md` 与 checklist 不再矛盾。

### 三、包去调用方耦合

- `gate-matrix.md` 缩成两部分：五个 cell 的定义、现象归属互斥表。删掉门禁枚举。
- `ROLE.md` 的 `gate` 改为由请求传入，正文的「只占 sdd-dev 的某格」改为「本角色占 CODE-XXX 格」。
- `role-result.md` 的 `role` 字段说明改为「调用方提供的角色标识」，不列具体名字。
- 被删掉的门禁枚举整段移进 dev 的 `references/review-pack-adapter.md`——那里已经有角色到 lens 的映射，是它该在的位置。

### 四、立请求契约

dev 侧新建 `references/review-request.md`，定义一份请求结构：格子、维度分配、冻结约束引用、豁免表、级别覆盖、证据纪元、路径变量取值。包侧五份 `ROLE.md` 的 `input_contract` 对齐到这份 schema 的字段名。

有了它，「默认值在包里、覆盖值在 dev」才成为可执行规则。

### 五、restore 接线为第五格

**现状是一个定义完整但没有调用路径的死角色。** `gate-matrix.md` 把 CODE-RESTORE 列为一格，包的 [`SKILL.md`](../../../skills/sdd-review-frontend/SKILL.md) 说它「不进入 `manage_review_pipeline.py`」，dev 的 `review-pack-adapter.md` 说「不要增加第五个 role」。脚本侧证实了后两条：`ROLES` 是硬编码四元组，`ROLE_DIMENSIONS` 只有 L/C/Q。

**脚本与 checklist 的实际分工**：`verify_restore_contract.py` 产出**颜色**——按容差与 CSS 归一化比对，攒 red/yellow 原因，汇总成「有 RED 即 RED，无 RED 有 YELLOW 即 YELLOW，全 GREEN 才 GREEN」。它不产出严重度。checklist 产出**级别**，这是它真正增加的东西：

- 同一条 RED 分级：关键区块缺失或父子关系颠倒判 P0，数量约束越界而主路径仍可完成判 P1——脚本对两者给的都是同一个 red。
- YELLOW 的四路分流：补证、`UNVERIFIED`、`DEFERRED`、真 RED。
- 两类 Open Question：把原型 class 名当成实现义务、需要改变布局结构才能适应的视口缺口。

**但有三条是 no-op**，脚本上游已解决，lens 拿到报告时看不到：

| checklist 条目 | 为什么空转 |
| --- | --- |
| 「CSS 序列化等价不是还原偏差」 | 比对器已拉平，这类差异不会以 RED 出现 |
| 「命中 `EX-n` 的字段任何级别都不报」 | 规则带冻结豁免时脚本直接判 green 并附豁免 ID |
| 「`visual` 缺补证 → YELLOW」 | 脚本已经这么标了 |

第三条作为「不许把 YELLOW 改写成 GREEN」的处置约束仍然有意义（对应硬门禁 11），作为判据是空转。

**接线的真正收益不是重跑一轮。** [`validation-policy.md`](../../../skills/sdd-dev-frontend/references/validation-policy.md) 规定 Phase B 只跑当前变更区块的契约，Phase C 按最终 diff 重编译组合——但现在没有任何一步用最终 diff 重跑全部区块的契约。后续 Task 改了公共样式，先前区块的 GREEN 无人推翻。第五格补的是这个洞，职责为两件：按最终 diff 重跑契约，把颜色翻译成级别。

改动清单：

| 项 | 内容 |
| --- | --- |
| `manage_review_pipeline.py` | `ROLES` 加第五角色，`ROLE_DIMENSIONS` 加 R1–R6；聚合与收口摘要分节跟进 |
| 单测 | 现有 13 条补第五角色的聚合、维度越界、跨格同 `canonical_key` 合并 |
| `agents/` | 新建还原检视提示词，须含前置校验、只读声明、输出格式三节 |
| `validation-policy.md` | 新增模块与触发条件：`visual` 且存在冻结 R 行 |
| `review-pack-adapter.md` | 删「还原不走 Phase C 角色」整段，补映射行 |
| 包 `SKILL.md` | 改写「机器执行器未搬 / 不进管道」那段 |
| `restore.md` | 删三条 no-op，只留颜色到级别的映射、YELLOW 分流、Open Question 类 |
| `phase-review-closeout.md` | Phase C 第 1 步明确包含按最终 diff 重跑契约 |

**待定细节**：还原格的 `dimension` 用维度号还是基线行号。self-test 用行号，L/C/Q 用维度号。倾向用维度号、finding 编号用行号形态，与 L/C/Q 一致。

### 六、种子缺陷用例归位

用例测的是包里的 checklist（[`模块与评测.md`](./模块与评测.md) 已如此记载），按「改谁回看谁」应跟 checklist 走。

`cases/` 与各自的 ground truth 搬到 `skills/sdd-review-frontend/evals/`；fixture 生成器留在 dev——它产出的是 `dev-baseline.md`、`tasks.md` 与仓库现场，属标准约束的样本。生成器的用例查找目录改指过去，[`模块与评测.md`](./模块与评测.md) 的归属表与 fixture 说明同步。

准入规则不变：四项分每项不降，跑三次取最低。

## 守卫检查

前六项落地后需要一条机械检查兜底，否则会慢慢漂回去。在 `tests/check-consistency.mjs` 第 9 节新增一项：

- 扫 dev 侧文件，出现 `default_severity` / `max_severity` / `normative_level` 即失败；
- 扫 review 包，出现 `<story-dir>` / `验证组合` / `Phase C` / `sdd-dev` 即失败。

按本仓既有约定，新增检查项必须做变异测试：人为制造对应缺陷后确认它报失败。抓不到东西的检查只会让人学会忽略它。

## 接缝契约同步

[`接缝契约.md`](./接缝契约.md) 需要同步的条目：

- 第 2 节 ID 命名空间：R1–R6 那行补上 restore checklist 的 `legacy_id` 归属。
- 第 7 节两档分级：消费方清单加入请求契约与还原格。
- 第 10 节子代理派发协议：把请求契约登记为该条的组成部分。
- 第 3 节机械检查表：追加守卫检查一行。

按该文件的变更流程，契约变更不得与功能改动混在同一个提交。

## 执行顺序

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| 1 | 判据唯一、`skip_when` 收敛、包去耦合 | 低，纯文档 |
| 2 | 请求契约 | 中，改五份 ROLE 的 `input_contract` |
| 3 | restore 接线 | 高，动脚本与单测 |
| 4 | 用例归位 | 中，动 fixture 路径 |
| 5 | 守卫检查 | 低，但要做变异测试 |

阶段 1、2 互不依赖，可合成一个提交。阶段 3 最容易因其他改动返工，宜单独走并跑绿单测。阶段 5 必须最后做——早做会把还没修完的偏差全部报成失败。

## Assumptions

- 包要能被独立调用，所以请求契约的字段一律有默认值，dev 提供覆盖而非必填。
- 还原的机器执行器留在 dev：它做的是确定性比对，产出的是事实层的颜色，不是严重度判断。
- R/F 分类定义留在 dev 的基线模板，包内 checklist 通过 `legacy_id` 参数化引用，不重写定义。
- 设计文档里的取舍理由保留，判据不保留——前者不随 checklist 漂移，后者会。
- 当前工作树有多份未提交修改，实施前先读取相关 diff，基于现状增量合并。
