# 前端 SDD 执行契约

本文件是 `sdd-task-frontend` 与 `sdd-dev-frontend` 的共享事实源。前者定义计划与验收声明，后者实现并取证；两边都不复制这里的字段语义。

## 所有权

| 所有者 | 负责 | 不负责 |
| --- | --- | --- |
| `sdd-task-frontend` | `tasks.md`、`alpha-tests.md` 初始骨架、Task 切分、可观察验收声明、候选风险事实 | 代码、命令、浏览器矩阵、QA 维度取舍、证据结论 |
| `sdd-dev-frontend` | 代码、QA 基线冻结、验证组合、证据、声明状态、交付收口 | 改写上游验收内容 |

判断计划细节是否越界：**改掉它会改变 AC 或 mock 集成测试断言，则写入 Task；否则留给 Dev。** URL、字段名、用户可见行为和 testability 锚点属于契约；内部 helper、DOM 层级、class、指定 API 调用和视觉数值属于实现或冻结基线。

## 声明与状态

每条 AC/AT/QA 行都是验收声明，最终状态只有：

| 状态 | 判据 |
| --- | --- |
| `PROVEN` | 有覆盖该声明、环境正确、对最终相关依赖仍新鲜的证据，且没有未清零的确证阻断 |
| `UNVERIFIED` | 本阶段做得到但未执行、证据不足或工具能力不可用 |
| `DEFERRED` | 外部依赖未就绪；必须写明解除条件 |

`UNVERIFIED` 与 `DEFERRED` 都不计已验收。缺少某种证据只影响依赖它的声明，不扩大到无关声明。

## TaskPacket

接缝沿用 `tasks.md` 的 `TaskPacket` 头，不新增第三份文件。字段缺席表示旧格式输入，由 Dev 按实际事实补判；不表示低风险。

| 字段 | 计划侧写法 | Dev 侧消费 |
| --- | --- | --- |
| `baseline_source` | 必填：`prototype` / `reference_page` / `text_spec` / `none` | 作为候选输入，Phase A2 确认后才冻结 |
| `prototype_dir` | `prototype` 时填写真实目录 | 定位 `<prototype-dir>` 并实测 |
| `reference_route` | `reference_page` 时写候选，不写成既定结论 | Phase A2 让用户确认 |
| `affected_routes` | 逗号分隔的受影响路由 | 页面识别与风险闭包 |
| `required_states` | 只列明确要求的 `hover,focus,disabled,selected,loading,empty,overflow` 子集 | 合并候选场景，不自动逐 Task 执行 |
| `restore_tasks` | 还原轮 Task 编号；无还原轮留空 | 形态索引；冲突时以 Task 内容为准 |
| `risk_triggers` | 只写计划事实直接支持的 token | 与仓库事实、实际 diff 合并后编译验证组合 |

风险 token 的唯一完整注册表在 [validation-policy.md](../../../skills/sdd-dev-frontend/references/validation-policy.md#三风险触发器)。计划侧通常只会直接识别 `visual`、`interaction`、`navigation`、`shared-boundary`、`auth`、`write`；需要代码勘察的 token 留给 Dev。

## 基线源

先判断 Story 是否产生或改变静态形态，再选第一个成立的来源：

| 档位 | 成立条件 | 计划承诺 |
| --- | --- | --- |
| `prototype` | HTML 原型确含对应页面 | 给出原型、路由和区块名；锚点与数值由下游抽取、冻结 |
| `reference_page` | 无原型，但仓内有同类已上线页面 | 给候选参照页，等待下游确认 |
| `text_spec` | 只有可逐条落地的文字规格 | 只承诺仓内 token、一致性、无横向滚动/重叠/截断及文字规格 |
| `none` | 没有外部基线，或 Story 纯逻辑 | 写明原因与缺口；不发明视觉规格 |

没有原型不等于没有还原 Task。只要静态形态发生变化，仍需还原 Task；`text_spec` / `none` 只是收窄可证明的范围。

## Task 切分与六步形状

1. 跨页公共骨架先成 Task。
2. 每页静态结构和样式集中为一个还原 Task，排在该页逻辑 Task 前；还原 Task 独占样式文件。
3. 逻辑 Task 按紧邻 AC 分组。确需改样式时登记文件、原因和被失效的还原 Task。
4. 每个还原 Task 写视觉来源、路由和职责单一的区块名；class 锚点由 Dev 抽取。
5. 不创建“样式微调”“统一优化”“走查修复”类收尾 Task。

保留上游六步 checkbox，但只写因果意图：

| Step | 计划内容 |
| --- | --- |
| 1 暴露缺口 | 受影响声明、证据形态、改动前可观察缺口 |
| 2 确认原因 | 什么现象说明原因判断正确 |
| 3 最小实现 | 文件范围与目标行为；不写实现代码 |
| 4 证明声明 | 应变成 `PROVEN` 的声明与最小可观察结果 |
| 5 重构 | 按需 |
| 6 记录并提交 | 回填证据账本并沿用上游提交规范 |

证据形态只有逻辑、还原、机械三类。优先按形态拆 Task；确实切不开时在同一 Task 分轮，每轮独立引用声明，不互借证据。
