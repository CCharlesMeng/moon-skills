# 前端 SDD 链路：模块与评测

这份文档回答一个问题：**一个人想优化其中一块，他改什么、怎么知道自己改好了。**

覆盖 `skills/sdd-init-frontend/`、`skills/sdd-dev-frontend/` 与 `skills/sdd-review-frontend/`。接缝清单见 [接缝契约.md](./接缝契约.md)。

---

## 一、独立演进需要三个条件

| 条件 | 含义 |
| --- | --- |
| **能单独跑起来** | 这一块可以脱离整条流程被调用，输入是一组固定文件而不是「上一步的实际产出」 |
| **输入可复现** | 有一份冻结的 fixture 现场，任何人任何时候跑得到同样的输入 |
| **改完有分数** | 有一组用例和一个分数，改之前改之后可比；分数掉了就是改坏了 |

三条里缺任何一条，这一块就只能靠整链跑一遍来验证——那意味着几个人不可能并行优化。

**一条硬规则**：模块的用例只依赖 fixture 里**冻结的上游输出样本**，不实跑上游。否则上游一改，下游用例全红，独立性就没了。上游输出格式真的变了，走[接缝契约](./接缝契约.md)的流程同步更新 fixture 样本。

#### `collect_restore_facts.js` 的测试矩阵按现象建，不按栈建

**「技术栈和组件库很多」不会让这个矩阵变大。** 采集器读的是渲染后的 DOM 与计算样式：React / Vue / Svelte / Angular 渲染完收敛到同一棵 DOM，CSS Modules / CSS-in-JS / Tailwind / SCSS 收敛到同一份 `getComputedStyle` 输出。所以按栈建 fixture 是永远收敛不了的错方向——**新增一个组件库不新增用例，除非它引入一个新现象**。

现象是有限的，各自状态：

| 现象 | 状态 | 测它需要什么 |
| --- | --- | --- |
| open shadow root 穿透 | **已修**，逐 root 查再合并 | 静态 HTML 快照 + 一个 DOM 实现 |
| closed shadow root 报专用 reason | **已修**，与「选择器写错」区分开 | 同上 |
| 伪元素内容（`collect.pseudo`） | **已修** | 同上 |
| 虚拟列表 `count` 语义 | **已修**，返回 `rendered` / `declared`，不给一个「看起来对」的错数 | 同上 |
| 注入时机（Suspense / 骨架屏 / 字体加载） | **未定**：采集器是同步的，没有「何时算稳定」的契约 | 先定契约，再谈测试 |
| 几何（`rect` / `overflow` / `overlap` / `clip`） | 实现已有，**零覆盖** | 真浏览器——`getBoundingClientRect` 在无布局的 DOM 实现里返回全零 |

**待做，按此顺序**：前四条用静态快照钉住，但本仓当前**零 npm 依赖**（无根 `package.json`、无 `node_modules`、`check-consistency.mjs` 裸 node 跑），引入一个 DOM 实现是一次架构决定，要先定；注入时机先定契约；几何那四种必须等真浏览器现场，与 `review-layout`、`self-test` 共用同一个前置，一次投入解锁三个模块。

`sdd-init-frontend` 已无确定性脚本：原先 1556 行的 baseline 扫描器随 baseline 改版整体删除，发现工作改由 agent 按 [`references/discovery-rules.md`](../../../skills/sdd-init-frontend/references/discovery-rules.md) 的结构判据做。这不是覆盖率倒退——那 9 条单测测的是「扫描器能不能把 `package.json` 重排版成 Markdown」，而扫描器真正的失败是识别率 1/5，单测一条都没测到。

## 三、两套评分口径

**不要用一套口径覆盖所有模块。** 脚本和提示词的失败方式不一样。

### 确定性脚本 → 断言

标准 unittest / golden file。输入进去，输出必须逐字段等于期望。已有 `evals/test_extract_design_spec.py` 作为样板。

### 编排与行为 → 情景题（`evals.json`）

沿用全仓既有约定（`skills/refine-skill/references/evaluation.md`）：一条用例 = `prompt` 情境 + `expectations` 行为断言，由 executor 子代理重放、grader 子代理逐条判 pass/fail，无部分得分。通过标准是「新增用例跑 3 次取多数不复发，存量用例全过」。

它判的是**做没做某个动作**（有没有先校验哈希、有没有拒绝放宽容差），不判结论质量。

**已给每条用例加上 `target` 字段**，标明它考的是哪个模块（分布见第二节的 `target` 反向索引）。`target` 的用途不止是分类：它是**反向索引**——改一份提示词或脚本前，先按 `target` 捞出该模块的存量用例，改完回看是否仍成立。当前 50 条里有 4 条考 `SKILL.md` 自身编排：Phase -1 那道极轻的门、指路失效与规范不成立的分界、Phase B 的进入条件、Phase D 的四类攒批。

**`gates` 字段是第二条反向索引**，37 条用例标了它，指向自己断言的硬门禁 / 退出门禁。它解决的是一个结构性问题：22 条门禁没有一条被脚本引用，所以"门禁被遵守了吗"本来无法机械测量，改动后只会静默失效。有了这条链接，`fe-gate-coverage` 能要求每条门禁至少有一条用例，并且是双向棘轮——补了用例必须把它从豁免表删掉。**当前 22/22 全覆盖，豁免表已空。加一条门禁的门槛因此变成：能不能写出一条会因为它不成立而失败的用例。** 写不出来就别占编号。

最后补上的四条门禁值得记一下：硬门禁 1（缺 `tasks.md` 的两条分支，正反各一条用例）、9（原型隔离）、14（退出码 4 的登记—确认—重跑）、16（退出码 5 不得变成豁免）。**它们恰好是三条有真实事故记录的门禁**——9 对应[「设计稿抽取下沉子代理」那条 ADR](../sdd-dev-frontend/adr/0003-design-spec-extraction-goes-to-subagent.md)记的上下文爆掉，16 对应 `EX-2`–`EX-5` 四条工具债被写成永久豁免。正因为它们只在事故复盘里被写成散文，才一直没人想到配用例。

### 检视结论质量 → 种子缺陷四项分

检视类模块的好坏是**查全和查准**，情景题的 pass/fail 判不了。做法是在 fixture 的 diff 里预埋已知缺陷，标注每个缺陷应当被哪个维度以什么级别报出，然后算四项：

| 指标 | 含义 | 不达标说明 |
| --- | --- | --- |
| 命中率 | 预埋缺陷中被报出的比例 | 提示词漏检，通常是维度定义太窄或检索方式没写清 |
| 误报率 | 报出的结论中不在 ground truth 里的比例 | 提示词太激进，会淹没真问题 |
| 级别正确率 | 命中的缺陷里级别判对的比例 | 定级规则没被理解，或与 `sdd-review-frontend/SKILL.md#定级` 冲突 |
| 格式合规 | 回传是否满足提示词「输出格式」节的自检清单 | 主 agent 会因此退回重跑，白烧一轮 |

两套口径并存，不互斥：同一个模块可以既有情景题（行为）又有种子缺陷（结论质量）。
