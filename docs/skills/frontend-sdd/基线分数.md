评分口径见 [模块与评测.md 第三节](./模块与评测.md)。模块清单与覆盖状况见同一份文档第二节。

## 一、准入规则

| 模块类型 | 准入条件 |
| --- | --- |
| 确定性脚本 | 全部 unittest 通过，且用例数不减。改了行为的，先改测试并在下表记明为什么 |
| 判定类提示词 | 四项分**每项都不低于**下表当前值，且四项都在及格线内。跑 3 次取最低那次 |
| 编排 | `evals.json` 存量用例全过，新增用例跑 3 次取多数不复发 |

**跑 3 次取最低**，不取平均也不取多数：判定类提示词的失败方式是偶发漏检，平均会把它抹平，而漏检一次在真实使用里就是一次漏检。

**命中率、误报率、级别正确率满分，格式合规 3 次全部卡在同一项，说明这是可复现的真实缺陷而不是偶发。** 3 次都正确识别了两处硬编码（穷尽性达标）、都没有误把 `orderExportFormat.ts` 的默认导出判成违反 `PATTERN-COMP-1`（适用场景边界达标）——**但 3 次都对「失败批次」卡的 `String(data.failedCount)` 保持完全沉默，从未提及 `EX-1`**。结果本身是对的（没报违规），可提示词没有留下任何"检查过豁免表后判定不报"的痕迹，这与"根本没检查那一行"在输出上无法区分。命中率之所以还能满分，是因为 ground truth 的必报分母里没放这条——它本来就该判"不报"，只是"不报"这件事本身需要能证明是判断而非遗漏。

这是一处值得改的真实提示词缺陷（不是 ground truth 的问题）：`agents/review-convention.md` 目前没有指示子代理对"看起来可能违反某条已冻结基线，但代码里没报错"的行为显式核对豁免表并留痕。可考虑的修法：在 C5/规则 3 附近补一句，要求任何触及 `R<n>-<m>`/`F<n>-<m>` 判定对象的代码都要在结论或已知缺口里留一行核对记录，哪怕结论是"不报"。这条改进本文档暂不代实施，留给下一轮改 `review-convention.md` 时对照本基线验证有没有把格式合规拉到 1.0。

### `agents/review-quality.md`

用例 [`evals/cases/quality-01`](../../../skills/sdd-review-frontend/evals/cases/quality-01/ground-truth.md)（7 条必报 / 2 条诱饵 / 4 条可选），复用同一套 `repo/`/`baseline/`，专为 Q1–Q8 设计的独立 Story。

**这条用例的第一轮跑就纠出了两处 ground truth 自己的错**，都发生在实测阶段而非设计阶段：

| 问题 | 修正 |
| --- | --- |
| `getRowTone` 原本只有 4 层条件嵌套，独立子代理正确数出"未超 4 层参考线"判无发现，判断是对的，是 ground truth 把嵌套层数数错了 | 给函数加一层防御性判断（`Number.isFinite`）让嵌套真正达到 5 层；`GT-5` 改为基于修正后代码 |
| `NG-3` 原判"`HoldingsTable` 未达三类以上职责，不得报 Q1"，但两次独立跑都判出组件确实承担状态编排/业务规则/呈现三类职责，理由站得住 | 改记为 `GT-7`（Q1 建议级，必报分母 6 → 7），`NG-3` 删除（误报分母 3 → 2） |

修正后又跑了 3 次（前两轮暴露 ground truth 问题的那两次不计入基线，只算修正后的 3 次独立跑）：

| 日期 | 命中率 | 误报率 | 级别正确率 | 格式合规 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 2026-08-10 | **0.857** | **0.00** | **0.833** | **1.00** | 首次基线。3 次命中率逐字节一致（6/7）、误报 3 次均 0/2、格式合规 3 次均 6/6；级别正确率 3 次里 2 次 6/6=1.00，1 次 5/6=0.833，取最低 |
| 及格线 | ≥ 0.80 | ≤ 0.17 | ≥ 0.90 | = 1.0 | |

**级别正确率没过及格线**（0.833 < 0.90），这不是噪音，两处原因都在 3 次跑里稳定复现：

1. **GT-6（Q8：`sort` 未缓存）3 次全部漏检。** 每次都正确抓到了"500 条无虚拟化"这条大的性能问题（Q8-1），但都没有再往下找同一维度里第二条更小的性能问题（每次渲染重新排序）。`review-quality.md` 明文要求"逐条穷尽，不得找到几条就收敛"，这条规则显然只在跨维度层面被遵守，同一维度内部找到一条就停的倾向在这份小样本里三跑三中。
2. **GT-1（Q4：可推导状态存成 state）1/3 次被升成阻断级。** 论证方式是"能描述出一帧不一致，所以符合规则 2『确证的功能缺陷』"——这套话术能套用到**任何**"可推导值存成 state 再用 effect 同步"的写法上，如果这就够格升阻断级，Q4 的默认建议级形同虚设。已在 ground truth 里写清楚这条不该升的理由，供下次改提示词时对照。

**这两处合起来指向同一件事**：`review-quality.md` 目前缺一条"同一维度内部也要穷尽，不能找到大的就漏小的"的强调，以及缺一条"规则 2 的确证门槛需要多严"的判例（不是所有能编出触发序列的推断都够格）。这条基线的价值就是把这两处钉住，留给下一轮改提示词时验证有没有把命中率拉到 7/7、级别正确率拉到 1.00。

## 四、跨文件一致性

`node tests/check-consistency.mjs` — 11 项通过、0 失败、0 WARN。脚本现在只覆盖前端链路，11 项是：`fe-link`、`fe-path-var`、`fe-gate`、`fe-dimension`、`fe-id-prefix`、`fe-agent-shape`、`fe-script-path`、`fe-script-owner`、`fe-registry-target`、`fe-gate-coverage`、`fe-review-ownership`。

**这里只记项数与通过与否，不抄各项报出的明细计数。** 链接数、前缀数、文件数会随任何一次正常改动漂移，抄进来只是制造下一处过期数字——它们的正确值由脚本每次实跑给出，不需要第二份副本。只有两个数字值得钉在文档里，因为它们是别处的交叉校验：

- **`fe-script-owner` 报的脚本数 = 第三节表格的脚本行数。** 它说 6 个，第三节就必须有 6 行。不一致就是漏列，先信脚本。
- **`fe-gate-coverage` 的 22/22 与空豁免表。** 那张豁免表只许变短；往里加条目必须写明为什么这条门禁不值得测。
