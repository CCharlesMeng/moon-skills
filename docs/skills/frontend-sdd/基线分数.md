# 前端 SDD 链路：模块基线分数

「改完有分数」这个条件靠这份文档成立：**每个模块的当前分数记在这里，改完重跑，分数不降才合并。**

评分口径见 [模块与评测.md 第三节](./模块与评测.md)。模块清单与覆盖状况见同一份文档第二节。

## 一、准入规则

| 模块类型 | 准入条件 |
| --- | --- |
| 确定性脚本 | 全部 unittest 通过，且用例数不减。改了行为的，先改测试并在下表记明为什么 |
| 判定类提示词 | 四项分**每项都不低于**下表当前值，且四项都在及格线内。跑 3 次取最低那次 |
| 编排 | `evals.json` 存量用例全过，新增用例跑 3 次取多数不复发 |

**跑 3 次取最低**，不取平均也不取多数：判定类提示词的失败方式是偶发漏检，平均会把它抹平，而漏检一次在真实使用里就是一次漏检。

## 二、判定类提示词

### `agents/review-convention.md`

用例 [`evals/fixtures/cases/convention-01`](../../../skills/sdd-dev-frontend/evals/fixtures/cases/convention-01/ground-truth.md)（16 条必报 / 6 条诱饵 / 6 条可选）。

| 日期 | 命中率 | 误报率 | 级别正确率 | 格式合规 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 2026-08-06 | **0.94** | **0.00** | **1.00** | **1.00** | 首次基线。3 次分别为 16/16、15/16、16/16，取最低 |
| 及格线 | ≥ 0.80 | ≤ 0.17 | ≥ 0.90 | = 1.0 | |

三次里唯一的漏检是 GT-15（`String(data.highRiskCount)` 让 `R5-1` 不成立）。四条定级陷阱三次全部躲过：GT-9 无 token 不判阻断、GT-11 无基线覆盖不升级、GT-13 等价实现不升级、GT-15 基线不成立必须升级（漏检那次不计）。

**这轮的真正产出不是分数，是 ground truth 被跑出了四处错**，都已修正：

| 问题 | 修正 |
| --- | --- |
| 漏登记 `String(data.highRiskCount)` 违反 `R5-1`，两次跑都报了阻断级且判得对 | 补为 GT-15，必报分母 14 → 16、阻断级 6 → 7 |
| 漏登记 `App.tsx` L2 未走 `@/` 别名，三次都报了 | 补为 GT-16 |
| NG-3 的行号写成 L36，实际在 L30 | 已改 |
| 格式项写「diff 取法第 2 条」，但取值表给了 `<base-ref>`，正确答案是第 1 条 | 已改；三次都答第 1 条 |

**这份分数的局限**：接近满分说明 convention-01 区分度不足，再优化提示词也看不出变化。下一条用例要往这三个方向加难度——多文件跨目录的同类违规（考穷尽而非考识别）、`PATTERN-*` 之间互相冲突时该听谁、以及一条同时命中 `EX-n` 豁免的偏差（考「命中豁免的不报」这条反向规则）。

### 其余七个判定类提示词

尚无用例，因此没有分数。`extract-prototype` / `extract-block-spec` / `recon-spec` / `recon-codebase` / `review-quality` 可以复用现有 fixture 现场；`review-layout` / `self-test` 要等一个装得起依赖的现场。
