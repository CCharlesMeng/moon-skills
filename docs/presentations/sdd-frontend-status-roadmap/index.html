WHAT YOU GET
核心能力
给出正确的阶段目标，
Skill 会把一个前端 Story
带到可验收结果。

使用者不需要记住内部编排，只需要确认目标 app、Story、设计来源，以及关键阶段产出的内容是否正确。

APP 级
建立可复用的仓库公共事实

识别技术栈与应用形态，准备开发环境，产出九份 baseline。

STORY 级
完成设计、计划和受控实现

组件、数据、对接、文件职责、验收声明和执行顺序都能落盘。

验收级
用证据回答“哪些已经成立”

按风险选择验证与五格检视，最终生成可接手的验收结论。

SDD-TASK-FRONTEND

实现计划落到文件职责、验收声明和顺序

tasks.md
告诉开发“改哪里、做什么、按什么顺序”
  • TaskPacket：app、Story、基线来源与风险事实
  • 受影响路由、组件层级、状态归属与数据流
  • 精确文件范围，以及每个文件的功能职责
  • Task 顺序、依赖、可能扩散、风险与回滚
开发者检查：文件清单是否完整但不过宽；每个 Task 是否真的会改代码；计划是否忠于设计。
alpha-tests.md
告诉团队“每条需求准备怎样证明”
  • SC / BR / GWT 到 AT，再到具体 Task 的映射
  • S1 组件、S2 页面、S3 用户路径验证记录
  • verification_scope 与 verification_method
  • 声明初始状态、Deferred AC 与人工验收记录
开发者检查：每条 AC 是否有覆盖；判据是否可观察；人工验收是否真的只能由人完成。
示例指令
“根据 Story 前端设计生成 tasks.md 和 alpha-tests.md；只规划，不写代码。”
计划写到文件职责，不提前写 JSX、CSS、函数体或具体测试实现06 / 12

SDD-DEV-FRONTEND

执行阶段只在一个 Story 内冻结、实现和取证

可以从头执行，也可以续跑；`tasks.md` 管进度，`alpha-tests.md` 管声明状态与证据。

PHASE -1 / 0
进入与校验

定位 app 与 Story，校验 baseline、任务计划和起点质量能力，确定需要哪些验证。

dev-baseline.md
PHASE A1 / A2
规格与冻结

从原型、参照页或文字规格抽取 QA 基线；由使用者确认后冻结期望。

design-spec/* · restore-contract.json
PHASE B
按 Task 实现

逐 Task 修改代码、回填因果证据并更新 checkbox，不把勘察或评审伪装成实现 Task。

code · tasks.md · alpha-tests.md
PHASE C / D
检视与收口

按最终 diff 执行适用检视；修复阻断项，重取失效证据并逐声明收口。

review-* · acceptance.md
使用者最重要的一次参与：认真确认 QA 基线；它会成为后续实现与还原的共同期望。
示例：“执行这个 Story；HTML 原型是设计基线，先给我确认 QA 基线。”07 / 12

SDD-REVIEW-FRONTEND

五格审查分别回答五类问题

LENS
审查什么
开发者重点看
RESTORE
冻结区块、顺序、父子关系、数量和样式容差是否成立
RED / YELLOW 原因与契约 ID
LAYOUT
不同视口、跨页结构、真实数据与层叠关系是否稳定
触发场景与可复现影响
CONVENTION
是否遵守 app baseline 中的 PATTERN 与 Requirement 决策
适用场景、依据 ID 与豁免
QUALITY
职责、重复、状态归属、副作用、复杂度和性能是否有可观察问题
不要只看风格，要看真实后果
TEST
冻结功能声明、异常分支、接口契约与回归闭包是否被证据覆盖
证据是否真正覆盖声明
示例指令
“以这个 Story 的冻结声明和 base-ref 为准，执行适用的五格检视并返回可复现 Finding。”
审查只判断；选哪些 lens、采集哪些事实、如何汇总由执行阶段负责09 / 12

ACCEPTANCE

最终交付是一份可接手的验收结论

PROVEN

已有覆盖声明、并且仍然新鲜的证据。

UNVERIFIED

尚未证明，同时给出需要怎样补验。

DEFERRED

明确暂缓，并记录影响范围与解除条件。

人工验收只能由真实人员执行并签署；Agent 负责准备环境、步骤和所需证据。
acceptance.md
把机器事实翻译成开发、测试和负责人都能继续行动的结果。

本次实际交付了什么
声明状态

需要你处理
待决项与人工验收动作
你该知道
建议级问题与已知限制
证据索引
如何回到命令、场景和 Finding
唯一下一步
现在最该执行的动作

USER CHECKLIST

使用者做好三次确认，就能把链路用好

开始前
确认范围与输入

目标 app 唯一、Story / AC 明确、设计来源可定位；需要安装、登录或外部副作用时及时授权。

开工前
确认 QA 基线

逐项检查必须出现的内容、状态、行为和视觉期望；有歧义当场改，不在实现阶段放宽。

交付前
确认 acceptance.md

检查声明状态、证据、人工验收、待处理项和唯一下一步；不要只看“代码已经写完”。

使用原则
给清楚目标，
认真确认期望，
按证据完成验收。

Skill 负责读仓、编排、实现和取证；使用者对目标范围、关键期望和最终人工签字负责。

从正确入口开始，按产物完成交接。
