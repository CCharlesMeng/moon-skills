FRONTEND SDD
SDD-TASK-FRONTEND

计划：把“做什么”和“怎样证明”分开写

必须有 story_dir、需求锚点和两份文件 schema；前端设计或后端契约缺失可以降级，但必须在“风险与回滚”中显式登记。

tasks.md
执行清单，也是验证范围与方法的唯一作者
  • TaskPacket：project、Story、搜索路径、视觉基线来源和风险 token。
  • 受影响路由、组件层级与挂载点、状态归属、数据流、复用决策。
  • 每个 Task 的精确文件范围；每个文件写清位置、职责和对外契约。
  • “用例追溯”把 SC-* / BR-* / GWT → AT → Task。
  • 每条 AT 只在这里定义 verification_scope 与 verification_method。
alpha-tests.md
声明状态与证据账本；计划阶段不伪造证据
  • AC ↔ 证据映射只引用 AT，不重复抄验证范围和验证方法。
  • 初始状态统一为 UNVERIFIED。
  • Deferred 记录外部依赖、影响范围、解除条件和恢复入口。
  • manual_acceptance 必须写依据、所需环境和所需证据；验收人/时间留空。
  • 还原证据、完整代码指纹和计划外承接由 Dev 阶段追加。
审查时拒绝：可粘贴运行的 JSX / CSS / 函数体、固定测试命令、为保险而扩大文件清单、把“缺测试通道”改判成人工验收。示例指令：“生成两份计划文件；只规划，不写代码。”
一个 Task 一种形态；还原先于逻辑；样式文件归还原 Task；计划外风险写“可能扩散”而不是偷偷放宽范围06 / 12

SDD-DEV-FRONTEND · PHASE B

实现中：每个 Task 都走一次证据闭环

tasks.md 管实现进度，alpha-tests.md 管声明状态；两者必须在同一轮同步更新。

选一个未完成 Task读取它的文件职责、受影响 AT、形态和“可能扩散”；不把多个 Task 混成一轮。
还原 Task 先取得 RED用冻结的同一份 restore-contract.json + restore-adapter.json，证明当前实现尚未满足期望。
按文件职责实现计划外连带改动按扩散承接登记；不能借实现过程改设计或放宽已冻结期望。
只取本 Task 改变声明的因果证据不在每个 Task 后固定跑全量测试；浏览器模块只有被 portfolio.json 选中才解析。
取得 GREEN 并回填账本勾选 checkbox，写证据引用和合法状态；样式文件只归还原 Task。
tasks.md只更新 checkbox；验收内容仍由计划阶段所有。
alpha-tests.md回填证据、声明状态、Deferred、计划外承接；GREEN 行保存权威代码指纹。
evidence/restore-report-red.json实现前差异；与 GREEN 使用同一冻结契约。
evidence/restore-report-green.json实现后逐规则三色结果；新一轮覆盖当前文件。
.work/static-results.json同轮过程件；报告已吸收规则结论后可覆盖重算。
还原工具公开动作：contract、validate、static、report。新产物写 v3；v2 只用于历史兼容读取。
机器盲区不塞进契约假装可判：图片裁切焦点、透明叠层观感等进入 manual_acceptance08 / 12

SDD-DEV-FRONTEND · CLOSEOUT

收口阶段：只在需要人判断时找你

最终差异怎么复判、哪些证据要重取、检视结果怎么聚合，都是 Skill 内部工作；使用者不需要跟这些步骤。

默认继续规格清楚、权限齐全、证据可取得时，Skill 会继续完成验证、修复和收口，不逐步等待确认。
需要你拍板只有选择会改变需求、范围或设计结论，或者需要新的外部授权时，才会带着明确选项暂停。
需要你验收声明属于 manual_acceptance 时，会给出路由、操作、预期和证据要求；真实人员执行后再回填。
发现未通过能在既定规格内修复的先修复；需要改规格或超出授权范围的，写进交付入口请你决定。
acceptance.md
收口后只先打开这一份
先读第一句直接判断当前是可验收、部分验证，还是有明确阻断。
再看“需要你处理”这里才是需要拍板、补权限或执行人工验收的动作。
有疑问再往下追按文件引用进入 alpha-tests.md 或 evidence/，不用从内部过程文件猜结论。
使用边界：内部出现的三色、检视角色和过程文件不要求使用者逐项解读；它们最终都要落成可执行的结论。
如果没有拍板项或人工验收项，收口阶段不会额外打断你09 / 12

ACCEPTANCE GUIDE

验收：先读acceptance.md给出的结论

acceptance.md · 人工验收入口

验收摘要第一句直接说明可验收、部分验证，或因哪些阻断暂不可验收。
需要你处理拍板项、补权限动作与 manual_acceptance 的执行步骤。
你该知道，但不用动建议级问题、交接信息和不影响当前验收的提醒。
这次判了什么哪些范围已经判定，哪些未判，以及主动收窄了什么。
按需章节改进建议、未决问题、暂缓项和规范候选有内容才出现。
要往下追的话给出 dev-baseline.md、alpha-tests.md 与机器结果路径。
人工验收不能代签：manual_acceptance 只有真实人员可执行。示例见 dashboard-sdd/acceptance.md；权威登记在 dashboard-sdd/alpha-tests.md。

需要追证时 · restore-report-*.json

GREEN该还原规则通过。
YELLOW条件未闭合，需要补证或落成明确状态。
RED规则未满足，需要修复或调整声明。

需要查声明时 · alpha-tests.md

PROVEN已验证，证据有效。
UNVERIFIED未验证，按说明补验。
DEFERRED等外部依赖，按解除条件恢复。
人工验收完成后再回填 manual_outcome、manual_checked_by、manual_checked_at 与 evidence_refs11 / 12
